## 0. 서론

저번에

- 가상 메모리 : 각 프로세스가 독립되고 연속된 메모리 공간을 가지고 있다고 착각하게 만드는 것
- 세그먼테이션 : 프로세스의 각 영역을 세그먼트라는 단위로 메모리에 올리는 것
- 세그먼테이션의 문제점 : 외부 단편화
- 빈 공간 관리 기법 : 빈 공간 리스트 / 빈 공간 알고리즘

이 정도를 배웠었지?

이번에는 세그먼테이션의 문제점인 외부 단편화,

즉 메모리에 남아있는 빈 공간의 총합은 충분하지만,
그 빈 공간들이 흩어져있어서
필요한 크기의 연속된 메모리를 할당할 수 없는 현상

을 막을 수 있는 페이징에 대해 배워볼거야.

## 1. 페이징이란?

페이징이 뭐냐면,
정말 쉽게 세그먼테이션으로 비유해보자면,

1. 모든 세그먼트의 크기를 똑같이 맞춘다(보통 4KB)
2. 메모리에 그 세그먼트들을 넣을 수 있는, 세그먼트의 크기와 같은 프레임이라는 단위를 준비한다.
3. 세그먼트를 프레임에 하나씩 넣는다.
    - 세그먼트 크기 : 프레임 크기이므로 어느 세그먼트가 어느 프레임에 들어가든 쏙쏙 잘 들어간다.
    
이렇게 설명할 수 있겠네.

여기서 세그먼트 == 페이지로 보면 돼.

1. 모든 페이지의 크기를 똑같이 맞춘다.
2. 메모리에 그 페이지들을 넣을 수 있는, 페이지의 크기와 같은 프레임이라는 단위를 준비한다.
3. 페이지를 프레임에 하나씩 넣는다.
    - 페이지 크기 : 프레임 크기이므로 어떤 페이지라도 모든 프레임에 넣을 수 있다.
  
정말 쉽게 설명하자면,

> 물리 메모리의 프레임과 프로세스 조각인 페이지를 같은 크기로 둬서,
> 물리 메모리의 프레임에 프로세스 조각인 페이지를 끼워넣으면 되게 한다.
> 모든 프레임과 페이지의 크기가 같으므로 어느 페이지든 어느 프레임에도 끼워넣을 수 있게 한다.

라고 할 수 있어.

이러면 모든 프로세스 조각의 크기가 같으니까
중간에 빈 틈이 없어서 외부 단편화가 발생하지 않겠지?

페이징은 어쨌든 상당히 유연한 가상 메모리 방식이야.
그리고 빈 공간 관리도 쉽지.
(모든 페이지 크기가 같으니..)

### 1-1. 각 페이지 관리 - 페이지 테이블

페이지 테이블이란,
각 페이지에 대한 정보가 적혀있는 테이블이야.

가상 주소로 물리 주소를 얻는 것도 페이지 테이블로 해.

페이지 테이블에는 각 페이지가 저장된 물리 메모리 주소가 있어서,
프로세스의 가상 주소 -> 페이지 테이블 -> 물리 주소로 변환할 수 있는거야.

그리고 이런 페이지 테이블은 프로세스마다 있어.

그리고 페이지 테이블 베이스 레지스터(PTBR)은 
현재 실행 중인 프로세스의 페이지 테이블의 시작 주소(물리 주소)를 저장해.
PTBR을 통해 페이지 테이블에 접근할 수 있는거지.

가상 주소를 보고 찾는 페이지가 몇 페이지인지는 어떻게 아냐고?
그건 전에 봤던 세그먼테이션에서 그대로 이어져.
상위 N비트(보통 한 페이지가 4096바이트니까 13번째 비트 이상의 비트)를 보고
몇 페이지인지 특정할 수 있어.

저렇게 상위 N비트를 보고 나오는 페이지 번호를 가상 페이지 번호(VPN)이라고 해.
나머지 비트들은 오프셋으로 보면 되고.

그리고 가상 페이지 번호는 프레임 번호로 변환할 할 수 있고,
그 프레임 번호는 물리 프레임 번호(PFN)이라고 해.

그리고 구체적인 변환 과정은

1. 가상 주소 -> 가상 페이지 번호 + 오프셋
2. 가상 페이지 번호( -> 물리 프레임 번호
3. 물리 프레임 번호 -> 중간 물리 주소
4. 중간 물리 주소 + 오프셋 -> 최종 물리 주소

이렇게 된다는거지.

페이지 크기가 프레임 크기와 동일하기 때문에,
가상 주소의 오프셋을 물리 주소의 오프셋으로 그대로 쓸 수 있어.

#### 1-1-1. 페이지 테이블 자세히 알아보기

한 프로세스의 페이지 테이블은 굉장히 커질 수 있어.

가상 페이지 번호가 20비트만 되어도 $2^20$개의 페이지 테이블 엔트리가 필요하겠지.
(대략 100만개)

그래서 이걸 그대로 MMU같은 주소 변환 장치에 저장하지는 않아.
그래서 각 프로세스의 페이지 테이블은 일반적으로 메모리에 저장되지.
(운영체제의 가상 메모리에 저장돼.

페이지 테이블에는 

- 해당 페이지의 프레임 번호
- 기타 정보(유효 비트 / 보호 비트(RWX) 등)

이렇게 저장되어있어.

해당 페이지의 프레임 번호는 다 알거라고 생각하고,

유효 비트는 말 그대로 해당 페이지가 유효한지에 대한 비트야.
말 그대로 유효하지 않은 페이지에 접근을 막는 용도로 쓰여.
유효하지 않은 페이지에 접근한 경우 바로 세그폴트 맞거든?
대충 무슨 느낌인지 알겠지?

보호 비트(RWX)는 해당 페이지에 대한 권한에 대한 비트야.
해당 페이지에 대해 읽을 수 있는지(Read), 쓸 수 있는지(Write),
실행할 수 있는지(eXecute)를 저장해.

존재 비트는 해당 페이지가 메모리에 존재하는지에 대한 비트야.
나중에 스왑을 배울텐데,
대충 설명하면 해당 페이지는 메모리에 있을 수도 있고 디스크에 스왑되어있을 수도 있게 되기 때문에
해당 비트가 있는거야.

더티 비트는 해당 페이지가 메모리에 들어온 후 페이지가 변경되었는지를 나타내는 비트야.
이것도 나중에 스왑에서 보자.

참조 비트는 어떤 프로세스가 해당 페이지를 참조하고 있는지에 대한 비트야.
나중에 나올 페이지 교체에서 어떤 페이지가 주로 쓰이는지를 알 수 있기도 하지.

이런 비트들은 외울 필요는 솔직히 없어.
그냥 이런 비트들이 페이지의 상태를 나타내준다고 이해하기만 하면 돼.

특이하게도(?) 프레임의 물리 주소는 저장되어있지 않은데,
어차피 프레임 크기가 다 같으니까 
프레임의 물리 주소는 $\text{프레임 번호} \times \text{프레임 크기}$를 해버리면 돼.

### 요약

1. 페이징은 일정한 크기의 페이지를 같은 크기의 프레임에 할당하는
가상 메모리 기법이다.
세그먼테이션의 외부 단편화를 해결할 수 있다.
2. 각 페이지에 대한 정보는 페이지 테이블에 있으며,
페이지 테이블은 각 페이지가 어느 프레임에 할당되어있는지,
해당 페이지의 속성(유효 / 보호 / 스왑 여부 / 참조 여부 등)은 어떤지를 저장한다.
3. 페이지 테이블은 프로세스마다 존재하며,
PTBR에는 현재 실행중인 프로세스의 페이지 테이블의 첫 주소가 들어가서
PTBR을 이용해 페이지 테이블에 대한 참조를 수행한다.
4. 페이징에서의 메모리 참조는
    - 가상 주소 -> 가상 페이지 번호(가상 주소의 상위 N비트로 찾음) + 오프셋
    - 가상 페이지 번호 -> 물리 프레임 번호(페이지 테이블에서 찾음)
    - 물리 프레임 번호 -> 중간 물리 주소(물리 프레임 번호 * 프레임 크기)
    - 중간 물리 주소 + 오프셋(가상 주소의 오프셋 그대로) -> 최종 물리 주소
    의 형태로 수행된다.

## 2. TLB - 페이지 테이블을 저장하는 캐시 메모리

페이지 테이블의 대다수는 방금 말한대로
메모리에 저장되어있지.

근데 메모리 접근은 많이 일어나잖아?
메모리에 접근할 때마다
페이지 테이블을 참조하려 메모리에 한 번 더 접근하는건
상당히 비효율적이겠지?

그래서 페이징의 효율성을 높이기 위해
TLB(Translation Lookaside Buffer, 변환 색인 버퍼)라는
약간 '페이지 테이블의 캐시 메모리'느낌의 하드웨어를 추가로 사용해.

TLB는 MMU의 일부로써,
메모리를 참조할 때 우선적으로 TLB에서 
찾으려는 페이지의 페이지 테이블 엔트리를 찾게 돼.
찾으면 TLB 히트로 바로 프레임 번호 따서 메모리에 접근하게 되는거고.

없으면 TLB 미스로 페이지 테이블을 찾으러 메모리까지 내려가는거고..
메모리에도 없으면 디스크까지.
(딱봐도 오래걸릴 것 같지?)
그리고 TLB에 캐싱하지.

TLB는 그냥 말 그대로 캐시야 캐시.
페이지 테이블을 다루는.

Translation Lookaside Buffer보다
Translation Lookaside Cache가 더 맞는 느낌이지 않나 싶지..

이것도 결국 캐시인지라,
새 캐시 라인(페이지 테이블 엔트리)가 들어왔을 때
어느 캐시 라인(페이지 테이블 엔트리)를 내보낼지를 고르는 정책이 필요해.
보통은 LRU(Least Recently Used)같은거 많이 쓰지.

TLB 미스에 대해 좀 더 설명해보자면,
사양에 따라 처리하는 방법이 달라져.

CISC에서는 보통 단순 하드웨어(CPU) 명령어로 처리되기도 하고,
RISC에서는 보통 트랩을 이용한 소프트웨어(OS)로 처리되기도 하고..
(트랩을 이용하면 계속 TLB 미스가 나는 상황을 주의해야함)
(일반 메모리 참조에서 TLB 미스 -> 트랩 핸들러에서 TLB 미스 -> ...)

트랩을 이용해서 처리를 할 때는 일반적인 트랩처럼
다음 명령어를 이어서 실행하지 않고,
현재 명령어를 이어서 실행한다는 점이 다르겠네.
(메모리 주소를 읽어온 다음에 현재 명령어를 가지고 뭘 하는거니까.)

그리고 TLB는 완전 연관 캐시(세트가 하나, 한 세트에 모든 캐시 라인을 저장하는 식)로,
`VPN / PFN / 다른 비트들`의 형식으로 각 페이지 테이블 엔트리가 저장되어있어.

`다른 비트들`은 유효 비트(페이지 테이블과 다름) / 보호 비트 / 더티 비트 정도가 있어.

이게 TLB에 있는 정보들은 현재 실행하고 있는 프로세스에만 유효한 정보라,
컨텍스트 스위칭이 있을 경우 TLB에 있는 모든 데이터가 무효가 되게 되어있어.

근데 이게 이전 프로세스와 다음 프로세스에서 동일한 VPN을 사용할 수가 있거든?
그러면 VPN이 같은 두 개의 페이지 테이블 엔트리가 TLB에 저장되게 돼.

이 문제는 보통

- PTBR이 바뀔 때 기존 TLB를 비우거나
- ASID(Address Space Identifier)로 어떤 프로세스의 페이지인지를 식별하거나

함으로써 해결할 수 있어.

### 요약

1. TLB는 더 빠른 페이지 테이블에 대한 접근을 위한 캐시이다.
2. TLB에 찾는 페이지 테이블 엔트리가 있는 경우 TLB 히트이고,
TLB에 찾는 페이지 테이블 엔트리가 없는 경우 TLB 미스이다.
   - TLB 미스가 발생한 경우, 사양에 따라
   하드웨어적(CPU)으로 처리하거나 소프트웨어적(예외)으로 처리할 수 있다.
   - 어떻게 처리하든 메모리에서 해당 페이지 테이블 엔트리를 가져오는 것은 같다.
3. TLB도 결국 캐시이기 때문에, 페이지 테이블 엔트리 교체 정책이 필요하다.
    - 보통 LRU를 많이들 쓴다.
4. 컨텍스트 스위칭을 할 때 TLB에 저장되어있는 페이지 테이블 엔트리들의
소속 프로세스(?)를 구분하기 위해서
PTBR이 바뀔 때 TLB를 Flush하거나(PTBR은 컨텍스트 스위칭이 발생하면 무조건 바뀜)
ASID를 설정해서 페이지 테이블 엔트리 별로 프로세스를 구분하는 방식을 사용할 수 있다.
   - 소속 프로세스가 구분되어있지 않으면
   VPN이 중복되어 저장될 수 있다.

## 3. 페이지 테이블 크기 줄이는 법

페이지 테이블의 크기가 크면 안좋아.
당연한 소리겠지?

페이지 테이블도 결국 메모리에 올라가는데,
한 페이지 테이블 엔트리가 4바이트라고 해도
페이지가 100만개면
4MB나 메모리를 차지하게 돼.

생각보다 좀 많거든?
딸랑 페이지 테이블을 저장하는데 4MB라..

게다가 이런 프로세스가 100개 돌아가고있으면
400MB를 페이지 테이블이 처먹어.

안좋지?

그래서 다양한 페이지 테이블 크기를 줄이는 법이 나와있어.

### 3-1. 첫 번째 아이디어 - 페이지 크기 키우기

이건 제일 간단한 방법이지.
한 페이지의 크기가 커지면
페이지 테이블 엔트리의 갯수도 줄어들잖아?

근데 이건 문제점이 있어.

바로 내부 단편화로,
페이지의 크기가 커지니
페이지의 일부만 사용하는 경우가 늘어나서
더 많은 메모리가 낭비될 수 있어.

### 3-2. 두 번째 아이디어 - 페이징과 세그먼트 합치기

이건 이해가 잘 안될 수도 있는데,
그냥 프로세스를 세그먼트 단위로 나누고, 세그먼트 단위로 페이지 테이블을 둔다는거야.

예를 들어,
프로세스를
힙 세그먼트 / 스택 세그먼트 / 코드 세그먼트로 각각 나누고
각 세그먼트마다 분리된 페이지 테이블을 두는거지.

이렇게 하면, 장점이
여러 영역 사이의 VPN이 낭비되지 않는다는 점이야.

```text
[ 0번 페이지 ] <- 코드
[ 1번 페이지 ]
[ 2번 페이지 ]
[ 3번 페이지 ]
[ 4번 페이지 ]
[ 5번 페이지 ] <- 힙
[ 6번 페이지 ]
[ 7번 페이지 ]
[ 8번 페이지 ]
[ 9번 페이지 ] 
[ 10번 페이지 ] 
[ 11번 페이지 ] <- 스택
[ 12번 페이지 ] <- 스택
```

이렇다고 할 때,
코드는 0번 페이지 / 힙은 5번 페이지, 스택은 11 ~ 12번 페이지에 있는데,
그 사이사이의 페이지들은 아무 역할을 하지 않음에도
페이지 테이블에 들어와있게 되어서
페이지 테이블 용량이 더 커진다는거지.

```text
[ 스택 0번 페이지 ]
[ 스택 1번 페이지 ]

[ 힙 0번 페이지 ]

[ 코드 0번 페이지 ]
```

이렇게 각 영역대로 세그먼트로 만들어서
각 영역마다 따로 페이징을 해주면 중간중간에 빈 페이지를 고려할 필요가 없어진다는거야.

뭐 VPN에 이어서 최상위 N비트를 세그먼트 종류를 나타내는 비트로 사용하고,
MMU에 Base / Bound 두고 하는 세부 구현이 있긴 한데,
그건 지금은 무시하자.

어쨌든 이 방식은
낭비되는 페이지 테이블 엔트리를 줄일 수 있어서
페이지 테이블의 크기를 줄일 수 있어.

하지만 이것도 문제점이 있어.

결국 이것도 세그먼테이션이기 때문에,
빈 공간이 많은 힙의 경우에는 여전히 페이지 테이블이 낭비될 수 있어.

그리고 이게 세그먼테이션인 만큼 외부 단편화를 유발할 수 있어.
세그먼트의 길이가 제각각이라서,
각 세그먼트에 종속된 페이지 테이블의 크기도 가변 길이가 되잖아?
근데 페이지 테이블은 물리 메모리에 연속적으로 배치되어있어야 하거든.
세그먼트가 아니라 페이지 테이블에서 외부 단편화가 나는거지.

### 3-3. 세 번째 아이디어 - 다단계 페이지 테이블 사용하기

이게 제일 나은 해결 방법이야.

페이지 테이블을 다단계로 만들어놓은건데,

```text
   [ PTBR ]
      │
      ▼
┌─────────────────────────────────────────┐
│  Page Directory (외부 페이지 테이블)   │  <-- 4KB 프레임 1개 크기
├───────┬─────────────────────────┬───────┤
│ Index │ PFN (하위 테이블 위치) │ Valid │
├───────┼─────────────────────────┼───────┤
│   0   │ 0x001A3              │   1   │ ──┐ (사용 중인 영역만 하위 테이블 할당)
│   1   │ NULL                 │   0   │   │
│   2   │ NULL                 │   0   │   │  <-- 미사용 공간은 하위 테이블 자체가 없음
│  ...  │ ...                  │  ...  │   │
│ 1023  │ 0x008F1              │   1   │ ──┼──┐
└───────┴─────────────────────────┴───────┘   │  │
                                          │  │
      ┌───────────────────────────────────────┘  │
      ▼                                      │
┌─────────────────────────────────────────┐      │
│   Page Table #0 (실제 PTE 조각 0)     │      │ <-- 4KB 프레임 1개 크기
├───────┬─────────────────────────┬───────┤      │
│ Index │ PFN (실제 데이터 프레임)│ Valid │     │
├───────┼─────────────────────────┼───────┤      │
│   0   │ 0x00450              │   1   │      │
│   1   │ 0x00451              │   1   │      │
│  ...  │ ...                  │  ...  │      │
│ 1023  │ NULL                 │   0   │      │
└───────┴─────────────────────────┴───────┘      │
                                             │
      ┌──────────────────────────────────────────┘
      ▼
┌─────────────────────────────────────────┐
| Page Table #1023 (실제 PTE 조각 1023) │      <-- 4KB 프레임 1개 크기
├───────┬─────────────────────────┬───────┤
│ Index │ PFN (실제 데이터 프레임)│ Valid │
├───────┼─────────────────────────┼───────┤
│   0   │ NULL                 │   0   │
│  ...  │ ...                  │  ...  │
│ 1022  │ 0x00910              │   1   │
│ 1023  │ 0x00911              │   1   │
└───────┴─────────────────────────┴───────┘
```

이런 느낌이야.
(이건 2단계 페이지 테이블.)
(제미나이가 그려줌. 아스키아트 어려워..)

상위의 페이지 테이블은 다른 페이지 테이블을 가리키는
페이지 디렉터리의 형태를 가지고,
실제 페이지 테이블은 하위 페이지 테이블의 형태로 저장해놓는거야.

페이지 테이블로 트리 구조를 만들어놨다고 생각하면 돼.

그리고 페이지 디렉터리 / 하위 페이지 테이블은
전부 페이지의 크기로 만들어놓는거지.
(이러면 모든 페이지 테이블의 크기가 같아져서
새 페이지 테이블이 필요할 때 기존의 빈 페이지 테이블 가져다 쓰면 됨.)

페이지 디렉터리는 페이지 디렉터리 엔트리들로 구성돼.
페이지 테이블 엔트리와 비슷한데,
유효 비트 / 페이지 프레임 번호가 있어.
(물론 실제 구현에는 추가적인 요소가 있을 수도 있지만, 이게 핵심이야.)

유효 비트는 해당 페이지 디렉터리 엔트리의 하위 페이지 중 하나라도 유효한 경우에 설정돼.
(페이지 테이블과 좀 다르지..)

이 구조의 장점은,
일단 첫 번째로 사용된 주소 공간의 크기에 비례해서 페이지 테이블 공간이 할당돼.
페이지 테이블 디렉터리에서 아예 안 쓰는 페이지 테이블(유효 비트가 0)은
메모리에 할당을 안 해버릴 수 있다는거지.
(앞서 설명한 세그먼트-페이징의 장점과 비슷해.)

선형 페이지 테이블은 모든 페이지 테이블 엔트리가 물리 메모리에 연속적으로 놓여있어야 하기 때문에
중간에 빈 페이지 테이블 엔트리들이 크게 있어도
그 페이지 테이블 엔트리도 전부 메모리에 올려놓아야 했기 때문에
페이지 테이블의 용량이 컸던거거든.

그리고 두 번째로 페이지 테이블 자체를 페이지 크기로 분할하기 때문에
메모리 관리가 매우 용이해.
앞서 설명했듯,
새 페이지 테이블이 필요할 때 기존의 빈 페이지 테이블을 가져다 쓰는 식으로..

물론 단점이 있는데,
결국 페이지 디렉터리 -> 페이지 테이블 엔트리로 두 번 접근을 해야하다보니까
TLB 미스가 나면 두 번 메모리에 로드해야해.
(페이지 디렉터리에 한 번, 페이지 테이블 엔트리에 한 번)

즉, 페이지 테이블 접근에 걸리는 시간과
페이지 테이블이 차지하는 공간을 트레이드-오프한거지.

그리고 이 방식은 구현 복잡도가 증가해.
자세한건 뒤의 예시에서 보자.

#### 3-3-1. 다단계 페이지 테이블 예시

앞서 다단계 페이지 테이블이 어떻게 구성되는지는 알았지?
트리의 형식으로,
상위 페이지 디렉터리가
하위 페이지 테이블들을 하나의 인덱스 씩으로 가리키는거.
그리고 각 페이지 테이블은 페이지 크기 만큼을 차지한다는거.

여기서 이런 의문이 들 수 있어.
VPN으로 어떻게 페이지 디렉터리 -> 페이지 테이블 엔트리를 어떻게 찾을 수 있냐는거지.

VPN을 페이지 디렉터리 엔트리를 가리키는 부분과
페이지 테이블 엔트리를 가리키는 부분으로 나누면 돼.

```text
31                22 21                12 11                 0
┌────────────────────┬────────────────────┬────────────────────┐
│ PD Index (10비트) │ PT Index (10비트) │  Offset (12비트)  │
└────────────────────┴────────────────────┴────────────────────┘
          │                    │                    │
          ▼                    ▼                    ▼
  [Page Directory]         [Page Table]     [실제 물리 프레임 내부]
```

이런 느낌이지.

먼저 최상위 N비트를 보고 페이지 테이블 디렉터리에서 어느 하위 페이지 테이블을 볼지 정하고,
상위 M비트를 보고 페이지 테이블에서 어느 페이지 테이블 엔트리를 볼지 정하는거야.

단순히 2단계아 아니라
여러 단계여도 상관없이,
VPN을 여러 구역으로 분할해서 보게 되는거야.

### 요약

1. 페이지 테이블의 크기가 크다면 
연속적으로 물리 메모리에 배치되어야하는 페이지 테이블 특성상
문제가 발생하게 된다.
2. 페이지 테이블 크기를 줄이기 위한 첫 번째 방법은,
페이지 크기 자체를 늘리는 것이지만,
해당 방법은 내부 단편화가 발생할 수 있다.
3. 페이지 테이블 크기를 줄이기 위한 두 번째 방법은,
각 영역을 세그먼트로 나누고 페이징을 해서
프로세스 전체의 필요없는 페이지들을 페이지 테이블에 두지 않는 것이지만,
힙 사이사이가 비어있는 문제나 페이지 테이블의 외부 단편화 문제가 발생할 수 있다.
4. 페이지 테이블 크기를 줄이기 위한 세 번째 방법은,
페이지 테이블을 페이지 디렉터리-페이지 테이블의 계층 구조로 만들어서
필요 없는 페이지 테이블을 굳이 할당하지 않는 것이지만,
페이지 테이블 엔트리에 접근할 때
페이지 디렉터리 계층의 수만큼 연속적으로 메모리에 접근해야 한다는 문제가 발생할 수 있다.

## 4. 총 요약

1. 페이징은 동일한 크기의 가상 페이지와 물리 프레임을 활용해서
어느 가상 페이지든 모든 물리 프레임에 할당되게 함으로써
외부 단편화를 없애는 가상 메모리 기법이다.
2. 페이징을 위한 정보(PFN / 상태 비트 등)는 페이지 테이블에 저장되며,
해당 프로세스의 페이지 테이블의 주소는 PTBR에 저장되어있다.
3. 가상 주소를 물리 주소로 변환하기까지의 과정은
    - 가상 주소 -> VPN + 오프셋
    - VPN -> PFN
    - PFN -> 중간 물리 주소
    - 중간 물리 주소 + 오프셋 -> 최종 물리 주소
    이다.
4. TLB는 페이지 테이블의 캐시 메모리라고 할 수 있으며,
캐시처럼 TLB 히트 / TLB 미스가 발생할 수 있다.
TLB 히트가 발생하면 TLB에 저장되어있는 페이지 테이블 엔트리를 그대로 사용하며,
TLB 미스가 발생하면 페이지 테이블 엔트리를 직접 메모리에서 가져오고 TLB에 캐싱한다.
5. 페이지 테이블의 크기를 줄이기 위한 방법으로는
페이지 크기 늘리기 / 세그먼트 개념 사용하기 / 다단계 페이지 테이블 사용하기 등이 있고,
이 중 제일 효과적인 다단계 페이지 테이블은
하나의 페이지 테이블을 여러 개로 분할한 후
페이지 테이블 디렉터리가 각 페이지 테이블을 가리키게 만들고,
필요없는 페이지 테이블은 할당하지 않게 하는 페이지 테이블 크기 축소 기법이다.
단, 계층이 깊어질 수록 TLB 미스 시 메모리에 더 많은 횟수를 접근해야한다.
