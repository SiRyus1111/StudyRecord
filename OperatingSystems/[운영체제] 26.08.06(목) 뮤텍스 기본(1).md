## 1. 멀티스레딩과 레이스컨디션, 상호 배제

일단 근본적인 질문 하나.
왜 멀티스레딩을 하는걸까?

솔직히 이거 없으면 머리 아플 일 확실히 줄어들텐데말야.
나도 지금 멀티스레드 환경에서 룸 시스템 구현하느라 죽을맛임..

왜 그렇냐면,

1. 병렬성(Parallelism)을 극대화하려고.
    - 요즘 컴퓨터가 죄다 멀티프로세서로 나오는데,
    솔직히 싱글 스레드면 한 프로세서만 쓸 수 있잖아?
    - 프로세서는 여러갠데 한 프로세서만 쓰면 비효율적이니까
    스레드를 여러개 쓰는거임.
2. blocking되는 I/O가 실행되는 도중에 다른 작업을 하려고.
    - I/O 속도는, 입출력을 처리하는 속도는 한계가 있어.
    - 그래서, 결국 싱글 스레드만 쓰면 입출력을 blocking(대기 상태)으로 처리하는 동안
    다른 작업을 할 수 없잖아? 해당 스레드가 blocking되어있으니..
    - 그래서 blocking되어있는 동안 다른 스레드가 다른 작업을 하게 하기 위해서
    스레드를 여러개 쓰는거임.
    
이런 이유들 때문에 멀티스레딩을 하는거야.

근데 스레드를 여러개 쓸 때는 주의할 점이 있는데,
바로 실행 순서가 일정하지 않다는거.

이게 사실상 레이스컨디션 등등 동시성 문제의 핵심인데,

```text
스레드 1 생성 -> 스레드 2 생성 -> 스레드 1 join() -> 스레드 2 join()
```

이렇게 코드를 짜놨다고 해도,
실제 스레드 1과 스레드 2가 실행되는 순서는 OS의 스케줄러에 따라

```text
스레드 1 완료 -> 스레드 2 완료
```

가 될 수도 있고

```text
스레드 2 완료 -> 스레드 1 완료
```

가 될 수도 있어.

코드 상으로는 `스레드 1`이 먼저 생성됐는데도!

근데 이게 제일 문제가 터지는게,
여러 스레드 사이에서 공유하는 데이터가 있을 때야.

두 스레드가 해당 공유 데이터를 마구마구 바꾼다고 해보자.

```cpp
#include <iostream>
#include <thread>

int counter = 0;

void MyThread(){
    for (int i = 0; i < 10000000; i++) {
        counter++;
    }
}

int main(){
    std::thread t1(MyThread);
    std::thread t2(MyThread);
    
    t1.join();
    t2.join();
    
    std::cout << "counter : " << counter << std::endl;
    
    return 0;
}
```

이렇게, 1천만번씩.

이게 `counter`의 값은 실행하고 나서 `10000000 * 2`니 `20000000`이 되겠지?

하지만 이거, 실행할 때마다 `counter`의 값이 달라져.

```text
counter : 19220343
```

```text
counter : 19376023
```

결국 이게 하드웨어 레벨에서는 1을 더하는게 하나의 명령어로 실행되지가 않아서,
앞서 말한 우리가 컨트롤 할 수 없는 OS 스레드 스케줄링 때문에
이런 문제가 발생하는거야.

```asm
; counter++의 개념적인 어셈블리

mov eax, [counter]    ; 1. 메모리에서 counter 값을 읽는다.
add eax, 1            ; 2. 레지스터의 값을 1 증가시킨다.
mov [counter], eax    ; 3. 결과를 메모리에 저장한다.
```

결국 여기 2와 3 사이에 다른 스레드로 전환되는 컨텍스트 스위칭이 일어나서
결과를 메모리에 저장 못한 채 다른 스레드가 해당 명령어를 실행하면,

| 시간 | 실행 중인 스레드 | 수행 명령어               | A의 `eax` | B의 `eax` | `counter` |
| -: | --------- | -------------------- | -------: | -------: | --------: |
|  1 | A         | `mov eax, [counter]` (A - 1) |        0 |        — |         0 |
|  2 | A         | `add eax, 1` (A - 2)         |        1 |        — |         0 |
|  3 | OS        | **A → B 컨텍스트 스위칭**     |        1 |        — |         0 |
|  4 | B         | `mov eax, [counter]` (B - 1) |        1 |        0 |         0 |
|  5 | B         | `add eax, 1` (B - 2)         |        1 |        1 |         0 |
|  6 | B         | `mov [counter], eax` (B - 3) |        1 |        1 |         1 |
|  7 | OS        | **B → A 컨텍스트 스위칭**     |        1 |        1 |         1 |
|  8 | A         | `mov [counter], eax` (A - 3) |        1 |        1 |         1 |

이렇게 다른 스레드가 연산 후 저장하기 전의 값을 읽어서
증가 연산 하나가 사라진 것처럼 보이게 되는거지..

결국 이렇게

> 두 개 이상의 실행 흐름이 공유 데이터(공유 자원)에 동시에 접근할 때,
> 접근하는 타이밍이나 순서에 따라 결과가 달라져서
> 예상치 못한 오류나 오작동이 발생하는 상태

를 레이스 컨디션(Race Condition, 경쟁 상태)이라고 해.

결국 이걸 막기 위해 뮤텍스같은 동기화 도구가 필요한거고.

그리고 이렇게 레이스 컨디션이 발생할 수 있는 코드 구역을
임계 구역(Critical Section)이라고 해.
쉽게 설명하면 공유 자원에 접근하는 코드 구역이라고 보면 돼.

결국 저런 레이스 컨디션을 막으려면,
한 스레드가 해당 공유 자원(`counter`)에 접근하는 임계 구역에서 실행 중일 경우,
다른 스레드가 해당 공유 자원(`counter`)에 접근하는 임계 구역에 들어오지 못하게 해야겠지?

그걸 상호 배제(Mutual Exclusion)라는 이름으로 표현할 수 있어.

> 한 스레드가 한 공유 자원에 접근하는 임계 구역의 코드를 실행 중일 경우,
> 다른 스레드가 해당 공유 자원에 접근하는 임계 구역의 코드를 실행할 수 없는 성질.

이걸 상호 배제라고 불러.

뮤텍스라는 이름도, 이 상호 배제에서 나온거야.

MUTual EXclusive - MUTEX

## 2. 원자성의 필요성

레이스 컨디션을 해결하는 방법으로는 상호배제 말고 다른 확실한 방법이 있어.

하드웨어 자체에서 해당 연산을 다른 프로세서의 접근과도 관련해서
하나의 단위로 수행하는 것.

```text
; counter++의 개념적인 어셈블리

mov eax, [counter]    ; 1. 메모리에서 counter 값을 읽는다.
add eax, 1            ; 2. 레지스터의 값을 1 증가시킨다.
mov [counter], eax    ; 3. 결과를 메모리에 저장한다.
```

이 `counter` 값을 1 더하는 어셈블리 명령어를,

```text
; 예시, 실제 이런 명령어 없음

memory-add [counter], 1 ; 명령어 한 개로 앞의 세 개를 처리!
```

이런 식으로 하나의 명령어로 **더이상 쪼개질 수 없게**
하드웨어 수준에서 막아버리는거지.

만약 컨텍스트 스위칭 같은 인터럽트가 발생하면,
이 명령어는 결국 

- 완전히 실행되거나
- 완전히 실행되지 않거나

이 두 상태 중 하나가 되는거고,
**그 중간 상태는 존재하지 않는**거지.

결국 이렇게 하나의 단위로 실행하는 것 자체를,
더이상 쪼개질 수 없는, 중간 상태가 존재할 수 없는 성질을
원자성(Atomicity)라고 해.

좀 더 자세히 설명하자면,
다른 스레드가 관측했을 때 연산 전 또는 연산 후만 보이고,
중간 상태를 끼어들어서 관찰하거나 수정할 수 없는 성질을 원자성이라고 해.

그래도 모든걸 이렇게 명령어 하나로 처리할 수는 없겠지?
공유자원에 대한 매우 복잡한 연산같은걸 전부 원자적으로 실행해주는 명령어를
하드웨어가 지원하지는 않을테니까.

그래서, 우리는 이런 하드웨어의 원자적 명령어들과
운영체제의 도움을 받아서,
임계 구역에 대한 동기화되고 컨트롤할 수 있는 코드를 작성하게 되는거야.

## 3. 락의 기본 아이디어

락이란 공유 데이터(공유 자원)에 오직 한 개의 스레드만 수정할 수 있도록 해서,
즉 상호 배제(Mutual Exclusion)를 해서
레이스 컨디션을 막는 도구를 통칭하는 말이야.

- 이번 글의 주제인 뮤텍스
- 지정된 개수만큼의 스레드가 동시에 접근할 수 있게 허용하는 세마포어

등등이 있지.

이런 락들의 기본적인 아이디어를 알아보자.

일단, 락을 사용하려면 이렇게 임계 구역 주위에 코드를 사용하면 돼.
락은 변수니까, 변수처럼 선언해주고.(예시는 뮤텍스)

```cpp
std::mutex mtx;

mtx.lock();
// 임계 구역
mtx.unlock();
```

그리고 이 변수는

- 어떤 스레드도 락을 보유하지 않은, 즉 unlock 상태.
- 한 스레드가 락을 보유하고 있는, 즉 lock 상태.

이렇게 두 상태를 가져.

만약 한 스레드가 락을 보유하고 있다면,
그 스레드는 임계 구역의 코드를 실행하고 있겠지.

그리고 이 락 변수에는 어떤 스레드가 락을 보유하고 있는지,
즉 누가 이 락을 unlock 할 수 있는지,

그리고 해당 락이 unlock 되었을 때 
다른 스레드가 락을 획득하는 순서를 나타내는 대기 목록같은 것들이 있어.

하지만 이런 것들은 보통 외부에는 안 보이게 숨겨져있지.

이제 `lock()` 함수와 `unlock()` 함수를 알아보자면,

`lock()` 함수는 락을 얻는걸 시도해.

다른 스레드가 해당 락을 보유하고 있지 않으면
그 스레드가 임계 구역 안으로 들어갈 수 있게,
`lock()` 함수 다음의 코드를,
즉 임계 구역의 코드를 실행할 수 있게 해줘.

이렇게 락을 획득한 스레드는 그 락의 소유자라고 할 수 있고,
이 스레드만 `unlock()`을 호출했을 때 락을 해제할 수 있겠지.

만약 다른 스레드도 이후에 `lock()` 함수를 호출했고,
아직 해당 스레드가 해당 락을 보유하고 있다면,

다른 스레드가 `lock()` 다음의 코드,
즉 임계 구역의 코드를 실행하는게 막혀.
그리고 해당 락의 대기 목록에 들어가지.

락을 보유하고 있는 스레드가 `unlock()`을 호출한다면,
락은 아무도 보유하고 있지 않은 상태가 돼.

만약 어떤 다른 스레드도 해당 락에 대해 `lock()` 함수를 호출하지 않았었다면,
락의 상태는 아무도 보유하지 않은 상태가 돼.

만약 어떤 다른 스레드가 해당 락에 대해 `lock()` 함수를 호출해서
대기 목록에 있다면,
대기 목록의 스레드 중 하나가 해당 락을 획득하게 돼.
그리고 그 스레드는 임계 구역의 코드를 실행하게 되겠지.

물론 대기 목록이나 락의 소유자는 구현마다 다를 수 있어.
이건 예시야 예시.

이렇게 락은 프로그래머에게 스레드 스케줄링에 대한 최소한의 제어권을 제공해줘.
스레드는 일반적으로 OS가 선택한 방식에 따라 OS가 스케줄링하지만,
락은 해당 락을 획득하지 못한 스레드는 임계 구역의 코드를 실행할 수 없게 함으로써
프로그래머에게 스레드 스케줄링에 대한 최소한의 제어권을 제공해주는거지.

아, 그리고 책에서는 이 이후에
다양한 방식의 락 획득 구현 시도와 실패들이 있는데,
그 파트들은 스킵할게.

무슨

- 인터럽트 막아서 락 시도(싱글 프로세서에서만 가능)
- load / store를 이용해서 락 시도(상호 배제 안됨)

이런 시도들이 있는데,
뮤텍스 배우기에는 분량도 많고 쓸데없는 내용이라 스킵함.

## 4. 원자적 연산들과 락의 구현

사실상 이 챕터는 이걸 다뤄.

> 어떻게 여러 스레드가 동시에 락을 얻으려 시도해도 딱 한 스레드만 락을 얻을 수 있을까?

앞서 실패 사례들은 이걸 구현하기 위한 시도였고.
이것들은 성공사례라고 볼 수 있어.

하지만 상호 배제 이외의 문제가 있는것도 있고, 그것보다 더 좋은 것도 있고.

### 4-1. Test-And-Set과 스핀락의 구현

앞서 설명했듯 인터럽트 막아서 락을 시도하는 방식이나
load / store를 이용해서 락 시도하는 방식은 실패했어.

그래서 Test-And-Set(atomic exchange) 이라는 원자적 연산이 나왔어.

Test-And-Set이란 대략 이런 코드 스니펫으로 설명할 수 있어.

```cpp
int TestAndSet(int* old_ptr, int new_value){
    int old_value = *old_ptr; // 1. 기존 값 저장
    *old_ptr = new_value; // 2. 새 값을 기존 값이 저장되어있는 주소에 저장
    return old_value; // 3. 이전 값 반환
}
```

대충 이런 느낌으로 연산이 되고,
이 연산은 **원자적으로** 실행돼.

1 ~ 3번 과정이 원자적으로 실행된다는거야.

쉽게 설명하자면,
현재 값을 읽어서 반환하면서
동시에 새 값을 저장하는거라고 할 수 있어.

이게 왜 Test-And-Set이라는 이름이냐면,

기존 값을 읽어서 검사(Test)하고,
새 값을 설정(Set)하는 과정이 원자적으로 일어나기 때문에 
이름이 Test-And-Set인거야.

그리고 이 명령어 만으로 스핀락을 구현하기에 충분해.

```cpp
typedef struct __lock_t {
    int flag; // 0 : 락이 비어있음, 1 : 락을 누가 잡고있음
} lock_t;

void lock(lock_t* lock) {
    while (TestAndSet(&lock->flag, 1) == 1) // lock.flag가 1이라면 누가 잡고있다는 뜻
    ; 
}

void unlock(lock_t* lock) {
    lock->flag = 0;
}
```

이 코드의 `lock()` 매커니즘을 설명하자면,

- `lock.flag`를 1로 바꾸고 원래 값을 반환한다.
- 원래 값이 1이라면, 누가 이미 해당 락을 잡고있다는 뜻이므로 
`lock.flag`는 바꿔도 1인 채로 계속 while문을 진행한다.
- 원래 값이 1이 아니라면(0이라면), 아무도 해당 락을 잡고있지 않다는 뜻이므로 
`lock.flag`는 0에서 1로 바뀌고 while문을 나오며 락을 잡는다.

라고 할 수 있어.

결국, 

> 기존 값이 0이었는지 확인하는 동시에 그 0을 1로 선점하는 것

이라고 할 수 있어.

만약 기존 값이 0이었으면 1로 바꿨을 경우 1로 바뀌며 해당 락을 선점하게 되고,
기존 값이 1이었으면 1로 바꿔도 그대로 1이고..

그리고 반환값을 보는거지.

만약 누가 이미 락을 잡고 있어서 반환값, 즉 기존에 저장되어있던 값이 1이라면
계속 spin-wait를 하는거고,
만약 락이 비어있어서 반환값, 즉 기존에 저장되어있던 값이 0이라면
while 루프를 탈출하는거야.

솔직히 이게 일반적인 생각이랑 좀 달라.

일반적으로는

```text
기존 값을 확인한다
-> 비어 있으면
-> 새 값으로 바꾼다
```

이런 아이디어일텐데,

TAS 기반 스핀락은

```text
일단 새 값 1을 써놓는다
-> 동시에 예전 값은 반환받는다
-> 예전 값을 보고 내가 성공했는지 판정한다
```

이런 느낌이라..

물론 새 값을 쓰는 과정과 기존 값을 반환하는건 원자적으로 일어나고.
그리고 반환받은 기존 값으로 락 획득 성공 여부를 판정하는거지.

새 값을 쓰는 과정과 기존 값을 반환하는 과정 자체가 원자적이기 때문에
두 스레드가 동시에 빈 락을 획득할 수 없게 돼.

요약해서 설명하자면,

> 무조건 잠긴 값으로 만들되, 바꾸기 전 값으로 내가 실제로 락을 선점했는지 판정한다.

### 4-2. 스핀락의 평가

이제 기본적인 스핀락을 이해했고,
구현까지 해봤으니
스핀락의 효율을 평가해보자.

세 가지 항목으로 평가해볼거야.

1. 정확성(제일 중요) : 상호 배제가 제대로 동작하는가
2. 공정성 : 얼마나 공정하게 스레드들이 임계 구역에 진입하게 할 수 있는가
3. 성능 : 지불해야하는 비용은 무엇인가

일단 정확성부터 보자면,

락을 잠그는 것과 이전 값을 반환하는게 원자적으로 일어나니
상호 배제는 제대로 동작해.

공정성부터 보자면,
솔직히 스핀락은 공정하지는 않아.
특정 스레드는 타이밍을 잘못 만나서 다른 스레드들이 계속 임계 구역에 들어가도
계속 while문 루프를 돌고있을 수도 있어.

성능을 보자면, 
스핀락을 사용할 때는 

- 단일 코어 CPU인 경우,
  - 성능적 오버헤드는 꽤 클 수 있어.
  - 스레드 여러개가 계속 실행되면서 한 CPU에서 계속 컨텍스트 스위칭이 발생하기 때문에.
- 멀티 코어 CPU인 경우,
  - 스핀락이 단일 코어 CPU인 경우보다는 꽤 합리적으로 동작해.
  - 스레드의 개수가 CPU의 개수와 대충 같다면 말이야.
  - 임계 구역이 길지 않다면, 다른 프로세서에서 락을 획득하기 위해 while문을 돌면서 기다리는건
  그렇게 많은 사이클을 낭비하지 않아.
  
### 4-3. Compare-And-Swap

또, 락을 구현하기 위한 하드웨어 원자적 연산으로는, 
Compare-And-Swap(Compare-And-Exchange)이 있어.

의사 코드로는,

```cpp
int CompareAndSwap(int *ptr, int expected, int new) {
    int original = *ptr;
    if (original == expected) *ptr = new;
    return original;
}
```

이렇게 되겠네.

이 연산은 대충,

1. 현재 원본 값 저장
2. 원본 값과 expected 값이 일치하는지 검사 후 일치한다면 새 값으로 교체
3. 저장해놨던 원본 값을 반환

이렇게 볼 수 있어.
이 세 과정이 원자적으로 일어나지.

그리고, CAS는 2번 과정이 핵심이야.

expected 값이란, 
현재 해당 값이 이 값일 것이라고
해당 변수에 기대하는 값이야.

락같은 경우에는,
락이 비어있음을 나타내는 값이겠지.
앞의 `TAS` 예시에서는 `0`일테고.

이전에 저장해둔,
해당 변수에 기대하는 값을 나타내는 값을
바꾸기 전의 해당 변수의 현재 값과 비교(Compare)해서
현재 값이 기대하는 값과 다르지 않다면(다른 스레드가 해당 값을 바꾸지 않았으면)
값을 새 값으로 교체(Swap)한다는거지.

이 연산으로 스핀락을 구현해보자면,

```cpp
void lock(lock_t* lock) {
    while (CompareAndSwap(&lock->flag, 0, 1) == 1) // lock.flag가 1이라면 누가 잡고있다는 뜻
    ;
}
```

이렇게 구현할 수 있어.

이것도 앞서 설명한 Test-And-Set과 비슷한데,
차이점으로는
expected 값과 현재 값을 비교해보고 다르면 현재 값을 그대로 냅둔다는거야.

Test-And-Set은 무조건 교체하는 반면에.

그 외에는 Test-And-Set의 로직과 비슷해.

```text
expected = 0
new = 1
```

이니까

현재 값이 0일 때만 1로 교체하는거고,
현재 값이 0이 아니라면(1이라면) 교체하지 않는거지.

TAS와 비교해서 CAS의 장점으로는,
TAS가 무조건 값을 교체하게 되는 것에 반해,
CAS는 무조건 값을 교체하지 않는다는 점이라고 할 수 있어.

그래서 TAS보다 훨씬 강력하지.

#### Load-Linked / Store-Conditional

이건 결은 같은 이야기인데,
사실상 CAS와 비슷한 목적에 사용할 수 있는 원자적 연산 쌍이야.

CAS와 상당히 비슷해서, 이 챕터에 우겨넣어봤어.

정말 쉽게 설명하면,

> Load와 Store 사이에 값에 변경이 일어났다면 Store하지 않는 로직

이라고 할 수 있어.

Load한 값을 저장해놓고,
Store할 때 Load한 값과 현재 해당 데이터의 값이 동일한가 한 번 더 확인하는거야.

더 정확히는, 동일한 주소에 다른 Store가 없었던 경우에만 저장을 성공시키는거지.

이걸로도 스핀락을 구현할 수 있어.

Load / Store 구조가 그대로지만,
Load-Linked / Store-Conditional 매커니즘을 사용하는거지.

Store 할 때 다른 스레드에서에 Store이 없었나 확인해보는거.

### 4-4. Fetch-And-Add와 티켓락

이건 좀 다른 종류의 락을 구현하기 위한 원자적 연산인데,
Fetch-And-Add야.

대충 의사 코드는 이 정도.

```cpp
int FetchAndAdd(int *ptr) {
    int old = *ptr;
    *ptr = old + 1;
    return old;
}
```

일단 

1. 현재 원본 값을 저장
2. 원본 값을 1 증가
3. 저장한 원본 값을 반환

이 세 가지가 원자적으로 일어나.

예를 들어, 현재 값(`value`)이 7이라면

```cpp
int result = FetchAndAdd(&value);
```

이런 코드가 실행되었을 때

```text
result = 7 (현재 값 반환)
value = 8 (FAA로 증감)
```

이렇게 된다는거지.

이게 여러 스레드가 동시에 실행해도
앞에서 설명한 세 가지 동작이 원자적으로 실행되기 때문에
`result`는 반드시 서로 다르게 돼.

티켓 락은, 이 점을 이용하는거야.

```cpp
typedef struct __lock_t {
    int ticket; // 다음의 대기자에게 발급할 번호, 초기값 : 0
    int turn; // 락을 얻을 수 있는 번호, 초기값 : 0
} lock_t;

void lock(lock_t* lock) {
    int myturn = FetchAndAdd(&lock->ticket);
    
    while (lock->turn != myturn)
    ;
}

void unlock(lock_t* lock) {
    FetchAndAdd(&lock->turn);
}
```

같은 변수에 대한 Fetch-And-Add 연산의 값은
(오버플로우가 발생하지 않는 한) 중복되지 않는다는 점을 이용해서,

- 본인의 차례에 Fetch-And-Add로 현재 `ticket`(`myturn`)을 받고, `ticket`을 1 증가시킴
- `myturn`과 `turn`이 같다면, 락을 잡음
- 락을 해제할 때, Fetch-And-Add로 `turn`을 1 증가시키며 
다음 `ticket`을 가진 스레드가 락을 잡을 수 있게 해줌

이렇게 돌아가는 락이야.

왜 `ticket`과 `turn`이 둘 다 필요하냐면,
둘이 역할이 완전히 달라서그래.

- `ticket` : 새로 온 스레드의 순번을 발급
- `turn` : 현재 누가 락을 잡을지 표시

이렇게 달라.

TAS 기반과 다르게,
공정성이 보장되는 방식이지.

먼저 기다린 순서대로 락을 얻을 수 있으니까.
TAS 기반은 먼저 기다린다고 해도 락을 못 잡아서 계속 밀릴 수 있고.

그리고 굳이 Fetch-And-Add를 쓰는 이유는 `myturn`의 중복을 피하기 위해서야.

상호 배제가 보장되는 이유도 `myturn`의 중복이 없고,
`turn`이 한 시점에 하나의 값만 가지기 때문이고.

임계 구역에 들어가기위한 조건이

```cpp
lock->turn == myturn
```

이라서, 서로 다른 번호를 받은 두 스레드가 동시에 조건을 만족할 수가 없어.

예를 들어, `turn == 3`이라면 오직 `myturn == 3`인 스레드만 들어갈 수 있고,
`myturn == 3`인 스레드는 Fetch-And-Add에 의해 오직 하나뿐이니까.

### 4-5. 스핀락의 문제와 해결법

스핀락도 물론 제대로된 락이긴 하지만,
한계가 있어.

결국 스핀하며 대기하는 동안에는 CPU를 그대로 점유한다는거야.

멀티프로세서일 때도 프로세서 개수와 스레드 수가 맞을 때나 그나마 나은거지
보통은 프로세서 개수보다 스레드 수가 많은 경우도 많기 때문에..

게다가 락을 보유한 스레드가 실행되는 중간에 인터럽트가 발생하거나 해서
blocking된다고 생각해봐..

훨씬 CPU 자원을 많이 낭비하겠지.

그 문제를 해결하는게 총 두 가지가 있어.

첫 번째는 완전히 해결하는건 아니고
두 번째는 상당히 해결하는건데,

첫 번째부터 설명해볼게..

첫 번째는,
락을 못 잡은 경우 
자신에게 할당된 CPU를 다른 스레드에게 넘겨주는거야.
양보(yield)하는거지.

물론 계속 실행은 가능한 상태로..

```cpp
void lock(lock_t* lock) {
    while (TestAndSet(&lock->flag, 1) == 1) {
        yield(); // CPU 사용 포기하기(양보하기)
    }
}
```

하지만 이 방식은 그저 양보일 뿐 
컨텍스트 스위칭은 여전히 발생해서
컨텍스트 스위칭에 대한 비용은 계속 떠안을 수 밖에 없어.
여전히 비용이 크지.

그래서, 두 번째 방법인
락을 못 잡은 경우 스핀하는 대신에
해당 스레드를 재우고,
큐에 넣은 후

락을 잡은 스레드가 `unlock()`을 호출하고 나오는 시점에
큐에 들어있는 스레드를 깨우는 방법이 필요해.

이렇게 하면 
TAS 기반 스핀락보다 공정성 / 성능에서 확실한 이득을 챙길 수 있어.

먼저, 큐에 재운 스레드들을 넣어서 
큐 맨 앞의 스레드부터 차례대로 락을 획득할 수 있게 해서,
어떤 스레드가 계속 락을 못 잡는 문제를 해결할 수 있어.
즉, 공정성이 보장된다는거지.

그리고 스레드를 재우니 불필요하게 CPU를 점유하지 않아서
(TAS 기반 스핀락에 비해) 성능도 확실히 챙길 수 있는거지.

이건 책에 나와있는 Solaris 방식의 구현이야.
스스로 구현을 떠올리려니까 OS API를 모르는 나로써는 어렵겠어서
책의 구현을 빌렸어.

`park()` 함수는 호출한 스레드를 잠재우는 함수이고
`unpark(threadID)` 함수는 `threadID`로 명시된 스레드를 깨우는 함수야.

```cpp
#include <queue>

typedef struct __lock_t {
    int flag;
    int guard;
    std::queue<thread_id> *q;
} lock_t;

void lock(lock_t* m) {
    while (TestAndSet(&m->guard, 1) == 1)
    ; // 스핀하면서 임계 구역이 매우 작은 guard 락을 획득(guard 락은 해당 락의 상태 변경에 대한 상호 배제를 수행)
    if (m->flag == 0) {
        m->flag = 1; // 락 획득
        m->guard = 0; // guard 락 해제
    }
    else {
        m->q->push(gettid()); // 스레드 ID를 Queue에 Push()
        setpark(); // park() 전에 도착한 깨우기 신호가 유실되지 않도록 준비
        m->guard = 0; // 해당 락의 상태 변경을 끝냈으니 guard 락 해제
        park(); // 이걸 마지막에 해줘야 모든 일을 끝마치고 스레드가 잠에든다.
    }
}

void unlock(lock_t* m) {
    while (TestAndSet(&m->guard, 1) == 1)
    ; // 스핀하면서 guard 락을 획득
    
    if (q->isEmpty()){ // 큐가 비어있어서 누구도 락을 잡으려하지 않을 경우
        m->flag = 0; // 그냥 락을 놓음
    }
    else { // 큐에 threadID가 들어있어서 다른 스레드가 락을 잡으려할 경우
        unpark(q->front()); // 맨 앞의 스레드 하나 깨우기
        q->pop();
    }
    m->guard = 0; // 해당 락의 상태 변경을 끝냈으니 guard 락 해제
}
```

일단, `guard` 변수로 해당 뮤텍스에 대한 상태 변경의 상호 배제를 수행해.
이건 임계구역이 짧다는게 확실히 보장이 되기 때문에 잠시 스핀해도 상관없어.

그리고, 해당 락을 못 잡았을 경우에 스핀하는게 아니라
큐에 해당 스레드의 `threadID`를 `push()`하고 해당 스레드를 재우지.

그리고, `unlock()` 함수를 호출했을 때 

- 큐가 비어있다면 어떤 스레드도 락을 기다리지 않다는 뜻이라서
락만 풀고 종료하고
- 큐에 하나라도 원소가 있다면 적어도 한 스레드는 락을 기다리고 있다는 뜻이기 때문에
큐 맨 앞의 스레드 하나를 깨우고 종료해.

`setpark()`는 `park()` 직전에 호출해서, 
잠들기 전에 `unpark()`가 호출되더라도 깨우기 신호가 유실되지 않도록 해줘.
(이건 좀 복잡한데 분량상 생략함.)

그리고 이렇게 스레드를 재우고 깨우며 락을 걸고 푸는게
현대적인 블로킹 뮤텍스 구현의 기본 아이디어야.
