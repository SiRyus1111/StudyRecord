## 1. Command 패턴이란?

책에 나와있는 정의로는

> 1. 요청을 객체에 담아 캡슐화해서
> 2. 요청을 보내는 객체와 요청을 수행하는 객체를 서로 분리하는 디자인 패턴

이라고 해.

솔직히 이걸로는 감이 잘 안 잡힐 것 같은데 
그냥 그거야.

> 1. 말 그대로 객체에 실행할 함수를 담고
> 2. 그 객체의 함수를 실행하는 부분과 실제로 실행되는 부분을 분리한다.

이거야.

더 쉽게 말하면,

> 그냥 함수 자체를 객체에 담는다.

라고 할 수 있겠네.

좀 어렵게 말하면,

- 객체에 실행할 함수와 실행에 필요한 데이터, 즉 요청을 담고
- 그 객체의 함수를 직접 실행하는 부분과(`Execute()` 하는 부분, Invoker)
실제로 실행되는 부분(`Execute()`가 실제로 건드리는 부분, Receiver)을 분리한다.

## 2. Command 객체

Command 객체란,
작업을 실행하기위한 인터페이스(C++에는 가상함수만 있는 클래스)를 선언하는 추상 클래스야.

가장 기본적인 형태에서는
이 인터페이스에 `Execute()` 함수가 포함돼.

```cpp
class Command {
public:
    virtual ~Command();
    virtual void Execute() = 0;
};
```

그리고 이 `Command` 인터페이스를 상속한 하위 클래스는
해당 작업(요청)의 실행에 필요한 별도의 정보를 들고,
`Execute()`을 오버라이딩(재정의)해서 작업을 구현해서 요청을 호출하게 해.

```cpp
class InputCommand : public Command {
private:    
    std::shared_ptr<std::string> string_ptr;
public:
    InputCommand(std::shared_ptr<std::string> s_p) : string_ptr(s_p) {
    
    }
    void Execute() override {
        getline(cin, *string_ptr);
    }
};
```

근데 호출하는 쪽에서는 `Execute()`가 실제로 뭘 하는지 몰라도 돼.
해당 `Execute()` 함수가 뭘 필요로 하는지 몰라도 돼.
그저 `Execute()` 함수를 실행하면 어떤 작업인지는 몰라도 작업이 실행되는 느낌이지.

## 3. Invoker / Command / Receiver / Client

> Invoker / Command / Receiver / Client

이 네 가지로 Command 패턴을 나타낼 수 있어.

일단 Invoker부터 보자.

Invoker는 실제로 Command 객체의 `Execute()`를 실행하는 쪽이야.
그러니까 `Execute()`가 실제로 뭘 하는지 모르는 채,
`Execute()`를 실행하는거지.
즉, Command를 실제 언제 실행할지 결정하는 쪽이야.

Command는 말 그대로 해당 요청의 정보가 들어있는,
`Execute()` 함수의 구현이 들어가있는 쪽이야.
그러니까 실제 `Execute()` 함수의 구현과,
`Execute()` 함수가 실행되기 위해서 필요한 정보들이 들어가있겠지.

Receiver는 실제 Command의 요청인 
`Execute()` 함수의
내부의 작업들이 실제로 실행되는 곳이야.

그리고 마지막으로 Client는, Command를 생성하고 Receiver과 연결해서 Invoker에게 넘겨주는,
그냥 Command를 생성하는 쪽이라고 보면 돼.

```text
              생성 / 연결
     ┌-----------(1)---------┐
     │                       ↓
[ Client ]              [ Receiver ]
    │                        ^
   (1) Command 생성           |
    ↓                       (4) 실제 작업 호출
[ Command ] -----------------┘
  ^    ^ 
  |    └------┐
 (2) 보관      |            
  |          (3) Execute()
  │           |            
[ Invoker ] --┘                 

```

이 그림에서 보이듯이,

1. `Client`는 `Receiver`를 `Command`에 연결하고 `Command`를 생성해준다.
2. 생성된 `Command`를 `Invoker`에 넘겨준다.
3. `Invoker`는 원하는 타이밍에 `Command.Execute()`를 실행한다.
3. `Command.Execute()`의 내부 작업은 `Receiver`에서 실행된다.

맨 앞에서

> 요청을 객체에 담아 캡슐화해서
> 요청을 보내는 객체와 요청을 처리하는 객체를 분리한다.

라고 했었지?

- 요청을 캡슐화하는 객체 : Command
- Command를 만드는 객체 : Client
- 요청을 보내는 객체 : Invoker
- 요청을 처리하는 객체 : Receiver

라고 보면 돼.

## 4. 내가 써본 사례

나는 룸 시스템을 구현하는데 이 디자인 패턴을 썼어.

기존에는 이게 여러 스레드가 동시에 한 룸의 상태를 변경해서

- 레이스컨디션 지옥
- 데드락 회피 지옥
- 삭제 후 참조(Use-After-Free) 지옥

이런 지옥들을 견뎌내고 있었는데,
도저히 못해먹겠어서

모든 클라이언트 스레드는
오직 메시지 큐에 작업을 Push하기만 하고,
룸 전용 스레드가 그렇게 Push된 작업들을 Pop해서 처리하는 구조로 갈아엎었어.

![](https://velog.velcdn.com/images/siryus0907/post/7e36d0b7-5872-4fac-aefb-1da9c2006129/image.jpg)

(위의 그림을 바탕으로 제미나이가 그려준 아스키 아트)
```text
[Thread 1]   [Thread 2]   [Thread 3]
       |            |            |
       V            V            V
       +-------------------------+
       | +---------------------+ |
       | |      Task Queue     | | <--- PROTECTED QUEUE
       | +---------------------+ |
       | |       [TASK 1]      | |
       | +---------------------+ |
       | |       [TASK 2]      | |
       | +---------------------+ |
       | |       [ ... ]       | |
       | +---------------------+ |
       |   << TASKS_MUTEX >>     | <--- MUTEX (PROTECTS QUEUE)
       +-------------------------+
                    |
                    | (Pop Task)
                    V
           [Room Thread (Actor)]
                    |
                    | (Executes on)
                    V
               +---------+
               |   Room  |
               +---------+
```

위의 사진처럼, 메시지 큐(사진에서는 Task Queue)에 대한 접근을 `tasks_mutex`로 보호하고,
여러 스레드는 그저 메시지 큐에 `push()`만 수행하고,
룸 스레드는 해당 메시지 큐에서 작업을 `pop()` 해서 룸에 적용하는 구조야.

흔히 Actor 모델이라고 하는 구조와 비슷한 구조지.

- 외부에서 해당 룸(Actor)을 직접 수정할 수 없고
- 오직 중간의 메시지 큐(Mailbox)로만 소통할 수 있는 구조.

그리고 그 메시지 큐에 뭘 어떻게 넣어야 할까 고민하다가
이 디자인 패턴을 알게됐어.

내가 기존에는 단순히 `std::function`같은걸 이용해 볼 생각이었는데(스레드 풀 구현하다 알게됨),
이게 단점이 한 시그니처 형태의 함수만 넣을 수 있다는 점이었어.

`void()`면 `void()`만,
`int(int, bool)`이면 `int(int, bool)`만..

물론 람다 식으로 넣을 수도 있겠지만,
그건 그 때 솔직히 몰랐고,
지금도 좀 복잡해보여서 배제했어.

근데 룸에 필요한 작업들은 되게 다양한 정보들이 필요했고..
결국

> 같은 클래스로 다양한 데이터가 필요한 다양한 작업을 나타낼 수 있는 기법

이 필요했고,
거기서 찾은게 Command 패턴이었어.

Command 패턴은 상속을 이용해서
같은 클래스로 다양한 데이터가 필요한 다양한 작업을 나타낼 수 있었어.

그리고 여러 객체로 각 작업을 확실하게, 명시적인 타입으로 나타낼 수 있을 뿐만 아니라,
작업 별 상태나 인터페이스(`std::future` 등)를 가질 수 있었지.

솔직히 내가 집중한 것도 Invoker과 Receiver의 분리보다는,
**다양한 데이터가 필요한 다양한 작업을 하나의 클래스로 나타낼 수 있다**는 점이었어.

Invoker과 Receiver의 분리는 결국 덤 정도였고.

하지만, 이번 구현에서 결국 Task Queue의 Task를 어떻게 설정해야하는지 잘 배운 것 같아.

### RoomTask

```cpp
class RoomTask {
public:
    virtual ~RoomTask() = default;
    virtual void Execute(Room& room) = 0;
};
```

#### JoinRoomTask

```cpp
class JoinRoomTask : public RoomTask {
private:
    std::shared_ptr<ClientSession> client;
public:
    JoinRoomTask(std::shared_ptr<ClientSession> _client) : client(_client) {
        
    }
    void Execute(Room& room) override {
        room.AddMember(client);
    }
};
```

#### LeaveRoomTask

```cpp
class LeaveRoomTask : public RoomTask {
private:
    SessionID session_id;
    std::promise<void> done;
public:
    LeaveRoomTask(SessionID _session_id) : session_id(_session_id) {

    }
    std::future<void> GetFuture() { // 작업이 끝났음을 나타내는 future를 get하는 getter 함수
        return done.get_future(); 
    }
    void Execute(Room& room) override {
        room.RemoveMember(session_id);
        done.set_value(); // 해당 작업이 실제로 처리되었다는 신호
    }
};
```

#### BroadcastRoomTask

```cpp
class BroadcastRoomTask : public RoomTask {
private:
    std::shared_ptr<Packet> packet;
    SessionID sender_id;
public:
    BroadcastRoomTask(std::shared_ptr<Packet> _packet, SessionID _sender_id) : packet(_packet), sender_id(_sender_id) {

    }
    void Execute(Room& room) override {
        room.RoomBroadcast(packet, sender_id);
    }
};
```

#### ShutdownRoomTask

```cpp
class ShutdownRoomTask : public RoomTask {
public:
    ShutdownRoomTask() {

    }
    void Execute(Room& room) {
        room.Shutdown();
    }
};
```
