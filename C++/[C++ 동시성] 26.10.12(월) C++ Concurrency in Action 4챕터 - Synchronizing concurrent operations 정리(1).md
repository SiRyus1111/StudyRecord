## 1. 스핀락, Sleep, Condition Variable

여러 스레드 간의 실행 순서를 동기화하는 방법은,
크게 

- 스핀락 : 대기하는 스레드가 조건이 만족되었는지를 계속 확인하기
- Sleep : 대기하는 스레드가 조건이 만족되었는지를 계속 확인하되, 
한 번 확인되었으면 잠시 대기하다 다시 확인하기
- Condition Variable(Event) : 조건이 만족되었으면 신호를 보내서 대기하는 스레드를 깨우기

이 세 가지 정도가 있어.

스핀락 같은 경우는 계속 CPU를 점유하기 때문에,
프로그램의 실행 속도가 크게 저하되겠지.

Sleep 같은 경우는 스핀락보다 훨씬 CPU를 적게 점유하지만,
Sleep 시간이 너무 길면 작업이 완료되어도(조건이 만족되어도) 계속 Sleep이 되어
지연이 발생하고,
Sleep 시간이 너무 짧으면 스핀락과 다를 바가 없어져.

앞선 두 방법과 다르게,
Condition Variable은 다른 스레드가 이벤트를 트리거하기를 기다리는 방식으로써,
조건이 만족되면(이벤트가 트리거되면) 바로 대기하는 스레드에 신호를 보내서
작업이 완료되었음을 확인하고 대기하는 스레드가 깨어나도록 할 수 있어서,
스핀락의 단점(CPU 점유) / Sleep의 단점(지연)을 해결할 수 있어.

그래서 일반적으로는 Condition Variable이 다른 스레드의 작업을 기다리는데는
제일 좋은 방법이야.

뭐 여기까지는 튜토리얼이라 모든 내용을 설명했는데,
지금부터는 많은 생략이 있으니까,
앞서 링크를 삽입한 두 글을 보면 돼.

## 2. Condition Variable

[링크](https://velog.io/@siryus0907/C-26.07.25%ED%86%A0-stdconditionvariable)

```cpp
// 대충 짠 CV 예시
#include <condition_variable>
#include <mutex>
#include <queue>

template<typename T>
class ThreadSafeQueue {
private:
    std::mutex mtx; // 동일한 뮤텍스를 사용해 조건 변경 / 조건 확인을 함
    std::queue<T> q; // 예시에 필요한 큐(Push / Pop)
    std::condition_variable cv; // CV
public:
    void Push(T& data) {
	
        { // 뮤텍스를 잡고 조건 변경
            std::lock_guard<std::mutex> lock(mtx);
            q.push(data);
        }
    
        // 조건 변경 후 notify 신호 보내기
        cv.notify_one();
    }

    void WaitAndPop(T& data) {
        {
            std::unique_lock<std::mutex> lock(mtx);
            wait(lock, [this] { return !q.empty() }); // q가 비어있지 않으면 wait() 하지 않도록 predicate 작성
        
            data = q.front();
            q.pop();
        }
    }
    
    bool TryPop(T& data) {
        {
            std::lock_guard<std::mutex> lock(mtx);
            if (q.empty()) return false;
            
            data = q.front();
            q.pop();
            
            return true;
        }
    }
};
```

### 2-1. 추가 내용

1. `std::condition_variable` 말고도, 뮤텍스와 유사한 것들을 넣을 수 있는 
`std::condition_variable_any`도 있지만, 성능은 낮기 때문에
`std::condition_variable`을 우선적으로 사용한다.

## 3. `future` / `promise`

대기하는 스레드가 계속 대기하는 상황이 발생한다면,
즉 여러 번 `wait()`으로 대기한다면
Condition Variable이 적합해.

하지만,
딱 한 번만 대기하면 되고,
조건이 참이 된 이후에는 해당 CV에서 다시 기다릴 필요가 없게 된다면,
CV가 최선의 동기화 수단은 아니야.

여기서 쓰이는게 바로 future / promise야.

[링크](https://velog.io/@siryus0907/C-Standard-Library-26.05.07%EB%AA%A9-%EC%8A%A4%EB%A0%88%EB%93%9C-%EA%B4%80%EB%A0%A8-%EB%9D%BC%EC%9D%B4%EB%B8%8C%EB%9F%AC%EB%A6%ACthread-promise-future)

(`future` / `promise`가 뭔지, 동작 원리(shared state)가 어떻게 되는지)
(`packaged_task`가 뭔지는 이 글에 나와있음.)

하지만 `async` / `shared_future`는 안 나와있어서
이번 글에서는 그 두 가지 정도를 쓸거야.

결국 CV는 여러 번 대기하고 신호를 받으며,
`future` / `promise`는 `promise::set_value()` / `promise::set_exception()` / `future::get()`으로
일회성으로 대기하고 반환 값 / 예외를 받아온다고 할 수 있어.

`std::packaged_task`는 callable 객체까지 묶어서
해당 callable 객체의 예외 / 반환 값을 자동으로 shared state에 넣어주는거고.

### 3-1. `async`

`async()` 함수는 쉽게 말해서
자동으로 별도의 스레드로 함수를 실행 + `future`를 반환해서
실행한 스레드의 결과가 해당 `future`를 통해 전달되게 하는 함수야.

이게 솔직히 제일 간단한데,
그냥 스레드 생성하는 것 마냥

```cpp
#include <future>

int doSomething();

int main() {
    // 반환값이 int로 나오므로 int형의 future로 받음
    std::future<int> result = std::async(doSomething);
    
    // 다양한 작업들 수행
    
    // async로 실행한 결과 받음
    int res = result.get();
}
```

이렇게 callable 객체를 넘겨버리면 돼.
물론 인자를 넘기는 것도 똑같아.

그리고 이것도 결국 decay-copy 때문에
레퍼런스 변수는 `std::ref()`로 넘겨야 함.

그리고 `async`는 실행 정책을 정할 수 있어.

- 새로운 스레드를 생성해서 해당 스레드에서 함수를 비동기적으로 실행 
: `std::launch::async`
- 함수 실행을 미뤘다가 `future::get()` / `wait()`을 호출한 스레드에서 실행
: `std::launch::deferred`
- 둘 중 어떤 방식을 사용할지 구현체가 결정
: `std::launch::async | std::launch::deferred`

기본적으로는 세 번째 정책을 택하지만,
프로그래머가 직접 새로운 스레드를 생성해서 비동기적으로 실행할지,
동기적으로 실행할지 결정할 수 있어.

하지만 무조건 별도 스레드로 실행해야하는 작업이라면
`std::launch::async` 옵션을 명시해야겠지.

그리고 만약 `std::launch::deferred`로 실행했는데
`get()` / `wait()`를 호출을 안했다?
그러면 영원히 해당 작업은 실행되지 않게 돼.
(`get()` / `wait()`를 호출해야 실행되니 당연하겠지?)

### 3-2. `shared_future`

여러 개의 `future`와 하나의 `promise`가 연결되어있는 `future`로,
shared state에 데이터가 준비되면
여러 개의 `shared_future`에서 데이터를 꺼낼 수 있어.

`shared_ptr`처럼,
모든 `future` 객체에서 데이터를 꺼냈으면
shared state가 소멸하게 되겠지.

그리고 이건 같은 `shared_future`를 사용하면 안돼.
같은 `shared_future`를 사용해서 `get()`을 하면
해당 멤버 함수는 동기화가 안 되어있기 때문에 데이터 레이스가 발생해서
무조건 `shared_future`를 복사해서 각 스레드가 사용해야해.

그리고 `shared_future` 객체는 `future` 객체로부터 `std::move`를 사용해서 
생성된다는 것 정도?

```cpp
std::promise<int> p;
std::future<int> f(p.get_future());

std::shared_future<int> sf(std::move(f));

// std::shared_future<int> sf(p.get_future()); / 이것도 됨(암시적 소유권 이전)
// std::shared_future = p.get_future().share(); / 이것도 됨(share() 함수 이용)
```

## 4. 시간 제한 동안 기다리기

`future::get()`이나 `condition_variable::wait()`같은 함수는
이벤트가 발생할 때 까지 스레드를 무제한 대기시키는데,

종종 무제한이 아니라 일정 시간만 기다리고
해당 작업이 완료가 안 되었다면 다른 작업을 실행해야할 필요가 있을 수가 있어.

그럴 때 사용하는 시간 제한은 두 종류가 있는데,

- 기간 기반(duration-based) 타임아웃 : 일정 시간 만큼 기다림
- 절대(absolute) 타임아웃 : 절대적인 특정 시점까지 기다림

이 정도.

그리고 저런 시간 제한을 넣는 대기 함수도 있어.

기간 기반 타임아웃에는 `_for` 접미사가 붙고,
절대 타임아웃에는 `_until` 접미사가 붙어.

예를 들어,
CV에는 `wait()`의 두 가지 바리에이션이 있는데,
`wait_for()`는 최대 특정 시간 만큼만 기다리는 함수고,
`wait_until()`은 절대적인 특정 시점까지만 기다리는 함수야.

일단 기초는 이 정도면 됐고,
이제 좀 더 심화 느낌으로 살펴보자.

그리고 솔직히 이 파트 왜 배우는지 의문이 들 수 있는데,
그냥 타임아웃이 필요할 때 시간을 어떻게 다룰 수 있는지에 대해 배우는 용도야.
(그말인 즉슨, 세부 사항은 스킵해도 된다는 것. 메인 줄기가 아님..)

### 4-1. C++에서 시간이 저장되는 방법

기본적으로 시간은 이렇게 네 가지 정보를 가지고 있는 `clock` 클래스를 기반으로
시간의 정보가 제공돼.

- 현재 시간
- `clock`에서 얻은 시간을 나타내는데 사용되는 값의 타입
- `clock`의 틱 주기
- `clock`의 틱이 일정한지에 대한 여부

현재 시간은 `now()`를 호출해서 얻을 수 있어.

```cpp
std::chrono::system_clock::now(); // 시스템 클락의 현재 시간을 반환
// 반환 유형은 std::chrono::system_clock::time_point
```

`clock` 클래스 자체의 틱 주기는 초 단위의 분수로 저장돼.

그리고 결국 틱이 일정한지가 상당히 중요하기 때문에,
`std::chrono::steady_clock`의 형태로 안정된 `clock`이 제공돼.

이 `clock`을 사용하면, 무조건 틱 주기가 안정되어있다는거야.
그래서 일반적으로는 되게 좋지.
(이건 안정성을 생각한다면, 시간이 정확해야한다면 좋겠지.)

그리고 시스템의 실시간 시각을 타나내는 `std::chrono::system_clock`도 있고,
(시스템의 시간이 필요한 경우에 좋겠지.)
틱 주기가 가장 짧은 `clock`은 `std::chrono::high_resolution_clock`이 있고.
(이건 좀 작은 시간 단위가 필요하면 좋겠지?)

그리고 이런 `clock` 클래스들은 `<chrono>` 헤더에 저장되어있고.

그리고 C++에서는 시간이

- duration - 특정 기간
- absolute - 절대 시간

이렇게 나뉜다고 했었지?

### 4-1. duration : 특정 시간 만큼 대기하기

duration부터 보자면 `std::chrono::duration<>` 클래스 템플릿을 통해 처리되고,
말 그대로 특정 기간을 나타내는 클래스라고 보면 되는데,
첫 번째 인자는 시간의 표현 타입 / 두 번째 인자는 duration의 1틱이 몇 초를 나타내는지를 나타내는 분수야.

`std::chrono::duration<double, std::ratio<1>>`으로 선언하면
시간이 `double`로 표현 / 1틱(최소 표현 단위)가 1초인 표현이 되겠지.

예를 들어,

```cpp
// 1틱이 60초(1분)고 short로 표현되는 시간 표현
std::chrono::duration<short, std::ratio<60>>

// 1틱이 1/1000초(1밀리초)고 double로 표현되는 시간 표현
std::chrono::duration<double, std::ratio<1, 1000>>
```

이런 식으로..

그리고 저렇게 분수로 단위가 몇 초인지를 써놓는거 말고도,
`std::chrono` 네임스페이스 내에서
나노초 / 마이크로초 / 밀리초 / 초 / 분 / 시간 등 다양한 duration을 위한
미리 정의된 `typedef` 집합을 제공해.

- `std::chrono::nanoseconds` (`duration<..., std::nano>`)
- `std::chrono::microseconds` (`duration<..., std::micro>`)
- `std::chrono::milliseconds` (`duration<..., std::milli>`)
- `std::chrono::seconds` (`duration<..., std::ratio<1>>`)
- `std::chrono::minutes` (`duration<..., std::ratio<60>>`)
- `std::chrono::hours` (`duration<..., std::ratio<3600>>`)

생성자에 정수를 넣으면 딱 그 단위 만큼을 나타내는 객체가 생성되는거지.

시간을 표현하는 방법으로는 `C++14`부터 사용가능한
시간 단위 리터럴 접미사 연산자도 있어.

`std::chrono_literals` 클래스에 있는 연산자들인데,
`15ns`라고 써놓으면 `std::chrono::nanoseconds(15)`와 같은 의미를 지녀.

그리고 값의 절삭이 필요하지 않은 경우(더 큰 단위에서 작은 단위로 변환하는 경우)에는
다른 duration 형식으로의 변환이 암시적으로 일어나고,
절삭이 필요한 경우에는 암시적으로 변환하는건 불가능해.

명시적 변환은 `std::chrono::duration_cast<>()`를 이용하면 되는데,

```cpp
// ms -> sec 변환 예시
std::chrono::milliseconds ms(54802);
std::chrono::seconds s = std::chrono::duration_cast<std::chrono::seconds>(ms);
```

이런 식으로 하면 돼.
절삭도 잘 되지.

그리고 duration은 산술 연산을 지원하기 때문에,
더하거나 뺄 수 있고 / 같은 자료형으로 나누거나 곱할 수도 있어.

그리고 해당 duration에 포함된 시간 단위의 갯수는
`count()` 함수로 얻을 수 있는데,
예를 들어
`std::chrono::miliseconds(1234).count()` 해놓으면
`1234`가 나온다는거야.

지금까지 특정 기간을 다루는 `std::chrono::duration`에 대해 알아봤는데,
여기서부터가 동시성이랑 연관돼.

```cpp
std::future<int> f = std::async(std::launch::async, some_task);
```

이런 비동기 작업을 수행할 때,
딱 15초 동안만 기다려야 하는 경우에는

```cpp
if (f.wait_for(15sec) == std::future_status::ready) {
    res = f.get();
}
```

이렇게 `future`의 값이 준비된지 확인하는 것을 더해서
15초만 기다린 후 결과를 반환받을 수 있는거야.

그리고 이런 duration-based 대기는,
내부 `steady_clock`을 사용하여 시간을 측정하지.

결국 duration-based 대기를 요약하자면,

> `_for` 접미사의 함수와 `std::chrono::duration<>` 객체로
> **어느정도만큼 기다릴지** 나타낸다.

라고 할 수 있어.

솔직히 기타 내용들은 치워버려도 됨ㅋㅋ

### 4-3. time point : 특정 시간까지 대기하기

`clock`의 특정 지점(time point)는
`std::chrono::time_point<>` 클래스 템플릿으로 표현되고,

- 첫 번째 템플릿 인자로 참조하는 `clock`을
- 두 번째 템플릿 인자로 측정 단위를

지정해.

그리고 각 time point의 값은
특정 지점(epoch, 에포크)으로부터 경과한 시간을 기준으로 나와.

`clock`의 에포크는 기본 속성이지만,
직접 조회 / 지정할 수는 없고,

보통 1970년 1월 1일 00:00이나,
해당 애플리케이션을 실행한 컴퓨터가 부팅된 순간을 써.

그리고 `clock`들은 에포크를 공유하거나 독립적인 에포크를 써.

자, 이제 `time_point`의 예시를 들어보자면,

```cpp
// system clock 사용 / 분 단위
std::chrono::time_point<std::chrono::system_clock, std::chrono::minutes>

// steady clock 사용 / 밀리초 단위
std::chrono::time_point<std::chrono::steady_clock, std::chrono::miliseconds>
```

이렇게 쓰면 돼.

각 `time_point`가

- 어느 `clock`을 기반으로 나오는지,
- 얼만큼의 단위로 표현이 되는지

를 템플릿 인자로 넘기는거야.

그리고 `time_point` 객체에다가
`duration`을 더하거나 뺄 수 있기 때문에
그렇게 산술 연산을 해서 새로운 time point를 생성할 수 있어.

```cpp
// high resolution clock의 현재 시간 + 500 나노초
std::chrono::high_resolution_clock::now() + std::chrono::nanoseconds(500);
```

이건
중간에 어떤 작업을 얼마나 오래 수행했든
딱 데드 라인까지만 기다릴 수 있게 할 수 있어.

```cpp
ProcessData();  // 2초 소요

cv1.wait_for(lock1, std::chrono::seconds(10)); // 6초 대기

ProcessMoreData(); // 1초 소요

cv2.wait_for(lock2, std::chrono::seconds(10)); // 5초 대기
```

이렇게 중간에 다른 작업들이 끼어있으면,
duration만으로는 전체 작업의 제한 시간을 지킬 수 없기 때문에,

```cpp
auto deadline = steady_clock::now() + seconds(10);

ProcessData();

cv1.wait_until(lock1, deadline);

ProcessMoreData();

cv2.wait_until(lock2, deadline);
```

이렇게 변동되지 않는 절대 시간으로 데드 라인을 박아놓으면
전체 작업의 제한 시간을 걸어버릴 수 있어.

그리고 동일한 `clock`을 공유하는 두 time point에서
한 time point - 다른 time point를 할 수도 있어.

그렇게 하면 두 time point 사이의 시간 길이를 나타내는
duration을 얻을 수 있겠지.

이건 코드의 실행 시간을 측정하는데 되게 유용해.

```cpp
auto start = std::chrono::high_resolution_clock::now();

ProcessData();

auto end = std::chrono::high_resolution_clock::now();

// ProcessData()의 실행 시간
std::chrono::duration<double, std::chrono::seconds> time = end - start; // 명확한 시간 단위가 필요하므로 auto를 쓰지 않음
```

이렇게 말이야.

그리고 이게 `clock` 인자도 되게 중요한데,
결국 시간을 재는건 `time_point`의 `clock`이라,
따라서 
시스템 시각이 조정될 수 있는 `system_clock`을 사용하면 실제 대기 시간이 짧아지거나 길어질 수 있어.
반면,
`steady_clock`은 일정한 시간을 기준으로 타임아웃을 처리할 때 적합하겠지.

결국 요약하면,

> `_until` 접미사의 함수와 `std::chrono::time_point` 객체로
> 특정 시점까지 기다릴 수 있다.

> `std::chrono::duration` 객체 만으로는 불가능한
> 여러 작업 전체에 대한 데드라인을 만들 수도 있다.

이 정도가 되겠네..
