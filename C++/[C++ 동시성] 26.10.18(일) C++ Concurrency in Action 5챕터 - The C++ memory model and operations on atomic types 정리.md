## 1. 메모리 모델 기본

메모리 모델은 기본적으로 두 가지 측면이 있어.

- 구조적 측면 : 데이터가 어떻게 배치되는지
- 동시성 측면 : 데이터가 보이는 시점 / 순서가 어떻게 되는지

로우 레벨의 Atomic Operation을 다룰 때는 구조적 측면이 중요하니까,
일단 첫 번째인 구조적 측면부터 알아보자.

### 1-1. 객체와 메모리 위치

C++ 표준은 기본적으로 객체를 '저장 장치의 영역'으로 정의해.
그리고 각 객체에는 유형 / 수명같은 속성이 있지.

객체의 타입이 `int`든 / `float`든 / 따로 정의된 클래스든 간에
결국 객체가 저장되는건 하나의 메모리 위치라고 할 수 있어.
(메모리 주소와 다름.
여러 메모리 주소를 점유하는 객체가 있다면 하나의 메모리 위치를 점유하고 있는거임.)

여기서 중요한건,

- 멤버 변수를 포함해서 모든 변수는 C++에서 말하고 있는 객체이다.
- 모든 객체는 적어도 하나의 메모리 위치를 차지한다.
- 기본 유형의 변수는 크기와 상관 없이, 
인접해있거나 배열의 일부더라도 정확히 하나의 메모리 위치를 차지한다.
- 인접한 비트(바이트 아님) 필드는 동일한 메모리 위치의 일부이다.

이 정도겠네..

근데 왜 이게 동시성과 연관이 있는걸까 싶지?

바로 데이터 레이스를 정의하기 위해서야.
데이터 레이스를 정의하려면 메모리 위치라는 개념을 명확히 정의해놔야하거든.

이어서 보자.

### 1-2. 객체, 메모리 위치, 그리고 동시성

여러 스레드가 서로 다른 메모리 위치에 접근한다면 아무 문제가 없을 테지만,
여러 스레드가 동일한 메모리 위치에 접근한다면 문제가 발생할 수 있어.
(물론 읽기만 한다면 문제는 발생하지 않지만,
한 스레드라도 쓰기를 한다면 문제가 발생할 수 있음)

이 문제를 레이스 컨디션이라고 하고,
레이스 컨디션이란
여러 스레드가 동일한 메모리 위치에 접근하게 되어 실행 시 마다 실행 순서에 따라
결과가 달라지는 것을 말해.

레이스 컨디션을 막으려면
여러 스레드의 접근 사이에 강제적인 순서가 보장되어야 하는데,

이 접근 순서를 강제적으로 보장하는 방법이 예전에 설명했던 뮤텍스야.

같은 메모리 위치에 대한 접근에 대해서
동일한 뮤텍스를 사용하면
하나의 스레드만 해당 메모리 위치에 접근할 수 있으니까,
한 번에 한 스레드의 접근만 허용이 되겠지.
(무조건 한 스레드 접근 -> 또 다른 스레드 접근의 순서 보장이 됨.)
(그리고 한 스레드 접근의 결과가 또 다른 스레드가 접근했을 때 보임.)

또 다른 방법은
동일한 메모리 위치나 다른 메모리 위치에서
원자적 연산(Atomic Operation)의 동기화 속성을 사용해서
여러 스레드 간의 접근 순서를 강제하는거야.
(이건 나중에 3번 파트에서 알아보자.)

결국 여러 개의 스레드가 동일한 메모리 위치에 접근하는 경우에는
각 접근에는 정의된 순서가 있어야 한다는거야.

그렇지 않은 경우,
데이터 레이스가 되어서 정의되지 않은 동작이 발생하게 돼.

데이터 레이스는 같은 메모리 위치에
별도의 순서 고정 없이(동기화 없이) 적어도 하나는 쓰기 연산인 상태로 동시에 접근하는 상황이야.

여기서 개념 하나 제대로 잡고 가자.

- 레이스 컨디션 : 스레드 간 실행 순서에 따라 결과가 달라지는 상황
- 데이터 레이스 : 동기화 없이 **같은 메모리에 동시에 접근 / 쓰기**하는 상황(메모리 관점)

이렇게 분리해서 보면 돼.

- 레이스 컨디션 : 논리적인 상황
- 데이터 레이스 : C++에서 정해놓은 특정(메모리 접근에 대한) 상황

으로 놓고 보면 편해.

### 1-3. 수정 순서

앞에서 결국 중요한건

> 메모리 위치에 접근할 때의 순서 보장을 해주어야 한다.

라고 했었지?

근데 이게 예외가 되는 부분이 하나 있어.

바로 같은 메모리 위치에 여러 스레드가 접근할 때
각 스레드가 원자적 연산을 사용하면 정의되지 않은 동작을 피할 수 있다는 점이야.

이게 왜 그럴까?

바로 원자적 객체의 수정 순서(Modification Order) 때문이야.

말 그대로, 해당 객체에 대해 초기화부터 시작해서
수정이 발생하는 순서라고 볼 수 있는데,
이 수정 순서가 여러 스레드 간에 맞지 않으면
여러 스레드 간의 같은 객체에 대한 정보가 일치하지 않게 되어서
큰일이 날 수 있어.

일반적인 객체는 모든 스레드에서 보여지는 수정 순서가 다를 수도 있어서
사용자가 직접 뮤텍스 등으로 수정 순서를 동일하게 맞춰줘야하지만,

원자적 객체(`std::atomic`)는 모든 스레드에서 보여지는 수정 순서가 같아.
컴파일러가 보장해주지.

(아, 그리고 이건 개별 객체에만 적용되고,
서로 다른 객체들 간의 상대적 연산 순서까지 동일하게 맞추는건 아니야.)

그래서 같은 메모리 위치에 여러 스레드가 원자적 연산을 수행할 때는,
모든 스레드에서 보여지는 수정 순서가 같게 되므로
정의되지 않은 동작을 피할 수 있게 되는거지.

그래서

```cpp
std::atomic<int> a = 0;

// thread 1
a.store(10, std::memory_order_relaxed);


// thread 2
a.store(20, std::memory_order_relaxed);
```

이렇게 두 스레드에서 동시에 한 `std::atomic` 변수에 대해
`relaxed` 메모리 배리어로 쓰기 작업을 해도
자체적으로 전역적인 수정 순서가 같다는 것은 보장이 되기 때문에
문제가 없게 되는거야.

물론, `10`이 먼저 쓰여질지 `20`이 먼저 쓰여질지 자체는 결정되지는 않아.
그냥 동일한 수정 순서를 보게 된다는거야.

그리고 하나 더 살펴보자면,
수정 순서는 무조건 시간의 흐름에 따라 단방향으로 관측되야해.

그러니까, 한 값을 관측했다고 하면
다음에 관측하는 값은 이전의 수정 순서의 값일 수 없다는거야.

솔직히 이건 당연한 소리지?
(실제로 무조건 당연하지는 않지만..)

#### 요약

> C++의 각 객체들은 하나의 메모리 위치에 올라간다.

> 각 메모리 위치에 동기화 없이(정의된 순서 없이) 여러 스레드가 동시에 
쓰기 / 접근하는게 데이터 레이스이다.

> 데이터 레이스를 막기 위해서는 정의된 순서대로 각 메모리 위치에 접근해야한다.

> 수정 순서는 해당 객체에 대한 쓰기의 순서이고,
> 여러 스레드 간의 같은 객체에 대한 수정 순서는 일치해야한다.

> 일반적인 객체에서는 뮤텍스 등으로 같은 객체에 대한 수정 순서를 일치시켜야한다.

> `std::atomic` 객체에서는 해당 객체에 대한 모든 스레드의 수정 순서가 일치함이 보장된다.

## 2. 원자적 연산(Atomic Operation) / `std::atomic` 타입

원자적 연산은 더이상 쪼개질 수 없는,
오직 시작과 끝만 다른 스레드에 관측되고
중간 상태는 관측되지 않는 연산이야.

객체에 대한 load / store가 원자적이라면,
해당 객체에 load를 했을 때 아직 store되지 않은 이전 값 or store 이후의 다음 값만 볼 수 있는거지.
(중간 상태가 없음)

그리고 원자적이지 않은 연산은
다른 스레드에서 반쯤만 진행된 상태로 관측될 수 있어서,

원자적 멤버를 가지고 있는 비원자적 구조체 같은 것 같이
원자적 / 비원자적이 섞여있다면

원자적 멤버는 시작과 끝만 보이고
비원자적 구조체는 중간 과정이 보이는 상태같은 느낌으로
뒤섞인 조합이 나올 수가 있어.

어쨌든, `C++`에서는 원자적 연산을 하기 위해서
무조건 `std::atomic` 타입을 사용해야해.

### 2-1. 표준 `std::atomic` 타입에 대한 기본적인 정보들

표준 원자적 타입(atomic types)은 `<atomic>` 헤더에서 찾을 수 있어.

이런 `std::atomic` 타입에 대한 모든 연산은
원자적으로 실행되고,

C++의 정의 상 원자적인 모든 연산은
오직 이런 `std::atomic`에 대한 연산 뿐이야.

물론 뮤텍스를 이용해서 다른 연산들이 원자적으로 보이게 만들 수도 있긴 하지만..ㅋㅋ

사실, 이런 `std::atomic`에도 특정 상황에서는
**내부 구현에서 뮤텍스를 추가로 사용**할 수 있고
이렇게 추가로 락을 사용하는지 감지하는
`is_lock_free()`라는 함수도 있어.
(이건 뒤에 나올 `is_always_lock_free` 상수와 다르게 런타임에 검사를 함.)

솔직히 상식 밖이지.
`std::atomic`이 내부적으로는 뮤텍스를 사용할 수도 있다니..

생각보다 이건 꽤 중요한데,
원자적 연산이 주로 사용되는 곳은 성능 향상을 위해 뮤텍스를 대체하는거라,
원자적 연산이 뮤텍스와 함께 실행되면 성능 향상이 없을 수 있기 때문에,
이런걸 따로 감지하는거야.

이건 생각보다 훨씬 중요하기 때문에,
라이브러리는 다양한 정수형에 대한 `std::atomic` 타입이
락-프리인지 컴파일 시점에 식별할 수 있는 매크로 집합도 제공해.
(근데 이 매크로는 구식(지원하는 타입이 제한적임)이라, 잘 사용되지는 않고,
바로 뒤에 나오는 `is_always_lock_free`를 주로 사용해.)

그리고, `C++17`부터 모든 `std::atomic` 타입은 정적 `constexpr` 멤버 변수인
`is_always_lock_free`를 가지고
컴파일 결과물이 실행될 수 있는 모든 하드웨어에서
해당 `std::atomic` 타입이 락-프리일 때만 `true`를 가지게 하는거야.
(**컴파일 시점의 결과에만 한정**해서 락-프리인지를 판별해.
런타임의 조건들은 고려 안하고 런타임에는 락-프리가 아닐 수도 있으면 `false`야.)

`is_lock_free()` 함수를 제공하지 않는 유일한 `std::atomic` 타입은
`std::atomic_flag`인데,
이 타입은 `bool` 플래그이고, 해당 타입에 대한 연산은 락-프리인게 보장돼.
(이 타입은 단순한 `std::atomic<bool>`하고 혼동하면 안됨.)

TAS(`test_and_set()`)를 여기에다가 써서 락을 구현할 수 있어.
(`std::atomic_flag`는 가장 기본적인 `std::atomic` 타입이라고 할 수 있어.)
(TAS밖에 없으니..ㅋㅋ)

그리고 그 외의 `std::atomic` 타입들은
모두 `std::atomic<>` 클래스 템플릿을 통해 사용할 수 있고,
기능은 더 풍부하지만 무조건 락-프리가 아닐 수도 있어.
(앞서 설명했듯 뮤텍스가 내부 구현에 쓰일 수 있음)

(물론 대부분의 상황에서는 모든 기본 타입의 `std::atomic` 타입 변형이
실제로 락프리일 가능성이 높지만, 무조건은 아니야.
예를 들어 포인터에 비트 연산을 한다거나.
일반 포인터에 정의되어있지 않으니 `std::atomic` 포인터에도 정의되어있지 않음)

그리고 일반적으로는 다른 형식의 `atomic` 타입을 사용하는 것보다는,
`std::atomic<T>` 형식의 `atomic` 타입을 사용하는게 호환성 면에서 좋아.

그리고 표준 `std::atomic` 타입들은
복사 생성자 / 복사 대입 연산자가 없어서
일반적인 의미에서 복사하거나 할당할 수는 없어.

물론 해당 `std::atomic` 변수를 복사할 수 없다는거고,
원시 타입과의 대입 / 암시적 캐스팅은 허용해.
(`load`-`store`로 이어지는 두 단계의 연산이라, 원자적으로 실행할 수 없음)

```cpp
std::atomic<int> a;

std::atomic<int> b = a; // 불가능(복사 생성자 없음)
b = a; // 불가능(복사 대입 연산자 없음)

int x = 10;
a = x; // 가능(내부적으로 a.store(x) 호출)
int y = a; // 가능(내부적으로 a.load() 호출 + int로 암시적 캐스팅)
```

그리고 직접적인 `load()` / `store()` / `exchange()` / `compare_exchange_*()`을 지원하지.

그리고 적절한 경우 복합연산자(`+=` 등)도 지원하고,
`++` / `--`같은 단항 연산자도 지원해.
(이건 `fetch_add()` / `fetch_or()` 등과 같은 효과가 있음)

물론 사용자 정의 타입도 `std::atomic<T>`로 템플릿으로 만들 수는 있지만,
정수 / 포인터의 산술 / 비트 연산(`++` / `--` / `fetch_add()` / `fetch_or` 등)은 못 쓰고,
`load()` / `store()` / `exchange()` / `compare_exchange_*()`만 쓸 수 있어.

그리고 일반적인 대입 연산자는 자기자신에 대한 참조를 반환하지만,
`std::atomic` 타입은 복사된 값을 반환해.
(참조를 반환하면 데이터 레이스 발생 가능.)

그리고 각 연산에는 `std::memory_order`를 추가적으로 넣을 수 있는데,
이 인자는 필요한 메모리 순서 시멘틱을 지정하는데 쓰여.
(대충 메모리 배리어 타입이라는 이야기)

이 메모리 순서에 허용되는 값은 각 연산마다 다른데,

- `store` : `relaxed` / `release` / `seq_cst`만 됨
- `load` : `relaxed` / `consume` / `acquire` / `seq_cst`만 됨
- `read-modify-write` : `relaxed` / `consume` / `acquire` / `release` / `acq_rel` / `seq_cst`만 됨(다 됨)

(`read-modify-write`는 `compare_exchange_*()`같은 명령어)

이렇게 돼.

기본적으로 아무것도 지정 안하면
`seq_cst`(제일 강한거)가 지정되고.

이제 기본적인건 다 했으니 하나하나씩 세부적으로 파보자.

#### 요약

1. `std::atomic` 타입은 무조건 락-프리인 것은 아니고,
내부 구현에는 뮤텍스가 사용될 수 있어서,
컴파일 시점 : `is_always_lock_free` / 런타임 : `is_lock_free()` 로
실제 해당 `std::atomic` 타입이 락-프리인지를 확인할 수 있다.
2. `std::atomic_flag`는 가장 기본적인 `std::atomic` 타입으로,
`test_and_set()`(TAS)와 `clear()`만 지원한다.
3. `std::atomic`은 두 번 연산을 해야하기 때문에(load 한 번, store 한 번)
기본적으로 복사 생성자 / 복사 대입 연산자를 지원 안하지만,
원시 타입과의 대입 / 암시적 캐스팅은 허용한다.
4. `std::atomic`은 참조를 반환하지 않고 복사된 값을 반환한다.
(참조를 반환하면 데이터 레이스가 발생할 수 있기 때문이다.)
5. `std::atomic`의 각 연산에는 메모리 오더 시멘틱을 지정하는 인자를 넣을 수 있다.
기본적으로는 `std::memory_order_seq_cst`가 지정된다.

### 2-2. `std::atomic_flag`와 연산들

앞에서 설명했듯 가장 기본적인 `std::atomic` 변수야.

이 `std::atomic_flag` 객체는
set / clear 두 상태를 가질 수 있어.

(이 클래스는 솔직히 잘 사용되지는 않음..)
(하지만 `std::atomic` 타입을 설명할 때 좋은 점이 많아서
이 책에서도 설명하는거래.)

`std::atomic_flag`는 원래는 `ATOMIC_FLAG_INIT`으로 초기화되어야만 했지만,
`C++20`부터는 기본 생성자를 통한 초기화도 자동으로 해당 초기화와 동일한 역할을 하게 되어있으니까,
그냥 기본 생성자로 생성하자.

저렇게 초기화하는건 해당 `std::atomic_flag`의 상태를 clear 상태로 바꿔줘.

이 `std::atomic_flag` 객체에 할 수 있는 연산은 세 가지야.
소멸(소멸자) / 초기화(`clear()`) / 값 세팅과 이전 값 조회(`test_and_set()`)
TAS는 예전의 OSTEP 글에서 설명했었지..

(물론 다른 연산들도 있는데 그건 글 범위가 아니라..)
(그냥 스핀락 말고 다른 락들을 구현하기 편한 기능들이 추가됐다고 보면 됨)

`clear()`와 `test_and_set()`은 메모리 오더를 지정할 수 있는데,
`clear()`는 `store` 연산이니까
`relaxed` / `release` / `seq_cst`를 지정할 수 있어.

그리고 `test_and_set()`은 `read-modify-write` 연산이라서
모든 메모리 오더를 적용할 수 있어.

둘 다 기본값은 `seq_cst`고.

그리고 모든 `std::atomic` 객체가 그렇듯
복사 생성자 / 복사 대입 연산자는 막혀있어.
(서로 다른 두 객체에 대한 load-store를 해야하기 때문에)
(앞에서도 설명했지?)

그리고 이게 `test_and_set()` / `clear()`만 지원하고
무조건 락-프리이기 때문에
스핀락 뮤텍스로 사용하기 딱 좋아.

자세한건 예전에 정리했던 뮤텍스 글([링크](https://velog.io/@siryus0907/OS-26.08.06%EB%AA%A9-%EB%AE%A4%ED%85%8D%EC%8A%A4-%EA%B8%B0%EB%B3%B81))을 참고하면 좋을 듯.

요약하면, 플래그의 경우 값이 단 두 개이고, 
이미 `true`(set)인 경우 다시 `true`로 바꿔도 문제가 없고,
`false`인 경우 test(이전 값 저장)와 `true`로 set하는 과정이 원자적으로 일어나기 때문에
반환되는 이전 값이 `false`(clear)를 반환하는 경우에 락을 채가고,
이전 값이 `true`(set)를 반환하는 경우에 락을 채가지 않는 거랄까..

그리고 책에서는 추가로 `unlock()-release` / `lock()-acquire`로 설정해서
스핀락을 구현하는데,
이건 happens-before로 메모리 연산의 순서를 강제하기 위한거야.
(쉽게 설명하자면, 
`unlock()` 이전의 메모리 연산들이 다른 스레드의 `lock()` 이후 시점에 보이게 하기 위한 것)
(자세한건 3-4챕터에서 설명)

```cpp
class SpinLockMutex {
private:
    std::atomic_flag f;
public:
    // 기본 생성자로도 초기화 수행됨
    void lock() {
        while (f.test_and_set(std::memory_order_acquire));
    }
    
    void unlock() {
        f.clear(std::memory_order_release);
    }
};
```

그리고 `std::atomic_flag`는 이런 뮤텍스 구현에 몰빵된 `atomic` 타입이라,
(물론 `notify_*()` / `wait()`가 추가되어도 뮤텍스 구현에 몰빵임..)
일반적으로 `std::atomic` 타입의 플래그를 사용하려면 `std::atomic<bool>`이 훨씬 좋아.

#### 요약

1. `std::atomic_flag`는 뮤텍스를 구현하는데 쓰이는 `atomic` 타입이다.
2. set(`true`) / clear(`false`) 상태를 가지며, 생성 시에는 초기화해주어야 한다.
3. `test_and_set()`(TAS) / `clear()` 함수를 지원한다.
4. `C++20`에는 더 뮤텍스를 구현하기 편하도록 `notify_*()` / `wait()` 함수가 추가되었다.
+ `test()`도..

### 2-3. `compare_exchange_*` 함수들 (+ `std::atomic<bool>`)

`std::atomic<bool>`은 `std::atomic_flag`보다 훨씬 유연한 `std::atomic` 타입이야.

물론 복사 생성자 / 복사 대입 연산자가 없고
원시 타입과의 대입 / 암시적 캐스팅은 지원한다는 점은 같고,
대입 연산자가 참조가 아닌 복사된 값을 반환한다는 것도 똑같고..

초기 값을 `true` / `false`로 설정할 수 있고,
`store()`로 유연하게 쓰기 작업을 수행할 수 있다는 점이 차이점이야.
`load()`로 값을 편리하게 얻어올 수도 있고.
(set / clear 중 clear로만 초기값을 설정할 수 있는 `std::atomic_flag`와는 다름)

그리고 물론 `test_and_set()`도 대체 함수가 있는데,
`exchange()`가 있어.
TAS와 같은 역할을 하지.

뭐 근데 이 정도는 다 예측 가능하잖아?

이번 챕터는 뭐가 핵심이냐면,

`compare_exchange_weak()` / `compare_exchange_strong()`의 차이야.
현재 시점에서 가장 대표적인 `read-modify-write` 연산이지.
(CAS 연산, 쉽게 말하면 **조건부 저장** 연산이라고 보면 됨.
현재 값과 예상된 값이 같으면 저장 + `true`를 반환하고, 
아니라면 저장하지 않고 예상된 값을 현재 값으로 바꾼 후 `false`를 반환하는..)
(TAS와 대조적이지. 그건 **무조건 저장**하고 이전 값을 반환하니까..)

이 CAS 연산은 `std::atomic`을 이용한 프로그래밍의 초석이 되는 연산이야.
(실제로 나도 락-프리 스택 짜볼 때 CAS 연산 많이 쓰게 되더라고..)

`compare_exchange_*()`의 정확한 동작은,

- 해당 `std::atomic` 변수의 값을 `expected`와 비교
  - 두 값이 같으면 해당 변수의 값을 `desired`로 교체하고 `true`를 반환
  - 두 값이 다르면 해당 변수의 값을 `expected`에 넣고 `false`를 반환
  
그리고 이렇게 비교하고(compare) 교체하는(swap) 과정이 원자적으로 일어나서
CAS(Compare And Swap)라고 불리는거야.

그리고 이제 `strong` / `weak`이 왜 있는지 설명을 해야할 때가 왔는데,
결국 Spurious Failure를 고려하려고 하는거야.

CPU 아키텍처에 따라 
해당 `std::atomic` 변수의 값이 `expected`와 다르지 않은데도
(해당 변수의 값이 변하지 않았는데도)
해당 CAS 연산이 실패하는 경우가 생길 수 있어.
(세부적인건 LL/SC라고 있긴 한데, 그건 생략..)
(그냥 CAS 연산에서 원래 값이 `expected`와 같은지 비교하는 기준이
원래 값이 바뀌지 않았는지로 감지하는 그런거임..)
(근데 가끔씩 오탐지가 난다 이거지. 더럽게 민감해서..)

이게 좀 착각같은 느낌의 동작이기는 한데,
엄연히 발생할 수 있는 느낌의 동작이거든?

`compare_exchange_weak()`은 이런 Spurious Failure를 고려하지 않고,
일단 실패했다는 판정이 있으면 무조건 `false`를 반환해.

`compare_exchange_strong()`은 이런 Spurious Failure를 고려해서,
정말로 실패했는지를 판정하는 동작이 추가로 들어가서 
확실히 실패한 경우에만 `false`를 반환해.

그래서, `compare_exchange_weak()`은 Spurious Failure를 고려하지 않기 때문에
일반적으로 반복문 내에서 사용하게 돼.

```cpp
bool expected = false;
extern std::atomic<bool> a;

while (!a.compare_exchange_weak(expected, true) && !expected);
```

`compare_exchange_strong()`은 Spurious Failure를 고려하기 때문에
반복문 없이 사용될 수 있지.

그리고 실패 시 `expected`가 자동으로 현재의 해당 변수 값으로 갱신된다는 점은
되게 좋은 점이 될 수 있어.

여러 번 CAS 연산을 될 때까지 수행하는 경우에는,
`expected`는 **해당 변수가 변하지 않은 경우의 값**이라는 의미를 가지거든.

그래서 별도로 `expected` 값을 새로 갱신된 해당 변수의 값으로 고치는 수고가 덜어져.

그리고 추가적으로 각 함수를 어따가 쓰는지가 헷갈릴 수 있는데,

- `weak` : `compare_exchange_strong()`의 실패 검증 절차를 피하고 싶을 때
- `strong` : 한 번 한 번의 `desired`값(교체할 값) 계산 시간이 길어서
Spurious Failure가 허용되는 것이 안 좋을 때

이럴 때 쓰면 돼.

결국 교체할 값을 만드는 과정이 가벼우면 `weak`을 쓰고,
무거우면 `strong`을 쓰면 끝이야.

솔직히 더 정확히는 Spuirous Failure를 허용하냐 / 허용하지 않냐에 따라
다르게 쓰면 되긴 함..

그리고 `compare_exchange_*()` 함수들은
메모리 오더 인자를 두 개 넣을 수 있어.

값 교체에 성공한 경우의 메모리 오더 / 값 교체에 실패한 경우의 메모리 오더.
이렇게 두 개를 넣을 수 있어.

그리고 값 교체에 실패한 경우에는 `store`가 수행되지 않기 때문에,
`release` / `acq_rel` 메모리 오더는 쓸 수 없어.
(그리고 실패 시에 성공 시보다 더 엄격한 메모리 오더를 적용할 수도 없고..)

실패 시의 메모리 오더를 지정하지 않는다면,
메모리 오더의 `release` 부분이 사라진 메모리 오더가 실패 시 적용 돼.
(`release` : `relaxed` / `acq_rel` : `acquire`)

둘 다 지정하지 않으면
성공 / 실패 둘 다 `seq_cst`가 지정되고.

#### 요약

1. `compare_exchange_*()` 함수들은 CAS 연산을 수행하는 함수이다.
2. CAS 연산이란, `expected`와 현재 값이 같으면 값을 `desired`로 바꾸고,
다르면 값을 바꾸지 않고 `expected`에 현재 값을 저장하는 조건부 원자적 연산이다.
3. `compare_exchange_weak()`은 Spurious Failure를 고려하지 않고
실패 판정이 나는 경우 무조건 `false`를 반환(실패)하는 함수이다.
4. `compare_exchange_strong()`은 Spurious Failure를 고려해서
실패 판정이 나도 실패 판정을 검수해서 `true` / `false`를 나눠서 반환하는 함수이다.
5. `desired` 값을 계산하는 과정이 짧다면 Spurious Failure를 허용해서
루프를 더 돌더라도 검수 과정이 없는 `weak`를 사용해보자.
6. `desired` 값을 계산하는 과정이 길다면 Spurious Failure를 허용하지 않아서
루프를 덜 도는 `strong`을 사용해보자.


### 2-4. 정수 / 포인터 `std::atomic` 타입

일단 포인터부터 보자.

`std::atomic<T*>`로 적고,
기존 `std::atomic`과 같이 복사 생성자 / 복사 대입	연산자 없고,
원시 타입에 대한 대입 / 암시적 캐스팅만 지원해.
물론 대입 시 값으로 복사되고.
`load()` / `store()` / `exchange()` / `compare_exchange_*()` 다 지원되고.

근데 결국 다른 점은 `T*`(포인터)를 저장하기 때문에
포인터 산술 연산을 할 수 있다는 점이 있지.
`fetch_add()` / `fetch_sub()` / `+=` / `-=` / `++` / `--` 등으로.

여기서 복합 연산자 / 단항 연산자는 솔직히 포인터와 똑같게 동작하니까
설명할 필요는 없는데,
`fetch_add()` / `fetch_sub()`는 좀 달라서 추가적인 설명이 필요할 것 같네.

이 함수들은 해당 포인터의 값을 증가 / 감소시키고,
증가 / 감소 되기 전의 값을 반환해.
(FAA지. Fetch And Add.)

그리고 이 함수들을 사용하면 추가 인자로 메모리 오더도 지정할 수 있어서 좋아.
단순한 연산자 형태의 연산들은 강제적으로 `seq_cst` 메모리 오더가 되고.

정수형도 보자면,

`fetch_add()` / `fetch_sub()` / `fetch_and()` / `fetch_or()` / `fetch_xor()`
`+=` / `-=` / `&=` / `|=` / `^=`
`++` / `--`

다 돼.

곱셈 / 나눗셈 / 시프트 연산 빼고.

`std::atomic<T*>`의 `fetch_add()` / `fetch_sub()`와 비슷한 느낌이지.

`std::atomic` 타입 정수 값은 일반적으로
카운터 / 비트 마스크로 사용되기 때문에 크게 눈에 띄는 문제는 아니야.

#### 요약

1. `std::atomic<T*>`는 
포인터 연산 + `fetch_add()` / `fetch_sub()`를 추가로 가지고있고,
`fetch_add()` / `fetch_sub()`는 증가 / 감소하기 이전 값을 반환 후 원자적으로 증가 / 감소시킨다.
2. `std::atomic<T>`(T는 정수)는 
곱셈 / 나눗셈 / 시프트를 제외한 연산자 + `fetch_*()` 함수를 가지고 있고,
`fetch_*()` 함수들은 `std::atomic<T*>`와 동일하게 작동한다.
3. `fetch_*()` 함수들은 메모리 오더를 설정할 수 있지만,
단순 연산자들은 메모리 오더가 `seq_cst`로 고정된다.

### 2-5. 사용자 정의 `std::atomic<UDT>` 타입 + 그 외의 `std::atomic` 타입

템플릿 덕분에 표준 `std::atomic` 타입 외에도
사용자 정의 타입의 `std::atomic<UDT>` 타입을 생성할 수 있어.

사용자 정의 `std::atomic<UDT>` 타입은 `std::atomic<bool>`과 같이
`store()` / `load()` / `exchange()` / `compare_exchange_*()`를 제공해.

`std::atomic<bool>`과 다른 점은
오직 보관되는 값이 `T`의 타입으로 바뀐다는 것 정도가 있겠네.

여기서 중요한게,
아무런 사용자 정의 타입이나 `std::atomic<UDT>`에 사용할 수 있는게 아니라,
특정 기준을 만족하는 사용자 정의 타입만 사용할 수 있다는 점이야.

어떤 사용자 정의 타입 `T`에 대해
`std::atomic<T>`가 되려면,
해당 타입은 trivially copyable해야해.
(trivial은 사소한, 하찮은이라는 뜻인데,
C++에서는 메모리 복사나 생성 / 소멸 시에 복잡한 로직이 개입하지 않는다는 뜻이야.)
(복사 / 대입을 사용자 코드 없이 단순하게 수행할 수 있다는 거라고 생각하면 됨.)

뭔가 말이 복잡하지?
그냥 메모리에서 단순히 바이트 단위로 복사하는 연산자(흔히 `memcpy()`)가 지원이 되야 한다는거야.
(즉, trivial copy가 가능한 생성자(컴파일러가 생성한 생성자)가 하나라도 있어야 한다는 것.)
(소멸자도 trivial해야한다는 것.)
(그리고 가상 함수 / 가상 기반 클래스가 없어야하고.)

왜 이렇냐면,
결국 사용자 정의 코드가 호출되면 컴파일러가 알 수 없는 사이드 이펙트들이 발생할 수 있기 때문이야.

그리고 애초에 `store()` / `compare_exchange_()`같은 명령어는
메모리 복사의 형식으로 원자적 연산을 수행하는데,
메모리 복사 과정에서 사이드 이펙트가 없으면 안전하게 바로 복사할 수 있으니
trivially copyable 해야 하는거야.

만약 `std::atomic`의 구현에 뮤텍스가 들어간다고 해도,
추가적인 사이드 이펙트가 없이 메모리 복사만 해도 해당 객체가 복사되니
문제가 없게 되는거지.

사이드 이펙트가 있다면,
단순한 메모리 복사로는 원자적 연산이 구현될 수 없을테니까,
애초에 사용자 정의 코드 없이 복사 생성 / 복사 대입을 함으로써
그런 사이드 이펙트가 없다는게 보장이 되고,
맘편하게 메모리 복사만으로 원자적 연산을 할 수 있게 되는거야.

그리고 이게 결국 `compare_exchange_*()` 함수들은
`UDT` 내부의 비교 연산자를 사용하지 않고,
비트 단위로 비교해서 교체하는게 좀 특이한 점이겠네.
(`memcmp()` 처럼!)

그래서 값을 비교(`compare`)할 때는
일반적인 비교에는 고려되지 않는 패딩 비트를 가지고 있다면,
실제 객체 자체의 값은 동일하더라고 
패딩 비트가 다른 경우에 `compare_exchange`는 실패할 수 있어.
(물론 `C++20`부터는 패딩 비트를 자동으로 0으로 맞춰주는 기능이 있어서
문제가 많이 완화되었긴 해.)

결국 `std::atomic<UDT>`에 넣을 수 있는 `UDT`의 조건을 요약하면

> 어떤 방식으로든 `memcpy()`로 바이트 그대로 복사가 가능(trivially copyable)한 
> 사용자 정의 객체만 `std::atomic`에 넣을 수 있다.

라고 할 수 있어.

이번엔 `UDT`의 크기에 대해 생각해보자.
기본적으로는 `int` / `void*`의 이하 크기(~8바이트)까지는
대부분의 일반적인 플랫폼에서는 원자적 연산 명령어를 사용할 수 있어.

그 두 배(~16바이트) 까지는 일부 플랫폼에서 원자적 명령어를 사용할 수있고.

그보다 큰 경우에는 원자적 연산 명령어 지원이 제한적일 수 있어.
여기서부터 본격적으로 연산의 원자성을 구현하는데 뮤텍스가 붙기 시작하지.

그리고 애초에 `std::atomic<UDT>`에 할 수 있는 연산이
`store()` / `load()` / `exchange()` / `compare_exchange_*()`밖에 없어서,
다른 조작을 해야하는 객체에 쓰기가 애매하기도 하고..

예를 들어 `std::atomic<std::vector<int>>`이 있다고 하자.
(실제로는 `std::vector`는 
복사 생성자 / 복사 대입 연산자가 trivial하지 않기 때문에 못 씀)

근데 저 `std::vector`에 `store()` / `load()`만 하는게 아니잖아?
원소 추가 / 삭제 / 크기 변경 등의 연산들도 있어서,
애초에 `std::atomic`이 적합하지 않은 객체들도 있어.

#### 요약

1. 사용자 정의 `std::atomic<UDT>` 타입에 들어갈 수 있는 `UDT`는
trivially copyable한(`memcpy()`로 완전히 복사할 수 있는) 타입 뿐이다.
2. trivially copyable한, `memcpy()`(메모리 복사)로만으로도 복사할 수 있는 성질이 필요한 이유는,
사용자 정의 코드로 메모리 복사(원자적 연산)를 하게 될 경우에 발생하는
사이드 이펙트(사용자 정의 복사 동작)를 없애기 위함이다.
메모리 복사(`memcpy()`)만으로 해당 객체를 복사할 수 있으면,
즉 사용자 정의 코드 없이 복사할 수 있다면 사이드 이펙트가 없고,
오직 메모리 복사만 해도 해당 객체를 복사할 수 있게 된다.
3. `UDT`에 크기 제한은 없지만, 크기가 커지면 원자적 연산 명령어를 활용하기 어려워져
원자적 연산(락-프리)이 아닌 뮤텍스가 적용될 수 있다.
(물론 내부의 연산은 atomic이든 mutex든 원자적이다.)
4. 애초에 사용자 정의 `std::atomic<UDT>` 타입은
`store()` / `load()` / `exchange()` / `compare_exchange_*()`만 지원하므로
`UDT`가 추가적인 연산을 필요로 하는 경우 적합하지 않고,
`std::mutex`가 더 적합할 수 있다.

### 2-6. C언어와의 호환성을 위한 추가적인 함수들

지금까지는 `std::atomic`의 멤버 함수들만 봤었는데,
말 그대로 C언어와의 호환성을 위한 별도의 원자적 연산 함수들도 있어.

`atomic_` 접두사가 붙은 함수들인데,

- 메모리 오더를 지정할 수 없는 경우 `atomic_` 접두사만 붙고,
- 메모리 오더를 지정할 수 있는 경우 `_explicit` 접미사가 추가로 붙는

함수들이야.

`std::atomic`의 멤버 함수가 참조하는 객체는 암시적이지만,
이런 함수들은 첫 번째 인자로 원자적 객체에 대한 포인터를 받아.

뭐,

- `atomic::is_lock_free` : `atomic_is_lock_free()`
- `atomic::load` : `atomic_load` : `atomic_load_explicit()`

이런 느낌으로 `std::atomic` 객체의 멤버 함수와
별도의 함수들이 매칭돼.

`atomic_compare_exchange_*()` 함수들은 
`expected`도 포인터로 받고,

`atomic_compare_exchange_*_explicit()` 함수들은
무조건 성공 / 실패 메모리 오더를 지정해야한다는 차이점이 있어.

`atomic_flag`에 대한 별도의 함수들은
이름에 `atomic_flag`를 포함해서,
`atomic_flag_test_and_set()` 처럼 사용해.
(여기서도 메모리 오더 추가하려면 `_explicit` 붙여야함)

아, 그리고 `std::shared_ptr`와 `std::weak_ptr`도 `std::atomic`에 넣을 수 있게 되었어.
(`C++20`에서.)
물론 `is_lock_free()`는 잘 해봐야겠지만..
(trivial한 타입은 아니지만,
일부러 템플릿 특수화로 집어넣었어.)

#### 요약

1. C언어와의 호환성을 위해서, 별도의 자유 함수를 둔다.
2. `atomic_` 접두사를 붙이며, 메모리 오더를 적용하려면 `_explicit` 접미사를 붙이면 된다.
3. `std::shared_ptr` / `std::weak_ptr`도 `std::atomic<>`에 넣을 수 있다.

## 3. 연산 동기화와 순서 강제

자, 이제 메인 디쉬다..
지금까지 

- 메모리 위치
- 데이터 레이스
- 수정 순서
- `std::atomic`
- `std::memory_order`의 종류

를 배운게 전부 이 챕터를 위해서야..

`std::atomic`은 단일 변수에 대한 동기화 뿐만 아니라 
스레드 간의 연산의 순서를 강제하는 역할도 해주거든?

사실상 여기가 머리가 더럽게 아픈 파트일거야.
(난 이미 synchronizes-with / happens-before 해봤고 메모리 오더도 다 해봤지만..)

결국 이번 챕터를 요약하자면,

> 다른 스레드에 메모리 연산이 보이는 순서를 조정함으로써
> 어떻게 연산을 동기화할 수 있으며
> 실행 순서를 강제할 수 있을까?

라고 할 수 있겠네..

짧게 요약하고 가자면
(어차피 이 내용을 처음 보는 사람이라면 모를테지만..)

- `release` 배리어는 해당 배리어(연산)의 앞의 메모리 연산(읽기 / 쓰기)들이
해당 배리어 뒤로 밀리지 않게 해준다.
- `acquire` 배리어는 해당 배리어(연산)의 뒤의 메모리 연산(읽기 / 쓰기)들이
해당 배리어 앞으로 당겨지지 않게 해준다.
- 그렇다면, `release`로 `store`한 값을 `acquire`로 `load`한다면,
해당 변수에 대한 `release-store`이전의 연산의 결과들이
무조건 해당 `store`에 대한 `acquire-load` 이후에 보인다.
(이게 Happens-Before / Synchronizes-With)

순서도를 보면 편할텐데..

그리고, 이번 챕터를 설명하는데는 그림이 좀 많을거야..
(직접 A4용지에 그린거..)

> `seq_cst` 메모리 오더 : 앞뒤의 연산이 섞일 수 없고 
> 해당 `seq_cst` 메모리 오더의 연산들이 오직 하나의 전역적 타임라인을 가지게 하는 메모리 오더

> `release` 메모리 오더 : 해당 메모리 배리어 앞의 연산이 뒤로 넘어가지 못하게 하는 메모리 오더.
> 즉, 해당 `release` 연산이 다른 코어에 보일 때, 그 이전의 연산들도 이미 보이도록 순서를 강제함.
> `store` 연산에서 사용됨.

> `acquire` 메모리 오더 : 해당 메모리 배리어 뒤의 연산이 앞으로 당겨지지 못하게 하는 메모리 오더.
> `load` 연산에서 사용됨.

> `acq_rel` 메모리 오더 : `release` + `acquire`. 하지만 하나의 전역적인 타임라인을 가지지 않음.
> RMW(Read-Modify-Write) 연산에서 사용됨.

> `relaxed` 메모리 오더 : 오직 해당 `std::atomic` 객체의 수정 순서만 보장하는 최소 메모리 오더

> Sequenced-Before 관계 : 싱글 스레드에서 한 연산을 다른 연산이 관측할 수 있는 관계
> Happens-Before 관계의 부분집합이다.

> Synchronizes-With 관계 : `release-store`한 값을 다른 스레드가 `acquire-load`로 읽는 관계.
> 여러 스레드의 `store`-`load`가 동기화된다.

> Happens-Before 관계 : 멀티 스레드 / 싱글 스레드 둘 다에서 한 연산을 다른 연산이 관측할 수 있는 관계

> 멀티스레드에서의 Happens-Before 관계의 성립
> : 다른 스레드의 두 연산이 Synchronizes-With 관계를 가진다고 했을 때,
> `release-store` 이전의 연산을 `acquire-load` 이후에 관측할 수 있게 된다.
> (다른 스레드의 두 연산과 `release-store` / `acquire-load`는 각각 Sequenced-Before 관계를 가진다.)

---

### 3-1. 서론

기본적으로 컴파일러와 CPU(아키텍처에 따라 다르지만..)는
싱글 스레드 관점에서 코드를 최적화를 하기 때문에
멀티 스레드 관점에서는 해당 코드 최적화가 문제가 생길 수 있어.

```cpp
int data = 0;
std::atomic<int> ready = false;

// thread 1
data = 42;
ready.store(true, std::memory_order_relaxed);

// thread 2
while (!ready.load(std::memory_order_relaxed));
int result = data;
```

이 예시가 그걸 잘 보여줘.

이 코드는,
thread 1이 `data` -> `ready` 순서로 설정하고,
thread 2가 `ready`가 `true`라면 `data`를 읽게 돼.

즉, 직관적으로 보면
`ready == true`일 때 무조건 `data == 42`겠지..

하지만, 결국 싱글 스레드 기반으로 최적화가 들어와서,
(thread 1 관점에서는 `data`와 `ready`의 관계가 안 보이잖아?)
`data` -> `ready` 순으로 메모리 연산이 들어오는게 아니라,
`ready` -> `data` 순으로 메모리 연산이 들어오는 식으로 최적화가 되어서

`ready.load() == true`일 때 `data == 0`인 경우가 생길 수 있어.
`data`의 변경 사항이 `ready.load() == true` 했을 때 보이지 않는거지.
이건 컴파일러와 CPU의 Code Reordering(코드 재정렬)때문에 생기는 문제야.
연산의 순서가 강제되어있지 않아서 생기는 문제지.
(정확한 원인은
컴파일러의 코드 최적화 + CPU의 Out of Order Execution 정도야.)
(더 파면 store buffer까지 내려가긴 하는데,
이건 다른데서 보자.)

둘 다 `std::atomic`이어도 수정 순서로 인한 여러 스레드 간의 데이터 가시성 보장은
딱 해당 객체에만 적용되어 이 문제를 해결할 수 없어.

연산의 순서를 강제하려면 어떻게 해야할까?

바로 Happens-Before / Synchronizes-With 관계를 만들어주면 돼.
(이게 이번 챕터의 핵심 개념이야.)

이 이미지는 그 예시야.

![](https://velog.velcdn.com/images/siryus0907/post/e8c4bc07-02d9-41d9-ab19-0099e97d2489/image.jpg)

`data = 42`가 `ready.store(true)`보다 나중에 실행될 수 없게 하고
(`data = 42`가 `ready.store(true)` 뒤로 밀릴 수 없게 하고)
(`ready.store(true)`에 `release` 배리어를 치고)

`res = data`가 `ready.load() == true`를 인식하는 시점보다 먼저 실행될 수 없게 함으로써
(`res = data`가 `ready.load() == true`를 인식하는 시점보다 앞으로 당겨질 수 없게 함으로써)
(`ready.load()`에 `acquire` 배리어를 침으로써)

연산의 순서를 보장하는거지.

무조건

- thread 1 : `data` 쓰기 -> `ready` 쓰기 순서로 메모리에 반영
- thread 2 : `ready` 읽기 -> `data` 읽기 순서로 메모리를 읽음

이 순서를 강제하는거지.

이렇게 말이야.

```cpp
int data = 0;
std::atomic<int> ready = false;

// thread 1
data = 42;
ready.store(true, std::memory_order_release);

// thread 2
while (!ready.load(std::memory_order_acquire));
int result = data;
```

근데 솔직히 이거 그냥 기본 제공되는 `seq_cst` 쓰면
저렇게 실행 순서가 뒤바뀌는 문제는 없게 돼.

하지만 `seq_cst`는 강력하기 때문에,
자원을 많이 소모하지.
(물론 CPU 아키텍처에 따라서는 나름 적게 소모하는 경우도 있음)

그래서 저 메모리 오더의 강도를 낮춰야할 때가 있어.
그리고 그게 락-프리 프로그래밍의 참맛이지.

- 얼만큼 메모리 배리어의 강도를 낮춰도 실행 순서에 문제가 없을까?

를 고민해야하는게 락-프리 프로그래밍이 어려운 이유야.
저걸 다 논리적으로 증명해놔야하거든..

이제 이 문제의 핵심인 멀티스레드 간의 메모리 가시성(순서성)을 보장하는
메모리 배리어를 간단하게 훑어보고,
synchronizes-with과 happens-before에 대해 알아보자.

### 3-2. 메모리 배리어(메모리 오더) 기초

앞에서, 컴파일러와 CPU의 코드 Reordering으로 인해
코드의 실행 순서가 뒤바뀌어서
`data = 42` -> `ready.store(true)` 순서로 메모리 연산이 들어가서
`ready.load() == true`라면 `data == 42`라는게 보장이 되어야할 것이 

`ready.store(true)` -> `data = 42` 순서로 메모리 연산이 들어가서
`ready.load() == true`인데 `data == 0`이 되는 예시를 봤었지?

결국 저렇게 연산의 순서가 뒤바뀌지 않게 해주는 방법이 필요해.

메모리 배리어는, 정말 쉽게 말하면

> 해당 배리어를 기준으로 연산이 뒤섞일 수 없게 하는 도구

라고 할 수 있어.

솔직히 지금은 저 말이 뭔지 모를텐데,
차차 알아나가보자.

일단, 
가장 강력한 메모리 배리어인 `std::memory_order_seq_cst`(약칭으로 `seq_cst`)에 대해 알아보자.

이 메모리 배리어는, 잡다한 설명을 다 빼면 결국 이거야.

> 해당 메모리 배리어를 기준으로 앞 / 뒤의 연산이 서로 섞일 수 없다는 것.

+ 실행 순서를 전역적으로 고정한다는 것도 있긴 한데,
이건 나중에 심화 파트에서 알아보자.

`load()`로 예시를 들어볼게.
(`seq_cst`는 `load()` / `store()` / RMW 다 적용이 가능해서말이야..)

```text
          │  
          │  절대 위 쪽의 연산들이 
          ▼  해당 메모리 배리어 아래로 내려갈 수 없음!
   ============================================= [Barrier]
     if (ready.load(std::memory_order_seq_cst));
   ============================================= [Barrier]
          │  절대 아래 쪽의 연산들이
          │  해당 메모리 배리어 위로 올라갈 수 없음!
          ▼  

```

이런거야.

```cpp
int data = 0;
std::atomic<int> ready = false;

// thread 1
data = 42;
ready.store(true, std::memory_order_seq_cst);

// thread 2
while (!ready.load(std::memory_order_seq_cst));
int result = data;
```

이렇다고 할 때,
`data = 42`는 `ready.store(true, std::memory_order_seq_cst)` 아래로 내려갈 수가 없어.
물론 그 밑의 추가적인 연산들도 해당 `ready.store(true)` 위로 올라갈 수가 없고.

그리고 `result = data`도 `ready.load(std::memory_order_seq_cst)` 위로 올라갈 수가 없어.
물론 그 위의 추가적인 연산들도 해당 `ready.load()` 밑으로 내려갈 수가 없고.

그렇다면, `data = 42`가 무조건 `ready.store(true)`보다 먼저 실행되게 되고,
`result = data`가 무조건 `ready.load()`보다 나중에 실행되게 되니

thread 1이 무조건 `data = 42` -> `ready.store(true)` 순서로 메모리를 바꾸게 되고,
thread 2가 `ready.load() == true` -> `result = data`로 이어질 때
`ready.load() == true`를 읽은 경우 `data`도 `42`로 바뀌었다는게 보장이 되겠지.

이제 대충 메모리 배리어가 뭔지 이해했지?

> 특정 지점(메모리 배리어의 위치)를 기준으로 연산들이 뒤섞일 수 없게 만드는 도구

정도로 이해하면 오케이야.

근데 양방향 배리어인 `seq_cst`는 CPU 아키텍처에 따라 오버헤드가 다른 배리어들보다 상당히 커.

그래서 딱 필요한 방향으로만
해당 메모리 배리어를 기준으로 연산이 넘어갈 수 없게 하는
메모리 배리어도 있어.

그리고 이게 추후 설명할 동기화 관계인
Happens-Before 관계의 핵심이야.
한번 잘 봐보자.

`std::memory_order_release`(약칭으로 `release`)는
해당 배리어를 기준으로
해당 배리어 위의 연산이 밑으로 내려가는 것을 막아주는 단방향 배리어야.

```text
          │
          │  절대 위 쪽의 연산들이
          ▼  해당 배리어 아래로 내려갈 수 없음!
   ============================================= [Barrier]
     ready.store(true, std::memory_order_release);
          │
          │  여기에는 배리어 위 쪽의 연산들이 실행될 수 없음!  
          ▼  
```

이걸 어따 쓰냐?

- 특정 시점 이전의 연산들을 메모리에 확정적으로 저장하고 넘어가기 위해서 써.

방금의 `data = 42` -> `ready.store(true)` 예시가 직관적이지.
`data = 42`는 무조건 `ready.store(true)`보다 먼저 메모리에 반영되어야
타 스레드가 `ready.load() == true`를 읽었을 때 `data == 42`라는게 보장이 될 거 아니야?

그러면 `release` 메모리 배리어를
`ready.store(true)`에 쳐서
`data = 42`가 `ready.store(true)` 아래로 내려올 수 없게 함으로써
`ready.load() == true`일 때 무조건 `data == 42`라는게 보장이 되게 해주는거야.

그런 느낌이지..

- 추가적으로, 
여기서 앞에서 설명한 store buffer가 쓰여.
store buffer는 CPU와 캐시 메모리의 속도 차이를 보완하기 위해
store할 값들이 임시로 저장되는 버퍼인데,
`release` 배리어는 이 store buffer의 값들을 
해당 `release-store`보다 먼저 다른 코어에 보이도록 순서를 강제해줘.

`std::memory_order_acquire`(약칭으로 `acquire`)는
해당 배리어를 기준으로
해당 배리어 아래의 연산들이 위로 올라오는 것을 막아주는 단방향 배리어야.

```text
          │  
          │  여기에는 배리어 아래 쪽의 연산들이 실행될 수 없음!
          ▼  
     if (ready.load(std::memory_order_acquire));
   ============================================= [Barrier]
          │  절대 아래 쪽의 연산들이
          │  해당 배리어 위로 올라갈 수 없음!
          ▼  
```

이것도 어따 쓰냐?

- 특정 조건을 확인한 이후에 실행되어야 할 연산들이
조건을 확인하기 전에 미리 당겨져서 실행되는 것을 막을 때 써.

이것도 방금의 예시로 설명할 수 있어.

`ready.load() == true`를 확인한 후에만 `result = data`를 실행해야하잖아?
하지만 `result = data` -> `ready.load() == true` 순으로 코드 Reordering이 발생할 수 있기 때문에,
`ready.load() == true`를 확인한 후에만 `result = data`를 실행할 수 있도록 하기 위해
`acquire` 배리어를 쓸 수 있어.

그리고 지금까지 `release-acquire`로 다룬게
Happens-Before 관계거든?

이건 좀 이따 다뤄볼게.

그리고 마지막으로
`std::memory_order_relaxed`가 있어.
이거는 아예 메모리 배리어가 없다고 이해하면 편해.

```text
          │  
          │  위 쪽의 연산들이
          ▼  해당 배리어 아래로 내려갈 수 있음.
     if (ready.load(std::memory_order_relaxed));
          │  아래 쪽의 연산들이
          │  해당 배리어 위로 올라갈 수 있음.
          ▼  
```

근데 그러면 일반 변수랑 다를게 없어 보이잖아?
이건 순서 제약은 없지만
단일 `std::atomic` 변수에 대한
원자성 / 전역 수정 순서는 보장이 돼.

즉, 데이터 레이스를 피하면서 단순 카운터처럼 순서가 안 중요한
atomic operation을 할 때 극상의 성능을 내기 위해 쓰는거야.

결국,

- `seq_cst` : 해당 배리어를 기준으로 위에서 아래로, 아래에서 위로 연산이 섞일 수 없게 함
  - 가장 안전하지만 오버헤드가 제일 큼
- `release` : 해당 배리어를 기준으로 위에서 아래로 연산이 내려갈 수 없게 함
  - 이전까지의 작업 결과를 메모리에 전부 쓰기 위해서 사용
- `acquire` : 해당 배리어를 기준으로 아래에서 위로 연산이 올라갈 수 없게 함
  - 조건을 확인 후 최신 데이터를 안전하게 읽을 때 사용
- `relaxed` : 해당 배리어를 기준으로 연산이 섞이는걸 허용함
  - 원자성과 수정 순서 보장 만으로 동기화를 할 때 사용

이렇게 볼 수 있어.

#### 요약

1. `seq_cst` : 해당 배리어를 기준으로 양쪽으로 다른 연산이 뒤섞일 수 없게 하는 메모리 오더,
순차적 일관성을 보장함.
2. `release` : 해당 배리어를 기준으로 위에서 아래로 다른 연산이 내려올 수 없게 하는 메모리 오더
3. `acquire` : 해당 배리어를 기준으로 아래에서 위로 다른 연산이 올라갈 수 없게 하는 메모리 오더
4. `relaxed` : 해당 배리어를 기준으로 연산이 섞이는걸 허용하는 제일 약한 메모리 오더

### 3-3. Synchronizes-With 관계

이 파트는 Happens-Before를 위한 빌드업이라고 생각하면 돼.

Synchronizes-With 관계란,
`std::atomic` 타입에 대한 연산 사이에서 성립하는 관계로,

(`x`라는 변수에 대한 관계로 예시를 들어보면)

- `x`라는 변수에 대해 `release`가 지정된 원자적 쓰기 연산을 함
- 그 후에 원자적 쓰기 연산을 한 해당 값을 `acquire`가 지정된 원자적 읽기 연산으로 읽음

이라고 할 수 있어.

이게 Synchronizes-With 끝이야.

그냥

- 한 `std::atomic` 변수에 대해서
  - 스레드 A가 `release-store()`로 쓴 값을
  - 스레드 B가 `acquire-load()`로 읽었다.
  (꼭 스레드 A가 `release`로 `store()`한 값을 읽어야함,
  다른 값을 읽으면 안됨)

이 상태를 나타내는게 synchronizes-with 관계야.
진짜 이게 끝이야.

그냥 저런 상태를 편하게 부를 수 있도록 정의해놓은게
synchronizes-with 관계라고 생각하면 돼.

그리고 synchronizes-with관계는 
무조건 스레드 A의 쓰기가 스레드 B의 읽기보다 먼저 일어났다는걸 보장해주지.
이게 무슨 개소리인가 싶은데,
좀 이따 보자..

(결국 이걸로 
스레드 A의 이전 작업(`release` 배리어로 `x.store()`전에 실행되게 됨)
-> 스레드 A의 `x` 쓰기 
-> 스레드 B의 `x` 읽기 
-> 스레드 B의 이후 작업(`acquire` 배리어로 `x.load()` 이후에 실행되게 됨)
의 순서가 제대로 나오게 됨)
(이걸 Happens-Before라고 함..)
(`std::atomic` 변수를 기준으로 순서를 고정한다고 보면 됨..)

이러면 동기화 관계가 발생하는데,
그건 뒤에 나오는 Happens-Before 관계에서 설명해주겠지.

#### 요약

1. Synchronizes-With 관계는
한 스레드에서 `std::atomic` 변수에 `release` 메모리 오더로 쓰기를 하고,
**해당 값**을 다른 스레드가 `acquire` 메모리 오더로 읽었을 때의 관계이다.
2. Synchronizes-With 관계의 두 스레드는
무조건 쓰기를 한 스레드 -> 읽기를 한 스레드의 순서로 실행이 되었다는게 보장이 된다.

### 3-4. Happens-Before 관계

자, 이제 조각이 다 모였다.

- `std::memory_order_release` : `release` 배리어
  - 배리어 앞의 연산이 뒤로 밀리지 않게 함
  - 특정 시점 전의 연산들의 결과가 모두 메모리에 반영되게 하기 위해 사용
- `std::memory_order_acquire` : `acquire` 배리어
  - 배리어 뒤의 연산이 앞으로 당겨지지 않게 함
  - 조건 확인 이후의 연산들이 조건 확인 전으로 당겨지지 않게 하기 위해 사용
- Synchronizes-With 관계
  - 서로 다른 스레드에서 `release-store` / `acquire-load`를 통해 생기는 관계
  
이것만 알면 Happens-Before는 쉬워.

Happens-Before 관계는 직관적으로 설명하자면

> 한 연산이 다른 연산의 결과를 인식하는 관계

라고 할 수 있어.

싱글 스레드의 경우 간단하지.
싱글 스레드에서 연산 A가 연산 B보다 순서상 먼저(Happens-Before)라면
연산 B은 연산 A의 결과를 인식할 수 있잖아?

그러면 연산 A은 연산 B에 대해 Happens-Before 관계를 가진다고 해.
연산 A의 결과가 연산 B의 시점에 인식될 수 있다는거지.

물론 같은 구문에서 두 연산이 발생한다면,
두 연산의 순서가 정해져 있지 않아서
Happens-Before 관계는 없겠지만..
(이건 어느정도 무시해도 됨)

여기서 추가적인 개념이 Sequenced-before인데,
이건 단일 스레드에서 한 연산이 다른 연산보다 앞서는 관계라고 할 수 있어.

Happens-Before의 부분집합이라고도 볼 수 있지.

- Happens-Before : 단일 스레드 / 멀티 스레드 양 쪽을 포괄함
- Sequenced-Before : 단일 스레드만으로 한정됨

이렇게 보면 돼.

자, 이제부터가 본론이야.

멀티 스레드 환경에서의 Happens-Before 관계란,

![](https://velog.velcdn.com/images/siryus0907/post/23cedfe9-7814-431c-8c1a-e4f59682efbc/image.jpg)

이렇게 스레드 A의 연산 A(`data = 42`)가
Sequenced-Before -> Synchronizes-With -> Sequenced-Before를 타고
스레드 B의 연산 B(`res = data`) 시점에 관측되는 관계를 말해.

좀 일반화해보자면,
스레드 A의 `store()` 시점 이전의 메모리 변경 작업이
스레드 B의 `load()` 시점 이후에 100% 가시적으로 보이는 관계라고 할 수 있겠네.

제대로 설명해보자면,
(그림을 봐줘.)

1. `store(release)`로 `ready.store()` 전의 연산들은 해당 `store()` 시점에 다 반영이 되어있음.
    - 빨간색 화살표를 보면, `ready.store()` 이전의 연산(`data = 42`)가
    `release` 배리어 때문에 `ready.store()` 이후로 밀릴 수 없음.
    - 즉, `data = 42` -> `ready.store()` 순서가 보장이 된다는거임.
    (Sequenced-Before)
2. 그렇게 `store()` 한 `ready`를 다른 스레드가 `load()`함.
    - 파랑색 화살표를 보면,
    Synchronizes-With 관계로 `ready.store()` -> `ready.load()`가 보이지?
3. `ready`를 `load()`한 이후의 코드들에 `store()`이전의 연산들이 반영이 됨.
    - `acquire` 배리어 때문에,
    `ready.load()` 이후의 연산들이 앞으로 안 당겨짐.
    - 즉, `ready.load()` -> `result = data` 순서가 보장이 된다는거임.
    (Sequenced-Before)
    
결국 Sequenced-before -> Synchronizes-with -> Sequenced-before이
순서대로 연계되면서
스레드 A의 `data = 42` 쓰기가 스레드 B의 `res = data` 읽기 시점에
무조건 관측되는 Happens-before 관계가 완성되는 거지!

이번엔 논증 느낌으로 한번 해보자.

> 1. 연산 A(`data = 42`)는 `store(release)` 전에 수행된다. (`release`에 의해 메모리에 반영 확정)
> 2. 따라서 `store()` 시점에는 연산 A의 결과가 무조건 메모리에 반영되어 있다.
> 3. 그 `store()`된 값을 `load(acquire)`한 시점에도 연산 A는 당연히 메모리에 반영되어 있다. 
(`load(acquire)`한 시점에 연산 A의 결과가 보인다.)
> 4. `acquire` 배리어 때문에 `load()` 이후의 연산들은 절대 `load()` 이전으로 넘어갈 수 없다.
> 5. **결론:** `load()` 시점 이후에 실행되는 모든 연산은, 
연산 A의 결과가 100% 반영된 상태만을 관측하게 된다! (Happens-Before 성립)

여기서 중요한 점은,
꼭 `release-store()`한 값을 `acquire-load()` 해야한다는 점이야.

그리고 이건 단순히 두 스레드 간에 국한되지 않고,
여러 스레드에 전이적으로 발생할 수도 있어.

연산 A가 연산 B 시점에 관측되고,
연산 B가 C 시점에 관측되면
연산 A가 C 시점에 관측된다는거지.

#### 요약

1. Happens-Before는 연산 A의 결과가 연산 B에 관측되는 관계이다.
2. Sequenced-Before는 한 스레드에서 연산 A의 결과가 연산 B에 관측되는 관계이다.
3. 멀티스레드에서의 Happens-Before는
Sequenced-Before -> Synchronizes-With -> Sequenced-Before의 연계로
스레드 A의 `release-store()` 이전 연산의 결과가
스레드 B의 `acquire-load()` 이후에 관측되는 관계이다.
4. 멀티스레드의 Happens-Before는 전이적으로 발생할 수 있다.

### 3-5. 메모리 배리어(메모리 오더) 심화

이제 Happens-Before도 잘 알아보았으니
기존에 겉핥기 수준으로만 배웠던 메모리 배리어들을 자세히 알아보자.

사실 방금 전에 알아봤던 메모리 배리어들에 대한 정보는
되게 단편적인 정보였어.

그냥

> 해당 배리어를 기준으로 연산이 넘어가지 못한다.

정도였지..

#### 3-5-1. 메모리 배리어의 분류와 성능

기본적으로, 메모리 배리어는 세 가지 분류로 나눌 수 있어.

1. `seq_cst`(순차적 일관성, Sequentially Consistent) 배리어
    - `seq_cst`
2. `release-acquire` 배리어
    - `acquire`
    - `release`
    - `acq_rel`
    - (`consume`)(이건 안씀)
3. `relaxed` 배리어
    - `relaxed` 배리어
    
약한 메모리 오더(명령어를 많이 재배치하는)의 CPU 아키텍처의 경우,
기본적으로
`seq_cst` -> `release-acquire` -> `relaxed`의 순서로 성능을 적게 잡아먹어.
(`relaxed`가 성능을 제일 적게 잡아먹음)

근데 강한 메모리 오더(명령어를 적게 재배치하는)의 CPU 아키텍처의 경우,
애초에 명령어 재배치가 적게 일어나다보니까
셋 다 성능이 비슷한 경우도 왕왕 있지.

결국,
기본적으로 성능이 별로 중요하지 않은 곳에서는 `seq_cst`
성능이 중요한 곳에서는 `release-acquire` / `relaxed`를 쓴다고 보면 돼.

#### 3-5-2. `release-acquire` 메모리 오더

이건 Happens-Before 관계로 인한 동기화의 관점에서 보면 가장 기본적인 메모리 오더야.

- `seq_cst` : `acq_rel`에다 전역적인 하나의 접근 타임라인 추가
- `relaxed` : 수정 순서 제외 `acquire`  / `release`에서 보장하는거 보장 안함

이거라,
사실상 이 메모리 오더만 제대로 배워놔도 쓸데가 많아.

일단 이 메모리 오더는,
딱 특정 연산에만 쓸 수 있는게 특징이야.

- store : `release`
- load : `acquire`
- RMW(Read-Modify-Write) : `release` / `acquire`

이렇게 말이야.

그리고 이 메모리 오더는 후에 나올 `seq_cst`처럼 전역적인 접근 순서까지는 보장하지 않는데,
자세한건 `seq_cst` 파트에서 알아보자.
(거기서 설명하는게 적합해.)

그리고 솔직히 여기서 설명할 것들은
이미 메모리 오더 기초 파트와 Happens-Before 관계 파트에서 설명해서 남는게 없네..

결국 `release-store`한 값을 다른 스레드에서 `acquire-load`하면
`release-store`한 이전의 연산의 결과를 `acquire-load` 이후에 관측할 수 있다는게 끝이야..

Sequenced-Before -> Synchronizes-With -> Sequenced-Before로 이어지는거지.

`release-store`로 Sequenced-Before를,
(`release-store`이전의 메모리 연산이 `release-store` 시점에 관측됨)

`release-store`한 값을 `acquire-load`했다는 것으로 Synchronizes-With을,
(`release-store`한 값을 `acquire-load`로 읽었다면
`release-store`이 `acquire-load`보다 먼저 일어남)

`acquire-load`로 Sequenced-Before를 보장하니까.
(`acquire-load` 이후에 `acquire-load` 이후의 메모리 연산이 발생함)

그리고 앞에서 말했는데
`release-store` / `acquire-load`로 인한 Happens-Before 관계는 전이적이라서,

연산 A가 연산 B보다 Happens-Before이고
연산 B가 연산 C보다 Happens-Before이라면
연산 A는 연산 C보다 Happens-Before일 수 있어.

좀 말을 풀어보자면,
연산 A가 연산 B 시점에 관측되고
연산 B가 연산 C 시점에 관측되면
연산 A는 연산 C 시점에 관측된다는거지.

그리고 좀 더 컴파일러 / 컴퓨터 아키텍처적 관점에서 바라보자면,

`release` 배리어는 

- 해당 배리어를 기준으로 컴파일러가 앞의 연산을 뒤로 미룰 수 없게 하고
- 해당 배리어를 기준으로 OoO Execution이 앞의 연산을 뒤로 미룰 수 없게 하고
- 해당 배리어를 기준으로 모든 밀린 쓰기 작업을 수행하게 한다.
  - 3.2에서 설명한 Store Buffer에 대한게 이거야.

라고 할 수 있을 것 같아.

`acquire` 배리어는

- 해당 배리어를 기준으로 컴파일러가 뒤의 연산을 앞으로 당길 수 없게 하고
- 해당 배리어를 기준으로 OoO Execution이 뒤의 연산을 앞으로 당길 수 없게 하고
- 해당 배리어를 기준으로 최신 데이터를 읽는데 필요한 모든 정보를 가져온다.
  - 이건 Invalidation Queue에 있는 밀려있는 캐시 변경 정보를
  다 적용해서 이전 값을 읽는 것을 막는다는거야.
  (최신 값을 읽게 함)

라고 할 수 있을 것 같아.
(물론 대략적으로 이렇다는 말이고,
실제 구현은 CPU 아키텍처에 따라 달라질 수 있어.)

`acquire`가 굳이 필요한 이유가 이거야.
`release-store`가 보장한 최신 값을 정확히 `load`하기 위해서.
(나 전까지는 이거 하나도 몰랐었다?ㅋㅋ)

그리고 마지막으로
`acq_rel`은 두 배리어를 합친 것과 같아.

#### 요약

필요없을듯?

#### 3-5-3. `seq_cst` 메모리 오더

이건 말 그대로 모든 스레드가 동일한 연산 순서를 바라보는
순차적 일관성(Sequentially Consistent)을 보장하는 배리어야.

앞에 나온 `acq_rel`과 헷갈릴 수 있는데,
이거의 다른 점은
**`std::atomic` 변수들에 대해`seq_cst`를 사용하는 모든 스레드**에 대해
(프로그램의 모든 스레드 아님, 
해당 `std::atomic` 변수에 대해 다른 메모리 오더를 사용하는 스레드들은 해당 안됨)
해당 `std::atomic` 변수와 관련되어있는 연산들에 대한
**순차적 일관성**을 보장한다는거야.

근데 여기까지 읽었으면 순차적 일관성이라는 말이 이해가 잘 안될 수도 있는데,
좀 이해하기 쉬운 표현으로 설명해볼게.

> 여러 `std::atomic` 객체의 `seq_cst` 메모리 배리어를 통한 모든 접근이
> 하나의 전역적인 타임라인으로 관리된다.

> 여러 `std::atomic` 객체의 `seq_cst` 메모리 배리어를 통한 
> 총 접근 순서가 모든 스레드에서 동일하게 보이도록 관리된다.

라고 할 수 있어.

예시를 들어볼게.

```cpp
std::atomic<bool> x{false};
std::atomic<bool> y{false};
std::atomic<int> z{0};

void write_x() { x.store(true, std::memory_order_seq_cst); }
void write_y() { y.store(true, std::memory_order_seq_cst); }

void read_x_then_y() {
    while (!x.load(std::memory_order_seq_cst));
    if (y.load(std::memory_order_seq_cst)) ++z;
}

void read_y_then_x() {
    while (!y.load(std::memory_order_seq_cst));
    if (x.load(std::memory_order_seq_cst)) ++z;
}
```

이렇다고 할 때, `seq_cst`를 안 쓰면
`write_x()` / `write_y()`에서 `x == true` / `y == true`로 바꿨어도
`read_x_then_y()`는 `x == true`를 인식했지만 `y == false`(아직 해당 코어에 미반영)일 수도 있고,
`read_y_then_x()`는 `y == true`를 인식했지만 `x == false`(아직 해당 코어에 미반영)일 수도 있어.

그래서 다 실행하고도 `z == 0`이 나올 수도 있지.

실제로 프로그램이 실행되는 곳은 CPU(코어)잖아?
그래서 코어 A는 코어 B가 변경한 값을 못 볼 수 있어.

캐시 일관성 프로토콜(MESI)가 있지 않냐고?
그건 캐시 계층의 프로토콜이지 CPU의 Store Buffer에는 적용이 되지 않거든..
(MESI 프로토콜은 코어들이 메인 메모리에 반영하지 않은 데이터들을 일치시켜주는 프로토콜임.)
(Modified / Exclusive / Shared / Invalid로 관리함)
(하지만 이 프로토콜은 캐시 한정이라,
CPU의 Store Buffer에 들어있어서 메모리에 반영이 안 된 데이터까지
일치시키지는 않음..)

메모리 배리어가 Store Buffer의 내용을 다른 코어에 보이게 해서 가시성을 보장해주지 않냐고?
그것도 같은 스레드에 두 변경이 있을 때만 성립되지,
다른 스레드에서 두 변경을 같은 순서로 관측한다는 보장은 없어.

`std::atomic` 객체의 수정 순서 보장도 있지 않냐고?
그건 같은 `std::atomic` 객체에 대한 보장이잖아.
서로 다른 `std::atomic` 객체에 대해서는 수정 순서가 보장되지 않아.

다른 스레드의 여러 `std::atomic` 객체의 접근에 대한 전역적인 하나의 타임라인이 없다면,
**각각 다른 스레드의 여러 `std::atomic` 객체에 대한 총 접근 순서**는 
일치하지 않을 수 있다 보니까..

`seq_cst`를 쓰면 모든 `std::atomic` 변수의 접근에 대한 전역적인 타임라인이 생겨.
`seq_cst`를 쓰는 모든 스레드가 특정 한 순서만으로 해당 `std::atomic` 변수들의 접근을 인식해서,
전역적으로 `x = true` -> `y = true` 순서로 접근했다면(여기서는 `store`),
말 그대로 모든 스레드가 변경을 해당 순서로 인식하게 돼.

그래서 `read_x_then_y()`는 `x == true`를 인식해도 `y == false`일 수 있지만,
`read_y_then_x()`는 `y == true`를 인식하면 이미 `x == true`일테니 `z`를 증가시키게 돼.
(여기서는 `load()`)
(`store()` / `load()` / RMW 모두 `seq_cst`가 단일화하는 총 접근 순서에 포함돼.)

이렇게 `seq_cst`를 사용하는 모든 `std::atomic` 변수에 대해서까지도
전역적인 타임라인을 보장하는게 `seq_cst`의 총 접근 순서 보장이라고 보면 돼.

적어도 `seq_cst`를 사용하는 연산들만큼은
코어(스레드)마다 각자의 관측 순서를 두지 않고,
모든 코어(스레드)가 하나의 통일된 관측 순서를 가지게 하는거야.

정말 간단하게 말하자면,

> `acquire` + `release`
> **+ 같은 메모리 오더를 쓰는 `std::atomic` 변수들에 대한 전역적인 총 접근 순서 보장**

이라고 할 수 있겠네..

물론 이게 그만큼 강력하다보니까,
약한 메모리 오더의 CPU 아키텍처에서는 비용이 더럽게 많이들어.
그냥 다른 메모리 오더보다 압도적으로 많이 든다고 보면 편해.

하지만 강한 메모리 오더의 CPU 아키텍처에서는 비용이 훨씬 적게 들어.

#### 요약

1. `seq_cst`는 `acquire-release`의 양방향 Reordering 억제에 더해,
해당 배리어가 적용되어있는 모든 `std::atomic` 객체들에 대한 총 접근 순서를
전역적인 하나의 타임라인이 되도록 보장해준다.
2. 그래서 `seq_cst`는 
단일 변수에 대한 동기화를 넘어
여러 `std::atomic` 객체들이 여러 스레드에서 접근될 때
여러 `std::atomic` 객체들의 여러 스레드에서의 총 접근 순서를 하나로 통일하는데 사용된다.

#### 3-5-4. `relaxed` 메모리 오더

이 메모리 배리어는 정말로
동일한 `std::atomic` 변수에 대한 수정 순서를 제외한
아무런 보장도 하지 않는 메모리 배리어야.

진짜 그것 제외하고는 아무런 보장도 없어.

synchronizes-with / happens-before 관계도 만들 수 없어.
(물론 단일 스레드에서는 happens-before긴 해도..)

```cpp
std::atomic<bool> x{false};
std::atomic<bool> y{false};
std::atomic<int> z{0};

void write_x_then_y() {
    x.store(true, std::memory_order_relaxed);
    y.store(true, std::memory_order_relaxed);
}

void read_y_then_x() {
    while(!y.load(std::memory_order_relaxed));
    if(x.load(std::memory_order_relaxed)) ++z;
}
```

아무리 한 스레드에서 `x.store(true)` -> `y.store(true)` 순서로 코드가 짜져있다고 해도,
다른 스레드는 `y.load() == true`를 인식한 후 `x.load() == false`를 인식해버릴 수 있게 돼.
(앞서 나온 `seq_cst`의 예시는 여러 스레드에서 여러 객체에 대해 접근을 한거라면,
이 예시는 한 스레드와 다른 한 스레드 간에서 여러 객체에 대해 접근한거라 다른 예시야.)
(`seq_cst` / `release-acquire`이라면 `x` -> `y` 순서가 반영됨)

아무런 순서의 강제가 없으니,
`x = true`가 메모리에 반영되기 전에 `y = true`가 반영되어서,
다른 스레드가 `y`를 먼저 관측했지만 `x`가 반영이 안 되어있는 상황이 나올 수 있는거지..

근데 솔직히 이거 왜 쓰는지 모르겠잖아?

딱 이럴 때 써.

> 오직 수정 순서 보장만 필요할 때,
> 즉 다른 변수와의 동기화가 필요없고 오직 해당 변수 하나만으로 의미를 지닐 때.

라고 할 수 있어.

대표적으로 단순 카운터가 있겠네..

그래서 `relaxed` 메모리 오더는 쉽게 말하면

> 여러 `std::atomic` 변수의 전역적인 하나의 실행 순서나
> 다른 변수와의 가시성은 보장하지 않고,
> 오직 수정 순서만 보장하는 메모리 오더.

라고 할 수 있겠네.

#### 요약

1. `relaxed`는 해당 `std::atomic` 변수의 수정 순서 이외의
전역적인 실행 순서 / 타 변수와의 가시성은 보장하지 않는 메모리 오더이다.
2. 그래서 `relaxed`는
다른 변수와의 동기화가 필요 없고
수정 순서만 보장되면 되는 곳에 쓰인다.

### 3-6. Release Sequences

이번 개념은 정의 자체는 별로 어려운게 아니야.

그냥

> `release-store`와 `acquire-load` 사이에 어떤 메모리 오더의 `RMW` 연산이 끼어들어도
> `release-store`와 `acquire-load` 사이의 Synchronizes-With 관계는 성립한다.

이게 끝이야.

물론 RMW 연산의 메모리 오더가 `release`든, `acquire`든
심지어 `relaxed`든 상관이 없고.

좀 예외 규칙같은 느낌이지..

이게 왜 이런지를 설명하기에는 이제 글 분량이 한계에 다다라서 간단하게만 설명해볼게.
(사실 나도 정말 오래 고민했는데 명확한 답을 못 찾아서 이렇게 쓰는거임..)

`release-store`한 값을 `relaxed-RMW`가 읽으면
결국 `release-store`한 값을 읽었다는 관계가 생기고,
그 관계가 Synchronizes-With을 유지시킨다.

그냥 `relaxed-store`가 중간에 끼인거라면
`release-store`한 값과는 상관 없이 `store`만 한 것이고,
그런 무관계는 Synchronizes-With을 유지시키지 않는다.

이렇게 설명할 수 있겠네.

마치 `RMW` 연산이 징검다리가 되어주는거지.
그냥 `relaxed-store`가 중간에 끼이면 `release-store`과는 관계가 없으니
`release-store`와 `acquire-load` 사이의 징검다리가 끊기는 느낌이고.

#### 요약

1. `release-store`와 `acquire-load` 사이에 `RMW` 연산이 들어와도
Synchronizes-With 관계는 유지된다.
