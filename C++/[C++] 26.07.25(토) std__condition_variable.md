## 0. 서론

솔직히 요즘 글이 거의 없었는데,
좀 아파서 병원에 입원할 필요가 있어서 그랬음.
다시 달려보려고.

입원해있는 동안,
스레드 풀에 관심이 많이 생겼어.

그래서 돌아오면 스레드 풀 코드를 짜보려고 했는데,
솔직히 스레드 풀을 짜기 위해선 condition variable 공부를 좀 해야겠더라고..

결국 Task Queue에 push() 됐을 때 스레드 풀의 스레드가 깨어나야하다보니까..

그런데 나는 condition variable을 잘 몰라서
자꾸 막히더라.

그래서 선행으로 condition_variable을 먼저 해보기로 했어.

## 1. condition variable이 필요한 이유

다른 스레드의 작업을 기다려야할 때,
일반적으로는 어떻게 해야할까?

(그러니까, 작업 간의 순서성을 보장하는 느낌이지.
동시적인 작업 사이의 순서를 동기화하는거야.)

`std::promise`와 `std::future`를 생각할 수도 있는데,
그건 딱 한 번밖에 결과를 못 받아보잖아?
애초에 `std::promise`와 `std::future`의 주목적은
스레드의 반환값 / 예외를 처리하는 것이기도 하고..

이렇게 스레드 간의 의존성을 여러번 동기화 할 필요가 있을 때는 어떻게 하는게 좋을까?

결국 가장 쉬운 방법은 그냥 다른 스레드가 작업 완료하는걸 바쁜 대기(busy waiting)로 기다리는거지.

```cpp
// ready_flag는 다른 스레드가 작업을 완료한 후 true로 설정하는 플래그

void thread_1(){
    // 설명 단순화를 위한 예시.
    // 실제로 여러 스레드가 접근한다면 ready_flag는 atomic이거나
    // 적절한 동기화로 보호되어야 한다.
    while(!ready_flag) {
        
    }
    // 다른 스레드가 작업을 완료하면 실행할 코드
}
```

하지만 이거 너무 비효율적이지 않아?

다른 스레드가 작업 완료하는걸 기다릴 때 계속 CPU를 점유하잖아.

그냥 

- 다른 스레드의 작업을 기다려야할 때 blocking되고
- 다른 스레드가 작업을 완료했을 때 다시 실행되는

그런게 있으면 좋잖아?

그 역할을 해주는게 condition variable이야.

1. 다른 스레드의 작업을 기다려야할 때 `wait()`으로 blocking되고
2. 다른 스레드가 작업을 완료했을때 `notify_one()`으로 blocking된 한 스레드를 깨우거나
`notify_all()`로 blocking된 모든 스레드를 깨우거나..

이렇게 동작하지.

## 2. `std::condition_variable`의 사용법

일단, `std::condition_variable` 자체를 사용하기 위한`<condition_variable>` 헤더와
`std::condition_variable`를 제대로 사용하기 위한 `<mutex>` 헤더를 인클루드해야해.

```cpp
#include <mutex>
#include <condition_variable>

std::mutex ready_mutex;
std::condition_variable ready_cv;
```

다른 스레드의 작업을 기다리려면,

```cpp
std::unique_lock<std::mutex> lock(ready_mutex);
while (!ready) {
    ready_cv.wait(lock);
}
```

이렇게 `std::unique_lock`과 `wait()`을 이용해서
해당 `std::condition_variable`에 대해 blocking되어서 기다릴 수 있어.
(`std::unique_lock`은 `unlock()`했다가 `lock()`했다가 할 수 있는 `std::lock_guard`로 보면 됨)

굳이 `while`문을 쓴 이유는,

- 이미 다른 스레드의 작업이 완료, 즉 `ready == true`일 때는 `wait()`를 호출하지 않고
그대로 실행하고
- 다른 스레드의 작업이 완료되지 않았는데, `ready == false`인데, 
즉 `notify_one()`이 호출되지 않았는데
해당 스레드가 실행되는 문제(이건 좀 나중에 다룰텐데)를 막기 위해
`wait()`에서 스레드가 깨어날 때 `ready == true`인지 한번 더 검사를 해야하기 때문이야.

이건 좀 나중에 따로 다룰게. 
일단 사용할 때는 이렇게 `while`문이나 비슷한 역할을 하는 것과 함께 쓴다는거야.

그렇게 기다리는 스레드를 다른 스레드에서 깨우려면,

```cpp
ready_cv.notify_one(); // 기다리는 스레드 하나만 깨우기
ready_cv.notify_all(); // 기다리는 스레드 전부 깨우기
```

이렇게

- `notify_one()` : 기다리는 스레드 딱 하나만 깨우기
- `notify_all()` : 기다리는 스레드 전부 깨우기

두 함수를 사용하면 돼.

이게 기본적인 사용법이야.

```cpp
// 실사용 예시
{
    std::lock_guard<std::mutex> lock(ready_mutex);
    ready = true;
}

ready_cv.notify_one();
```

실제로는 이렇게, 
해당 스레드의 작업이 완료됐다는 조건을 갱신할 때
해당 조건에 맞는 뮤텍스를 잡고 갱신해놔야해.

자세한건 후술할텐데, 사용법이면 이렇게 알면 돼.

## 3. 추가적인 내용들

먼저 여기서부터 단어를 좀 다르게 쓸게.

결국 '다른 스레드의 작업이 끝나는 것'을 코드 관점에서 보면, 
다른 스레드가 작업을 마치고 특정 변수(플래그)의 상태를 바꾸는 
'조건(Condition)'이 만족되는 것을 의미해. 

그래서 이름부터가 condition variable인 거지.

그렇기 때문에

앞에서 설명했던

> '다른 스레드의 작업이 끝나는 것'

은

이제부턴

> '조건이 만족되는 것'

이라는 느낌으로 접근할게.

### 3-1. 왜 뮤텍스가 추가로 필요할까?

이거 솔직히 의문 들 수 있어.

그냥 `std::condition_variable`이면 될 것 같은데,
왜 `std::mutex`까지 필요한지..

제일 중요한 이유는,
**스레드를 재우는 조건을 확인하는 것과 스레드를 재우는 것 사이**의 원자성을 보장해주려고 하는거야.

이거 뭔가 문장만으로는 잘 안 와닫는데,

```cpp
while (!ready) {
    cv.wait(); // 원래 뮤텍스를 넣어야 하는데 없다고 치고!
}
```

이런 코드가 있다고 하자.

`ready == false`라면,
해당 `std::condition_variable`에 `wait()` 함수를 호출하는 코드지.
`std::condition_variable`은 실제로 이런 형태로 조건과 함께 써.

근데 만약 이렇게 실행되면 어떻게 될까?

```cpp
Thread 1                         Thread 2
------------------------------------------------
ready 확인: false

                               ready = true
                               cv.notify_one()

cv.wait()
```

조건을 확인하는 것과 실제 `cv.wait()`으로 잠드는 것 사이에 틈이 있기 때문에
조건을 확인하는 것과 `wait()` 사이에 조건이 `true`가 되면
`wait()`하는 시점에서는 조건이 `true`인데도 확인하지 못하고
스레드 1은 `cv.wait()`으로 잠들게 돼.

그리고 스레드 2에서는 `ready`를 `true`로 바꾸고 `notify_one()`을 호출했지만,
그 시점에는 `wait()`으로 잠든 스레드가 없어서 어떤 스레드도 안 깨어나게 돼.

문제는 이러면,
다시 기적적인 확률로 `cv.notify_one()`가 호출되지 않는 이상
잠든 스레드 1은 안 깨어날 확률이 높아서,

조건 확인과 `wait()` 호출 사이에
해당 조건에 대한 변경이 발생하면 안돼.

이런 문제를 Lost Wakeup 문제라고 해.

그래서

```cpp
std::unique_lock<std::mutex> lock(mutex);
while(!ready) {
    cv.wait(lock);
}    
```

이런 식으로 뮤텍스를 사용해서 조건을 바꾸는 것과 실제 `wait()`이 호출되는 것을
원자적으로, 중간에 다른 스레드가 해당 뮤텍스를 사용해서 조건을 바꿀 수 없게 실행해서
방금같은 상황을 막는거야.

아 그리고, 
이게 왜 `wait()` 함수에 `std::unique_lock`을 넣냐면,

`wait()` 함수의 동작이

1. 해당 스레드를 해당 `std::condition_variable`의 대기 스레드 목록에 등록
2. 뮤텍스를 해제
3. 해당 스레드를 재움

이 순서로 실행되거든.

조건을 확인하는 것에다가,
대기 스레드 목록에 등록하는 것과 뮤텍스를 해제하는 것까지 원자적으로 연결되어 처리되어서,

1. 아직 조건을 확인 중이면 다른 스레드는 락을 얻지 못해서
조건을 바꾸지 못하기 때문에
`wait()`이 호출되고 나서야 
다른 스레드가 조건을 바꾸고 `notify_one()`이 호출되어서
정상적으로 해당 스레드가 깨어나고,
2. 다른 스레드가 먼저 조건을 바꾼 경우에도
조건을 확인하고 잠들지 않게 되어서

어느 순서로 실행되어도 알림을 잃지 않게 돼.

그리고 이러면 `std::unique_lock`을 사용하는 이유도 설명 돼.

`wait()` 함수 내부에서 해당 뮤텍스를 해제한 뒤
깨어날 때는 해당 공유 자원(조건에 포함되는 것)을 다뤄야 할테니 다시 해당 락을 잡아야 할테니까.

이 정도면

- condition variable을 사용할 때 굳이 뮤텍스가 필요한 이유
  - 조건 확인과 `wait()` 사이에 조건에 대한 간섭을 막으려고
- 굳이 `std::unique_lock`을 사용하는 이유
  - `wait()` 도중에 락을 풀어야해서

이런 것들은 설명됐다고 생각해.

### 3-2. Spurious Wakeup(가짜 기상) 문제

앞에서 짧게 설명했었는데,

```cpp
while (!ready) {
    cv.wait(); // lock 생략
}
```

왜 굳이 여기에 이렇게 `while`문을 써야하느냐에 대한 답이야.

솔직히 이거 왜 이 문제가 발생하는지를 설명하려면 OS의 스케줄러 등등까지 설명해야해서
OS 글이 될 것 같거든?
~~애초에 condition variable이 OS쪽이긴 한데~~

그러니 자세한건 스킵하고,

딱 이 결론만 보고 생각해보자.

> C++에서는 OS 스케줄러 등의 요인에 의해, 
**`std::condition_variable`에서 `wait()` 함수로 재운 스레드가
`notify_*()` 함수들을 호출하지 않아도 깨어나서 실행될 수 있다.**

이거.

이제 감이 올거야.

다시 이 코드를 봐보자.

```cpp
while (!ready) {
    cv.wait(); // lock 생략
}
```

만약 저렇게 `notify_*()` 함수들을 호출하지 않아도 해당 스레드가 깨어나는 경우에는,
결국 **조건이 만족이 안 된 상태**로 깨어나는 거잖아?

그걸 `while`문이 검사하는거야.

1. Spurious Wakeup으로 `notify_*()`이 호출되지 않고 해당 스레드가 깨어난다.
2. 하지만 `while`문의 반복을 멈추는 조건(계속 말하고있는 조건)이 만족이 되지 않았으므로 
`while`문이 반복을 해서 다시 `cv.wait()`가 호출된다.

이거야.

그러니까, 
Spurious Wakeup같은 문제로 인해
`wait()`에서 깨어났다는 사실만으로는 조건이 만족되었다고 판단하면 안되니까,
스레드가 깨어난 뒤 다시 조건을 검사해서 실제로 조건이 만족되었는지 확인하는거야.
조건이 만족되지 않았다면 다시 `wait()`를 호출하게 되는거고.

결국 이렇게 `while`문을 두는 이유 중 하나는 Spurious Wakeup 문제에 대한 안전장치야.

그리고 `while`문 대신 `if`문을 쓰면 안되는 이유도 설명되지.

```cpp
if (!ready) {
    cv.wait(); // lock은 생략
}
```

이런 경우에, 
Spurious Wakeup 문제가 발생하면 깨어난 스레드가 그대로 실행되어버릴테니까..

`while`문은 조건이 만족이 안되면 다시 `wait()`를 호출하게 되는 반면에.

### 3-3. while문을 쓰는 이유 하나 더

`while`문은 Spurious Wakeup만 막는게 아니야.

좀 더 근본적인 이유지.

결국 `while`문이 Spurious Wakeup에 대한 안전 장치가 되는 이유가,
`wait()`에서 깨어나도 조건을 한번 더 검사하기 때문이잖아?

이게 그래서 Spurious Wakeup 뿐만 아니라,
`notify_*()` 함수를 써서 깨어났을 때 조건을 한번 더 검사하는 역할을 하는거야.

이게 문제가 될 수 있는건 결국,

```text
thread A : wait 중
thread B : wait 중

thread C : 
    ready = true
    notify_all()
```

이런 경우야.

둘 다 깨어날 수 있지만,

```text
Thread A :
    mutex 획득
    ready = false
    mutex 해제
    
Thread B :
    뒤늦게 mutex 획득
    이미 Thread A가 ready = false로 바꿔놓음
```

이렇게 되는 경우에 스레드 B는 정상적인 `notify_all()`을 받고 깨어났지만,
해당 스레드가 뮤텍스를 얻었을 때는 조건이 거짓으로 뒤바껴있을 수 있어.

실제로 이런 경우도 고려해야하고.

솔직히 좀 억지같지?

이게 왜 그렇냐면 내가 지금까지는 표현하기 쉬운 플래그를 조건으로 예시를 들었는데,
지금 내가 관심있는 스레드 풀에서는 
큐가 비어있을 때 `wait()`를 하는 식으로 `std::condition_variable`을 사용해.

그렇다면, 

```text
Thread A:
    mutex 획득
    Task를 queue에서 꺼냄
    mutex 해제

Thread B:
    뒤늦게 mutex 획득
    이미 queue가 비어 있음(조건이 이미 거짓이 됨)
```

이런 상황도 발생할 수 있겠지?

솔직히 방금 ready 플래그 예시는 잘 와닫지 않을 것 같아서 추가로 예시 하나 더 들었어.

결국, `while`문의 근본적인 역할은

> `wait()`에서 깨어난 이후에 조건 검사를 한번 더 해서 깨어나고도 조건이 거짓인 상황을 막는다.

이거야.
