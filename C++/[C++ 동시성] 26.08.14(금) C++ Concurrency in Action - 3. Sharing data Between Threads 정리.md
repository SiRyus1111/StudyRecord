### 1. 스레드를 사용할 때의 이점

> 제일 중요한거 : 스레드끼리 직접적으로 쉽게 데이터를 공유할 수 있다는 것.

솔직히 이런거 안되면 스레드 쓸 이유가 상당히 없어진다..

하지만 큰 힘에는 큰 책임이 따르듯이,
부작용이 있다.

### 2. 여러 스레드가 공유하는 데이터가 있을 때 발생하는 문제

레이스 컨디션.

이거 하도 설명 많이해서 간단히 설명해보자면,

> 여러 실행 흐름이 공유 자원에 접근할 때
> 실행 순서에 따라 공유 자원의 값이 달라지는 상황

이라 할 수 있음.

책에서는 영화관 예시를 들더라.

만약 해당 영화관에 자리가 한 자리 남아있는데,
티켓 판매처가 여러 곳이라 동시에 두 곳에서 다른 사람이 티켓을 사게 되면
상대적인 순서에 따라 누가 예매를 성공하는지가 달라질 수 있다는거.

그리고, 결국 레이스컨디션이 문제가 되는건
해당 레이스 컨디션이 프로그램의 불변식을 깰 때라고 하네..

즉,
해당 프로그램의 불변식을 깨지 않는 경우에는 ㅇㅋ라는거.

예를 들어, 
이중 연결 리스트에서 노드를 삭제하기 위해 앞 노드의 `next` 포인터를 다음 노드로 옮겼을 때,
하필 그 때 다른 스레드에서 해당 노드의 다음 노드도 삭제하려는 연산을 하고 있다면..?

이건 이중 연결 리스트의 불변식 중 하나인 
'이전 노드는 다음 노드를 가리키고, 다음 노드는 이전 노드를 가리킨다'
라는 불변식을 깨버림.

그래서 이런건 문제가 됨.

하지만,
큐에 실행 순서에 따라 순서가 다르게 원소가 들어가지만,
결국 해당 큐에 대한 불변식이 깨지지 않는다면
어떤 원소가 먼저 들어가고 나중에 들어가도 ㅇㅋ라는거.
(물론, 특정 원소가 먼저 들어가야한다는 불변식이 있다면 문제겠지..)

그리고 문제가 되는 레이스 컨디션은 
주로 두 개 이상의 서로 다른 공유 데이터를 수정해야만 작업이 완료되는 상황에서 
잘 벌어진다고 함.

두 개의 공유 데이터를 수정해야 특정 작업이 완료된다고 하면,
1 -> 2 실행 사이에 누가 해당 데이터들에 접근하면 레이스컨디션이 발생한다.

그리고 이런 레이스컨디션은 타이밍에 따라 발생하고 발생안하고가 달라져서
디버깅이 더럽게 어렵다..
관측하려고 하면 사라지는게 대표적.(하이젠버그)

### 3. 레이스컨디션을 방지하는 법

일단 첫 번째로,
가장 간단한 방법인 해당 데이터를 보호 매커니즘으로 감싸서
그렇게 수정을 실행하는 스레드만이 해당 수정의 중간 과정을 볼 수 있게 하는거.

그러니까 결국 원자성을 보장해주는거지.
이건 Lock / Mutex 느낌..

두 번째로,
그냥 그런 데이터나 자료구조를 락-프리로 설계하면 됨.

atomic operation같은 
하드웨어 단에서 더이상 쪼개질 수 없는 연산을 이용해서
불변식이 깨지지 않는 데이터나 자료구조를 구현하는거지.
이건 Lock-Free / Atomic 느낌..

세 번째로,
데이터 / 자료구조에 대한 업데이트 자체를 트랜잭션으로,
성공하면(중간에 다른 스레드가 해당 공유 자원을 안 건드렸다면) 커밋 느낌으로 성공하고
하나라도 실패하면(중간에 다른 스레드가 해당 공유 자원을 건드렸다면) 전부 롤백하게 구현해놓는거.
그리고 실패하면 재시도.
(근데 이건 잘 사용되지는 않음, DB같은데서 사용됨)
이건 Transactional Memory / STM 느낌.

## 4. 뮤텍스

뮤텍스란, 
한번에 한 스레드만 공유 자원에 접근할 수 있게 해주는 동기화 도구.

자료구조로 예시를 들어보면,
한 번에 한 스레드만 해당 자료구조에 접근할 수 있게 하고,
한 스레드가 해당 자료구조에 접근했으면 다른 스레드 들은 해당 자료구조에 접근하지 못하게 하는
그런 역할을 수행함.

물론 뮤텍스도 만능은 아님.

뒤에 나오는데,

- 올바른 데이터를 보호하도록 코드를 구성해야하고
- 함수 여러개를 쓸 때 내재된 레이스 컨디션을 피해야하고
- 데드락도 피해야하고
- 데이터 보호 범위가 지나치게 좁거나 넓은 문제도 해결해야하고

등등을 해결해주어야 함.

### 4-1. C++에서의 뮤텍스

C++에서의 뮤텍스는 `<mutex>` 헤더에 정의되어있어.

```cpp
#include <mutex>

int main() {
    std::mutex mtx; // 이렇게 선언한다.
    
    mtx.lock(); // 다른 스레드가 해당 뮤텍스를 소유하고 있으면 blocking된다.
    
    // 공유 자원에 접근하는 코드 구역(임계 구역)
    
    mtx.unlock();
    
    // 이렇게 lock() / unlock() 으로 뮤텍스를 얻고 / 헤제할 수 있다.
    // 하지만 실제로는 예외 안전성 등 때문에 
    // 스코프를 벗어나면 자동으로 락이 해제되는 RAII 패턴을 적용한
    // std::lock_guard를 사용한다.
    
    {
        std::lock_guard<std::mutex> lock(mtx);
        
        // 임계 구역
    }
    // 예외가 발생했든 무슨 상황이든 스코프를 벗어나면 락 자동 해제(RAII 패턴)
}
```

그리고 이렇게,
`lock()` / `unlock()`의 한계(예외 안전성 등) 때문에
실제로는 RAII 패턴을 적용하여 스코프를 벗어나면 자동으로 락이 해제되는 객체인
`std::lock_guard`를 사용해.

그리고 보통, 뮤텍스는 전역에 선언하지 않고,
보호할 대상과 같은 객체에 선언하는 경우가 많아.

이렇게 하면 해당 뮤텍스가 뭘 보호하는지 확실히 나타낼 수 있고,
캡슐화로 인해서 해당 뮤텍스가 함부로 획득되지 못하게 할 수 있어.

```cpp
class A { // 클래스 이름 짓기 귀찮음
private:
    std::mutex mtx;
    std::list<int> list; // 보호해야할 공유 자원
public:
    void add_to_list(int new_value) {
        std::lock_guard<std::mutex> lock(mtx); // 보호해야할 공유 자원에 접근할 때 뮤텍스를 획득하게 함
        list.push_back(new_value);
    }
    
};
```

그리고,
뮤텍스의 범위 외부에서 다른 스레드가 
참조 / 포인터로 해당 객체를 수정하려하면
뮤텍스를 쓰는 의미가 없어져.
해당 뮤텍스를 안 거치고 공유 자원에 별도의 보호 없이 접근하게 되니..

```cpp
class A {
private:
    std::mutex mtx;
    std::list<int> list; // 보호해야할 공유 자원
public:
    std::list<int>& GetList() {
        std::lock_guard<std::mutex> lock(mtx); // 여기서 뮤텍스를 걸어도
        return list; // 참조로 반환하기 때문에 이 객체 밖에서 해당 공유 자원을 사용할 때는
        // 뮤텍스를 안 거치기 때문에 문제가 됨
    }
}
```

그래서,
외부에서 참조하든 뭘 하든
공유 자원에 대해 접근할 때는 
무조건 해당 공유 자원을 보호하는 뮤텍스를 거치도록 인터페이스를 설계해줘야해.

굳이 참조 / 포인터로 접근하는게 필요하면 이렇게 단순히 해당 공유 자원의 복사본을 쓰던가.

```cpp
std::list<int> GetList() {
    std::lock_guard<std::mutex> lock(mutex);
    return list; // 복사로 반환해서 원본에는 영향을 끼칠 수 없음
}
```

한 줄로 요약하면,

> 공유 자원에 접근하는 모든 경로에서 예외없이 동일한 뮤텍스의 보호를 받아야 한다.

\+ 굳이 외부에서 참조가 필요할 경우, 단순 복사를 고려해볼 수 있다.

라는 뜻이야.

그리고 결국 뮤텍스를 쓸 때 주의해야하는 점이 이렇게 외부에서의 참조다보니까,
뮤텍스를 사용해서 코드를 짤 때는 함수들을 살펴보며 외부에서의 참조가 가능한지를 꼭 살펴봐야해.

물론, 직접적이 아니라 간접적으로도 참조로 전달될 가능성이 있는지를 잘 살펴봐야해.
이건 C++ 기능으로는 근본적으로 못 막고,
코드 수준에서 참조로 전달하지 않도록 잘 해줘야해.

### 4-2. 인터페이스들 자체에 내제된 레이스컨디션

이건 별도의 챕터로 빼볼게.

Thread-Safe(스레드 안전)한 스택까지 코드로 짜보는 것도 할거라.

이건 그러니까,
분명 단일 함수로는 코드 상으로는 문제가 없어보이지만,
그 함수(인터페이스)들을 엮어 쓸 때 레이스컨디션이 발생할 수 있다는거야.

책에서는 스택에서 `empty()` / `top()` / `pop()`을 쓰는 예시를 들어.

이런 코드가 있다고 해보자.
각각의 함수 내부에는 스레드 안전하게 락을 제대로 다 걸어놨다고 해보자고.

```cpp
int top_element = 0;
if (!stack.empty()) { // 스택이 비어있지 않다면
    top_element = stack.top(); // 스택의 최상위 원소를 기록
    stack.pop(); // 그 후 최상위 원소를 pop()
}
```

이런 코드는 각각의 인터페이스(함수)만 봤을 때는 스레드 안전해보여.

- `empty()` : 뮤텍스 제대로 걸려있음
- `top()` : 뮤텍스 제대로 걸려있음
- `pop()` : 뮤텍스 제대로 걸려있음

이렇게 모두 스레드 안전하니까.

하지만,

결국 `empty()` 호출과 `top()` / `pop()` 호출 사이에
다른 스레드가 끼어들 수 있기 때문에 문제가 있어.

1. `empty()` / `top()` 사이에 다른 스레드가 `pop()`을 수행했다고 해보자.
원소는 하나 뿐이었고..
2. 그렇다면, 결국 `empty()`를 확인했을 때는 빈 스택이 아니었지만,
`top()`을 호출하는 시점에는 빈 스택이겠지?
3. 그래서 `top()`을 빈 스택에 호출해버리는 대참사가 날 수 있어.

-

1. `top()`과 `pop()` 사이에 다른 스레드가 `pop()`을 수행했다고 해보자.
이것도 원소는 하나 뿐이었고..
2. 그렇다면, 결국 `top()`을 했을 때는 빈 스택이 아니었지만,
`pop()`을 호출하는 시점에서는 빈 스택일테고,
3. 그래서 `pop()`을 빈 스택에 호출해버리는 대참사가..

이렇다는거야.

하나의 인터페이스가 스레드 안전해도,
그 인터페이스들을 엮어서 코드를 짰을 때는 스레드 안전하지 않을 수 있다는거야.

그래서, 진짜로 스레드 안전한 스택을 만들려면,
`empty()` / `top()` / `pop()`을 원자적으로,
공통된 뮤텍스를 사용해서 묶어야해.

이렇게 말이야.

```cpp
struct empty_stack : std::exception { // 단순히 스택이 비어있을 때 예외를 나타낼 구조체
    const char* what() const throw();
};

template <typename T>
class ThreadSafeStack {
private:
    std::stack<T> stack;
    mutable std::mutex mtx;
public:

    // 복사 생성자 및 복사 대입 연산자는 분량 상 구현하지 않음
    
    void push(T new_value) {
        std::lock_guard<std::mutex> lock(mtx);
        stack.push(std::move(new_value));
    }
    std::shared_ptr<T> pop() { // 예외 안전성을 위해 shared_ptr를 반환
        std::lock_guard<std::mutex> lock(mtx); // empty() 확인, top() / pop()을 한 번의 뮤텍스 범위에서 함
        if (stack.empty()) throw empty_stack();
        std::shared_ptr<T> const res(std::make_shared<T>(stack.top()));
        stack.pop();
        return res; 
        // 결과적으로, empty() / top() / pop()이 중간 과정에서 다른 스레드의 간섭을 받지 않고 실행됨
    }
    void pop(T& value) { // 예외 안전성을 위해 레퍼런스 변수를 사용
        std::lock_guard<std::mutex> lock(mtx);
        if (stack.empty()) throw empty_stack();
        value = stack.top();
        stack.pop();
    }
};
```

그리고 추가로,
예외 안전성도 빠질 수 없지.
위의 `pop()` 함수들에서 각각 `std::shared_ptr`와 레퍼런스 변수를 쓴 이유야.

만약 저 과정 도중에 예외가 터진다?
그러면 확실히 문제가 생길 수 있어.

애초에 `top()`과 `pop()`이 분리되어있는 이유도 예외 안전성 때문이야.
`pop()`이 스택에서 데이터 가져오기와 스택에서 데이터 지우기를 같이 수행한다면
도중에 예외가 터져서 가져오기는 실패했지만 지우기는 성공하면
해당 데이터를 영원히 못 찾게 될테니까,
`top()`으로 스택에서 가져오기만을 담당하고
`pop()`으로 스택에서 지우기만을 담당하는 식으로
예외 안전성을 챙긴거거든.

물론 `return`하는 과정에서도 복사 / 이동 실패같은 예외 상황 때문에
`pop()`은 됐지만 데이터를 못 넘겨주는 경우가 있을 수 있어.

그래서

- 복사 과정에서 예외가 발생할리가 없는 포인터(객체 수명을 보장하기 위해 `shared_ptr`)로 넘겨주거나
- 레퍼런스 변수를 미리 받아서 메모리 할당으로 발생할 수 있는 예외를 차단하거나

할 수 있는거지.

그리고 항상 `top()`으로 인한 복사가 예외 상황 없이 성공해야만
`pop()`을 수행해서 해당 데이터를 영원히 못 찾는 오류도 해결하고.

결론을 내보자면,

> 원자성을 보장해야하는(도중에 다른 스레드에서 간섭받으면 안되는) 연산들은
> 하나의 락 안에서 실행해야한다. 물론 인터페이스도 그렇게 설계해야한다.

> 반환 시의 복사 예외 안전성을 보장하기 위해,
> 조회와 삭제가 원자적으로 일어나도록 작성한 코드에서는
> 포인터 / 레퍼런스 변수 등을 사용하는게 좋다.

라고 할 수 있을 것 같네.

사실, 이 파트는 두 가지 주제에 대해 다루고 있어.

1. 멀티스레드 관점의 원자성 보장.
    - 원자적으로 실행되어야하는 여러 함수를 각각 따로 부르면 
    중간에 다른 스레드가 간섭하는(여러 함수 간의 원자성이 지켜지지 않는) 레이스컨디션이 발생함
    - 그렇기 때문에 뮤텍스로 해당 함수들을 
    원자적으로 실행되도록(중간에 다른 스레드가 간섭할 수 없도록) 묶어줘야한다.
2. 그렇게 여러 함수를 묶었을 때의 예외 안전성 문제.
    - 여러 함수를 묶었을 때, 값 반환 시점에 예외가 터지면 기존의 데이터가 공중분해됨
    - 그렇기 때문에 값 반환 시 예외가 발생하지 않도록 
    `shared_ptr` 반환이나 레퍼런스 전달같은 테크닉을 써야한다.
    
ㅇㅋ 정리 끝.

### 4-3. 데드락과 데드락의 해결법

뮤텍스를 사용하다보면 두 개 이상의 락을 잠가야 실행할 수 있는 작업이 있는 경우가 있어.

이런 경우에는, 잘못 락을 잡을 경우 데드락이라는 심각한 문제가 발생할 수 있고.

일단 두 스레드가 서로 각각 락을 들고 있고,
서로가 들고 있는 락을 기다리는 상황을 상상해보자.

```text
   [ 스레드 A ] <---( 점유 )--- [ 뮤텍스 1 ]
       |                           ^
       |                           |    
    ( 대기 )                    ( 대기 )
       |                           |
       ↓                           |
   [ 뮤텍스 2 ] ---( 점유 )---> [ 스레드 B ]
```

이런 상황에서는,
서로가 가진 락을 서로가 안 놓기 때문에
프로그램이 더이상 진행되지 않고 막혀버려.

- 스레드 A는 뮤텍스 1을 들고 뮤텍스 2를 기다리지만 스레드 B가 뮤텍스 2를 들고있어 기다리게 되고,
- 스레드 B는 뮤텍스 2를 들고 뮤텍스 1을 기다리지만 스레드 A가 뮤텍스 1을 들고있어 기다리게 되고..

이런 식이지.

이런 데드락이 발생하는 네 가지 조건이 있는데,
바로

- 상호 배제 : 한 뮤텍스를 여러 스레드가 얻을 수 없음
- 점유 대기 : 한 뮤텍스를 점유하고 있을 때 해당 뮤텍스를 놓지 않음
- 비선점 : 다른 스레드의 뮤텍스를 강제로 뺏을 수 없음
- 순환 대기 : 위의 아스키아트처럼 서로가 서로의 자원을 기다림

이 네 가지 조건이야.

데드락을 막는 것도 결국 이 네 가지 조건 중 하나를 무력화하는 식으로 진행돼.

이런 데드락을 막는 제일 보편적인 방법은
전역적으로 락을 잡는 순서를 고정해놓는거야.(순환 대기 무력화)

하지만, 이 방식은 다양한 경우에 문제가 많아.
지금 내가 하고있는 룸 시스템 같은 경우도 그렇고(데드락 막으려다가 이걸 공부하기 시작함..),

동일한 클래스의 두 객체 간에 락을 잡고 데이터를 교환하는 경우는,
아무리 첫 매개변수 -> 두 번째 매개변수 순서로 들어오는 락을 잡는다고 해도,
실제 락을 잡는 뮤텍스 기준으로는 서로 반대 순서로 락을 잡게 되어서
데드락이 발생하게 되지.

```text
[ 객체 A ] <-( 먼저 소유 )-- [ 뮤텍스 A ]
    |                           ^
    |                           |
( 획득 시도 )                ( 획득 시도 )
    |                           |
    ↓                           |
[ 뮤텍스 B ] --( 먼저 소유 )-> [ 객체 B ]

두 스레드의 객체들이 같은 클래스로 생성한 객체라고 할 때, 
객체 자신의 뮤텍스 -> 타 객체의 뮤텍스 순서로 락을 잡는다면
이렇게 데드락이 발생한다.
```

순서를 고정해서 락을 잡는다고 인식해도,
이런 착각을 할 수가 있는거야.

그리고 C++에는 `std::lock()` 이라는 해결책이 있어.
이 함수는 데드락 위험 없이 두 개 이상의 뮤텍스를 한 번에 잠글 수 있게 해주는 함수야.

이 코드가 방금 말했던 동일한 클래스 두 객체 간에 락을 잡고 데이터를 교환하는 경우의 코드야.
이 코드는 데드락 위험이 있어.
(예외 안전성은 빼고 생각하자. `unlock()`을 확실히 보여주기 위해 이렇게 짰어.)

```cpp
// 데드락 위험이 있는 코드
void swap(Object& a, Object& b) {

    a.mtx.lock();
    b.mtx.lock();
    
    swap(a.some_data, b.some_data);
    
    a.mtx.unlock();
    b.mtx.unlock();
}
```

한 스레드에서 `a = A` / `b = B`,
다른 스레드에서 `a = B` / `b = A`로 매개변수를 넣고
두 함수를 동시에 실행하면 어떻게될까?

```text
[ 객체 A ] <-( 먼저 소유 )-- [ 뮤텍스 A ]
    |                           ^
    |                           |
( 획득 시도 )                ( 획득 시도 )
    |                           |
    ↓                           |
[ 뮤텍스 B ] --( 먼저 소유 )-> [ 객체 B ]
```

바로 이 꼴이 나는거야..

하지만, 여기서 `std::lock()` 함수를 사용할 수 있어.

```cpp
void swap(Object& a, Object& b) {

    std::lock(a.mtx, b.mtx); // 두 뮤텍스를 데드락 없이 한 번에 std::lock() 함수로 잠그기
    
    // 잠근 뮤텍스를 RAII 객체에 넘겨서 관리만 맡기기
    // std::adopt_lock은 이미 잠긴 뮤텍스를 맡긴다는걸 명시적으로 알려주는거임(소유권 이전)
    std::lock_guard<std::mutex> lock_a(a.mtx, std::adopt_lock);
    std::lock_guard<std::mutex> lock_b(b.mtx, std::adopt_lock);
    
    swap(a.some_data, b.some_data);
    
}
```

`std::lock()` 함수는 내부적으로 데드락을 발생시키지 않는 알고리즘을 기반으로 해서
데드락이 발생하지 않도록 입력받은 뮤텍스들을 잠가줘.

그리고 락 획득 도중에 예외가 발생하면
이미 잠가둔 락도 풀어버려.

그래서 

- 전부 잠그거나
- 전부 못 잠그거나

최종적으로 이렇게 두 가지의 경우만 나오게 해주지.
이 함수가 락 여러 개를 잠그는 함수다보니까
락을 잠그는 도중에 발생한 예외에 대한 예외 안전성을 챙겨준거야.

그리고 `std::scoped_lock`에도 `std::lock()` 함수와 비슷한 작용(?)이 있어.

방금의 코드 예시도, 이렇게 바꿀 수 있지.

```cpp
void swap(Object& a, Object& b) {

    // scoped_lock에 여러 뮤텍스를 넣으면, std::lock() 함수처럼 데드락이 발생하지 않게 여러 락을 잠금
    std::scoped_lock<std::mutex, std::mutex> lock(a.mtx, b.mtx); 
    
    swap(a.some_data, b.some_data);
}
```

이렇게 간결하게.

이렇게 `std::scoped_lock`을 쓰면 `std::lock()` 함수와 같은 효과를 얻을 수 있고,
후에 다른 가드 객체로 `std::mutex` 객체를 넘겨줄 필요가 없어서
확실히 실수가 줄어들겠지.

물론 쓸 수 있을 때만 사용해야겠지만..

그리고, 결국
`std::lock()` / `std::scoped_lock` 같은 것들은
두 뮤텍스를 동시에 얻을 때나 의미가 있고,

한 뮤텍스를 얻고 작업을 수행하다가 또 다른 뮤텍스를 얻는 경우같이
두 뮤텍스를 따로 얻어야 하는 경우에는 이런 편리한 데드락 방지 인터페이스들의 도움을 받을 수 없어.

그래서 그런 경우에는 프로그래머가 별도로 코드를 잘 짜야해..
하지만 잘 짤 수 있는 지침같은 것도 있어.
책에서 소개하는건 이 정도야.

결국 지침들의 관점은 하나래.

> 해당 스레드가 다른 스레드를 기다리고 있을 가능성이 있다면 다른 스레드들 기다리지 말자.

이 관점을 중심으로 앞으로 설명할 지침들이 있는 셈이고.

1. 락 잡고 또 다른 락을 잡지 마라.
    - 애초에 이렇다면 데드락 자체가 발생할 수가 없음
2. 락을 잡은 도중에 내가 내부를 모르는 함수(외부 코드) 등을 절대 호출하지 마라.
    - 내가 내부를 모르는 함수에서 락을 잡는다면 그 함수가 무슨 락을 잡을지,
    또는 내 객체를 또 다시 호출할지 알 수가 없어서
    데드락이 발생할 수 있고,
    외부 코드의 실행 시간이 길다면 추가적인 락 경합이 발생할 수 있음
3. 락을 고정된 순서로 잡게 해라.
    - 락을 고정된 순서로 잡으면 서로가 서로의 락을 기다리는 상태(순환 대기)가 발생하지 않아서
    데드락이 발생할 위험이 없다.
    - 하지만 이건 항상 시도할 수 있는 해결책은 아니다.
    앞에서 설명한 같은 클래스로 생성된 여러개의 객체 예시도 그렇고..
    내 뮤텍스 -> 상대 뮤텍스 순서로 잡으면 데드락이 발생한다.
    - 그래서, 전역적으로, 시스템 전체에서 엄격하게 고정된 하나의 순서로 락을 잡아야한다.
    - ~~(내가 룸 시스템에서 마주친 머리아픈 포인트도 이것이다..)~~
4. 코드 자체에 락 계층을 사용해서 무조건 고정된 순서대로 락을 잡게 해라.
    - 앞의 고정된 순서대로 잡게하는건 결국 휴먼 에러가 발생하면 무용지물이지만,
    각 락마다 계층을 부여하고, 스레드가 마지막으로 잡은 락의 계층을 기록해서
    높은 순서 -> 낮은 순서로 잡게 한 후
    마지막으로 잡은 락의 계층이 새로 잡아야 하는 락의 계층보다 낮다면
    예외를 던지게 하는 식으로..
    - 결국 목적은 락을 잡는 순서 규칙을 개발자의 기억에 의존하지 않고
    코드가 알아서 검사하게 만드는 것
    - 순서가 틀리면 실행 중에 바로 예외를 터뜨려 데드락 가능성 자체를 사전에 차단
    
물론 이런 지침들은 lock 뿐만 아니라 다른 스레드가 blocking 될 수 있는 곳에도 적용 가능해.

예를 들어 `join()` 함수라던지. 
양 쪽 스레드가 서로를 `join()`한다면 해당 스레드들은 영원히 안 끝나는 것처럼.
이런 것도 사실상 데드락이랑 같지.

### 4-4. `std::unique_lock`과 락 소유권 이전

기존의 `std::lock_guard`는 중간에 잠시 `unlock()`을 하진 못했지만,
`std::unique_lock`은 `std::lock_guard`와 다르게
중간에 풀었다 잠갔다 할 수 있는 유연한 락이야.

그리고 이렇게 풀었다 잠갔다 할 수 있다보니,
옵션으로 `std::defer_lock`을 넣어서
해당 객체 생성 시 락을 잠그지 않은 상태로 생성할 수도 있지.

```cpp
// 뮤텍스를 잠그지 않은 상태로 unique_lock 객체 생성
std::unique_lock<std::mutex> lock(mtx, std::defer_lock); 
```

그리고 앞서 중간에 풀었다 잠갔다 할 수 있다고 말했듯,
`lock()` / `std::lock()` / `unlock()`을 사용해서 잠갔다 풀었다 할 수 있어.

물론 이런 동작들 때문에 `std::lock_guard`보단 비용이 커.

그리고 `std::unique_lock`은 락을 안 잡은 상태일 수도 있기 때문에
내부에 락을 잡은 상태인지 안 잡은 상태인지를 기록하는 플래그를 둬.
그리고 객체가 소멸될 때 해당 플래그를 보고 락을 잡은 상태라면
해당 락을 `unlock()` 함수로 풀어주는 식으로 동작해.
그리고 이 플래그가 사실상 `std::lock_guard`와의 성능 차이를 보이는 지점이야.

`std::unique_lock`은 뮤텍스 포인터에다가 플래그까지 저장해야하니까.
그리고 락 상태를 변경할 때마다 플래그를 업데이트 / 검사하는 오버헤드도 존재할테고.

결국, 락에 유연성이 필요한 특수한 상황이 아니라면(지연 락 / 락 소유권 이동 등)
굳이 메모리 더 먹고 플래그 검사 오버헤드가 있는 `std::unique_lock`을 남발하지 말고
가벼운 `std::lock_guard`나 C++17의 `std::scoped_lock`을 쓰는게 좋아.

그리고 `std::unique_lock` 객체는 반드시 해당 뮤텍스를 소유할 필요가 없고,
`unlock()` 상태로 들고다닐 수 있기 때문에
해당 `std::unique_lock`을 다른 객체로 이동시킬 수 있어.

물론 `std::unique_lock`은 복사 금지 객체다보니,
`std::move`로 이동시켜야하지.
(정확히는 해당 `std::unique_lock`이 
r-value(자동 이동됨)인지 l-value(`std::move()` 필요)인지에 따라 달라져.)

이런 소유권 이동은,
한 함수가 락을 잠그고, 다른 함수에 해당 락을 넘겨줘서
해당 락을 계속 잡고 있는 상태로 작업을 할 수 있게 해줘.

```cpp
std::mutex mtx;

std::unique_lock<std::mutex> get_lock() {
    std::unique_lock<std::mutex> lock(mtx);
    return lock;
}

void process() {
    
    std::unique_lock<std::mutex> lock(get_lock());
    
    // 해당 락을 얻은 상태에서 함수 계속 실행
}
```

### 4-5. 락을 잡는 구간의 최소화

일반적으로,
락을 잡는 구간은 최소화하는게 좋아.

락을 오래 잡고 있으면
락을 기다리는 스레드들이 기다리는 시간이 늘어나거든.
이걸 락 경합(Lock Contention)이라고 하고.

물론 락을 잡아야하는 구간에는 무조건 락을 잡긴 해야할테지만,
적어도 락을 잡을 필요가 없는 구간까지 락을 잡진 말자는거야.

락을 잡아야 할 필요가 없는 구간에는 
적당히 락을 잡는 구간을 최소화한다는거지.
무작정 최소화하는게 아니라.

그리고, 파일 I/O같은 시간이 많이 걸리는 작업은 락을 잡지 않고 수행하는게 좋아.
그런건 일반적인 작업보다 락을 잡고 있는 시간을 훨씬 많이 늘리게 되어서,
멀티스레딩을 할 이유가 있었나 싶게 만들어버릴 수가 있어.

그 점에서 `std::unique_lock`은 참 유연한 락이지.
락을 잡을 필요가 없는 구간이나,
무거운 파일 I/O같은 작업을 할 때 `unlock()`으로 잠시 락을 풀 수 있으니까 말이지.

### 4-6. 특수한 뮤텍스들

지금까지의 뮤텍스는
쓰기든 읽기든 무조건 한 스레드만 임계 구역에 들어올 수 있는 뮤텍스였어.

하지만 모든 스레드가 공유 자원을 똑같은 방식으로 건드리는게 아니기 때문에,
단순한 `std::mutex` 대신 상황에 맞는 다른 종류의 뮤텍스를 써야할 때가 있어.

- 공유 자원을 초기화할 때만 뮤텍스가 필요하고 그 이후로는 읽기 전용으로 쓰인다거나
- 읽기 작업은 많이 수행되는데 불변식을 깰 수 있는 쓰기 작업은 적게 수행된다거나
- 뮤텍스를 여러번 잠가야 하는 상황이 있다거나

이런 경우들에 적합한 뮤텍스들이 있어.

공유 자원을 초기화할 때만 뮤텍스가 필요하고 그 이후로는 읽기 전용으로 쓰일 때 사용하는
`std::once_flag` / `std::call_once`를 먼저 보자.

자원이 비싸서, 
프로그램 시작 지점이 아니라 
실제로 필요할 때 처음으로 객체를 생성해야할 필요가 있을 때가 있어.
이걸 지연 초기화라고 하는데,

이 초기화는 평생 단 한 번 일어나겠지만,
그 뒤로 읽기 작업만 수행된다면
해당 공유 자원을 뮤텍스로 보호할 때는
읽기만 할 때도 매번 락을 잡았다 푸는 엄청난 성능 손해가 발생해.

```cpp
std::shared_ptr<resource> shared_resource;
std::mutex shared_resource_mutex;

void foo() {
    std::unique_lock<std::mutex> lock(shared_resource_mutex); // 매번 접근할 때마다 락을 잡음
    if (!shared_resource) { // 최초 한 번만 실행되는 초기화
        shared_resource.reset(new resource);
    }
    lock.unlock();
    shared_resource->do_something(); // 이렇게 읽기 작업만 실행됨
}
```

이 코드를 보면,
실질적으로 락을 잡아야 할 부분은 최초 한 번만 실행되는 초기화를 하는 부분이지만,
초기화 후에 읽기 작업을 실행할 때도 락을 잡았다 풀게돼.

성능 손해가 극심하겠지.

그래서 C++에는 이런 문제를 언어 차원에서 깔끔하게 해결해주는 인터페이스가 있어.
`std::call_once` / `std::once_flag`인데,

`std::once_flag` 플래그는 해당 공유 자원이 초기화되었음을 나타내는 플래그로써 사용돼.
이게 뮤텍스같은 동기화 도구의 느낌이지.
동기화 데이터가 저장되어있어.
그래서 이걸 공유해야 다른 스레드에서 해당 공유 자원의 초기화를 인식할 수 있어.
`std::mutex`가 복사만 불가능했던 것과 다르게, 
`std::once_flag`는 복사 / 이동 둘 다 불가능해.

`std::call_once` 함수는 `std::once_flag`를 받아서 
해당 `std::once_flag`를 보고 지정된 함수가 딱 한 번만 실행되도록 동기화해줘.

방금 코드는, 이렇게 고칠 수 있어.

```cpp
std::shared_ptr<resource> shared_resource;
std::once_flag shared_resource_flag;

void init_resource() {
    shared_resource.reset(new resource);
}

void foo() {
    // std::once_flag를 보고 입력받은 함수를 락을 잡고 실행할지 실행하지 않을지 결정
    // 이미 누가 해당 std::once_flag로 해당 함수를 실행했다면 해당 스레드는 해당 함수를 실행하지 않음
    // 누가 해당 함수를 실행 중이라면, 다른 스레드는 해당 위치에서 blocking됨(초기화 완료 시까지 대기)
    // 즉, 첫 초기화는 해당 std::once_flag로 동기화됨.
    std::call_once(shared_resource_flag, init_resource);
    
    shared_resource->do_something(); // 초기화 후의 읽기 작업은 락을 얻지 않고 실행됨
}
```

그리고 이거랑 비슷한게,
`static`으로 선언된 지역 변수..

처음으로 실행한 한 스레드만 초기화를 해야하잖아?
두 스레드가 동시에 해당 변수를 초기화하려고하면 안될테니까..
근데 이건 C++11부터는 `std::once_flag` / `std::call_once`를 이용한 동기화마냥
처음으로 실행한 한 스레드만 초기화하게 되고
해당 코드를 실행하는 다른 스레드는 blocking되는 보호 매커니즘이 들어왔어.

이 `static` 지역 변수가 처음으로 초기화된 후 읽기 전용이 된다면,
`std::call_once`와 비슷하게 동작하겠지.

이건 싱글톤 패턴에도 적용되는데,
싱글톤 패턴이 외부에서 해당 객체를 생성하는 것을 막은 후
처음 해당 `static` 객체를 초기화한 다음에
계속 해당 객체를 사용하는거다보니까..

두 번째로,
불변식을 깨지 않는 읽기 작업은 많이 수행되는데
불변식을 깰 수 있는 쓰기 작업은 적게 수행될 때 사용하는
`std::shared_mutex` / `std::shared_timed_mutex`를 보자.

만약 읽기 작업은 많이 수행되는데
쓰기 작업은 적게 수행된다면
기존의 `std::mutex`로는 읽기 작업이든 쓰기 작업이든
한 번에 한 스레드만 통과할 수 있게돼.

하지만 읽기 작업이 압도적으로 많이 수행된다면
읽기 작업은 불변식을 깨지 않으니
읽기 작업도 한 번에 한 스레드만 실행할 수 있는건
기존의 `std::mutex`로써는 비효율적일거잖아?

이런 문제에서 탄생한 뮤텍스가 있는데,
reader-writer 뮤텍스야.
쓰기를 수행하는 스레드(writer)는 배타적으로, 다른 스레드의 접근을 막고
읽기를 수행하는 스레드(reader)는 다른 읽기를 수행하는 스레드와 동시접근 할 수 있어.

C++14에서 추가된 `std::shared_mutex`와
C++17에서 추가된 `std::shared_timed_mutex`가
이런 reader-writer 뮤텍스의 C++에서의 구현이야.

일반적으로는 두 reader-writer 뮤텍스 중 `std::shared_mutex`가 성능 면에서 유리해.

물론 `std::shared_mutex`가 `std::mutex`와 비교해서
읽기 작업이 많고 쓰기 작업이 적은 경우에는 
성능 면에서는 이점을 제공할 수 있지만,
이런 뮤텍스를 사용하는게 만능 해결책은 아니고,
실제 성능은 관련된 프로세서의 수와 reader 스레드 / writer 스레드의 상대적인 작업 부하에 따라 달라져.

그리고 해당 뮤텍스도 당연히 RAII Wrapper 락 객체를 적용할 수 있는데,
`std::lock_guard` 및 `std::unique_lock`은 기존의 `std::mutex`처럼 
다른 스레드가 해당 뮤텍스를 잡을 수 없게 해.
즉, 쓰는 작업은 해당 객체들로 나타낼 수 있어.

그리고 `std::shared_lock`은 
다른 reader 스레드도 해당 뮤텍스를 잡을 수 있게 해서,
읽는 작업은 해당 객체들로 나타낼 수 있어.
물론 이건 `std::unique_lock`과 동일하게 사용되지만,
여러 스레드가 동일한 `std::shared_mutex`에 대해 동시에 락을 획득할 수 있다는 점이 다른 점이야.

여기서 문제가 있는데,
어떤 스레드가 공유 락을 보유하고 있는 한,
다른 모든 배타적 쓰기 작업을 하려는 스레드들은
모든 공유 락을 보유하고 있는 스레드가 해당 락을 놓을 때까지 기다려야한다는 점이야.

그래서 배타적 쓰기 작업을 하려는 스레드에게 기아 상태(Starvation)가 발생할 수 있기 때문에,
나름 생각을 좀 잘 해서 써야해.

```cpp
resource shared_resource;
std::shared_mutex shared_resource_mutex;

void reader_thread() {
    std::shared_lock<std::shared_mutex> lock(shared_resource_mutex);
    resource.reading(); // 해당 읽기 작업은 여러 스레드가 동시에 실행 가능
}

void writer_thread() {
    std::unique_lock<std::shared_mutex> lock(shared_resource_mutex);
    resource.writing(); // 해당 쓰기 작업은 한 스레드만 실행 가능
}
```

세 번째로, 뮤텍스를 여러번 잠가야하는 상황이 있는 경우에 사용하는
`std::recursive_mutex`를 보자.

`std::mutex`의 경우, 스레드가 이미 소유하고 있는 뮤텍스를
다시 잠그려고 시도하면 정의되지 않은 동작이 발생해.

하지만 어떤 상황에서는,
스레드가 먼저 뮤텍스를 해제하지 않고도 같은 뮤텍스를 여러번 다시 얻어야 하는 상황이 있을 수 있어.
그래서 C++에는 `std::recursive_mutex`가 있어.

이 뮤텍스는 `std::mutex`와 비슷하게 작동하지만,
동일한 스레드에서 한 뮤텍스에 대해 여러 개의 락을 획득할 수 있다는 점이 달라.
다른 스레드가 해당 뮤텍스를 얻으려면
이전 스레드에서 모든 락을 해제해줘야해.

`lock()`을 3번 호출했다면, `unlock()`도 3번 호출해야
다른 스레드가 해당 뮤텍스를 얻을 수 있다는거지.

그리고 이것도 `std::lock_guard`와 `std::unique_lock`에 넣을 수 있어.

하지만, 이런 `std::recursive_mutex`가 필요한 대부분의 경우,
그냥 해당 `std::recursive_mutex`를 쓰지 않고 설계를 변경하는게
보통은 더 나아.
(나도 룸 시스템에 `std::recursive_mutex`를 사용했는데, 이거 바꿀 생각..)
