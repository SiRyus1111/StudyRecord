## 1. `future`와 함수형 프로그래밍

일단, 함수형 프로그래밍이 뭘까?

바로,

> 함수 내부에서는 외부 상태를 수정하지 않고,
> 오직 매개변수로 상태를 받고
> 반환값으로 해당 함수의 효과를 제한하는 프로그래밍 패러다임

을 함수형 프로그래밍이라고 해.

이렇게 외부 상태를 수정하지 않는 함수를 순수 함수라고 하지.

이런 프로그래밍 방식을 택하면 좋은 점이,
멀티 스레드 환경에서 함수가 공유 상태를 수정하지 않기 때문에
레이스 컨디션이 발생할 수 없으므로,
뮤텍스를 사용해서 공유 상태를 보호할 필요가 없어져.

그리고 여기서 `future`가 중요한 역할을 해줘.

`future`를 스레드 간에 전달함으로써,
공유 데이터에 명시적으로 접근하지 않고도
한 계산의 결과가 다른 계산의 결과에 의존하게 할 수 있기 때문이야.

말이 어려운데,
그냥 여러 스레드가 `future`를 통해 소통하고,
그 과정에서 각 스레드가 실행하는 작업이 서로 의존하는 식으로 동작하게 된다는거야.

그냥 `future`를 사용하면 그런 효과가 발생해.

예시를 들어볼게.

```cpp
#include <future>

int doSomething() {
    // 뭐시기 저시기
    // 해당 함수를 실행하는 스레드에서는 main()의 상태를 바꾸지 않음
}

int main() {
    std::future<int> f = std::async(std::launch::async, doSomething);
    
    // 기타 다른 작업
    
    int do_something_res = f.get();
    
    int res = do_something_res * 4; // 예시로 * 4만 함..
}
```

이렇게 코드가 있다고 할 때,
별개의 스레드로 실행되는 `doSomething()` 함수에 결과에
`main()` 함수가 의존하게 되지?

`get()`으로 얻어온 결과가 어떻게 되느냐에 따라
`main()` 함수가 계산하는 값이 달라지잖아?

그러면서 `doSomething()` 함수는 공유 상태를 바꾸지 않는다면?

완전히 함수형 프로그래밍 + `future`의 예시지.

책에서는 quick sort 예시를 들어.

함수형 프로그래밍 예시와,
그것에 더한 `future`를 이용한 병렬 처리 예시를 들면서 
`future`의 예시를 들어줘.

근데 뭐가 뭐의 상위호환이라기보단,
함수형 프로그래밍 -> `future`를 이용한 병렬 처리 순으로 나아가는거라고 보면 되겠네.
(이 글에서는 예시를 안 듬)

결국 중요한건 이거야.

1. 함수형 프로그래밍으로 외부의 공유 상태를 건들지 않는다.
2. `future`로 스레드 간에 정보를 주고 받아
공유 상태를 건들지 않으면서도 한 스레드의 동작이 다른 스레드의 결과에 의존하게 만든다.

근데 이게 바로 뒤에 나올 CSP랑 헷갈릴 수 있는데,
결국 단방향으로 결과만 수령하고 상태를 가지지 않는다는 점이 차이점이야.

`future`는 일회용 전송 통로잖아?

그냥 연산의 결과만 쏙 빼먹는게
함수형 프로그래밍 + `future`라는거지.

## 2. 스레드 간 메시지 전들을 이용한 연산 동기화

이렇게 공유 상태를 안 건드려서
동시성 문제를 피하는 프로그래밍 패러다임은 함수형 프로그래밍 뿐만이 아닌데,
CSP(Communicating Sequential Precesses)라는거야.

앞서 설명한 `future`과 비슷한데,
결국 

> 여러 스레드를 완전히 분리하고,
> 즉 공유 데이터를 두지 않고,
> 각 스레드는 서로 메시지를 주고받을 수 있는 통신 채널로 소통한다.

라는거지.

다른 점은,
한 번만 `future`를 사용해서 결과값만 쏙 빼먹는
함수형 프로그래밍 + `future`와 다르게,
지속적으로 여러 스레드들이 소통을 한다는 점과,
각 스레드가 상태를 가진다는 점이라고 할 수 있어.

결국 공유 데이터가 없다면,
각 스레드는 다른 스레드로부터 수신한 메시지에
어떻게 반응하는지로만
완전히 독립적으로 실행될 수 있어.

책에서는 이러면 각 스레드는 상태 머신과 같다고 하네.

메시지를 수신하면 상태를 업데이트하고,
상태에 따라 처리를 수행하며
다른 스레드에 메시지를 보낼 수도 있는거지.

뭐 유한 상태 머신이니 뭐니 하는데,
결론은 이거야.

> 각 스레드가 메시지로 소통하고 메시지에 따라 상태를 업데이트하며 상태에 맞는 작업을 수행한다.
> 각 스레드를 독립적으로 분리함으로써, 공유 데이터에 따른 동시성 문제의 복잡성을 상당 부분 해소할 수 있다.

그래서 이게 어떻게 구현되는지를 보여주자면,
쉽게 말하면 Actor 모델이야.

(제미나이가 그려준 Actor 모델 아스키아트)

```text
+-------------------------------------------------------------------------+
|                              Actor A (Thread)                           |
|                                                                         |
|  +------------------+         +-------------------------------+         |
|  |  Mailbox (Queue) |         |  Private State & Logic        |         |
|  |  [Msg3][Msg2][M1]| =======>|  - NO mutexes needed!         |         |
|  +------------------+ (pop)   |  - Process 1 msg at a time    |         |
|                               +-------------------------------+         |
+-------------------------------------------------------------------------+
       ^                                      |
       |  Message                             |  Message
       |  (e.g., via std::promise)            |  (e.g., Task/Event)
       |                                      v
+------------------+                   +----------------------------------+
|     Sender B     |                   |             Actor C              |
|  (Other Thread)  |                   |  +------------+   +-----------+  |
|                  |                   |  |  Mailbox   | =>| State/Logic| |
+------------------+                   |  +------------+   +-----------+  |
                                       +----------------------------------+
```

여러 스레드들은 메시지 큐(Mailbox)를 통해 소통하고,
각 스레드들은 각자의 상태를 소유하고,
각 스레드들만이 각자의 상태를 바꾸므로,
즉 한 번에 한 메시지만 각자의 상태에 반영하므로
뮤텍스같은 동기화 도구가 필요 없는 상태인거지.

딱 메시지 큐(Mailbox)에 대한 동기화만 해주면,
Thread-Safe Queue를 사용하면 되는거야.

책에서는 ATM 예시를 들어서 해줘.
(그림은 못 그리겠음..)

객체를 

- `ATM`
  - `incoming`
  - `bank`
  - `interface_hardware`

이렇게 나누고
각 객체를 Actor로 둬서 각자의 스레드의 메시지 큐로
메시지를 주고 받는 예시야.

그리고 각 객체의 Actor 스레드는 순서에 맞춰 메시지를 처리하고.

## 1, 2 파트 요약

> 함수형 프로그래밍(FP) + `future`이든 CSP / Actor든
> 여러 스레드 간의 공유 상태 접근 / 변경을 줄이거나 없애고
> `future`로 각 작업의 의존성을 명확히 줘서 스레드 간의 소통을 하거나
> 각 객체마다의 Actor 스레드와 메시지 큐를 둬서 스레드 간의 소통을 하는 식으로
> 추가적인 동기화 없이 동시성 프로그래밍을 가능하게 할 수 있다.

> 함수형 프로그래밍 : 매개변수 / 반환 값으로만 상태를 나타내고
> 함수 내부에서는 외부 상태를 바꾸지 않음 
> -> 그렇기 때문에 외부 공유 상태를 바꾸지 않게 됨
> 함수형 프로그래밍 + `future` : 함수형 프로그래밍만으로는
> 여러 스레드 간의 소통이 불가능. 그래서 `future`로 일회성이지만 여러 스레드 간의 소통을 진행함
> -> 그렇기 때문에 동기화 할 부분이 상당히 줄어듬

> CSP / Actor : 여러 스레드 간의 공유 상태를 두지 않고
> 각 스레드가 전용 채널(메시지 큐)을 통해 메시지로 소통함
> -> 그렇기 때문에 동기화 할 부분이 상당히 줄어듬

## 3. `future`의 확장 버전 - continuation

기존까지의 `future`과는 다른 확장 버전도 있어.

`<experimental/future>` 헤더를 인클루드하면 되는데,
`std::experimental` 네임스페이스에서도 `promise` / `packaged_task` / `future`의 새로운 버전인
`std::experimental::promise` / `std::experimental::future` 등을 제공해.

그리고 해당 `promise`에 `get_future()`를 호출했을 때는
`std::experimental::future` 객체가 나오지.
(기존의 `future`과는 다른 객체라는 말)

이런 확장 객체들의 핵심 기능은,
바로 continuation이라는 기능이야.

무슨 기능이냐면,
`future`가 준비 상태가 되었을 때
임의의 코드를 실행하는 기능이지.

이걸 어디다 쓰냐면,
`future`에 데이터가 준비되면 그걸 처리하기 위해 필요한 코드가 있을 거 아니야?
(물론 `future.get()`을 호출하는 스레드의 값에 의존성이 있는 경우는 제외하고)

그런 코드를 continuation에 쓰면,
데이터가 준비되면 바로 해당 코드가 실행이 되면서
복잡한 처리를 할 필요가 없어지겠지.

그렇게 `future`에 continuation을 추가하는 함수는
`then()` 함수야.

```cpp
f.then(continuation);
```

이런 형태로 쓰지.

그리고 이것도 `future`와 똑같이
해당 `future`에 저장되어있는 데이터가
continuation에서 사용되고 있다면,
다른 코드에서는 해당 값에 접근할 수 없어.

그리고 `future::then()`을 통해 continuation이 추가되면
원래의 `future`는 무효화되고,
해당 continuation의 결과를 담을 새로운 `future`를 반환하게 되지.

그리고 continuation은 상황에 따라 다른 곳에서 실행되는데,

- 딱히 지정 안해놓으면 상황에 따라,
  - **`then()`을 호출하는 시점에서**
  - 아직 `future`를 가지고 있는 스레드에 작업이 안 끝났으면 `set_value()`를 호출하는 스레드,
  - `future`를 가지고 있는 스레드가 작업이 끝났으면 해당 스레드
- `std::launch::async`로 지정해놓으면 해당 스레드와 비동기로 실행되고,
- `std::launch::deferred`로 지정해놓으면 해당 스레드에서 실행되는 식으로

이렇게 실행돼.

그리고 continuation 함수에는 인자를 전달할 수가 없어.
인자는 라이브러리 선에서 정의가 되어있어서,
continuation 함수에는 해당 continuation을 트리거한 `future`가 들어가거든.

이렇게 continuation으로 사용되는 함수의 경우,
`std::experimental::future`를 인자로 받아야 해.

왜 그렇냐면,
결국 `future`에 예외도 담길 수 있기 때문에,
`future`를 그대로 continuation 함수에 전달해서
해당 함수 자체에서 예외를 처리할 수 있게 하는거지.

그리고 이런 `std::experimental`은
`std::async()`를 명시적으로 제공하질 않아서,
따로 만들어써야한다는 차이점도 있어.

> 그런데 이 기능은 표준화에 실패했으니까 솔직히 몰라도 됨..

## 4. 특정 조건에 맞춰 완료될 때 까지 기다리기

### 4-1. 모든 스레드의 작업이 완료될 때 까지 기다리기

여러 비동기 작업을 하는데,
모든 작업이 완료될 때 까지 기다려야 하는 경우가 있잖아?

그럴 때, 일반적으로는

```cpp
f1.get();
f2.get();
f3.get();
```

이렇게 각각의 `future`에 대해 `get()`을 호출하는 방법이 있을 수 있어.

하지만 각 작업에 대해 개별적으로 대기하기 때문에,
결과가 하나씩 준비될 때 마다 계속 깨어났다 잠들었다를 반복할 수 있어.
그러면 컨텍스트 스위칭 오버헤드 때문에 별로 안 좋겠지?

`std::experimental::when_all()` 함수는 이런 불편한 컨텍스트 스위칭을 피할 수 있는 도구야.
완료를 대기할 `future`들을 해당 함수에 전달하면
해당 `future`들이 모두 준비되었을 때 데이터가 준비되는
새로운 `future`를 생성해.

그리고 이 `future`에 `get()`을 했을 때는,
`std::vector<std::future<void>>`같은 `future`의 목록을 반환해.

이 함수의 장점 중 또 하나는,
하나의 `future`로 여러 비동기 작업이 모두 완료되었다는 것을 표현할 수 있다는 것도 있어.

> 근데 이것도 정식 버전에 적용되진 않아서..ㅋㅋ
> 알 필요 없긴 한데 이런 방식도 있구나.. 느낌이지.

### 4-2. 한 스레드의 작업만이라도 완료될 때 까지 기다리기

여러 작업 중에 하나만 완료되어도 괜찮은 경우가 있어.
대표적으로,
특정 기준을 충족하는 값 하나를 찾을 때,
전체 데이터 셋을 여러 개로 분할해서 각각 비동기로 탐색하는 경우가 있겠네..

이건 비동기 작업 중 하나만 완료되어도 ㅇㅋ잖아?
그리고 다른 스레드는 작업을 중단해도 되고.

어쨌든 비동기 작업 중 하나라도 완료되었을 때 사용하는 함수는
`std::experimental::when_any()`야.

그리고 반환값이 중요한데,
반환값은 `std::experimental::future<std::experimental::when_any_result<...>>`인데,
솔직히 이게 뭔지부터 좀 헷갈릴 수 있어(가독성 쓰레기)..

결국, `std::experimental::when_any_result<>`를 `get()`으로 반환하는 `future`를 반환하고,

그 `when_any_result<>`는 어떤 `future`가 준비되었는지를 나타내는 `index`와
`when_any()` 함수로 입력받은 `futures`를 배열의 형태로 모아놓은
`futures`로 나뉘어서,

완료된 `future`를 찾으려면 `result.futures[result.index]`를 해주면 돼.
결과값을 얻으려면 `get()`을 추가로 호출해주면 되고..

결국 반환값은 `future`들과 그 `future`들 중 값이 준비된 `future`의 인덱스를 담은
`when_any_result`가 들어간다고 보면 돼.

굳이 이걸 쓰는 이유는 어느 `future`가 준비되었는지를 알 수 있게 하기 위해서야.

> 근데 이것도 정식 버전에는 적용되지 않아서,
> 이런게 있었구나, 정도로만 이해하면 됨.

## 3, 4파트 요약

> `std::experimental::future`들의 실험적 기능으로는,
> `future`의 값 준비 시 추가로 실행할 코드를 해당 `future`에 입력하는 `then()` 함수와
> '모든 `future`가 준비되었을 시 값이 준비되는 `future`'를 반환하는 `when_all()` 함수와
> '특정 `future`가 준비되었을 시 값이 준비되는 `future`'를 반환하는 `when_any()` 함수가 있다.
> 하지만 이 기능들은 C++ Concurrency TS의 실험적 기능이었던지라,
> 정식 버전에 도입되지는 않아서
> 그냥 `future`의 각 문제들을 어떻게 해결하려했는지의 관점으로 보면 된다.

## 5. 여러 스레드의 특정 작업 완료를 기다리기 : `latch` / `barrier`

이것도 C++ Concurrency TS의 실험 기능이긴 했는데,
`C++20`에서 정식 기능이 되어서 따로 설명할거야.

`latch`는 내부 카운터가 0이 될 때 까지 `wait()`한 스레드가 기다리는
일회성 동기화 도구이고,
(한 스레드가 여러 번 카운터를 감소시킬 수 있음)

`barrier`는 지정된 수의 스레드들이 특정 지점에 도달할 때 까지 각 스레드가 대기하는
재사용 가능 동기화 도구야.
(한 스레드가 여러 번 배리어에 도달할 수는 없음)

### 5-1. `std::latch` : 일회성으로 내부 카운터가 0이 될 때 까지 기다리기

`std::latch`는 `<latch>` 헤더에 정의되어있고,
생성자의 인자로 초기의 카운터 값을 받아.

그리고 카운터가 0이 될 때 까지 기다릴 스레드들은
`wait()`으로 해당 지점에서 대기하고.

그리고 대기 중인 이벤트가 발생하면
`std::latch` 객체에 대해 `count_down()`을 호출하고,
카운터가 0이 되면 준비 상태가 되어서,
해당 `latch` 객체에 대해 `wait()`을 호출한 스레드들을 출발시켜.

+ 카운터를 내리며 기다려야 하는 경우에는 `arrive_and_wait()`를 호출하면 됨.

그리고 책에서는,
추가적으로 `count_down()`을 호출하기 전의 변경 사항이
`wait()`을 호출한 후에 보이는게 보장된다고 하는데,
딱봐도 순서성 문제네..

### 5-2. `std::barrier` : 여러번 가능한 지정된 갯수에 스레드가 해당 지점에 도달할 때 까지 기다리기

`std::barrier`는 `<barrier>` 헤더에 정의되어있어.
생성자에는 몇 개의 스레드가 해당 `std::barrier`객체에 대해 대기하고 있을 때
대기를 해제할지에 대한 스레드 수를 입력받아.

이건 지정된 수의 스레드가 특정 지점에 도착할 때 까지
해당 스레드들을 대기 상태로 두는 객체인데,

각 스레드는 처리를 완료하면
`arrive_and_wait()`를 호출해서
다른 스레드들이 처리를 완료할 때 까지 대기해.

물론 `arrive()` 함수로 대기하지 않고 도착 횟수를 줄일 수도 있고.

어쨌든 마지막 스레드까지 도착하면,
모든 스레드의 대기가 해제되고
해당 `std::barrier` 객체가 재설정돼.

대기를 풀고 해당 스레드 그룹에서 탈퇴하려면,
`arrive_and_drop()` 함수를 호출하면 돼.
해당 함수를 호출하면 더이상 해당 스레드는 대기하지 않고, 해당 스레드 그룹에서 탈퇴하게 돼.
그러면서 다음 `std::barrier`를 사용할 때에
`arrive_and_wait()`에 도착해야 하는 스레드 수도 하나 줄여주지.
(한 스레드가 해당 스레드 그룹에서 탈퇴했으니..)

그리고 추가적인 기능이 있는데,
마치 `future`의 `then()`처럼 모든 스레드가 도착했을 때
추가적인 함수를 실행해주는 기능이야.

배리어가 한 번 사용되었을 때,
즉 모든 스레드가 `arrive_and_wait()`을 호출했을 때
해당 함수가 한 번 실행되는 기능인데,
생성자에 추가적으로 callable 객체를 넣으면 돼.

## `latch` / `barrier` 요약

> 두 도구의 공통점은,
> 몇 개의 스레드가 특정 작업을 완료했을 때에
> 다른 스레드 / 그 스레드들의 대기 상태를 해제하는 식으로
> 순서 동기화를 하는 도구라는 점이다.

> `future` / `condition_variable`은 여러 스레드의 작업 완료에 대해서는
> 여러 스레드가 대기하도록 하기 어렵기 때문이다.

> 결국, 상황에 맞게 두 도구를 이용하면 된다.
