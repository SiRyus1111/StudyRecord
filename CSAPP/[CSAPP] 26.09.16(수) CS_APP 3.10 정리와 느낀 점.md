## 1. Understanding Pointers - 포인터의 이해

### 정리

1. 포인터의 타입
    - 포인터는 타입이 있고,
    그 타입은 어셈블리 상에서는 의미가 없지만,
    C언어 자체에서 프로그래머가 실수하지 않게 도와주는 역할을 한다.
    
2. 포인터의 값
    - 모든 포인터는 값을 가지고 있다.
    - 해당 값은 지정된 타입의 어떤 객체의 주소이다.
    - `NULL`도 포인터 값이 될 수 있고,
    아무런 객체도 가리키지 않는 것을 나타낸다.
    
3. 포인터와 `&`연산자
    - 포인터(주소)는 `&` 연산자를 사용하여 생성되고,
    해당 연산자는 모든 l-value에 사용할 수 있다.
    (r-value에는 사용 불가능하다.
    임시값이니까 당연히 그렇겠지? 주소가 없을테니까.)
    - `&` 연산자의 기계어 구현에서는 
    해당 연산자로 주소 값을 구할 때 종종 `leaq` 명령어를 사용한다.
    (`leaq` 명령어 자체가 주소 값을 구하는 명령어임)
    
4. 포인터의 역참조
    - 포인터는 `*` 연산자를 사용해 역참조할 수 있다.
    - 역참조한 값의 타입은 포인터의 타입과 연동된다.
    (이 표현이 맞는지는 모르겠다..)
    - 포인터 역참조는 어셈블리에서 `( )`를 이용한 메모리 참조로 구현된다.
    
5. 포인터와 배열
    - 포인터와 배열은 밀접한 관련이 있다.
    - 배열의 이름은 포인터처럼 참조할 수 있고
    배열 인덱스 참조는 포인터 연산 + 역참조와 동일한 효과를 가진다.
    - 배열 인덱스 참조 / 포인터 역참조 모두
    `오프셋 * 객체 크기`의 값이 적용된다.
    (`p + i * L`)
    
6. 포인터와 캐스팅(형 변환)
    - 포인터는 형 변환해도 값이 달라지지 않는다.
    하지만 `L`(포인터 연산에서 사용하는 자료형의 크기)의 값은 달라진다.
    
7. 포인터와 함수
    - 포인터가 코드 영역을 가리킴으로써 함수도 저장할 수 있다.

### 느낀 점 & 배운 점

이번 내용은 솔직히 나한텐
상식같은 내용을 복습하는 느낌이었어.
별게 없달까?

그냥 포인터에 대한 상식같은 내용들을 줄줄 읊은 느낌?

1. 포인터 타입 : 해당 포인터가 가리키고 있는 대상의 타입
    - 어셈블리 상에서는 별 다른 표현으로 나타나진 않지만,
    컴파일러 영역에서는 프로그래머의 실수를 막아줌
    - 역참조 시, 해당 포인터의 데이터 타입으로 해당 포인터가 가리키고 있는 객체가 반환됨
2. 포인터의 값 : 해당 포인터가 가리키는 객체의 주소
    - `NULL`도 가능하며, 해당 포인터가 가리키는 객체가 없다는 뜻
3. 포인터와 `&` 연산자 : `&` 연산자로 해당 l-value의 주소를 획득
4. 포인터의 역참조 : `*`연산자로 가능, 어셈블리에서는 메모리 참조로 구현 가능
5. 포인터와 배열 : 특히 포인터 연산과 배열 참조가 비슷함(`p + index * L`)
6. 포인터와 캐스팅 : 포인터가 다른 포인터 타입으로 캐스팅되어도 주소값은 변하지 않음.
    - 하지만 `L`은 변할 수 있음, 역참조 시에도 캐스팅된 객체로 인식됨.
7. 포인터와 함수 : 함수도 포인터로 가리킬 수 있음. 코드 영역 참조.

그냥 너무 당연한 것들을 줄줄 읊은 느낌이야..

## 2. Out-of-Bounds Memory References and Buffer Overflow - 범위를 벗어난 메모리 참조와 버퍼 오버플로우

### 정리

1. 배열의 범위를 벗어난 메모리 참조와 버퍼 오버플로우
    - C언어는 배열 참조에 대한 범위 검사를 수행하지 않고,
    지역 변수는 프로시저 파트에서 설명했듯 스택에 저장된다.
    - 이 때문에, 배열 범위 밖의 요소에 대해
    배열에 대한 조작으로 쓰기를 해버린다면,
    스택에 저장된 상태가 손상되는 오류가 발생할 수 있다.
    - 이걸 버퍼 오버플로우(Buffer Overflow)라고 한다.
    - 특히, 버퍼 오버플로우로 인해 스택의 반환 주소가 덮어씌워지면,
    해당 함수가 반환되었을 때
    이상한 곳으로 점프하는 심각한 문제가 발생할 수 있다.
    - 버퍼 오버플로우는 프로그램이 본래 실행하지 않을 코드를
    강제로 실행하게 만들 수 있기 때문에 위험하다.

### 느낀 점 & 배운 점

솔직히 이번 파트는 좀 길어서 겁먹었는데,
실상은 그냥 세 줄 요약이 돼.

1. C언어의 배열은 범위 검사를 하지 않기 때문에 실수로 배열 범위 밖의 요소에 대해 접근하는
버퍼 오버플로우가 발생할 수 있다.
2. 버퍼 오버플로우가 발생하면 저장되어있는 상태들이 손상되는 문제가 발생한다.
대표적으로 반환 주소가 덮어씌워지면 함수 종료 시 이상한 곳으로 점프하는 문제가 발생할 수 있다.
3. 이런 버퍼 오버플로우는 본래 실행하지 않을 코드를 강제로 실행하게 만들 수 있기 때문에
버퍼 오버플로우를 이용한 공격이 들어올 수 있다.

이 정도로 끝..

## 3. Thwarting Buffer Overflow Attacks - 버퍼 오버플로우 공격 방어하기

### 정리

1. 스택의 주소를 예측 불가능하게 하기
    - 버퍼 오버플로우 공격을 하기 위해서는
    공격자가 임의로 실행할 코드를 넣을 메모리 주소로 점프해버릴 수 있도록
    스택의 주소를 알아야한다.
    - 하지만, 스택의 주소를 무작위로 설정해서 스택의 주소를 예측 불가능하게 하면
    점프할 주소를 알 수 없다.
    - 프로그램 시작 시 0 ~ n바이트 사이의 무작위 바이트 수의 공간을
    스택에 할당함으로써 구현된다.
      - 이 공간은 프로그램에서 사용되지는 않지만,
      실질직인 스택의 위치가 프로그램 실행마다 달라지게 된다.
      - n은 충분히 변동성을 줄 정도로 커야하지만,
      너무 많은 메모리 공간을 낭비하지 않도록 작아야한다.
    - 물론 이 방법은 브루트포스로 돌파될 수 있기에,
    이 방법 만으로는 부족하다.
    
2. 스택이 오염되는 것을 감지하는 Canary Value 넣기
    - 배열같이 버퍼 오버플로우가 발생할 수 있는 경우에
    뒤에 특별한 값을 두고,
    함수가 끝날 때 그 값이 바뀌었는지를 검사해서
    바뀌었으면 스택이 오염됐다는 것을 판단해서 즉시 프로그램을 중단한다.
    
3. 실행가능한 코드 영역을 제한하기
    - 스택 영역 자체를 실행 불가능한 영역으로 둬서
    공격자가 스택 영역에 코드를 밀어넣어도 실행할 수 없게 하는 것이다.
      - 오직 읽기 / 쓰기만 가능하고 실행은 불가능하게 하는 것이다.

## 4. Supporting Variable-Size Stack Frames - 가변 크기 스택 프레임 지원하기

### 정리

1. 프로시저가 호출되었을 때 일반적으로 스택 프레임의 크기는 고정되지만,
스택 프레임의 크기가 가변적이어야 하는 경우도 있다.
   - 스택에 임의의 바이트 수만큼 저장 공간을 할당하는 함수(`alloca()`) 사용
     - 애초에 스택에 추가적으로 저장 공간을 할당받으므로..
   - 가변 크기의 지역 배열(스택에 들어감)을 선언
     - 가변 크기의 배열은 런타임에 크기가 결정
   - 등등의 요인으로 스택 프레임의 크기가 가변적이어야 하는 경우도 있다.
   
2. 프레임 포인터와 가변 크기 스택 프레임
    - 스택 프레임의 크기가 가변적이라면 
    스택 포인터(`%rsp`)의 위치도 가변적으로 변한다.
    - 하지만 이렇게 될 경우, 
    스택 포인터를 기준으로 스택의 데이터들에 고정된 오프셋으로 접근하기 어려워진다.
      - 스택 포인터가 움직일 때 마다 오프셋이 달라지는데,
      어셈블리 코드는 실행 도중에 수정될 수 없다..
    - 그렇기 때문에 베이스 포인터(`%rbp`)를 프레임 포인터로써 사용한다.
      - `%rbp`는 스택의 최하단을 가리키고,
      변하지 않는다.
        - `%rsp`는 스택의 최상단을 가리키고 계속 변하기 때문에 `%rbp`는 변하지 않아도 된다.
      - 고정된 `%rbp`를 기준으로, 스택의 각 데이터에 접근한다.
    - `%rbp`는 피호출자 보존 레지스터(callee-saved registers)이기 때문에
    가변 길이 스택 프레임이 필요할 때 따로 스택 프레임에 보존해놔야 한다.
    - 스택의 끝 : `%rsp`
    - 절대 움직이지 않는 기준점 : `%rbp`
    - 물론 고정 크기 스택 프레임인 경우,
    `%rsp`가 움직이지 않으므로
    `%rbp`가 생략될 수 있다.

### 느낀 점 & 배운 점

이번 챕터는 뭔가 CS:APP 책에서 설명 들을 때는 이해가 안됐는데,

- `%rsp` : 그저 스택 최상단을 나타내는 포인터
  - 해당 프로시저 실행 도중에 변경될 수 있음
  - 특히 가변 크기 스택 프레임이 필요한 경우 그 값을 예측할 수 없기 때문에
  해당 포인터를 기준으로 특정 오프셋으로 접근하기 힘듬.
- `%rbp` : 스택 프레임의 기준이 되어주는 포인터
  - 해당 프로시저 실행 도중에 변경되지 않음
  - 특히 가변 크기 스택 프레임이 필요한 경우에 값이 바뀌지 않으므로
  `%rsp` 대신 해당 포인터를 기준으로 특정 오프셋으로 접근하면 됨.
  
이렇게 `%rbp`를 `%rsp` 대신 기준점이 되어주는 포인터라고 이해하니까
그나마 이해 잘 되더라고..

어렵다ㅋㅋ

결국 가변 크기 스택 프레임에서는 `%rsp`를 얼마나 움직여야할지 예측이 안 되기 때문에,
그 대신 스택에 데이터에 접근할 때의 기준점이 되어줄 수 있는 `%rbp`를 사용하는 것 같았어.

그리고 `%rbp`를 callee-saved register로 다뤄서
상위 프로시저가 `%rbp`를 쓰고 있을 때 그 값이 그대로 유지되도록 한 것도 아이디어 좋더라.

## 5. 요약

1. 포인터는 요약 안함(요약하기에는 너무 길어..)
2. C언어는 배열의 범위 검사를 하지 않기 때문에,
배열의 범위 밖에까지 접근을 해버리는 버퍼 오버플로우가 가능하고,
버퍼 오버플로우로 반환 주소에 접근하여 이상한 곳으로 점프를 시켜버릴 수도 있기 때문에
버퍼 오버플로우 공격은 위험하다.
3. 버퍼 오버플로우 공격을 막기 위해
스택의 주소를 예측하지 못하게 실행마다 무작위로 설정할 수도 있고,
스택이 덮어씌워졌는지 검사를 할 수도 있고,
애초에 스택 영역의 코드가 실행되지 않게 할 수도 있다.
4. 가변 크기 스택 프레임에서는 `%rsp`가 고정된 크기만큼 움직이지 않고
가변적인 크기만큼 움직이기 때문에 스택의 각 데이터에 접근하는 기준점이 되기 힘들다.
그렇기 때문에 따로 `%rbp`를 기준점으로 삼아 스택의 각 데이터에 접근한다.
