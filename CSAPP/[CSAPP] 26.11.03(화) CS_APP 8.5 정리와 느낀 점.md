## 1. Signal Terminology - 시그널 용어

### 정리

1. 시그널이 대상 프로세스로 전달되는 과정
    - 시그널 전송(Sending) : 커널이 시그널 전송 대상 프로세스의 컨텍스트 내 
    특정 상태를 업데이트함으로써 시그널을 전송한다.
      - 시그널은 커널이 따로 시스템 이벤트를 감지한 경우와
      프로세스가 커널에게 전송 대상 프로세스로 시그널을 보내는 것을 요청한 경우에 전송된다.
    - 시그널 수신(Receiving) : 대상 프로세스는 
    커널에 의해 시그널에 대해 반응하도록 강제될 때 시그널을 수신하게 된다.
      - 프로세스는 시그널을 무시(OS의 동작)하거나, 
      종료(해당 시그널을 처리하는 OS의 동작을 실행)하거나, 
      시그널 핸들러라고 하는 유저 레벨 함수를 실행해서 시그널을 포착하고 따로 처리할 수 있다.
      (시그널 핸들러는 유저 레벨 함수로,
      해당 프로세스가 특정 시그널을 수신했을 때
      프로그래머가 어떤 처리를 따로 할지 정해놓은 핸들러이다.)
      
2. 전송과 대기
    - 전송되었으나 아직 대상 프로세스가 수신하지 않은 시그널을
    대기(Pending) 중인 시그널이라고 한다.
      - 특정 시점을 기준으로 각 시그널 타입에 대한 대기 중인 시그널은
      하나씩만 존재할 수 있다.
      (같은 시그널 타입의 신호가 또 들어와도 그 시그널은 버려진다.)
      (물론 대기중인 시그널에 한정해서이다.)
    - 프로세스는 특정 타입의 시그널을 차단할 수 있다.
      - 차단 중인 시그널은 대기 중인 신호로써 쌓인다.
      - 프로세스가 차단을 해제할 때 까지 해당 타입의 시그널은 수신되지 않는다.
    - 대기 중인 시그널은 최대 한 번만 수신된다.
    - 각 프로세스에 대해 커널은
    대기 중인 시그널의 집합과
    차단된 시그널의 집합을
    대기(Pending) 비트 벡터 / 차단(Blocked) 비트 벡터에 관리한다.
      - 타입 k의 시그널이 전달될 때마다 대기 비트 벡터의 k번째 비트를 설정하고,
      타입 k의 비트가 수신될 때 마다 대기 비트 벡터의 해당 비트를 지운다.

### 느낀 점 & 배운 점

이번 파트는 말 그대로 시그널의 기본 개념을 배운 것 같아.

일단 시그널의 전송 / 대기 / 수신의 분류부터 보자면,

- 전송 : 말 그대로 시그널을 전송.
  - 커널이 전송 대상 프로세스의 컨텍스트를 바꿈으로써 전송한다.
- 대기 : 전송된 시그널이 수신되지는 않은 상태.
  - 대기 비트 벡터가 따로 관리하고,
  제대로 수신된 경우 해당 비트를 지운다.
    - 중복된 타입의 시그널이 대기 상태가 되는 경우
    나중에 대기 상태가 된 시그널은 버려진다.
  - 일부 시그널을 차단할 수도 있다.
  해당 정보는 차단 비트 벡터가 관리한다.
  - 차단된 시그널의 경우 계속 대기 상태로 보관되다가
  차단이 해제되면 수신된다.
- 수신 : 말 그대로 시그널을 수신.
  - 커널이 시그널을 수신하라고 강제하는 시점에 수신된다.
  
여기서 핵심은,
시그널을 전송했다고 바로 수신된다는 보장이 없다는 점이야.

그래서 따로 대기 상태 / 대기 비트 벡터가 필요한거겠지.
(수신한 신호를 바로바로 확인하는 구조가 아니니..)

이 이야기도 더 해보자.
수신한 신호를 바로바로 확인하는 구조가 아니지.

그래서 프로세스는
시그널이 전송됐을 시, 즉 대기 비트 벡터의 해당 타입을 표시하는 비트가 1이 되었을 시

- 시그널을 무시하거나(OS 동작)
- 종료하거나(OS 동작)
- 시그널 핸들러로 시그널을 포착해서 따로 처리하거나(유저 정의 동작)

이렇게 행동할 수 있는거지.
(`Pending & ~Blocked`로 대기 비트 벡터에 대기 중인 시그널이 있는지 판별,
추가로 무시해도 되는 시그널은 무시.)

정말 간단히 요약해볼게.

> 시그널의 전송은 
> 커널이 전송 대상 프로세스의 대기 비트 벡터의 특정 비트를 바꾸는 것으로 발생한다.

> 시그널은 대상 프로세스가 수신하기 전에는 대기 비트 벡터에 표기된다.

> 시그널은 커널이 대상 프로세스에게 시그널 수신을 강제하는 시점에 수신된다.
> 특정 타입의 시그널을 차단할 수도 있는데, 차단한 시그널은 차단 비트 벡터에 표기된다.

> 시그널의 처리는
> OS 레벨에서의 무시 / 종료와
> 유저 레벨에서의 시그널 핸들러를 이용해서 처리될 수 있다.

1. 시그널을 보내는 프로세스가 커널의 시스템 콜을 호출 / 다른 원인으로 시그널 전송 요청을 보냄
2. 시스템 콜 등을 받은 커널이 대상 프로세스의 컨텍스트(비트 벡터)를 변경
3. 변경한 컨텍스트를 커널이 강제로 확인하도록 하는 시점에 시그널 확인
4. 커널이 시그널 무시나 종료 처리를 하거나, 유저의 시그널 핸들러를 통해 처리

빈 자리는 좀 이따 보자.
(정확히 언제 시그널을 수신하는지 같은거..)

## 2. Sending Signals - 시그널 전송

### 정리

1. 프로세스 그룹
    - 기본적으로, 유닉스 시스템은 프로세스에 시그널을 전송하기 위한 여러가지 매커니즘을 제공하고,
    그 매커니즘의 기반이 프로세스 그룹이다.
    - 프로세스 그룹이란, 말 그대로 여러 프로세스를 묶어놓은 집합으로써,
    양의 정수인 프로세스 그룹 ID(PGID)로 식별된다.
      - 모든 프로세스는 정확히 하나의 프로세스 그룹에 속한다.
      - 기본적으로 자식 프로세스는 부모 프로세스와 동일한 프로세스 그룹에 속한다.
    - 프로세스 그룹의 존재 의의는,
    여러 프로세스를 하나의 단위로 묶어서 한꺼번에 제어하기 위함이다.
    (프로세스 그룹을 타겟 삼아서 시그널을 전송할 수 있다.)
    
2. 시그널 전송의 사례 1 - `/bin/kill`
    - `/bin/kill` 프로그램은 다른 프로세스에 임의의 시그널을 보내는 프로그램이다.
    - 예를 들어,
    `/bin/kill -9 12345`는 9번 시그널(`SIGKILL`)을 `12345`번 프로세스에 보낸다.
    - 음수를 붙이면,
    `/bik/kill -9 -12345`는 9번 시그널(`SIGKILL`)을 `12345`번 프로세스 그룹에 보낸다.

3. 시그널 전송의 사례 2 - 키보드 입력
    - 유닉스 셸은 프로세스 여러 개를 합칠 수 있는 개념인 작업(job)이라는 추상화 개념을 사용한다.
    (명확한 정의는 단일 명령줄을 평가한 결과로 생성되는 프로세스를 나타내기 위한 개념이다.)
      - 예를 들어,
      `ls | sort`를 입력하면 `ls` / `sort` 두 개의 프로세스로 구성된 포그라운드 작업이 실행된다.
      (하나는 `ls` 프로그램을 실행하고, 하나는 `sort` 프로그램을 실행한다.)
      - 셸은 작업마다 별도의 프로세스 그룹을 생성한다.
    - 키보드에서 `Ctrl + C`를 누르면 커널은 포그라운드 프로세스 그룹에 속한 모든 프로세스에
    `SIGINT` 시그널을 보내서 포그라운드 작업을 종료시킨다.
    - 키보드에서 `Ctrl + Z`를 누르면 커널은 포그라운다 프로세스 그룹에 속한 모든 프로세스에
    `SIGTSTP` 시그널을 보내서 포그라운드 작업을 일시중지시킨다.

4. 시그널 전송의 사례 3 - `kill` 함수
    - `kill` 함수를 호출하면 프로세스는 다른 프로세스에 임의의 시그널을 보낸다.
    `kill(pid, SIGKILL)`이라면 `pid`의 프로세스의 `SIGKILL` 시그널을 보내게 된다.
    
5. 시그널 전송의 사례 4 - `alarm` 함수
    - `alarm` 함수를 호출해서 자신에게 `SIGALRM` 시그널을 보낼 수 있다.
    - `alarm` 함수는 커널이 지정한 시간 후에
    호출한 프로세스에 `SIGALRM` 신호를 보내도록 예약한다.

### 느낀 점 & 배운 점

이번 챕터는 신호 전송이 실제로 어떻게 되는지에 대한 내용이었던 것 같아.

일단 프로세스 그룹으로 밑밥을 깔고,

- `/bin/kill`로 터미널에서 시그널을 보내는 방법을,
- 키보드 입력(`Ctrl + C` / `Ctrl + Z`)으로 작업(job)에 시그널이 보내지는 것을,
- `kill()`로 코드에서 타 프로세스에 시그널을 보내는 방법을,
- `alarm()`으로 코드에서 자신에게 시그널을 보내는 방법을

설명하는 것 같았어.

솔직히 별 감흥은 없는데,
그냥 
'이런 방식들로 타 프로세스 / 자신 프로세스에 시그널을 보낼 수 있어요~'
하는 느낌이었어.

그리고 충격이었던게
`/bin/kill` / `kill()`이 무조건 `SIGKILL`만 보내는게 아니라는거ㅋㅋ

## 3. Receving Signals - 시그널 수신

### 정리

1. 시그널 수신
    - 일반적으로 커널이 해당 프로세스를 커널 모드에서 유저 모드로 전환할 때
    커널은 해당 프로세스에 대해 차단되지 않은 대기 중인 시그널 집합을 확인해서,
    집합이 비어있지 않은 경우 해당 프로세스가 해당 시그널을 수신하도록 강제하게 된다.
      - 집합이 비어있는 경우 다음 명령어를 이어서 실행한다.
    - 시그널 수신은 프로세스에 의해 특정 동작을 유발하게 된다.
      - 특정 동작을 수행한 후, 제어 흐름은 해당 프로세스의 다음 명령어로 넘어간다.

2. 시그널 수신 시 동작
    - 각 시그널 유형에는 미리 정의된 기본 동작이 있다.
      - 프로세스 종료하기
      - 프로세스 종료하고 코어 덤프 생성하기
      - 프로세스가 `SIGCONT` 시그널에 의해 재개될 때 까지 일시 중지하기
      - 시그널 무시하기
    - 프로세스는 `signal` 함수를 사용해 시그널과 관련된 동작을 수정할 수 있다.
      - `sighandler_t signal(int signum, sighandler_t handler)`
      - 예외적으로는 `SIGSTOP` / `SIGKILL`의 기본 동작을 변경할 수 없다.
      - `signal` 함수는 세 가지 방법 중 하나로 `signam` 시그널에 대한 기본 동작을 변경할 수 있다.
        - `handler`가 `SIG_IGN`인 경우 해당 타입의 시그널 무시
        - `handler`가 `SIG_DFL`인 경우 해당 타입의 시그널에 대한 동작을 기본 동작으로 초기화
        - `handler`가 그 외인 경우는 `handler`를 그대로 시그널 핸들러로 놓음.(핸들러 설치)
        (사용자 정의 시그널 핸들러가 이거)
          - 해당 사용자 정의 시그널 핸들러를 호출하는 것을 시그널 포착,
          해당 사용자 정의 핸들러의 실행을 시그널 처리라고 한다.
          - 프로세스가 특정 타입의 시그널을 포착하면,
          해당 시그널에 대해 설치된 핸들러가 해당 타입의 단일 정수 인자와 함께 호출된다.
          (`signal_handler(int k)`, `k`는 시그널 타입)
          이렇게 하면 동일한 시그널 함수로 서로 다른 타입의 시그널을 포착할 수 있게 된다.
          - 핸들러가 `return` 문을 실행하면,
          제어 흐름은 일반적으로 프로세스의 순차적 제어 흐름이 중단되었던 명령어로 다시 넘어간다.
          - 시그널 핸들러는 다른 핸들러에 의해
          제어 흐름을 빼앗길 수도 있다.

### 느낀 점 & 배운 점

이번 챕터는 솔직히 쉬우면서 어려웠달까?

일단 이번 챕터는 세 가지 파트로 나눌 수 있어.

1. 시그널 수신을 하는 시점
    - 프로세스가 커널 모드에서 사용자 모드로 전환될 때 커널이 시그널 수신(대기 비트 벡터 확인)을 강제
2. 시그널 수신 시의 동작
    - 기본 동작 : 종료 / 종료 및 덤프 남기기 / 일시 중지 / 무시
    - 사용자 정의 동작 : 시그널 핸들러
3. `signal()`
    - 해당 함수로 사용자 정의 동작, 시그널 핸들러를
    특정 시그널 수신 시의 동작으로 설정 가능
    - 사용자 정의 시그널 핸들러가 반환되면 일반적으로 원래 명령어를 계속 이어서 실행
    
이 정도.

솔직히 별게 없지?

그냥

1. 시그널은 일반적으로 커널 모드에서 사용자 모드로 전환될 때 커널이 수신을 강제함으로써 프로세스에 수신된다.
2. 시그널 수신 시의 동작은 아무런 세팅을 하지 않으면 종료 / 종료 및 덤프 / 일시 중지 / 무시의
기본 동작을 실행하고,
`signal()` 함수로 사용자 정의 시그널 핸들러를 인스톨 할 수 있다.

이게 끝이야.

## 4. Blocking and Unblocking Signals - 시그널 차단과 차단해제

### 정리

1. 차단 매커니즘
    - 암시적 차단 매커니즘 : 기본적으로, 
    커널은 핸들러가 현재 처리 중인 타입의 모든 대기 시그널을 차단한다.
    - 명시적 차단 매커니즘 : `sigprocmask` 함수와 보조 함수를 사용해서
    선택한 시그널을 차단하거나 차단 해제할 수 있다.
      - `sigprocmask`의 사용 방법
      `int sigprocmask(int how, const sigset_t *set, sigset_t *oldset)`
      `int sigemptyset(sigset_t *set)`
      `int sigfillset(sigset_t *set)`
      `int sigaddset(sigset_t *set, int signum)`
      `int sigdelset(sigset_t *set, int signum)`
        - 기본적으로 `sigprocmask` 함수는 차단 비트 백터를 변경한다.
        - 구체적인 동작은 `how`의 값에 따라 달라진다.
          - `SIG_BLOCK` : `blocked = blocked | set`(추가)
          - `SIG_UNBLOCK` : `blocked = blocked & ~set`(삭제)
          - `SIG_SETMASK` : `blocked = set`(새 집합으로 대체)
        - `oldset`이 `NULL`이 아닌 경우 `blocked`의 이전 값이 `oldset`에 저장된다.
        - `set`에 대한 조작은
          - `sigemptyset` : `set`을 빈 집합으로 초기화
          - `sigfillset` : 모든 비트를 1로 설정
          - `sigaddset` : `signum`의 시그널 번호를 추가
          - `sigdelset` : `signum`의 시그널 번호를 제거
          - 이렇게 할 수 있다.

### 느낀 점 & 배운 점

이번에는 시그널에 대한 차단 / 차단 해제를 어떻게 할 수 있는지에 대해 배운 것 같아.

일단 현재 처리하고 있는 시그널은 임시적으로 차단하는게 기본이고,
`sigprocmask()` 함수로 차단(blocked) 비트 벡터에 값을 쓸 수 있고..

그리고 차단 비트 벡터의 쓸 값을 `set` 필드로 받고,
다양한 함수들로 `set`에 대한 변경을 수행하고..

이게 끝이야.

눈여겨볼만 한 부분은
암시적으로 현재 처리하고 있는 시그널은 자동으로 차단된다는거?

아마 같은 시그널을 처리하고 있는데 또 중복으로 처리하게 되면
너무 많이 재귀될 수 있어서 그런가봐..

## 5. Writing Signal Handlers - 시그널 핸들러 작성하기

### 정리

1. 시그널 핸들러 작성의 특성
    - 사용자 정의이기 때문에 메인 프로그램과 동시에 실행되며 동일한 전역 변수를 공유해서
    메인 프로그램이나 다른 핸들러와 상호 간섭을 일으킬 수 있다.
      - 핸들러와 메인 프로그램이 동일한 전역 자료 구조에 접근한다면
      레이스 컨디션 / 데드락이 발생할 수 있다.
    - 시그널을 수신하는 방식과 시기에 대한 규칙은 직관적이지 않다.
      - 예를 들어, 시그널은 쌓이지 않기 때문에
      여러번 시그널을 받는 것을 예상해도 한번만 받는 경우가 생길 수 있다.
    - 시스템에 따라 시그널 처리(핸들링)의 시멘틱이 다를 수 있다.
      - 시스템에 따라 시그널 API의 세부 시멘틱이 다를 수 있다.
      - `signal()` 함수는 시스템에 따라 시멘틱이 다르기에,
      `sigaction()` 함수를 사용하는 것이 바람직하다.
      
2. 시그널 핸들러 작성하는 법 1 - 최대한 단순하게 만들어라.
    - 시그널 핸들러의 특성으로 생기는 문제를 예방하기 가장 좋은 방법은
    시그널 핸들러 자체를 작고 단순하게 만드는 것이다.
      - 예를 들어, 단순히 전역 플래그만 설정하고 즉시 반환한다거나..

3. 시그널 핸들러 작성하는 법 2 - 비동기 시그널 안전한 함수만 호출해라.
    - 비동기 시그널 안전하다는 것은,
    해당 함수를 호출하고 있을 때 시그널을 수신해서
    또 다시 해당 함수가 호출되어도 안전한 함수이다.
      - `write()` / `_exit()` 등이 있다.
      - `printf()` / `exit()`는 비동기 시그널에 불안전하다.
    - 비동기 시그널 안전한 함수는
      - 재진입 가능 : 전역 변수나 락을 쓰지 않고 오직 자신의 지역 변수만 사용해서
      언제 덮어써도 안전함
      - 원자적 시스템 콜 : 락을 잡지 않고 커널 내부에서 원자적으로 처리되는 저레벨 시스템 콜
    - 이런 특성을 가지기 때문에 해당 함수를 실행 도중 시그널이 날아와도 안전하다.
    
3. 시그널 핸들러 작성하는 법 3 - `errno`를 저장 / 복원해라.
    - `errno`란 가장 마지막으로 발생한 에러를 저장하는 전역 변수이다.
    - 그래서 메인 프로그램에서 `errno`가 변경된 후 확인하기 전에
    시그널 핸들러가 호출되어서 `errno`가 변경된 경우에는
    메인 프로그램의 `errno`가 묻혀버리고
    메인 프로그램에서 `errno`를 확인할 때 메인 프로그램에서 발생한 에러가 아닌
    시그널 핸들러에서 발생한 `errno`를 확인하게 된다.
      - 그래서 메인 프로그램의 `errno`를 미리 저장해놓고,
      핸들러가 반환되기 전에 복원해놓아야 한다.
      
4. 시그널 핸들러 작성하는 법 4 - 공유 데이터에 접근할 때는 모든 시그널을 차단해라.
    - 핸들러가 메인 프로그램이나 다른 핸들러와 데이터를 공유하는 경우,
    해당 데이터에 대해 접근하는 동안
    핸들러와 메인 프로그램은 일시적으로 모든 시그널을 차단해야한다.
    - 왜 그렇냐면,
    메인 프로그램에서 해당 공유 데이터에 접근할 때(뮤텍스 잡고있어도)
    시그널이 수신되어
    해당 공유 데이터를 건드리는 상황이 나오면
    뮤텍스를 중복으로 잡는 등의
    동시성 문제(레이스 컨디션 / 데드락 등)가 발생할 수 있다.
      - 해당 공유 데이터에 접근할 때 잠시 모든 시그널을 차단하면
      해당 공유 자원에 접근하는 시그널 핸들러의 코드가 실행되지 않는다.

5. 시그널 핸들러 작성하는 법 5 - 전역 변수는 `volatile` 키워드를 붙여 선언해라.
    - `volatile` 키워드는 컴파일러의 최적화를 막는 키워드이다.
    - 메인 프로그램은 그저 읽기만 하고,
    시그널 핸들러는 쓰는 변수는
    메인 프로그램에서 해당 변수의 값이 절대 변하지 않는다고 컴파일러가 착각해서
    해당 변수에 대한 참조를 처리하기 위해
    레지스터에 캐시된 해당 변수의 복사본을 사용해버리는 참사가 날 수 있다.
    (이러면 핸들러에 의해 업데이트된 값을 확인할 수 없다.)
    - `volatile` 키워드를 씀으로써 컴파일러의 최적화를 막아
    해당 변수를 무조건 메모리에서 받아오도록 해서
    시그널 핸들러가 업데이트한 값을 확인할 수 있게 한다.

6. 시그널 핸들러 작성하는 법 6 - 플래그는 `sig_atomic_t`같은 원자형으로 선언해라.
    - 핸들러가 전역 플래그에 값을 기록하는 식으로
    시그널 수신을 기록하는 경우가 있다.
    - 그런 경우에, 플래그를 원자형으로 선언하면
    읽기 / 쓰기가 원자적(중간 상태 관측 불가능)이라서
    시그널을 일시적으로 차단하지 않고도 공유 데이터를 안전하게 읽고 쓸 수 있다.
    (물론 이건 시그널 핸들러가 변경해야할 공유 데이터가 해당 플래그 뿐일 경우에만 해당한다.)

### 느낀 점 & 배운 점

일단,
시그널 핸들러가 왜 작성하기 어려운지를 보자.

1. 사용자 정의이고 비동기적이기 때문에 메인 프로그램과 공유하는 데이터를 건드리면 문제가 발생할 수 있다.
    - 밑의 시그널 핸들러 안전하게 작성하는 법 파트 참조
2. 시그널은 쌓이지 않기 때문에 여러 번 시그널을 받아도 한 번만 수신하는 경우가 생길 수 있다.
    - 이 점을 생각하며 프로그래밍
3. 시그널 API의 시맨틱이 시스템마다 다를 수 있다.
    - `sigaction()` 함수같은 함수 사용

이렇게 되겠지..

시그널 핸들러 안전하게 작성하는 법 파트도 보자.

솔직히 여기서 말하는건 딱 이렇게야.

1. 일단 최대한 간결하게 짜라.
2. 함수를 호출할 때는 어느 시점에나 추가로 호출해도 되는 비동기 시그널 안전한 함수만 호출해라.
3. 시그널 핸들러의 동작으로 덮어씌워질 수 있는 `errno`를 미리 백업하고 복구해라.
4. 공유 데이터에 접근할 때는 시그널 핸들러가 호출될 수 없도록 미리 시그널을 차단해라.
5. 전역 변수는 메인 프로그램만 보고 컴파일러가 최적화할 수 없도록 `volatile` 키워드를 붙여라.
6. 플래그를 원자형으로 선언해서 중간에 시그널 핸들러가 변경해도 레이스 컨디션이 발생하지 않도록 해라.

결국 요약하면,

> 시그널 핸들러는 언제나 예외적 제어 흐름을 타고 호출될 수 있기 때문에,
> 언제나 호출되도 괜찮도록 시그널 핸들러를 만들거나(2, 3, 5, 6)
> 특정 시점에는 호출될 수 없게 막아야 한다.(4)

라고 할 수 있어.

이 파트 진짜 길더라..

## 6. Synchronizing Flows to Avoid Nasty Concurrency Bugs - 까다로운 동시성 버그를 피하기 위한 흐름 동기화

### 정리

1. 필요 없지 않을까?

### 느낀 점 & 배운 점

이 챕터에서는 고전적인 `fork()` / `SIGCHLD`에 의한 레이스 컨디션을 보여줘.

```cpp
/* 부모 프로세스의 루프 */
while (1) {
    if ((pid = fork()) == 0) { /* 자식 프로세스 */
        execve(...);
    }
    
    /* [위험 구간] 자식은 생성되었는데, 아직 addjob(pid)을 안 부름! */
    
    addjob(pid); /* 부모가 작업 목록에 자식 PID 추가 */
}

/* SIGCHLD 핸들러 */
void handler(int sig) {
    pid_t pid = waitpid(-1, NULL, 0);
    deletejob(pid); /* 작업 목록에서 자식 PID 제거 */
}
```

이 코드에서는 

1. `fork()` 하고,
2. 자식 프로세스를 작업 목록에 추가하고
3. 자식 프로세스가 종료되면(`SIGCHLD` 시그널을 수신하면) 작업 목록에서 자식 프로세스를 제거하는

동작을 해.

그냥 봤을 때는 문제가 없어보이지만,

1. `fork()`를 수행하고
2. 컨텍스트 스위칭으로 부모 프로세스가 실행되기 전에, 
`addjob()`을 호출하기 전에 자식 프로세스가 종료되어 `SIGCHLD` 시그널을 보내면
3. `addjob()`이 호출이 안 되었는데 `deletejob()`이 호출되는 레이스 컨디션이 발생

이렇게 되버려.
(물론 이게 동시성 버그다보니까 `addjob()`이 먼저 수행되면 문제가 없긴 함..)

결국 이런 레이스 컨디션을 막으려면,
`fork()` 전에 임시로 `SIGCHLD` 시그널을 수신하는걸 막고,
`addjob()` 까지 끝난 후에 `SAIGCHLD` 시그널을 수신할 수 있도록 하면 돼.

## 7. Explicitly Waiting for Signals - 명시적으로 시그널 기다리기

### 정리

1. 명시적으로 시그널 기다리기
    - 프로그램의 실행 중에, 명시적으로 시그널을 기다려야할 때가 있다.
    - 스핀락 / sleep을 통한 방법도 있지만,
    스핀락을 계속 CPU를 점유하게 되고,
    sleep은 대기 시간이 너무 길어지게 된다.
      - 그리고 차단 해제 + `pause()` 조합은
      조건 확인(자식 프로세스 종료 확인)과 
      `pause()` 사이에 틈이 있어서 레이스가 발생할 수 있다.
      (CV의 lost wakeup 느낌)
    - 그래서 일반적으로 특정 시그널을 명시적으로 기다릴 때는
    `sigsuspend` 함수를 사용한다.
      - `int sigsuspend(constg sigset_t* mask)`
      - `sigsuspend` 함수는 현재 차단된 세트를 `mask`로 일시적으로 대체하고
      핸들러를 실행하거나 프로세스를 종료하는 동작을 수행하는 시그널을 수신할 때 까지
      프로세스를 일시 중지한다.
        - 종료하게 되는 경우, 프로세스는 `sigsuspend`에서 반환되지 않고 종료된다.
        - 핸들러 실행인 경우, `sigsuspend`는 핸들러가 반환된 후 반환되고,
        차단된 세트를 원래대로 복원한다.
      - `sigsuspend()` 함수는 `mask` 세팅과 프로세스 sleep을
      하나의 비가공 동작으로 동시에 실행한다.

### 느낀 점 & 배운 점

이번에도 뭔가 API 설명같은 느낌이네..

스핀락 / 단순 sleep은 CPU를 낭비하거나 시간이 오래 걸리기 때문에,
그리고 거기에다 `pause()` 조합은 CV의 lost wakeup같은 레이스를 유발할 수 있기 때문에
명시적으로 시그널을 기다릴 때는 
시그널이 올 때까지 대기하고
차단 마스크 세팅 + 스레드 재우기가 원자적인 `sigsuspend()` 함수를 사용한다는거지.

그냥 `sigsuspend()` 함수에 대한 설명이 끝이야.
명시적으로 `mask`에 넣은대로 임시로 차단할 시그널을 설정하고
종료 / 핸들러에 대한 시그널이 올 때 까지 기다리는게 끝..

근데 이거 CV랑 상당히 닮았음..

```cpp
// sigsuspend()
sigset_t block_mask, prev_mask;
sigemptyset(&block_mask);
sigaddset(&block_mask, SIGUSR1);

sigprocmask(SIG_BLOCK, &block_mask, &prev_mask);
while (!flag) {
    sigsuspend(&prev_mask); // 여기서 단순 pause() 하면 안됨
}

sigprocmask(SIG_SETMASK, &prev_mask, NULL);
```

```cpp
// CV
std::mutex mtx;
std::condition_variable cv;

std::unique_lock<std::mutex> lock(mtx);
while (!ready) {
    cv.wait(lock); // 여기서 락 없이 wait() 하면 안됨
}

lock.unlock();
```

| 구분 | C++ `condition_variable` | `sigsuspend()` |
|---|---|---|
| 조건 | `while(!ready)` 등 | `while(!flag)` 등 |
| 알림 수단 | `cv.notify_one()` / `notify_all()` | 비동기 시그널 |
| 임계 구역 보호 | `unique_lock` | `sigprocmask()` |
| 위험한 취약 패턴 | 락 없이 `while (!ready)` 검사 후 `wait()` 호출 | 차단 해제 후 `while (!flag)` 검사 후 단순 `pause()` 호출 |
| 버그의 본질 | 조건 검사 시점과 `wait()` 진입 시점 사이의 `notify`를 놓치고 영원히 `wait()` | 조건 검사 시점과 `pause()` 시점 사이의 시그널을 놓치고 영원히 `pause()`|
| 해결책 | `cv.wait(lock)` (락 해제 + 대기 상태 진입을 원자적으로 처리)| `sigsuspend(&prev_mask)` (시그널 차단 해제 + 대기 상태 진입을 원자적으로 처리) |

이렇게말이야.

결국 

- 특정 신호(`notify` / 시그널)를 기다림
- 원자적으로 조건 확인 -> sleep을 처리하지 않으면 문제(Lost Wakeup)가 발생함

이런 점에서는 CV와 `sigsuspend()`가 정말 비슷한 것 같아.

## 8. 요약

1. 시그널은 전송 -> 대기 -> 수신의 상태를 거친다.
2. 시그널의 전송은 
커널이 대상 프로세스의 대기 비트 벡터의 해당 시그널을 나타내는 비트를 설정하는 것으로 진행된다.
(비트 OR 연산)
단순히 비트를 설정하기 때문에, 같은 시그널을 쌓이지 않는다.
3. 특정 시그널을 차단하는 차단 비트 벡터가 존재하고,
`sigprocmask()` 함수로 차단 비트 벡터를 설정할 수 있다.
다양한 `sigset_t`를 다루는 함수들로 마스크를 설정할 수 있다.
4. 시그널은 전송 즉시 수신되지 않고 대기 비트 벡터에 해당 시그널을 나타내는 비트만 설정된 후,
대상 프로세스가 커널 모드에서 사용자 모드로 돌아올 때 
커널이 대기중인 시그널 수신을 강제함으로써 수신된다.
(대기중인 시그널이 있는지를 판별하려면 `pending & ~blocked`를 하면 된다.)
5. 시그널 핸들러의 작성은
시그널 핸들러가 언제나 호출될 수 있다는 가정 하에 최대한 보수적으로 작성하고,
(비동기 시그널 안전한 함수를 쓰고 `errno`를 백업해놓는 등)
정 공유 데이터에 접근이 필요한 경우 해당 작업 중에는 시그널 자체를 차단하는 식으로 대처한다.
시그널은 쌓이지 않는다는 것을 고려해야한다.
시스템마다 API의 시맨틱이 다를 수 있다는 점도 고려해야 한다.
6. 명시적으로 특정 시그널을 기다릴 때는
차단 해제 -> sleep 사이에 시그널 수신이 들어올 수 없게
차단 해제 -> sleep을 원자적으로 수행하는 `sigsuspend()` 함수를 사용한다.
