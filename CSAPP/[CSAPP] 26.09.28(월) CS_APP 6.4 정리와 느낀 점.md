## 1. Generic Cache Memory Organization - 기본 캐시 메모리 구조

### 정리

1. 캐시 라인
    - 캐시는 $2^s$개의 캐시 집합으로 구성된 배열 형태로 구성되고,
    각 캐시 집합은 $E$개의 캐시 라인으로 이루어져 있다.
    - 각 캐시 라인은 
      - 실제 데이터가 들어가있는 데이터 블록
      - 해당 캐시 라인의 정보가 유효한지를 나타내는 유효 비트
      - 캐시 라인에 저장된 블록을 고유하게 식별하는 태그비트
      (현재 블록의 메모리 주소에서 추출된 비트의 부분집합)
        - 각 메모리 주소의 비트 수 : $m$ / 캐시 집합의 수 : $S = 2^s$
        각 캐시 라인의 데이터 블록의 바이트 수 : $B = 2^b$라고 할 때,
        태그 비트의 수는 $m - (s + b)$개이다.
      - 으로 구성되어있다.
      - 캐시의 크기($C$) : $C = S \times E \times B$
      
2. 이미 캐시에 있는 데이터를 판정하는 법
    - 메인 메모리의 주소는 캐시 메모리의 각 블록과 매핑되어있다.
    - 그렇기 때문에, 메인 메모리 주소로 사용하는 비트열은 
    태그(Tag) / 집합 인덱스(Set Index) / 블록 오프셋(Block Offset)으로 나눌 수 있다.
    - 
    1. 우선 집합 인덱스를 보고 해당 캐시 집합을 찾는다.
    2. 해당 캐시 집합의 캐시 라인 중 하나의 태그 비트와 태그가 일치하는지 찾는다.
    (이건 유효 비트가 활성화되어있을 때만 올바른 것으로 판정한다.)

### 느낀 점 & 배운 점

이 파트는 이미 알고 있었던 것도 있었고,
모르던 것도 있었어.

나 기존에는 캐시 라인이 그냥 데이터만 있는 바이트열인 줄로만 알았는데,
따로 유효 비트와 태그 비트가 있는게 신기했어.

솔직히, 그냥 바이트열만 있으면 각 캐시 라인을 어떻게 식별하는지에 대한 문제가 있으니까,
뭔가 속성값 느낌으로 그런게 필요하긴 할 것 같긴 했는데ㅋㅋ

그리고 캐시 라인이 캐시 메모리의 데이터를 다루는 단위이기도 하지만,
더 상위 단위로 캐시 집합(Cache Set)이 있다는 것도 처음 알았어.
그래서 이미 올라와있다는 것을 판정할 때
먼저 캐시 집합을 찾고
그 다음에 해당 캐시 집합의 캐시 라인을 찾는 식으로
빠르게 탐색 범위를 좁힐 수 있는거겠지.
여러 단계로 세분화해놓아서 한 번에 다 찾아야하는 부담을 덜 수 있는 것 같달까?

그리고 캐시에 이미 올라와있는 데이터를 판정하는 것도 신기했어.
캐시 메모리의 블록과 메인 메모리의 각 주소를 매핑해서,
메인 메모리의 주소를 태그 / 집합 인덱스 / 블록 오프셋으로 분할한 후,

1. 집합 인덱스(캐시 집합 찾기)
2. 태그(태그 비트 일치하는 캐시 라인이 있는지 검사)

이 순서로 탐색해서 실제로 캐시에 해당 데이터가 올라와있는지 판정하는건데,
되게 재밌었어.

그리고 블록 오프셋은 그 캐시 라인의 어느 바이트를 건드려야하는지를 나타내서
딱 그 바이트만 들고올 수 있게 해주는 느낌이고.

근데 솔직히 처음에는 메인 메모리 주소를 어떻게 저렇게 나누는지가 참 어려웠는데
(왜 저렇게 나눌 수 있는지)
결국 메인 메모리의 주소가 캐시 메모리의 각 캐시 집합과 매핑된다는걸 알고 나니
상당히 쉬워졌어.

## 2. Direct-Mapped Caches - 직접 매핑 캐시

### 정리

1. 직접 매핑 캐시의 뜻
    - 캐시 집합 당 하나의 캐시 라인을 가지는 캐시를 직접 매핑 캐시라고 한다.
    - 구현과 이해 모두에서 가장 간단한 캐시이다.
    
2. 요청된 워드를 추출하는 과정
    - 
    1. 캐시 집합 선택
    2. 라인 매칭
    3. 워드 추출
    - 이렇게 세 단계로 구성된다.
    - 캐시 집합 선택 : 주소 중간 부분에서 $s$개의 집합 인덱스 비트를 추출해서,
    캐시 집합을 선택한다.
    이 비트들은 부호없는 정소로 해석된다.
    - 라인 매칭 : 선택된 캐시 집합에서 
    해당 캐시 집합에 찾으려는 데이터가 저장되어있는지 확인한다.
    유효 비트가 설정되어있고, 캐시 라인의 태그가 주소의 태그와 일치할 때만 
    해당 데이터가 저장되어있다고 판단한다.
    직접 매핑 캐시에서는 캐시 집합 당 정확히 하나의 캐시 라인만 존재하기 때문에
    이 작업이 쉽고 빠르다.
    - 워드 추출 : 캐시에 해당 데이터가 있다면,
    원하는 데이터가 해당 캐시 라인의 어디에서 시작하는지를 결정 후,
    해당 데이터를 추출한다.
    블록 오프셋은 원하는 워드의 첫 번째 바이트에 대한 오프셋을 제공한다.
    
3. 캐시 미스가 발생한 경우
    - 캐시 미스가 발생했다면,
    메모리 계층의 다음 하위 계층에서 요청된 데이터를 가져와서
    집합 인덱스가 가리키는 캐시 집합의 캐시 라인 중 하나에 새로운 블록을 저장한다.
    - 캐시 집합이 유효한 캐시 라인으로 가득차있다면,
    기존 캐시 라인 중 하나를 제거하게 된다.
    - 직접 매핑 캐시의 경우,
    현재 라인을 새로 가져온 라인을 교체하기만 하면 된다.
    (각 캐시 집합 당 캐시 라인이 하나이므로)
    
4. 충돌 미스(Conflict Miss)의 발생
    - 직접 매핑 캐시에서 다른 데이터를 사용할 때
    같은 캐시 집합을 계속해서 사용한다면 충돌 미스가 발생할 수도 있다.
    - 이런 캐시 미스가 발생한 경우,
    캐시 라인 만큼의 패딩을 추가하는 것으로 문제를 어느정도 해결할 수 있다.

### 느낀 점 & 배운 점

솔직히 이번 장의 내용은
이미 저번 장의 느낀 점 & 배운 점 파트에서 다 해버린 것 같아..

1. 먼저, 집합 인덱스로 캐시 집합을 찾는다.
2. 해당 캐시 집합의 캐시 라인을 찾는다.
    - 직접 매핑 캐시이기 때문에 캐시 라인이 캐시 집합 당 하나이다.
3. 해당 캐시 라인을 찾았다면, 블록 오프셋으로 데이터에 접근한다.
    - 캐시 라인을 찾지 못했다면, 
    하위 계층에서 해당 데이터를 찾아서 캐시 메모리의 해당 캐시 집합에 캐싱한다.

이게 끝이야.

## 3. Set Associative Caches - 집합 결합성 캐시

### 정리

1. 집합 결합성 캐시의 뜻
    - 직접 매핑 캐시와 다르게,
    한 캐시 집합에 여러 개의 캐시 라인이 있는 캐시를 집합 결합성 캐시라고 한다.
    - 한 캐시 집합에 들어있는 라인 수($E$)는 1개보다 많아야하고,
    캐시 라인 전체 수($C/B$)보다는 적어야한다.
    - 즉, 여러 개의 캐시 집합을 가지고
    한 개의 캐시 집합은 여러 개의 캐시 라인을 가지는 캐시이다.
    
2. 요청된 워드를 추출하는 과정
    - 1. 캐시 집합 선택 : 직접 매핑 캐시와 같이, 집합 인덱스를 보고 캐시 집합을 선택한다.
    - 2. 라인 매칭 : 선택된 캐시 집합의 캐시 라인 중에
    찾으려는 데이터가 있는 캐시 라인이 있는지
    태그를 보며 확인한다.
    직접 매핑 캐시와 다르게,
    한 캐시 집합에 여러 캐시 라인이 있으므로 더 복잡한 과정을 거친다.
    - 3. 워드 추출 : 캐시 라인이 해당 캐시 집합에 있다면,
    블록 오프셋으로 원하는 데이터를 추출한다.
    
3. 캐시 미스가 발생한 경우
    - 캐시 미스가 발생한 경우,
    메모리 계층의 다음 하위 계층에서 해당 데이터를 가져와서
    해당 캐시 집합에 저장한다.
    - 캐시 집합의 모든 블록이 차 있을 경우,
    정책에 맞춰 기존 블록을 덮어쓴다.
    (LFU / LRU 등 사용)

### 느낀 점 & 배운 점

솔직히 이번 챕터는 저번 챕터의 반복이라는 느낌이 강했어.

결국 핵심은

- 하나의 캐시 집합에 여러 개의 캐시 라인이 있고
- 캐시 집합이 여러 개이다.

이렇게겠네.

그리고 이게 한 캐시 집합의 블록이 여러 개라,
해당 캐시 집합의 모든 블록이 차있는 경우에
어떻게 해야할지도 나왔는데,
이건 자세히 설명하지는 않았어.

- LRU : 가장 오래전에 사용된 캐시 라인을 교체
- LFU : 가장 저빈도로 사용된 캐시 라인을 교체

이런 정책들..

## 4. Fully Associative Caches - 완전 결합성 캐시

### 정리

1. 완전 결합성 캐시의 뜻
    - 하나의 캐시 집합에 여러 개의 캐시 라인이 있는 캐시를 완전 결합성 캐시라고 한다.
    - $E = C/B$, 즉 한 캐시 집합에 들어가있는 캐시 라인 수가
    전체 캐시 라인 수와 같은 캐시이다.

2. 요청된 워드를 추출하는 과정
    - 오직 하나의 캐시 집합이 있기 때문에
    캐시 집합을 선택할 필요는 없다.
    그래서 주소를 태그 / 블록 오프셋으로만 본다.
    - 1. 라인 매칭 : 집합 결합성 캐시와 같이,
    선택된 캐시 집합의 캐시 라인 중에
    찾으려는 데이터가 있는 캐시 라인이 있는지
    태그를 보며 확인한다.
      - 많은 캐시 라인과 태그를 비교해봐야하기 때문에
      훨씬 더 복잡하고 비싼 과정을 거친다.
    - 2. 워드 추출 : 캐시 라인이 해당 캐시 집합에 있다면,
    블록 오프셋으로 원하는 데이터를 추출하고,
    캐시 라인이 해당 캐시 집합에 없다면,
    하위 계층에서 해당 데이터를 받아와서 해당 캐시 집합에 저장한다.

### 느낀 점 & 배운 점

솔직히 이번 챕터는 기존의 단계에서

- 오직 하나의 캐시 집합이 존재하고,
모든 캐시 라인이 해당 캐시 집합에 소속된다.

이거만 바꾼거라고 할 수 있어.

어쨌든 세 가지의 캐시를 요약해보면,

- 직접 매핑 캐시 : 캐시 집합 여러 개, 캐시 집합 당 캐시 라인 하나
  - 그래서 캐시 집합에서 캐시 라인을 찾는 것이 간단함
- 집합 결합성 캐시 : 캐시 집합 여러 개, 캐시 집합 당 캐시 라인 여러개
- 완전 결합성 캐시 : 캐시 집합 한 개, 캐시 집합 당 캐시 라인 여러 개

이렇게 볼 수 있겠네.

그냥 캐시 집합과 캐시 집합 당 캐시 라인의 수를
어떻게 정할지에 대한 
캐시의 형태를 나타내는 것 같아.

## 5. Issues with Writes - 쓰기 이슈

### 정리

1. 캐시 메모리의 데이터를 쓸 때는 결국
캐시 메모리 뿐만이 아니라 다른 코어들이 공유하는 메인 메모리도 갱신해줘야한다.
   - 가장 기본적인 방법은,
   캐시에 쓰기가 발생할 때 마다 메인 메모리를 갱신하는 것이다.
   (write-through)
     - 하지만 이 방법은 버스 트래픽을 많이 먹는다.
   - 또 다른 방법은, 해당 캐시 라인이 캐시 메모리에서 쫒겨날 때에만
   메인 메모리를 갱신하는 것이다.
   (write-back)
     - 버스 트래픽을 줄일 수 있지만,
     추가적인 복잡성이 발생한다.
     (캐시의 각 캐시 라인에 대해 해당 블록이 수정되었는지를 나타내는 더티 비트를 둬야한다.)
     
2. 쓰기 시의 캐시 미스
    - 쓰기 시에 캐시 미스가 발생한다면,
    하위 계층에서 해당 블록을 캐시로 불러오고 캐시를 업데이트할 수 있다.
    (write-allocate)
      - 하지만 이 방법은 
      쓰기 미스가 발생할 때마다 하위 계층에서 블록을 캐시로 전송해야한다는 단점이 있다.
    - 또 다른 방법으로는, 캐시를 우회해서 하위 계층에 직접 쓰기를 해버리는 방법이 있다.
    (no-write-allocate)
    
3. 쓰기 시의 처리 방식은 어떻게 보는게 좋을까?
    - 세부 사항은 시스템마다 다르기 때문에,
    딱 통일된 쓰기 처리 방식은 없다.
    - 일반적으로는 write-through / write-allocate 방식을 가정하는게 좋다.
    - 쓰기 / 읽기 방식이 대칭적이기 때문에 이 방식을 사용하는 경우가 많다.
    - 물론 write-back / no-write-allocate 방식을 사용하는 시스템도 있는 만큼,
    시스템에 맞춰 최적화하려고 하기보다는,
    공간적 / 시간적 지역성을 잘 나타내도록 하이 레벨에서 코드를 짜는게 좋다.

## 6. Anatomy of a Real Cache Hierarchy - 실제 캐시 계층 구조의 해부

### 정리

1. 실제로는, 캐시는 프로그램 데이터만 저장하지 않고, 명령어도 저장한다.
    - 명령어만 저장하는 캐시를 i-Cache(Instruction Cache)라고 한다.
    - 프로그램 데이터만 저장하는 캐시를 d-Cache(Data Cache)라고 한다.
    - 이렇게 두 개의 캐시를 사용하는 이유는,
      - 명령어와 데이터를 동시에 읽을 수 있게 하기 위해서이기도 하고,
      - 데이터 접근과 명령어 접근이 충돌(Conflict) 미스를 일으키지 않게 하기 위해서이기도 하다.

2. 실제의 캐시 구조
    - 보통 코어 당 L1 / L2 캐시가 나뉘어져 있고,
    - L1 캐시는 i / d 캐시 둘 다 있다.
    L2 캐시는 통합 캐시로 동작한다.
    - L3 캐시는 모든 코어가 공유하게 된다.

### 느낀 점 & 배운 점

솔직히 이번 챕터는 책에서도 되게 짧았어.

사실상 남은건

- 명령어와 데이터를 동시에 읽을 수 있고,
- 명령어와 데이터 간에 충돌 미스가 나지 않는다.

## 7. Performance Impact of Cache Parameters - 캐시 매개변수가 성능에 미치는 영향

### 정리

1. 캐시 성능을 평가하는 지표
    - 캐시 미스율 : 전체 참조에서 캐시 미스가 발생한 비율
    - 캐시 히트율 : 전체 참조에서 캐시 히트가 발생한 비율
    - 캐시 히트 시간 : 캐시에서 CPU까지 데이터가 도착한 시간
      - 캐시 집합 선택 / 라인 매칭 / 워드 추출 시간도 포함한다.
    - 캐시 미스 패널티 : 캐시 미스가 발생했을 때 데이터를 가져오기까지 걸리는 시간
    
2. 캐시 크기의 영향
    - 캐시 용량이 클 수록 캐시 히트율은 늘어난다.
    - 하지만 캐시 히트 시간이 줄어든다.

3. 블록 크기의 영향
    - 한 블록의 크기가 커지면 공간적 지역성은 좋아진다.
      - 한 블록이 크기 때문에 더 많은 붙어있는 데이터를 가져올 수 있다.
    - 하지만 그렇다면 시간적 지역성은 안좋아진다.
      - 한 블록이 크기 때문에 전체적으로 캐싱할 수 있는 블록 수는 줄어든다.

4. 연관성(한 캐시 집합 당 캐시 라인의 수)의 영향
    - 높은 연관성은 충돌 미스에 대한 취약성을 줄여준다.
      - 한 캐시 집합의 캐시 라인이 많으므로 
      같은 캐시 집합에 여러 캐시 라인이 쓰여져서 생기는 충돌 미스가 적어진다.
    - 하지만 구현 비용과 복잡도가 높고 처리 속도를 높이기가 어려워진다.

5. 쓰기 전략의 영향
    - write-through 캐시는 구현이 더 간단하고,
    읽기 미스가 메모리 쓰기를 유발하지 않기 때문에
    처리 비용이 적게 든다.
    - write-back 캐시는 전송 횟수가 적어서 버스 트래픽을 적게 차지하고,
    I/O 장치에 버스 트래픽을 더 줄 수 있다.
    - 일반적으로 하위 계층으로 갈 수록 전송 시간이 증가하므로 전송 횟수를 줄이는 것이 중요해진다.

## 8. 요약

1. 캐시는 
캐시 집합 
-> 각 캐시 집합 내의 캐시 라인들 
-> 각 캐시 라인의 유효 비트 / 태그 비트 / 데이터의 구조로 돌아간다.
2. 먼저 캐시 집합 인덱스를 찾은 후, 
해당 캐시 집합 내의 캐시 라인들의 태그 비트를 기반으로 캐시 라인을 찾고,
마지막으로 오프셋을 사용해서 원하는 바이트에 접근한다.
3. 캐시 미스가 발생한 경우, 하위 계층에서 해당 블록을 받아오고
해당 캐시 집합에 저장한다.
4. 캐시 라인들을 몇 개의 집합으로 나누고,
하나의 캐시 집합에 몇 개의 캐시 라인이 들어가는지에 따라
직접 매핑 캐시 / 집합 결합성 캐시 / 완전 결합성 캐시가 나뉜다.
5. 쓰기 시, 
쓰기마다 데이터를 하위 계층에 저장 / 해당 캐시 라인이 쫓겨날 때마다 데이터를 하위 계층에 저장하는 식으로
메모리 갱신을 할 수 있다.
6. 쓰기 시 캐시 미스가 발생했을 때,
하위 계층의 데이터를 캐시에 올려놓은 후 쓰기 / 아예 하위 계층에 쓰기하는 식으로
대처를 할 수 있다.
7. i-cache / d-cache로 명령어와 데이터를 분리해서 저장할 수도 있다.
8. 캐시 크기 / 블록 크기 / 연관성 등을 키우면 캐시 미스를 줄이는 대신
속도 / 비용 / 복잡성 등의 트레이드오프가 있다.
