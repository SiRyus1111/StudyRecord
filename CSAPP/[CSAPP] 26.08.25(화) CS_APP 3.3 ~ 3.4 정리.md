## 1. Data Formats - 데이터 형식

### 정리

1. 각각의 데이터 형식의 의미
    - 기본적으로 `x86_64`는 16비트 시스템에서부터 출발해서
    16비트를 워드(`w`)라 부른다.
    - 물론 8비트 데이터는 바이트(`b`)라고 부른다.
    - 32비트 데이터는 더블 워드(`l`),
    64비트 데이터는 쿼드 워드(`q`)로 부른다.
    물론 같은 64비트(8비트)인 포인터도 쿼드 워드(`q`)로 부른다.
    - 부동소수점 수에서는 단일 정밀도는 `s`로 표시하고,
    이중 정밀도는 `l`로 표시한다.
    - 정수와 부동소수점은 다른 방식으로 연산을 해야하기 때문에,
    같은 산술 연산이라도 레지스터와 명령어 집합이 다르다.
    - 그렇기 때문에 부동 소수점 수의 이중 정밀도 수를 나타내는 `l`과
    더블 워드를 나타내는 `l`이 같아도,
    결국 명령어를 보고 더블 워드인지 / 이중 정밀도인지를 구분하게 된다.
    
2. `x86_64` 어셈블리에서는 오퍼랜드(피연산자)의 크기를 나타내는 한 글자의 접미사가 붙어있다.
    - 정수 이동 명령어를 기준으로 한다면,
      - `movb` : 바이트 이동
      - `movw` : 워드 이동
      - `movl` : 더블 워드 이동
      - `movq` : 쿼드 워드 이동
    - 이런 식이다.

## 2. Accessing Information - 정보 접근

### 정리

1. `x86_64` CPU에는 64비트 값을 저장할 수 있는 16개의 범용 레지스터가 있다.
    - 이런 레지스터들은 정수 데이터 / 포인터를 저장하는데 사용된다.
    - 처음부터 64비트 값을 저장할 수 있던게 아니고,
    초기에는 16비트 레지스터가 있었고
    32비트 레지스터를 거쳐 64비트까지 온 것이다.
    - 각 레지스터는 `%r`로 시작한다.
      - `%rax` : 반환값(범용적으로 사용 가능)
      - `%rdi` : 1번째 인자
      - `%rsi` : 2번째 인자
      - `%rdx` : 3번째 인자
      - `%rcx` : 4번째 인자
      - `%r8` : 5번째 인자
      - `%r9` : 6번째 인자
      - `%rsp` : **스택 포인터**(중요)
      - `%rbp` : 해당 함수에서 호출된 함수, 스택 프레임 포인터로 사용할 수 있음.
      - `%rbx` / `%r12` ~ `%r15` : 해당 함수에서 호출된 함수
      (일반적으로는 범용적으로 사용 가능)
      (이것들은 지금은 볼 필요 없음)
      - `%r10` / `%r11` : 해당 함수를 호출한 함수
      (일반적으로는 범용적으로 사용 가능)
      (이것들은 지금은 볼 필요 없음)
    - 그리고 레지스터의 어느정도 공간을 다루느냐에 
    같은 레지스터도 따라 다르게 부른다.
    (이건 지금은 안다룸)
    
    | 64bit  | 32bit  | 16bit  | 8bit   |
    | ------ | ------ | ------ | ------ |
    | `%rax` | `%eax` | `%ax`  | `%al`  |
    | `%rbx` | `%ebx` | `%bx`  | `%bl`  |
    | `%rcx` | `%ecx` | `%cx`  | `%cl`  |
    | `%rdx` | `%edx` | `%dx`  | `%dl`  |
    | `%rsi` | `%esi` | `%si`  | `%sil` |
    | `%rdi` | `%edi` | `%di`  | `%dil` |
    | `%rsp` | `%esp` | `%sp`  | `%spl` |
    | `%rbp` | `%ebp` | `%bp`  | `%bpl` |
    | `%r8`  | `%r8d` | `%r8w` | `%r8b` |
    | ...    | ...    | ...    | ...    |
    (이런 식으로)
    - 이런 식으로 하나의 64비트 범용 레지스터의 공간 중 
    어느정도에 데이터를 저장하는지를 나타내기 위해
    이렇게 같은 레지스터를 다른 이름으로 부르는 것이다.

## 3. Operand Specifiers - 오퍼랜드 지정자

### 정리

1. 명령어에는 하나 이상의 오퍼랜드가 필요하다.

2. `x86_64`의 오퍼랜드는 어디에 값이 저장되어있는지를 나타내는 여러가지 형태가 있다.
  - `Imm`은 즉시값, 즉 상수를 의미한다.
  - $R$ / `r`은 레지스터를 의미한다.'
    - `rb`는 베이스 레지스터를 의미한다.
    - `ri`는 인덱스 레지스터를 의미한다.
  - $M$은 메모리를 의미한다.
  - $A[n]$은 말 그대로 배열의 인덱스처럼 읽힌다.
    - $R[r]$ : 레지스터의 `r`에 해당하는 만큼의 데이터
    - $M[n]$ : 메모리의 주소 `n`의 데이터
    - 어셈블리는 메모리를 거대한 배열처럼 사용하므로,
    이런 표기를 사용한다.
  - 레지스터의 이름 앞에는 `%`가 붙는다.
  - 오퍼랜드는 크게 세 종류로 나눌 수 있다.
    - 1. 즉시값(상수)
      - 즉시값(바로 값 넣기) : `$Imm`($Imm$) - 앞에 `$`를 붙인다.
    - 2. 특정 레지스터의 값
      - 레지스터 값 : `r`($R[r]$) - 레지스터 이름을 적는다.
    - 3. 메모리의 특정 주소의 값
      - 이 오퍼랜드 타입은 네 가지 구성 요소로 이루어져 있다.
      - `Imm(rb, ri, s)`
        - 상수 오프셋 `Imm`
        - 베이스 레지스터 `rb` : 메모리 영역의 기준(Base)이 되어주는 주소가 저장된 레지스터.
        64비트 레지스터만 가능하다.
        - 인덱스 레지스터 `ri` : 기준 주소에서 얼마나 떨어져있는지(index)가 저장된 레지스터.
        64비트 레지스터만 가능하다.
        - 스케일 계수 `s` : 상수 오프셋 / 베이스 레지스터로 계산된 주소에서
        인덱스 레지스터에 저장된 값의 몇 배의 주소를 읽을건지,
        즉 각 인덱스가 몇 개의 주소를 차지하는지.
        인덱스 1이 증가할 때 메모리 주소가 몇 바이트 증가해야하는지를 나타낸다.
        값은 1, 2, 4, 8만 가능하다.
        - 상수 오프셋과 베이스 레지스터의 차이는
        오프셋이 상수이냐, 레지스터에 저장되어있냐의 차이다.
      - `Imm`($M[Imm]$) : 해당 위치의 메모리를 읽는다.
      - `Imm(rb)`($M[Imm + R[rb]]$) : `Imm`의 위치에서 `rb`만큼 떨어져있는 주소를 읽는다.
      - `(rb, ri)`($M[R[rb] + R[ri]]$) : `rb`의 위치에서 `ri`만큼 떨어져있는 주소를 읽는다.
      - `Imm(rb, ri)`($M[Imm + R[rb] + R[ri]]$) : `Imm`의 위치에서 
      `rb`만큼 떨어져있는 주소에서 `ri`만큼 떨어져있는 주소를 읽는다.
      - `(, ri, s)`($M[R[ri] * s]$) : `ri`의 주소를 `s`배 한 주소를 읽는다.
      - `(rb, ri, s)`($M[R[rb] + R[ri] * s]$) : `rb`의 주소에서 
      `ri`를 `s`배 한 주소를 읽는다.
      - `Imm(rb, ri, s)`($M[Imm + R[rb] + R[ri] * s]$) : `Imm`에 주소에서
      `rb`만큼 떨어져 있는 주소에서
      `ri`를 `s`배 한 주소를 읽는다.
  - 이 주소 지정 방식들 외에도 나중에 배열 / 구조체를 참조할 때는
  더 복잡한 주소 지정 방식이 있다.

### 배운 점 & 느낀 점

이번 챕터에서는
정말 쉽게 말하면

> 명령어의 오퍼랜드를 어떤 형식으로 써야 하는가?

- 상수(즉시값)
- 레지스터 값

상수는 앞에 `$`를 붙이고,
레지스터는 레지스터 이름을 적고(물론 `%`도 함께)
메모리 주소는 `( )`를 이용하고..

이렇게 완벽하게 세 가지로 분류되는거지.

메모리 주소는
`Imm(rb, ri, s)`로

(말하는거 전부 가상 주소라는 가정 하에 말하는거야.)
(해당 프로세스가 보는 가상 주소.)

- `Imm` : 메모리 주소에 대한 상수 오프셋
- `rb` : 절대 주소를 나타내는 값이 들어있는 레지스터
- `ri` : `Imm`과 `rb`로 결정된 메모리 주소에서 
`s`와 곱해서 주소 계산에 사용할 값이 들어있는 레지스터
- `s` : `ri`이 1 증가할 때 실제 주소가 증가하는 크기를 나타내주는 상수
1, 2, 4, 8 중 하나다.

이렇게 이해했어.

배열처럼 이해하니까 이해가 잘되더라.

- `rb` : 배열의 첫 주소를 나타내는 포인터
- `ri` : 배열의 인덱스
- `s` : 각 배열의 인덱스가 몇 바이트를 차지하는지 나타내는 상수,
즉 `ri`에 곱해져서 실질적인 메모리 주소를 나타내게 해주는 상수.
(`sizeof()`)
- `Imm` : 배열에 딱히 비유할 게 없는 상수 오프셋

이렇게.

결국 이 파트의 초반부에서 설명했듯
어셈블리에서는 메모리를 거대한 하나의 배열로 보니까
이 이해도 얼추 맞지 않을까?

그리고 앞서 설명한 데이터 포맷과도 연결되는 부분인데,
결국 메모리를 읽을 때 명령어가 다루는 바이트 수에 맞춰서
해당 메모리 주소부터 `N`개의 메모리 주소를 하나의 데이터로 읽는 것 같아.

`s`와는 별개야.
나는 처음에 스케일 상수 `s`와 
몇 바이트를 읽어야하는지 나타내는 데이터 포맷이 같다고 생각했는데,

- 결국 `s`는 한 **인덱스**(`ri`)가 몇 바이트를 차지하는지를 나타내고,
- 그것과 별개로 데이터 포맷(suffix)은 메모리에서 몇 바이트를 **읽어야하는지**를 나타내는 것으로

두 개념이 비슷하지만 다른 개념인걸로 이해했어.

사실 처음에 `Imm`을 절대 주소로 이해했는데,
이해를 절대 주소에서 그냥 상수 오프셋으로 바로잡았어.

## 4. Data Movement Instructions - 데이터 이동 명령어

### 정리

1. 기본적인 데이터 이동 명령어
  - `movb` : 바이트(1바이트) 이동
  - `movw` : 워드(2바이트) 이동
  - `movl` : 더블 워드(4바이트) 이동
  - `movq` : 쿼드 워드(8바이트) 이동
  - 접미사(suffix)에 따라 읽는 바이트 수가 달라진다.

2. 데이터 이동 명령어의 기본 규칙
  - 데이터를 복사할 위치(source)가 첫 번째 오퍼랜드이고,
  데이터가 복사될 위치(destination)가 두 번째 오퍼랜드이다.
  (AT&T 기준. Intel은 반대이다.)
  (`mov A, B`)라고 했을 때 `A` -> `B`로 데이터를 복사한다고 생각하면 된다.
  - source를 나타내는 오퍼랜드는 즉시값 / 레지스터 / 메모리 다 된다.
  - destination을 나타내는 오퍼랜드는 레지스터 / 메모리만 된다.
    - 즉시값에는 당연히 따로 저장될 곳이 없기 때문에..
  - `x86_64`에서는 두 오퍼랜드가 모두 메모리를 나타내는 경우는 불가능하다.
    - 먼저 메모리의 값을 레지스터로 이동시킨 후에
    레지스터에 복사된 값을 메모리에 복사하는 식으로
    두 줄의 코드를 작성해야 한다.
  - 16개의 레지스터 모두를 오퍼랜드로 올릴 수 있고,
  레지스터의 바이트 수와
  `mov` 명령어가 나타내는 바이트 수가 일치해야한다.
  - 그리고, `x86_64`의 32비트(더블 워드) 범용 레지스터에,
  즉 `l` 접미사를 사용하는 명령어를 사용해서 값을 쓸 때는(복사할 때는)
  해당 레지스터의 상위 4바이트(32비트)는 `0`으로 채워진다.
  (이건 `x86_64`의 규칙이다.)
    - 하지만 16비트(워드, `w`) / 8비트(바이트, `b`)는 해당되지 않고,
    하위 `N`비트만 변경된다.
    - 이 규칙은 값이 써지는 곳이 **레지스터**일 때만 적용된다.
    (이거 중요하다. 메모리에는 적용되지 않는다.)
    - 이 규칙은 `mov` 뿐만이 아니라 
    더블 워드(32비트) 크기의의 특정 레지스터에 값을 쓰는 명령어들이
    모두 해당된다.
    
3. `movabsq` (move absolute quad word)의 특수성
    - `movq` 명령어는 32비트 2의 보수로 표현될 수 있는 
    즉시값 오퍼랜드까지만 source 오퍼랜드로 가질 수 있다.
    (물론 부호가 확장되어 64비트 2의 보수 값이 되긴 하지만,
    64비트 2의 보수 값을 다루지 못한다.)
      - 64비트 값은 상수로 다루기엔 너무 커서 그렇다.
    - 그래서 `movabsq` 명령어가 필요하다.
    `movabsq` 명령어는 source 오퍼랜드로 64비트 즉시값을 가질 수 있고,
    destination으로는 레지스터만 가질 수 있다.
    
4. 더 적은 비트 수의 source 오퍼랜드를 더 많은 비트 수의 destination 오퍼랜드로 옮기는 명령어
    - `movz**` : move zero-extended - 빈 바이트가 0으로 채워진다(unsigned 전용)
      - 논리 시프트와 비슷한 느낌이다.
    - `movs**` : move sign-extended - 빈 바이트가 부호 비트로 채워진다(signed 전용)
      - 산술 시프트와 비슷한 느낌이다.
    - 두 명령어 모두 명령어 이름의 마지막 두 글자는 
    source 오퍼랜드와 destination 오퍼랜드의 크기를 나타낸다.
      - soruce 오퍼랜드의 크기는 첫 번째 글자로,
      destination 오퍼랜드의 크기는 두 번쨰 글자로 나타낸다.
      - 예 : `movsbw` - 바이트 크기의 source 오퍼랜드를 워드 크기의 dest 오퍼랜드로 복사
      - 예 : `movzlq` - 더블 워드 크기의 source 오퍼랜드를 쿼드 워드 크기의 dest 오퍼랜드로 복사
    - 하지만 4바이트의 오퍼랜드를 8바이트의 오퍼랜드로 
    zero-extend로 복사하는 명령어(`movzlq`)는 지원하지 않는다.
      - 이 명령어는 `movl`을 이용해서 8바이트 레지스터에 값을 채워넣는 식으로
      대체할 수 있다.
        - `movl`은 상위 4바이트가 자동으로 0으로 채워지기 때문에
        `movl`을 8바이트 레지스터에 하위 4바이트만 복사한다면
        사실상 `movelq` 명령어가 되기 때문이다.
      - 하지만 sign-extend는 지원된다.
        - `movl`의 상위 4바이트가 자동으로 0으로 채워지는 성질을
        사용할 수 없기 때문이다.
      
5. `citq` 명령어
  - 조금 특수한 명령어로, 오퍼랜드를 받지 않고 
  `%eax` 레지스터의 값을 `%rax` 레지스터로 sign-extend로 복사해준다.
  - (`movslq %eax, %rax`와 같다.)

### 느낀 점 & 배운 점

일단 어셈블리의 데이터 이동이
어떤 형태의 명령어로 일어나는지는 확실히 안 것 같아.

- `movb` - 바이트 복사
- `movw` - 워드 복사
- `movl` - 더블 워드 복사
- `movq` - 쿼드 워드 복사

이렇게 뒤에 어느 크기의 오퍼랜드를 다루는지 지정을 해줘야하고,

(여기서는 AT&T 기준으로 설명)
`mov* A, B`에서 
source(데이터를 복사할 위치, `A`) 오퍼랜드는 즉시값 / 레지스터 / 메모리가 가능하고,
destination(데이터가 복사될 위치, `B`) 오퍼랜드는 레지스터 / 메모리만 가능하지.

그리고 메모리에서 메모리로 데이터를 복사하는 것은 불가능하고,
메모리 -> 레지스터 -> 메모리 순으로 데이터를 복사해야 한다는 것.

그리고 신기했던게 딱 32비트(4바이트)의 레지스터에 값을 쓸 때만
상위 32비트(4바이트)의 값들을 0으로 덧씌운다는거.

이건 진짜로 그냥 `x86_64`의 규칙이 이렇구나 싶더라고.

그리고 `movq` 명령어로는 즉시값을 32비트로밖에 다룰 수 없다는게 신기했어.
그래서 굳이 `movabsq` 명령어를 사용해야만 64비트 즉시값을 source 오퍼랜드로 쓸 수 있고,
오직 레지스터로만 복사할 수 있다는 것도 참 이상했어..

근데 이건 결국 64비트 즉시값이 그대로 명령어의 오퍼랜드로 들어가면
오퍼랜드의 용량이 너무 커져서 생기는 문제라고 알게 됐어.

그리고 더 큰 데이터 포맷으로 데이터를 복사할 때도
부호를 확장하냐 / 안하고 0으로 채우냐에 따라 
`movs**` / `movz**`로 이분되는 것도 상당히 공감됐어.

위의 정리 파트에 써놨듯,
산술 시프트 / 논리 시프트와 비슷하게 체감했어.

사실 둘 다 비슷하긴 해.
산술 시프트 / 논리 시프트든
`movs**` / `movz**`든 
연산을 수행하고 빈 바이트를 어떻게 채울지에 대한 정책을 정하고 
그 정책에 맞춰 빈 바이트들을 채우는거니까..

그리고 솔직히 데이터 이동의 규칙들은 기억이 잘 안 남아있는 것 같아..
이거는 뭔가 다른 정보와 연결점이 없이 혼자 따로 떨어져있는 느낌인지라..

다시 정리해보자면
(괄호 안은 왜 이런지에 대한 이유임)

- `mov* A, B`의 형식으로 쓰고, `A`가 source `B`가 destination이다.
(그냥 개념 설명)
- `mov*` 명령어에서는 `A`와 `B`의 크기가 일치해야한다.
(당연한거)
- source는 즉시값 / 레지스터 / 메모리 전부 가능하지만, dest는 레지스터 / 메모리만 가능하다.
(목적지가 즉시값이 되는건 극히 부자연스러움, 데이터를 저장할 위치가 아니라 단순 값이니까..)
- 메모리에서 메모리로 값을 복사하는 경우에는 중간에 레지스터 하나를 끼고 가야한다.
(이건 자세히는 모르겠음.. 그냥 메모리에서 메모리로 복사할 수 없는 걸로 이해함.)
- 32비트 레지스터를 `movl`로 다른 32비트 레지스터로 값을 복사할 때,
남는 상위 4바이트는 자동으로 0으로 채워진다.
다른 바이트의 레지스터는 해당되지 않는다.
(이건 `x86_64`의 규칙으로 이해했음)
- 64비트 즉시값은 `movq`를 사용할 수 없어서 전용 명령어인 `movabsq`를 사용해야 한다.
(64비트는 즉시값으로 들어가기에는 너무 큼)
- 더 작은 크기의 오퍼랜드를 더 큰 크기의 오퍼랜드로 옮길 때,
빈 공간을 0으로 확장한다면 `movz**`을, 빈 공간을 부호 비트로 확장한다면 `movs**`을 사용하면 된다.
(마치 논리 시프트 / 산술 시프트)
- 더블 워드 오퍼랜드를 zero-extension으로 쿼드 워드 오퍼랜드로 확장할 때(`movzlq`)는
별도의 명령어가 없이 32비트 레지스터의 값 복사 특성을 이용해서
`movl`을 사용하면 된다.
(어차피 결과값은 같으니 굳이 명령어 따로 만들 필요 없음)

이 정도가 기억나네.

핵심은 나름 잘 정리된 듯.

## 5. Data Movement Example - 데이터 이동 예시

### 정리

1. 느낀 점 & 배운 점만 쓰는게 좋을 것 같다. 이 파트는..

### 느낀 점 & 배운 점

```c
// xp의 주소의 값을 y로 교체한 후 원래 xp가 가리키고 있던 값을 반환하는 함수
long exchange(long* xp, long y) {
    long x = *xp;
    *xp = y;
    return x;
}
```

(`x86_64`의 AT&T 문법에서는 주석을 `#`으로 담..)

```x86asm
# xp : %rdi(첫 번째 인자 레지스터)
# y : %rsi(두 번쨰 인자 레지스터)
# 이렇게 저장되었다고 하자.

exchange:
    movq (%rdi), %rax # *xp의 값을 %rax, 즉 x에 저장, x는 반환값이므로 %rax 레지스터를 사용
    movq %rsi, (%rdi) # y의 값을 *xp에 저장
    ret               # x(%rax)를 반환
```

일단 크게 내 머리에 꽂힌건

첫 번째로 반환값을 `%rax`나 그 하위 레지스터에 저장해놓으면
`ret` 명령어를 실행했을 때 그 값이 반환된다는건데,
일단 이건 중요한게 아니니까 넘어가고,
(더 자세히는 나중에 살펴봄)

두 번째로 C언어의 포인터 역참조가
어셈블리에서는 해당 데이터(포인터 값)가 들어있는 레지스터를 주소로 사용하고
괄호를 사용해서 메모리에 접근하게 하는 것으로 구현될 수 있다는 거였어.

그리고 이건 책에서 알려준건데,
위의 C언어 코드의 `x`같은 변수가
메모리를 한 번도 거치지 않고
그냥 레지스터에서 처리될 수 있다는 점이야.

지역 변수를 굳이 메모리에 넣지 않고 레지스터 선에서 처리할 수 있다는거지.
그리고 이게 뭔가 내 상식을 뒤틀어놓은 것 같아.

기존에는 '모든 변수는 메모리에 올라간다' 였다면,
현재는 '특정 변수들은 메모리에 올라가지 않고 레지스터 선에서 처리될 수 있다' 느낌이지.

이 코드 예시에서는 결국
메모리에서 값을 읽어와서 레지스터에 저장하는 연산과
레지스터의 값을 메모리에 저장하는 연산을
보여주고 있는 것 같아.

과제도 꽤 재밌었어.

```c
src_t* sp;
dest_t* dp;

*dp = (dest_t) *sp;
```

이렇게 두 가지 변수 `sp`(source ptr) / `dp`(destination ptr)를 가지고,
`sp`의 주소에 있는 데이터를 `dp`의 주소로 옮기는 상황에서,

각 자료형이 뭐냐에 따라 내부 어셈블리가 어떻게 달라지느냐에 대한 문제였어.
(`%rax` / `%eax` / `%ax` / `%al`만 사용(전부 같은 레지스터를 나타냄))
(`sp`는 `%rdi`에, `dp`는 `%rsi`에 저장되어 있음)

| `src_t` | `dest_t` | 명령어 | 설명 |
|---|---|---|---|
|`long`|`long`|`movq (%rdi), %rax`|같은 크기(8바이트)의 signed 자료형이므로|
|||`movq %rax, (%rsi)`|단순히 `movq`로 옮기면 됨|
|`char`|`int`|`movsbl (%rdi), %eax`|1바이트를 4바이트로 옮기므로|
|||`movl %eax, (%rsi)`|`movsbl`로 옮기면 됨|
|`char`|`unsigned`|`movsbl (%rdi), %eax`|1바이트를 부호없는 4바이트로 옮기는데,|
|||`movl %eax, (%rsi)`|부호 있는 수를 먼저 `%eax`로 옮기므로 `movsbl`을 사용함.|
|`unsigned char`|`long`|`movzbq (%rdi), %rax`|부호없는 1바이트를 8바이트로 옮기니까|
|||`movq %rax, (%rsi)`|`movzbl`로 옮기면 됨|
|`int`|`char`|`movl (%rdi), %eax`|4바이트를 1바이트로 옮기지만|
|||`movb %al, (%rsi)`|먼저 `%eax`에 저장한 후 하위 1바이트를 나타내는 `%al`만 옮기면 됨|
|`unsigned`|`unsigned char`|`movl (%rdi), %eax`|바로 위의 문제와 같음|
|||`movb %al, (%rsi)`|둘다 unsigned이므로 `mov***`을 굳이 고려하지 않아도 됨|
|`char`|`short`|`movsbw (%rdi), %ax`|부호 있는 1바이트를 부호 있는 2바이트로 옮기면 되므로|
|||`movw %ax, (%rsi)`|`movsbw`를 사용하면 됨|

정답은 이렇게 되고.
이게 딱 어셈블리로 어떻게 캐스팅이 되는지를 보여주는 것 같았어.

이게 업 캐스팅은 이미 다양한 `mov***` 명령어들을 보고 와서
별로 그렇게 신기하지는 않았는데,

다운 캐스팅은 딱 레지스터의 하위 `N`바이트만 읽음으로써 구현된게
너무 신기했어..

뭔가 이 문제를 풀어보면서
내 관점이 잡힌 것 같아.

> 결국 레지스터에 저장되어있는 것도 바이트열(비트열)이다.
> 레지스터는 그저 저장 용량이 매우 작고
> 어셈블리 문법상으로는
> 주소로 접근하지 않고 레지스터 이름으로 하위 `N`바이트(비트)에 접근할 수 있는 메모리인 것 뿐이다.

그리고 다른 연습 문제도 있는데,
어셈블리를 보고 그걸 C언어 코드로 옮겨보는 문제야.

```c
void decode1(long* xp, long* yp, long* zp);
```

이 함수를 컴파일 했을때,

```x86asm
# xp : %rdi
# yp : %rsi
# zp : %rdx
# 이렇게 저장되었다고 하자.
decode1:
    movq (%rdi), %r8
    movq (%rsi), %rcx
    movq (%rdx), %rax
    movq %r8, (%rsi)
    movq %rcx, (%rdx)
    movq %rax, (%rdi)
    ret
```

이런 어셈블리 코드가 나온다고 했을 때,
어떤 C언어 코드가 컴파일되었는지를 추론해보는 문제야.

결국 각 변수의 값을 각각 `%r8` / `%rcx` / `%rax`에 저장하고,
각 레지스터의 값을 다시 각 변수가 있는 메모리 공간에 쓰기하는 함수인데,
어느 레지스터의 값이 어느 메모리 공간에 쓰이는지가 중요하겠지..

```c
void decode1(long* xp, long* yp, long* zp) {
    long x = *xp;
    long y = *yp;
    long z = *zp;
    
    *yp = x;
    *zp = y;
    *xp = z;
    
    // 반환 값 형식이 void니까 값을 return하지 않음
}
```

내가 추론해본 바로는 이런 코드가 나오더라..

## 6. Pushing and Popping Stack Data - 스택 데이터의 Push와 Pop

### 정리

1. 프로세스의 스택은 프로시저 호출을 처리하는데 있어서 중요한 역할을 한다.
2. 스택은 높은 주소에서 낮은 주소로 확장된다.
3. 스택의 top(가장 낮은 주소)을 표시하는 `%rsp`(스택 포인터) 레지스터가 있다.
4. 스택의 top에 `push` / `pop` 하는 명령어
    - `pushq` / `popq`가 있다.
    - `pushq`는 내부적으로 top을 8 감소시킨 후에
    그 위치부터 8바이트에 쿼드 워드 원소를 추가한다.
      - (예 :`pushq %rax`는 스택의 top(`%rsp`)을 8 감소시킨 후에
      감소된 top(`%rsp`)부터 `%rax`에 저장되어있는 8바이트만큼을 추가한다.)
      ```x86asm
      subq $8, %rsp
      movq %rax, (%rsp)
      ```
    - `popq`는 내부적으로 스택의 top(`%rsp`)의 쿼드 워드 원소를 뺀 후
  top(`%rsp`)을 8 증가시킨다.
      - (예 : `popq %rax`는 스택의 top(`%rsp`)의 원소를 `%rax`로 복사한 후
      top(`%rsp`)을 8만큼 증가시킨다.)
      
5. 스택의 top에 `push` / `pop` 하는 명령어는 기본적으로 쿼드 워드 / 워드만 지원한다.
    - 기본적으로 쿼드 워드(8바이트)만 `push` / `pop`할 수 있게 해서
    메모리의 8비트 단위의 정렬이 깨지지 않도록 해주고,
    하드웨어의 복잡도를 감소시킨다.
    - 그리고 워드가 기본 크기였던 시절과의 하위 호환성을 위해 워드를 지원한다.
    - 그래서, 바이트 / 더블 워드를 스택에 `push`하고 싶다면,
    보통 쿼드 워드 크기로 상위 바이트를 확장한 뒤 `push`를 수행한다.
      - (예 : 더블 워드를 스택에 `push`)
      ```x86asm
      movslq %edi, %rax
      pushq %rax
      ```

### 느낀 점 & 배운 점

이건 지금 당장 쓰이는 내용이 아닌 것 같은 느낌을 상당히 받았어.
스택은 솔직히 나중에 프로시저 파트 가야 나오겠지만,
지금 이 파트의 주제가 데이터 이동 명령어다 보니까
그냥 멱살 잡혀 끌려 나온 느낌..

스택의 `push` / `pop`에서 가장 특이했던건
일반적으로는 쿼드 워드(64비트) 고정으로 `push` / `pop`을 한다는거?

결국 `x86_64`의 명령어 규칙 때문인 것 같아.
솔직히 이건 진짜 이것밖에 설명할 길이 없다..

그냥 스택 관련 명령어,
`%rsp`를 암묵적으로 사용하게 되는 명령어에서는
오퍼랜드 크기를 32비트가 아닌 64비트로 본다고 보면 돼.

이유를 어떻게든 끌어내보자면,
주소값 / 레지스터 / 스택 포인터가 모두 64비트니까 
`push` / `pop`의 주된 용도롤 64비트로 정하게 된 게 아닐까..
(추측임)

`pushq` / `popq`로 스택에 `push` / `pop` 하는건
`x86_64`에서는 무조건 8바이트로만 가능하고,
예전에 2바이트로 가능했던 흔적 때문에 하위호환으로 2바이트도 남겨둔 것이라고
설명할 수 있겠네..

그리고 스택 포인터와 오프셋으로
스택 최상단(가장 낮은 주소)에서 양으로 몇 바이트 떨어져 있는 원소에 접근하는 식으로
프로시저가 실행 중일 때 메모리에 저장되어있는 각 원소에 접근하게 되는 것 같았어.

```text
---- 0x118


---- 0x110


---- 0x108


---- 0x100 - (%rsp)
```

`pushq`를 여러번 실행해서 스택에 데이터가 이렇게 8바이트의 간격을 두고 쌓여있다고 했을 때,

스택의 두 번째 8바이트 값인 `0x108`의 데이터를 얻고 싶다면 `8(%rsp)`을 하면 되고,
스택의 세 번째 8바이트 값인 `0x110`의 데이터를 얻고 싶다면 `16(%rsp)`을 하면 되는 식으로.

## 7. 총정리

결론적으로 이번 장에서는

- `x86_64`의 오퍼랜드를 즉시값 / 레지스터 / 메모리에 따라 어떻게 쓰는지
  - 즉시값 : `$`붙이기
  - 레지스터 : 이름 그대로 + 앞에 `%`붙이기
  - 메모리 : `( )`를 이용, `Imm(rb, ri, s)` 형식으로 $M[R[rb] + R[ri] * r + Imm]$의 주소
- `x86_86`의 데이터 이동 명령어
  - 기본적인 `mov*` 형태의 명령어
    - 접미사에는 복사할 데이터의 크기를 나타냄
  - 서로 다른 크기의 오퍼랜드로 데이터를 복사할 때 사용하는 `movz**` / `movs**` 명령어
    - zero-extension을 하는 `movz**`, sign-extension을 하는 `movs**`
  - 32비트 레지스터로 데이터를 옮길 때는 상위 4바이트가 0으로 채워진다는 점
  - 두 개의 메모리 오퍼랜드는 한 `mov` 명령어에 사용할 수 없다는 점
- 스택에서의 `pop` / `push`
  - `popq` / `pushq`로 쿼드 워드 크기의 데이터를 `pop` / `push`
  
이 정도를 배웠다고 할 수 있겠네..

뭔가 내 머릿속에 어셈블리가 기본적으로

- 어떻게 오퍼랜드를 설정하는지
- 레지스터를 어떻게 사용할 수 있는지(이름에 따른 크기 차이)
- 메모리에 어떻게 접근하게 되는지
- `mov*` / `movz**` / `movs**` 명령어의 특징이 무엇인지

이런 것들은 확실히 들어온 것 같아.

C언어의 **대입 연산자**가 어떻게 어셈블리로 구현되는지를 나타내는 `mov` 명령어와,
즉시값 / 레지스터 / 메모리에 CPU가 어떤 형식으로 접근하는지를 알려주는 느낌이었어..
