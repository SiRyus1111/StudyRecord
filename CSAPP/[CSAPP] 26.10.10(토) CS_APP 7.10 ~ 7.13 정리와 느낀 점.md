## 1. Dynamic Linking with Shared Libraries - 공유 라이브러리를 이용한 동적 링킹

### 정리

1. 정적 라이브러리의 단점
    - 정적 라이브러리를 업데이트 했을 때는 다시 링크를 해줘야한다.
    - 여러 정적 라이브러리가 여러 프로세스에 중복으로 정의되어서
    메모리 공간을 낭비하게 된다.
    
2. 공유 라이브러리
    - 공유 라이브러리는,
    런타임 / 로드 시점에 로드되어 메모리 내의 프로그램과 링크될 수 있는 오브젝트 파일이다.
    - 이렇게 공유 라이브러리가 런타임 / 로드 시점에 링크되는 것을 동적 링크라고 하고,
    동적 링커라고 하는 프로그램에 의해 수행된다.
    - `.so` / `.dll` 확장자를 사용한다.
    
3. 공유 라이브러리의 공유
    - 공유 라이브러리는 정적 라이브러리와 대조적으로 
    실행 파일에 복사되어 내장되지 않고
    여러 실행 파일이 동일한 공유 라이브러리 파일을 사용하게 된다.
    - 공유 라이브러리는 실행 중인 프로세스들 간에 공유될 수 있다.
    (물론 코드에 한정해서)
    
4. 동적 링크
    - 기본적으로는 실행 파일을 생성할 때
    일부 링크 작업을 정적으로 수행하고,
    프로그램이 로드될 때 동적으로 링크 과정을 완료한다.
    - 이 과정 속에서,
    공유 라이브러리의 코드 / 데이터 중 어느 것도
    실행 파일에 복사되지 않는다.
    (물론 로드 시점에 참조를 해결할 수 있도록
    재배치 정보 / 심볼 테이블을 복사하긴 한다.)
    
5. 동적 라이브러리의 링크 시점
    - 동적 라이브러리는 로드 시점 뿐만이 아니라,
    실행 도중에도 로드 / 링크될 수 있다.

### 느낀 점 & 배운 점

결국 공유 라이브러리는 이거야.

> 여러 실행파일들이 공유할 수 있고,
> 여러 프로세스가 공유할 수 있는 라이브러리.

솔직히 나름 정확하지 않아?

이게 정적 라이브러리와의 차이를 보면 더 잘 와닿아.

정적 라이브러리는 
필요한 오브젝트 파일들이 그대로 실행 파일에 복사되고,
그래서 각 프로세스마다 같은 라이브러리라도 각자 메모리에 가지고 있게 되잖아?

공유 라이브러리는 
로드 과정에서 링크를 하기 위한 정보 정도만 정적 링크를 하며
실제 라이브러리는 복사하지 않아서,
그래서 여러 실행 파일이 같은 라이브러리를 공유하고,
여러 프로세스가 같은 메모리 영역의 라이브러리 코드를 공유하게 할 수 있는거지.

결국 내가 생각하는 최대의 차이점은

> 라이브러리를 그대로 실행 파일에 삽입하냐,
> 라이브러리에 대한 단편적인 정보만 들고 라이브러리는 로드할 때 연결하냐

의 차이인 것 같아.

## 2. Position-Independent Code(PIC) - 위치 독립 코드

### 정리

1. 공유 라이브러리가 어느 메모리 주소에 배치되어도 동작하게 하는 방법
    - 공유 라이브러리는 실행될 때 실행 파일과 분리되어있기 때문에
    메모리의 어디에 배치되는지를 미리(링크 시점에서) 알 수 없다.
    - 공유 라이브러리가 메모리의 어디에 배치되든
    공유 라이브러리의 내부 참조 / 공유 라이브러리의 외부 참조 
    / 외부에서의 공유 라이브러리에 대한 참조를 재배치하지 않게 할 필요가 있다.
      - 공유 라이브러리 내부의 참조는
      공유 라이브러리 내부의 참조를 상대 주소로 놓아서
      공유 라이브러리가 메모리의 어디에 위치하든지
      공유 라이브러리 내부의 참조를 수정할 필요가 없게 할 수 있다.
      - 공유 라이브러리 외부에서 해당 공유 라이브러리를 참조하는 경우에는
      별도의 기법(GOT / PLT)이 필요하다.
    - 그리고 이렇게 **공유 라이브러리가 어느 메모리 주소에 배치되어있든 동작하게 하는 방식**을
    **위치 독립 코드(Position-Independent Code, PIC)**라고 한다.
    
2. 모듈 간 외부 참조를 위한 기법 - GOT
    - 공유 라이브러리가 메모리 어디에 올라가든,
    프로세스의 코드 영역과 데이터 영역 사이의 거리는 변하지 않는다.
    - 그렇기 때문에 데이터 영역 시작 부분에 GOT(Global Offset Table)을 만들어서,
    프로그램이 로드될 때 동적 링커가 해당 GOT 안에
    공유 라이브러리의 심볼의 메모리 주소를 적어두고,
    해당 심볼들이 필요할 때 해당 테이블에 접근해서 주소를 읽은 후,
    해당 주소에 접근하는 식으로
    공유 라이브러리와 실행 파일 간의 참조를 해결할 수 있다.
    - 이 방식은 코드의 참조를 재배치하지 않기 때문에, PIC에 적합하다.
    
3. 모듈 간 외부 함수 호출을 위한 최적화 기법 - 지연 바인딩 / PLT
    - 지연 바인딩이란,
    공유 라이브러리의 프로시저를 호출할 때,
    컴파일 / 링크 시점에 프로시저의 주소를 결정하지 않고
    해당 프로시저가 처음 호출될 때 까지 바인딩(공유 라이브러리와 연결)을 미루는 것이다.
      - 이렇게 하면,
      딱 필요한 프로시저만 바인딩을 할 수 있게 된다.
      - 단점은, 프로시저를 처음 호출할 때 상당한 런타임 오버헤드가 발생한다.
      - 하지만, 필요하지 않은 프로시저들의 주소를 일일히 다 찾아서 적어두는 것 보다는 낫다.
    - 지연 바인딩은 GOT / PLT(Precedure Linkage Table)의 상호작용을 통해 구현된다.
    - PLT는 코드 영역의 일부로,
      - GOT의 해당 프로시저의 주소가 비어있다면 
      해당 프로시저에 대해 동적 링크를 수행하고 점프하고
      - GOT의 해당 프로시저의 주소가 이미 있다면 
      해당 프로시저로 바로 점프하는
    - 코드가 각 프로시저에 대해 들어있다.

### 느낀 점 & 배운 점

이번 파트를 요약하면,
결국

> 공유 라이브러리가 실행 파일과 분리되어있고
> 실행 파일과 별개로 임의의 메모리에 적재되는 것 때문에
> 코드에 쌩으로 절대 주소를 박아넣을 수 없으니
> 상대 주소 사용, GOT 사용을 통해 **코드의 참조를 재배치하는 것을 막아주는**
> PIC를 사용한다.

라고 할 수 있어.

결국,
공유 라이브러리가 메모리의 어디에 적재되든
그 공유 라이브러리를 참조하는 실행 파일의 코드와 공유 라이브러리 자체의 코드가
재배치되지 않아도 되도록 하는 방식이 PIC라고 보면 돼.

참조하는 심볼과의 상대적 위치를 알 수 있는 참조의 경우에는
심볼을 참조할 때 절대 주소를 쓰지 않고 상대 주소를 씀으로써
공유 라이브러리가 어떤 메모리 공간에 적재되어도 참조를 재배치할 필요가 없어지고,

실행 시에 주소를 결정해야 되는 심볼의 참조의 경우에는
공유 라이브러리의 심볼들을 참조하는 부분을
GOT의 각 인덱스의 주소를 참조하는 식으로
간접적으로 참조해서
공유 라이브러리가 어떤 메모리 공간에 적재되어도 코드 자체는 수정(참조 재배치)할 필요가 없이
GOT의 값만 갱신되게 하면 되게 하는거지.

그리고 PLT / 지연 바인딩의 개념도 있는데,
이건 근본적으로 공유 라이브러리의 참조 주소 문제를 해결하는건 아니고,
함수를 호출할 때의 최적화를 해주는 부분이랄까..

처음에 공유 라이브러리의 모든 함수의 주소를 다 GOT에 기록해두는건 너무 무거우니
함수를 최초로 호출할 때에 동적 링커로 해당 함수의 주소를 GOT에 기록해두는
최적화 기법이 지연 바인딩인데,

여기서 GOT에 기록이 되어있는지 안되어있는지를 판단하고
기록이 안되어있다면 동적 링커를 호출해서 GOT에 해당 함수에 주소를 기록한 후 점프하고,
기록이 되어있으면 GOT에서 해당 위치로 점프하게 하는 코드가 저장되어있는 테이블이
PLT인거야.
(물론 실제 로직은 좀 다르긴 한데,
이렇게 이해해도 됨.)

### 공유 라이브러리 / 동적 링크 요약 1

1. 여러 실행 파일이 하나의 라이브러리를 공유하고,
여러 프로세스가 메모리에 적재되어있는 하나의 라이브러리를 공유할 수 있는 라이브러리를
공유 라이브러리라고 한다.
2. 공유 라이브러리를 사용하여,
링크 과정에서는 그저 공유 라이브러리 링크에 필요한 단편적인 정보만을 실행 파일에 추가한 채,
로드 시점 / 런타임에 공유 라이브러리를 유연하게 동적으로 링크하는 것을 
동적 링크라고 한다.
3. 공유 라이브러리는 실행 파일과 별개이고, 
실행 파일이 예측하지 못하는 메모리의 임의의 주소에 적재될 수 있으므로,
공유 라이브러리가 메모리의 어디에 적재되든지 
기존 실행 파일 / 공유 라이브러리의 참조를 재배치하지 않아도 되게 만드는
PIC(위치 독립 코드) 방식을 사용할 수 있다.
4. PIC가 기존 실행 파일 / 공유 라이브러리의 참조를 재배치하지 않아도 되게 만드는 방법으로는,
공유 라이브러리 내부 참조의 경우 상대 주소를 사용하는 것이 있고,
공유 라이브러리 외부 참조의 경우 GOT(Global Offset Table)을 사용하는 것이 있다.
5. GOT란, 공유 라이브러리의 각 심볼의 주소를 저장해놓은 테이블로,
해당 테이블을 거쳐 공유 라이브러리의 각 심볼에 접근하게 되어,
실행 파일 / 공유 라이브러리가 공유 라이브러리를 참조하는 경우 
실행 파일 / 공유 라이브러리의 코드를 수정할 필요가 없게 한다.
(코드에서는 오직 GOT의 해당 심볼의 주소가 저장되어있는 인덱스만 참조)
6. 공유 라이브러리를 사용할 때 함수 호출 시의 최적화 기법으로는
지연 바인딩이 있고, 지연 바인딩을 보조하는 PLT(Precedure Linkage Table)이 있다.
7. 지연 바인딩이란, 
공유 라이브러리를 링크할 때 모든 공유 라이브러리의 함수를 링크하는게 아닌 
공유 라이브러리의 특정 함수를 호출할 때에 해당 함수만 동적으로 링크하는 것이다.
8. 지연 바인딩을 위해, PLT가 사용될 수 있다.
PLT란, 
해당 함수를 가리키는 GOT의 인덱스가 비어있는 경우 동적으로 링크하게 하고
해당 함수를 가리키는 GOT의 인덱스가 채워져있는 경우 바로 해당 함수로 점프하게 하는
코드가 들어있는 테이블이다.

## 3. Library Interpositioning - 라이브러리 인터포지셔닝

### 정리

1. 라이브러리 인터포지셔닝
    - 라이브러리 인터포지셔닝이란,
    공유 라이브러리의 함수에 대한 호출을 가로채고
    사용자 정의 코드를 실행하는 기법이다.
    - 인터포지셔닝을 사용하면,
    특정 라이브러리 함수가 호출된 횟수를 추적하거나,
    해당 함수의 입력 / 출력 값을 검증하고 추적할 수 있고,
    아예 완전 다른 구현체로 해당 함수를 대체할 수도 있다.
    - 라이브러리 인터포지셔닝은 컴파일 시점 / 링크 시점 / 런타임 시점에 발생할 숭 맀다.
    
2. 라이브러리 인터포지셔닝의 동작
    - 인터포지션할 함수가 주어지면,
    해당 함수와 시그니처가 동일한 래퍼 함수를 생성하고,
    특정 인터포지션 매커니즘을 사용해서
    시스템이 래퍼 함수를 호출하도록 유도한다.
    - 래퍼 함수는 일반적으로 자체 로직을 실행 / 대상 함수를 호출하고
    그 반환 값을 호출자에게 전달한다.
    
3. 컴파일 시점 인터포지셔닝
    - `#define` 등으로 인터포지션할 함수의 이름을 래퍼 함수로 대체하고,
    래퍼 함수를 호출하도록 시킨다.
    - 그리고 컴파일 시 `-I` 옵션을 주어 기존 헤더보다
    사용자가 정의한 헤더를 먼저 참조하게 한다.
    - 구현이 매우 직관적이고 간단하지만,
    소스 코드를 재컴파일해야하는 문제가 발생할 수 있다.
    그래서 소스 코드를 재컴파일할 수 있는 경우에만 사용 가능하다.
    
3. 링크 시점 인터포지셔닝
    - 각 함수에 `--wrap` 플래그를 활용해서,
    인터포지션할 함수를 나타내는 심볼을 호출하는 부분을
    `__wrap_(symbol)`로 연결하고,
    진짜 심볼은 `__real_(symbol)`으로 바꿔서 남겨두는 방식이다.
    - 래퍼 함수를 `__wrap_(symbol)` 식으로 작성한 후,
    진짜 함수를 호출하려고 할 때는 `__real_(symbol)`을 호출하게 작성한다.
    - 컴파일 / 링크 시 `-Wl` / `--wrap` 옵션을 전달한다.
    - 소스 코드를 수정하지 않고 재링크만으로 인터포지셔닝이 가능하지만,
    재링크를 해야하므로 오브젝트 파일들이 남아있어야하고,
    실행 파일에는 적용할 수 없다.
    
4. 런타임 인터포지셔닝
    - 동적 링커 / 로드의 `LD_PRELOAD` 환경변수를 이용해서,
    동적 로더가 공유 라이브러리를 로드할 때, 
    `LD_PRELOAD`에 지정된 공유 라이브러리를 먼저 로드하게 해서,
    심볼을 찾을 때 먼저 로드된 라이브러리에서 심볼을 발견하면 즉시 검색을 종료하도록 한다.
    - 소스 코드나 오브젝트 파일이 없고 실행 파일만 있어도 적용 가능하지만,
    동적 링크를 사용하는 프로그램만 적용 가능하고
    로딩 순서 차이로 인한 디버깅이 까다로울 수 있다.

### 느낀 점 & 배운 점

솔직히 이번 파트는 너무 어려워서 대강 흝고 지나간 느낌이 크네..

그냥 라이브러리 인터포지셔닝을 한 문장으로 설명하면 이거야.

> 함수를 호출하는 부분을 원래 함수를 래핑한 사용자 정의 함수(주로 래퍼 함수)로 가로채서
> 사용자 정의 함수를 실행하게 한다.

나 솔직히 이게 왜 쓸모있을지는 잘 모르겠었거든?

근데 라이브러리 인터포지셔닝은 생각보다 다양한 곳에 쓸 수 있더라고?

예를 들어

- 디버깅(사용자 정의 함수로 래핑해서 해당 함수에 대한 정보를 알 수 있음)
- 성능 측정(특정 함수가 실행되는데 걸리는 시간을 따로 측정할 수 있음)
- 기능 대체 / 테스트(특정 라이브러리 함수나 시스템 콜을 대체하여 단위 테스트나 에러 상황 시뮬레이션을 수행할 수 있음)

이 정도가 있겠네..

결국 **함수 실행을 가로채서 테스트하기 좋다**는거임..

그리고 내가 생각해본게 있는데,
결국 많이 쓰이는건 컴파일 시점 / 링크 시점보다 런타임 인터포지셔닝이 훨씬 더 쓰기 쉬울 것 같다는 생각이 들었어.

이게 왜 그러냐면,

- 컴파일 시점 인터포지셔닝 : 원본 소스 코드가 필요함
- 링크 시점 인터포지셔닝 : 원본 소스 코드는 불필요함, 오브젝트 파일이 필요함
- 런타임 인터포지셔닝 : 원본 소스 코드 / 오브젝트 파일은 불필요함, 실행 파일만 있으면 됨

이렇기 때문인데,

상식적으로 프로그램의 원본 소스 코드와 오브젝트 파일을 구하는게 쉬울까
실행 파일을 구하는게 쉬울까?

결국 실행 파일만 있는 경우(+ 공유 라이브러리가 있는 경우)에 테스트하려면 
런타임 인터포지셔닝을 해야하는거고,
오브젝트 파일이 남아있으면 링크 시점 인터포지셔닝을 해도되는거고,
소스코드마저 남아있으면 컴파일 시점 인터포지셔닝을 해도되는거지.

그리고 이건 어떻게 보면 헷갈리기 쉬운 지점인데,
나 처음에 컴파일 타임 / 링크 타임에는
공유 라이브러리가 연결되지 않는데
어떻게 호출을 가로챌 수 있을지 모르겠다는 생각을 했었는데,

결국 공유 라이브러리가 연결되기 전에
미리 가로채는거야.

그렇게 가로채는 방법은

- `#define`으로 컴파일 시점에 원래 함수의 이름 가로채기
- `-Wl` / `--wrap`을 사용해서
링크 시점에 `wrap` 버전 / `real` 버전을 분리하게해서 `wrap` 버전 함수 호출하도록 하게 하기

이렇게 되는거고.

그리고 그렇다면 런타임 인터포지셔닝은 이름만 보면

- 로드 시점에 공유 라이브러리가 링크될 수도 있는데 어케함?

이라는 의문이 들 수 있는데,

런타임 인터포지셔닝은 
`LD_PRELOAD` 환경 변수에 사용자 정의 함수(공유 라이브러리 파일)를 지정해놓고
동적 링커가 공유 라이브러리의 함수보다
`LD_PRELOAD`에 들어가있는 사용자 정의 함수(공유 라이브러리 파일)를 먼저 링크하도록 하는거잖아?

`LD_PRELOAD`에 들어가있는 함수(공유 라이브러리 파일)는
로드 시점 / 런타임에 가장 먼저 링크되니까,
로드 시점에 공유 라이브러리가 링크되어도 `LD_PRELOAD`에 있는게 먼저 링크되니까
문제 없어.
