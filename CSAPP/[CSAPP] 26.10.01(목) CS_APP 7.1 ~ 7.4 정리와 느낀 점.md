## 1. Static Linking - 정적 링킹

### 정리

1. 링크 기본
    - 정적 링커는 Relocatable(재배치 가능) 오브젝트 파일을 받아서,
    실행할 수 있는 파일을 출력한다.
    - 입력으로 주어지는 재배치 가능한 오브젝트 파일은 다양한 코드 / 데이터 섹션으로 구성되고,
    각 세션은 연속된 바이트열이다.

2. 실행 파일을 빌드하기 위한 작업
    - 1. 심볼 해석(Symbol Resolution)
      - 함수 / 전역 변수 / 정적 변수 등을 나타내는 심볼들의
      심볼 참조와 심볼 정의를 연결한다.
    - 2. 재배치(Relocation)
      - 코드 및 데이터 섹션을 생성해서,
      각 심볼 정의에 메모리 위치를 할당하고
      해당 심볼을 참조하는 모든 부분을 수정해서 메모리 위치를 가리키도록 하는 식으로
      섹션을 재배치한다.
      - 링커는 재배치 엔트리라는 상세한 지침으로 이런 재배치 작업을 자동으로 수행한다.

### 느낀 점 & 배운 점

이번은 튜토리얼 파트의 튜토리얼이라고 할만한 파트였어.

결국 링커는

재배치 가능한 오브젝트 파일을 받아서,
실행 파일을 출력하는 프로그램이고,

실행 파일을 생성하는 과정은

- 함수 / 전역 변수 / 정적 변수들의 참조 / 정의를 서로 연결하는 심볼 해석
- 각 심볼 정의에 메모리 위치를 할당하고 해당 심볼의 참조들을 수정해서
해당 메모리 위치를 가리키도록 하는 재배치

이렇게 두 단계가 핵심이야.

근데 참조 / 정의를 연결한다는게 이해가 잘 안될 수도 있는데,
해당 심볼이 정의되어있는 곳과 실제로 해당 심볼을 참조하는 곳들을
이어준다는거야.

이게 여러 오브젝트 파일에 걸쳐 같은 심볼이 참조될 수 있다보니까,
링크 과정에서 이걸 해주는거지.

그리고 그렇게 정의된 심볼을 참조하는 부분들이
정확히 어떤 메모리 주소를 참조하는지를 표시해주는게 재배치야.
정확히 말하면 코드를 수정해서 심볼들을 참조하는 부분을
명확한 메모리 주소로 고쳐준다고 할 수 있겠네.
물론 각 심볼들을 메모리(파일)에 배치해주는게 메인이긴 하다만..

이게 끝이야.

앞으로는 

- 심볼 해석
- 재배치

에 대한 내용을 배울 것 같아.

물론 이것들은 정적 링킹에 한정된 이야기지만.

결국

1. 심볼(정적 변수 / 전역 변수 / 함수)의 정의와 참조를 잇고,
2. 심볼을 최종 메모리 위치에 배치하고, 
그에 맞춰 심볼에 대한 참조를 하는 부분을 해당 메모리 위치들을 가리키도록 수정하는 것이

정적 링크 과정이라고 할 수 있겠네.

## 2. Object Files - 오브젝트 파일

### 정리

1. 오브젝트 파일의 종류
    - 오브젝트 파일은 세 종류로 나뉜다.
      - 재배치가능 오브젝트 파일 : 
      다른 재배치가능한 오브젝트 파일과 결합해서
      실행가능한 오브젝트 파일을 생성하는 바이너리 코드 / 데이터를 포함한 파일
      - 실행가능 오브젝트 파일 :
      실제 실행이 가능한 바이너리 코드 / 데이터를 포함한 파일
      - 공유 오브젝트 파일 :
      로드 시점이나 실행 시점에 메모리에 로드되어
      동적으로 링크될 수 있는 특수한 유형의 재배치가능한 오브젝트 파일
    - 컴파일러와 어셈블러는 재배치가능한 오브젝트 파일을 생성하고,
    링커는 해당 파일들로 실행가능한 오브젝트 파일을 생성한다.
    
2. 오브젝트 파일의 포맷(규격)
    - 오브젝트 파일도 여러 포맷이 있다.
      - 오브젝트 파일 내부를 어떻게 구성할지 정해놓은 포맷이라고 할 수 있다.
    - 초기 유닉스에서는 `a.out` 포맷을 사용했고,
    윈도우에서는 `PE` 포맷을 사용한다.
    맥OS에서는 `Mach-O`를 사용하고,
    현대 `x86_64` 리눅스 / 유닉스 시스템에서는 `ELF`를 사용한다.
    (이 책에서는 `ELF`를 기준으로 오브젝트 파일을 설명한다.)
    - 링커가 오브젝트 파일을 읽기 위해,
    이런 포맷들을 정해서 사용한다.

### 느낀 점 & 배운 점

이번은 오브젝트 파일의 종류와 규격에 대한 내용이었네.

오브젝트 파일은

- 재배치가능(relocatable) 오브젝트 파일
  - 링커로 엮어서 실행가능한 오브젝트 파일을 만드는데 사용된다.
- 실행가능(excutable) 오브젝트 파일
  - 실제로 실행가능한 오브젝트 파일이다.
- 공유(shared) 오브젝트 파일
  - 동적 링크를 하는데 사용되는 오브젝트 파일이다.
  
이 정도로 이해했어.

결국 지금 당장의 정적 링크에서 우리가 알아볼만한건
사실상 재배치가능 오브젝트 파일이겠네.

그리고 이 오브젝트 파일도 정해진 형식(포맷)이 있어야
링커가 재배치가능 오브젝트 파일을 읽고
실행가능 오브젝트 파일을 생성할 수 있기 때문에,

정해진 포맷으로 오브젝트 파일을 구성한다고 이해했어.

책에서는 `ELF` 포맷을 써서 설명을 한다고 하네.
(물론 다른 포맷과 비교해서 링크 방식이 크게 다르지는 않대.)

다음 챕터에서는 이 `ELF` 포맷을 가지고,
재배치가능 오브젝트 파일이 어떻게 생겼고 어떻게 돌아가는지를 배울 것 같아서 기대가 되네..

## 3. Relocatable Object Files - 재배치 가능 오브젝트 파일

### 정리

1. `ELF` 포맷 재배치가능 오브젝트 파일의 구조
    - 섹션 헤더 테이블 : `ELF` 파일에 들어있는 각 섹션에 대한 메타데이터
    - `ELF` 헤더 : `ELF` 파일 전체에 대한 메타데이터
      - `ELF` 파일임을 나타내는 매직 넘저
      - 해당 파일에 대한 시스템 정보(바이트 순서 / 워드 크기 / 머신 유형 등)
      - 해당 파일의 타입(relocatable / executable 등)
      - 세션 헤더 테이블의 파일 오프셋 등
    - `ELF` 헤더와 섹션 헤더 테이블 사이에 섹션들이 위치한다.
      - `.text` : 기계어 코드
      - `.rodata` : 읽기 전용 데이터
      - `.data` : 초기화된 정적 / 전역 데이터들
      - `.bss` : 초기화되지 않은(+ 값이 0인) 정적 / 전역 데이터들
        - 초기화되지 않은 변수를 굳이 메모리에 올리지 않고
        해당 변수들에 대한 정보만 포함하기 위해서 `.data` / `.bss`를 분리한다.
      - `.symtab` : 심볼 테이블
        - 함수 / 전역 변수 / 정적 변수에 대한
        정의 / 참조를 저장하는 테이블
      - `.rel .text` : 다른 파일과 링크(재배치)할 때 수정되어야할 코드 위치 목록
      - `.rel .data` : 다른 파일과 링크(재배치)할 때 수정되어야할 정적 / 전역 데이터 위치 목록
      - `.debug` : 디버깅 관련 정보(심볼 / 타입 등을 테이블로 저장)
      - `.line` : 라인 관련 정보
        - 원본 소스 코드의 각 라인과 기계어 사이의 대응 관계를 정리해놓은 테이블
      - `.strtab` : 문자열 테이블
        - `.symtab` / `.debug` / 섹션 헤더의 각 이름들을 저장하기 위한 공간

### 느낀 점 & 배운 점

이번에는 솔직히 암기성이 짙은 내용이었는데,

쉽게 설명하면
(여기서 데이터라는건 심볼 테이블에 기록되는 정적 / 전역 데이터)

- `ELF` 헤더 : 해당 파일 자체의 메타데이터
- 섹션 헤더 테이블 : 각 섹션의 메타데이터
- `.text` : 바이너리 코드
- `.rodata` : 읽기 전용 데이터(Read Only DATA)
- `.data` : 초기화 된 데이터
- `.bss` : 초기화 안된 데이터
- `.symtab` : 심볼 테이블
  - 이거 컴파일러 배울 때 배웠음. 
  - 함수 / 전역 / 정적 데이터들의 다양한 정보들을 모아놓은 테이블!
- `.rel .text` : 다른 파일과 링크할 때 수정되어야할 코드 위치들(RELocation)
- `.rel .data` : 다른 파일과 링크할 때 수정되어야할 데이터 위치들
  - 다른 코드의 코드 / 데이터를 참조하고 있는 경우 같은 경우에는
  링크 과정(재배치)에서 해당 코드 / 데이터의 메모리 주소를 표기해줘야 함
- `.debug` : 디버깅 할 때 필요한 정보들(심볼 / 타입 등을 저장한 테이블)
- `.line` : 기계어와 원본 소스 코드 줄 번호 사이의 대응관계를 저장하는 테이블
- `.strtab` : 다른 이름들을 저장하기 위한 문자열 테이블

이 정도로 이해했어.

이름은 보고 적어도
세부 내용을 스스로 적은거니까 ㅇㅋ지 않을까?

그리고 앞에서 설명한 심볼 해석 단계에서는
`.symtab`(심볼 테이블)같은게 쓰일테고,

재배치 단계에서는
`.rel`이 붙은 섹션들이 쓰이겠지?

## 4. 요약

1. 링크는 각 재배치가능 오브젝트 파일을 하나의 실행 파일로 만들어주는 과정이며,
    - 1. 각 심볼(데이터 / 함수)의 정의 / 참조하는 곳을 잇는 심볼 해석 단계와
    - 2. 각 심볼의 최종 메모리 주소를 확정하고
    해당 심볼들을 참조하는 곳의 코드를 해당 메모리 주소를 가리키도록 하는 재배치 단계로,
    - 두 단계로 이루어진다.
2. 오브젝트 파일은 다음과 같은 종류가 있다.
    - 재배치가능 오브젝트 파일 : 링크할 때 사용하는 오브젝트 파일
    - 실행가능 오브젝트 파일 : 링크의 결과로 나오는 실제 실행할 코드와 데이터가 담겨있는 오브젝트 파일
    - 공유 오브젝트 파일 : 동적 링크를 통해 링크되는 오브젝트 파일
3. 오브젝트 파일은 다양한 포맷이 있는데, 그중 `ELF`의 재배치가능 오브젝트 파일은
    - `ELF` 헤더 : 해당 오브젝트 파일에 대한 정보
    - 섹션 헤더 테이블 : 각 섹션들에 대한 정보
    - `.text` : 바이너리 코드
    - `.rodata` : 읽기 전용 데이터
    - `.data` : 초기화된 데이터
    - `.bss` : 초기화되지 않은(+ 0으로 초기화된) 데이터
    - `.symtab` : 각 함수 / 데이터들의 정보가 정리된 심볼 테이블
    - `.rel .text` : 링크 과정에서 수정될 코드 위치들
    - `.rel .data` : 링크 과정에서 수정될 데이터 위치들
    - `.debug` : 디버깅 과정에서 사용되는 정보(심볼 / 타입 등)들의 테이블
    - `.line` : 소스 코드와 바이너리 코드 사이를 이어주는 테이블
    - `.strtab` : 다른 이름들을 저장하기 위한 문자열 테이블
    - 이런 섹션들로 구성되어있다.
