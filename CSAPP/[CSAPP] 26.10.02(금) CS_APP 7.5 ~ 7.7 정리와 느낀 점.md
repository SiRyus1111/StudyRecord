## 1. Symbols and Symbol Tables - 심볼과 심볼 테이블

### 정리

1. 링커 입장에서에 심볼의 종류
    - 전역 심볼(Global Symbols) : 전역에 정의되어 여러 개의 오브젝트 파일이 공유하는 심볼
    - 외부 심볼(Externals) : 타 오브젝트 파일에 정의되어있는 전역 심볼
    - 지역 심볼(Local Symbols) : 해당 오브젝트 파일에서만 접근할 수 있는 심볼
      - 지역 변수와 다르게, 
      해당 프로그램 실행 동안 유지되지만
      해당 오브젝트 파일에서만 접근할 수 있는 심볼이다.
      (그렇기 때문에 링커가 위치를 고려해야함)
      - 지역 변수는 `.symtab`에 저장 자체가 되지 않는다.
      (지역 변수는 그저 런타임 스택에서 관리하기 때문이다.)
      - 대표적으로 `static`으로 선언한 변수 / 함수 등이 있다.
      
2. 심볼 테이블
    - 심볼들의 세부사항을 모아놓은 테이블이다.
    - 해당 테이블은 `.symtab`에 저장된다.
    - 각각의 엔트리는
      - `name` : `.strtab`에서 해당 심볼의 이름을 나타내는 문자열이 시작하는 위치(오프셋)
        - 끝은 널 문자로 나타내짐
        - 문자열의 길이는 일정하지 않기 때문에 이렇게 포인터같은 방식을 사용함
      - `value` : 심볼의 주소
      - `size` : 해당 심볼의 크기
      - `type` : 해당 심볼이 데이터인지 함수인지 여부
      - `binding` : 해당 심볼이 로컬인지 전역인지 여부
      - `section` : 해당 심볼이 어느 섹션에 할당되는지를 나타내는 섹션 헤더 테이블의 인덱스
    - 이렇게 나뉜다.
    
3. 특수한 섹션들
    - 섹션 헤더 테이블에 항목이 없는 세 가지의 특수한 의사 섹션이 있다.
      - `ABS` : 재배치되면 안되는 심볼
      - `UNDEF` : 해당 오브젝트 파일에서 정의되지 않은 심볼(Externals)
        - 재배치가능 오브젝트 파일에서는 해당 심볼이 어느 섹션에 있는지 알 수 없음
      - `COMMON` : 아직 할당되지 않은, 초기화되지 않은 심볼
        - (해당 섹션에서 `value`는 정렬 요구사항을 나타내고,`size` 필드는 최소 크기를 나타냄)
        - `GCC 10`부터는 해당 의사 섹션의 심볼도 자동으로 `.bss`에 배치된다.
    - 해당 의사 섹션들은 재배치가능 오브젝트 파일에서만 존재한다.

### 배운 점 & 느낀 점

이번 파트는

- 링커 관점에서의 심볼은 어떤 종류로 나뉘나
- 재배치가능 오브젝트 파일의 심볼 테이블 엔트리는 어떻게 나뉘나
- 재배치가능 오브젝트 파일이어서 생기는 특수한 의사 섹션들은 뭐가 있나

이 세 가지 내용이 전부야.

첫 번째부터 해보자면,

- 링커 관점의 심볼은,
  - 전역 심볼(Global Symbols) : 말 그대로 해당 오브젝트 파일에 정의되어있으며 
  다른 오브젝트 파일과 공유하는 심볼
  - 외부 심볼(Externals) : 해당 객체가 참조하고 있지만 해당 객체에 정의되어있지 않은,
  다른 오브젝트 파일에 정의되어있을 것으로 여겨지는 전역 심볼
  - 지역 심볼(Local Symbols) : 해당 프로그램이 종료될 때 까지 남아있으나(링크의 범위에 있으나)
  해당 오브젝트 파일에서만 사용하는 심볼
  
이렇게 이해했고,

- 재배치가능 오브젝트 파일의 심볼 테이블 엔트리는,
  - 이름(`name`) : `.strtab`의 특정 문자열을 가리키는 정보
  - 값(`value`) : 해당 심볼의 주소(해당 심볼이 속한 섹션으로부터의 오프셋)
  - 크기(`size`) : 해당 심볼의 크기
  - 타입(`type`) : 해당 심볼이 객체인지 함수인지를 나타내는 정보
  - 바인딩(`binding`) : 해당 심볼이 전역인지 지역인지를 나타내는 정보
  - 섹션(`section`) : 해당 심볼이 어느 섹션에 정의되어있는지를 나타내는
  섹션 헤더 테이블의 인덱스를 가리키는 정보
  
이렇게 이해했고,

- 특수한 의사 섹션들은
  - `ABS` : 해당 심볼의 주소가 절대적이어야함(재배치되면 안됨)
  - `UNDEF` : 해당 심볼이 해당 오브젝트 파일에 정의되어있지 않음
    - 재배치가능한 오브젝트 파일은 타 오브젝트 파일을 알지 못하기 때문에..
  - `COMMON` : 아직 해당 심볼이 초기화되지 않음
    - `.bss`와 헷갈릴 수 있는데,
    `.bss`에는 초기화되지 않은 정적 변수, 0으로 초기화된 정적 / 전역 변수가 들어가고,
    해당 의사 섹션에는 초기화되지 않은 전역 변수가 들어간다.
    
이렇게 이해했어.

다시 되짚어보니까,

심볼 테이블 엔트리의 정보들과
특수한 의사 섹션들로
맨앞에서 설명한 세 가지의 심볼 유형들을 표현할 수 있겠다는 생각이 드네.

- 전역 심볼 : 바인딩이 `GLOBAL`, 섹션이 `UNDEF`가 아님
- 외부 심볼 : 바인딩이 `GLOBAL`, 섹션이 `UNDEF`임
- 지역 심볼 : 바인딩이 `LOCAL`임

이렇게 말이야.

## 2. Symbol Resolution - 심볼 해석

### 정리

1. 링커가 각 심볼에 대한 참조와 정의를 연결할 때 생기는 문제
    - 참조와 동일한 오브젝트 파일에 정의된 지역 심볼에 대한 참조의 경우,
    컴파일러 선에서 각 지역 심볼에 대해 하나의 정의만 허용하게 함으로써
    각 심볼에 대한 참조와 정의를 연결할 때 문제가 발생하지 않게한다.
    - 참조와 정의가 다른 오브젝트 파일에 있는 전역 심볼의 경우,
    컴파일러는 해당 전역 심볼에 대한 참조에 대한 처리를 링커로 넘기고,
    링커에서는 오브젝트 파일 중 어느 곳에서도 참조된 심볼에 대한 정의를 찾을 수 없는 경우
    오류 메시지를 출력하는 식으로 문제를 처리한다.
      - 전역 심볼에 대한 심볼 해석은
      여러 오브젝트 파일이 동일한 이름의 전역 심볼을 정의할 수 있기 때문에,
      링커는 오류를 표시하거나 어떤 식으로든 정의 중 하나를 선택하고 나머지는 무시하게 한다.

### 느낀 점 & 배운 점

이번 챕터는 말그대로 심볼 해석 튜토리얼 챕터야.

지역 심볼과 전역 심볼에 대한 심볼 해석(정의와 참조 잇기)을 진행할 때,
어떻게 동일한 심볼이 여러 개의 정의를 가지는 것을 막고,
심볼의 정의를 찾을 수 없는 경우에는 어떻게 하는지를 설명하고 있는 것 같아.

솔직히 처음에는 이해가 잘 안됐는데,

결국 요약하면 이거야.

- 지역 심볼의 경우, 컴파일러가 정의가 중복되지 않았는지 검사를 해준다.
- 전역 심볼의 경우, 컴파일러는 그저 
해당 전역 심볼의 정의와 참조의 연결에 대한 처리를 링커에 넘기고,
링커는 여러 오브젝트 파일을 보며 
해당 전역 심볼에 대한 정의가 없는지, 아니면 중복으로 정의되어있는지를 검사한다.

난 이렇게 생각해.

## 3. How Linkers Resolve Multiply Defined Global Symbols - 링커가 다중 정의된 전역 심볼을 해석하는 방법

### 정리

1. 리눅스에서 이름이 동일한(정의가 중복된) 전역 심볼을 처리하는 방법
    - 리눅스에서는 정의가 중복된 전역 심볼을 처리하기 위해
    컴파일러에서 전역 심볼에 대한 weak / strong을 나누고,
    재배치가능 오브젝트 파일의 심볼 테이블에 암시적으로 인코딩한다.
      - strong : 함수 / 초기화된 전역 변수
      - weak : 초기화되지 않은 전역 변수
    - 그리고, 이 세가지 규칙을 이용해 중복 정의된 전역 심볼 문제를 해결한다.
      - 1. 동일한 이름의 strong 전역 심볼은 허용하지 않는다.
      - 2. 동일한 이름의 strong 전역 심볼 하나와 weak 전역 심볼 여러개가 있는 경우,
      strong 전역 심볼을 선택한다.
      - 3. 동일한 이름을 가진 여러 개의 weak 전역 심볼만 있는 경우,
      그 중에 하나를 임의로 선택한다.

### 배운 점 & 느낀 점

이번 파트는 별게 없었어.

결국 정의가 중복된 경우에 리눅스 시스템에서는 어떻게 처리하는지를 보여주는건데,

- strong 전역 심볼 : 함수 / 초기화된 전역 변수
- weak 전역 심볼 : 초기화되지 않은 전역 변수

이렇게 놓고,

1. strong 전역 심볼이 중복 정의되어있는 경우에는 오류를 뱉고,
2. strong이 한 개 + weak이 여러 개가 중복 정의되어있는 경우에는 strong을 택하고,
3. weak만 여러 개 중복 정의되어있는 경우에는 임의로 하나를 택하는 것으로
    
이렇게 전역 심볼의 중복 정의를 다루는거지.

그런데 책에서는 여기서 문제가 발생할 수 있다고 해.

이게 `int`(4바이트) 변수를 초기화해놓고
다른 파일에서는 `double`(8바이트) 변수를 같은 이름으로 쓰고 초기화하지 않은 상태로 쓴다면

```c
// a.c
int x = 12345;


// b.c
double x;

void foo() {
    x = -0.0;
}
```

(이렇게)

정책 상 링커는 `a.c`에 정의되어있는 `int` 형의 변수로 중복 정의를 처리하겠지만,
해당 오브젝트 파일만 보는 컴파일러는 `b.c`에 정의되어있는 `double` 형의 변수도 `x`로 보기 때문에
코드에서 `double` 형 `x`(링커에서는 `int`형인..)에 대입을 해버리면

기존 `int`가 4바이트기 때문에 8바이트인 `double` 변수는 바이트가 초과되어서
뒤쪽을 덮어쓸 수 있다고 하더라고.

결국 타입 검사는 하지 않고(함수 / 변수인지 정도만 검사함)
심볼의 이름만 보고 심볼 해석을 하기 때문에 이런 문제가 발생하지.
(이런 문제는 찾아내기 어렵다고도 하고..)
(나도 내가 무슨 말을 하는지 모르겠다..)

## 4. Linking with Static Libraries - 정적 라이브러리와 링크하기

### 정리

1. 정적 라이브러리
    - 링커는 실제로 무조건 재배치가능 오브젝트 파일들을 읽어와
    이를 하나로 연결해서 실행 파일을 생성하지는 않는다.
    - 컴파일 시스템은 
    관련된 오브젝트 파일들을 정적 라이브러리라고 하는 단일 파일로 묶는 매커니즘을 제공하고,
    이 파일을 링커에 입력으로 전달할 수 있다.
    - (기존에는 컴파일러 자체에서 표준 함수를 기계어로 변환하는 기능을 넣거나,
    한 파일에 모든 표준 함수를 넣거나 해서 해결했지만,
    전자는 표준 함수가 많아지면서 처리가 어려워졌고,
    후자는 하나의 파일이 커지고 수정 사항이 발생하면 그 하나의 파일을 다시 컴파일해야했기 때문에
    정적 라이브러리라는 형식으로,
    여러 재배치가능 오브젝트 파일을 하나로 묶고
    실제 실행 파일에는 필요한 오브젝트 파일만 골라 넣음으로써 그런 문제들을 해결할 수 있다.)
    - 정적 라이브러리란,
    여러 오브젝트 파일들을 하나의 파일로 패키징하고,
    링크 시점에는 필요한 오브젝트 파일만 링크되게 하는 형식이다.
    - 딱 필요한 오브젝트 파일만 링크하게 되므로
    전체 오브젝트 파일을 링크하는 것에 비해 실행 파일 크기도 줄어들고,
    프로그래머는 소수의 라이브러리 파일 이름만 포함시키면 된다.
    - 정적 라이브러리는 `.a`(archive)라는 확장자를 사용한다.

### 느낀 점 & 배운 점

이번에는 정적 라이브러리에 대해 배웠어.

근데 솔직히 별거 없어.
정적 라이브러리를 한 문장으로 요약하면,

> **필요한 오브젝트 파일만 꺼내쓸 수 있게** 오브젝트 파일들을 모아놓은 상자

정도로 요약할 수 있겠네.

이게 결국,

- 컴파일러에 구현을 포함하는 방식
  - 라이브러리와 컴파일러 분리 안됨 / 필요한 코드만 링크됨 / 사용하기 편함
- 거대한 `.o` 하나에 구현을 전부 담아 링크하는 방식
  - 라이브러리와 컴파일러 분리됨 / 필요한 코드만 링크 되지 않음 / 사용하기 편함
- `.o`를 각각 링크하는 방식
  - 라이브러리와 컴파일러 분리됨 / 필요한 코드만 링크됨 / 사용하기 불편함
  
이렇게 기존 방식들이 각각 어느 부분에서는 단점이 있었는데,

정적 라이브러리는

1. 컴파일러와 분리된 `.a` 파일을 사용하므로 라이브러리와 컴파일러 분리됨
2. `.a` 파일 중 필요한 `.o` 파일만 링크되므로 필요한 코드만 링크됨
3. 일일히 `.o`를 링크할 필요 없고 `.a` 파일 하나만 링크해주면 되기 때문에 사용하기 편함

이렇게 앞서 설명한 모든 방식의 장점을 쏙쏙 가져가는 방식이라고 이해했어.

그리고 마지막으로 이게 솔직히 그냥 봤을 때는 심볼 해석과 관련 있다고 보기에는 뭔가 애매해보이잖아?
그냥 재배치가능 오브젝트 파일을 어떻게 편하게 링크하는지를 다루는 것 같지.

근데 결국 저렇게 필요한 오브젝트 파일을 고르는 과정이,
정의와 참조를 잇는 심볼 해석 과정과 깊은 연관이 있어서 그래.

필요한 오브젝트 파일을 고른다는 것은
결국 참조되는(미해결된 심볼의 정의가 있는) 오브젝트 파일을 고른다는거고,
그렇게 정의가 있는 오브젝트 파일과 참조하는 오브젝트 파일을 잇는게
심볼 해석이니까.

이 챕터는 결국

> 여러 오브젝트 파일에 대해 심볼 해석을 할 때
> 필요한 오브젝트 파일만을 링크하기 위해서
> 이런 기능이 사용된다.

라는걸 알려주는거야.

재배치가능 오브젝트 파일과 실행 파일 사이에 계층을 하나 더 깔아주는거지.

## 5. How Linkers Use Static Libraries to Resolve References - 링커가 참조를 해석하기 위해 정적 라이브러리를 사용하는 방법

### 정리

1. 정적 라이브러리 링크 문제
    - 정적 라이브러리를 링크할 때,
    순차적으로 각 파일들의 심볼들을 확인한다.
    - 링커가 정적 라이브러리를 읽을 때,
    **지금까지 발견된** 정의가 없는 심볼을 해결하는데 필요한 오브젝트 파일만 
    정적 라이브러리에서 꺼내게 된다.
    - 만약 정적 라이브러리가 
    해당 라이브러리의 심볼을 참조하는 오브젝트 파일보다 먼저 읽힌 경우,
    **지금까지 발견된** 정의가 없는 심볼을 해결하는데 필요한 오브젝트 파일만
    정적 라이브러리에서 꺼내므로,
    추후에 링커가 읽는 해당 정적 라이브러리를 참조하는 오브젝트 파일은
    해당 정적 라이브러리를 읽을 때 반영이 되지 않는다.
    
2. 정적 라이브러리 링크 문제의 해결법
    - 해결법은 간단하다.
    - 무조건 정적 라이브러리보다 해당 정적 라이브러리의 오브젝트 파일을 참조하는 오브젝트 파일을
    먼저 링커로 읽으면 된다.
    - 같은 정적 라이브러리 내의 참조의 경우에는
    정의가 없는 심볼이 있을 경우 해당 심볼의 정의를 해당 정적 라이브러리 내에서 찾아주기 때문에
    링크 문제가 발생하지는 않는다.
    - 정적 라이브러리가 정적 라이브러리를 참조하는 경우에는
    참조가 있는 정적 라이브러리를 먼저 읽고 정의가 있는 정적 라이브러리를 나중에 읽으면 된다.
    - 정적 라이브러리가 서로를 참조하는 경우에는
    `A -> B -> A`순서로 링크해주면 해결된다.

### 느낀 점 & 배운 점

정적 라이브러리의 링크 문제는 결국,

> **현재까지 읽은** 정의가 없는 심볼을 
해결하는데 필요한 오브젝트 파일만을 정적 라이브러리에서 꺼내기 때문에 발생한다.

라고 할 수 있어.

**현재까지 읽은** 정의가 없는 심볼을 기반으로 오브젝트 파일을 고르기 때문에,
정적 라이브러리를 먼저 읽고 해당 정적 라이브러리의 심볼을 참조하는 파일을 나중에 읽으면
정적 라이브러리를 읽을 때 해당 라이브러리를 참조하는 심볼들을 고려하지 않고 
링크가 될 수 있는거지.

그러면 바로 정의가 없다고 하면서 터지는거고.

그래서 무조건 참조 -> 정의 순으로 읽어야 한다는거지.

그리고,
한 정적 라이브러리 내의 정의 / 참조 관계는 신경쓸 필요가 없어.
정적 라이브러리 내의 정의 / 참조는 순서와 상관없이
정적 라이브러리를 읽을 때 자동으로 정의와 참조가 이어지기 때문이야.

그리고 정적 라이브러리끼리 서로를 참조할 때는
`A -> B -> A` 순서로 읽게 해가지고
`A`의 참조를 `B`의 정의와 연결하고
`B`의 참조를 `A`의 정의와 연결하는 식으로 처리할 수 있다고 해.

### Symbol Resolution Summary - 심볼 해석 요약

1. 심볼 해석은 정의와 참조를 잇는 단계다.
2. 지역 심볼은 중복 정의 문제를 컴파일러 단에서 처리한다.
3. 전역 심볼은 strong / weak으로 심볼을 분류해서 규칙에 따라 처리한다.
4. 정적 라이브러리로 오브젝트 파일을 모아 필요한 오브젝트 파일만 링크할 수 있다.
5. 정적 라이브러리를 링크할 때는 
해당 지점까지의 정의 없는 심볼만 가지고 링크할 오브젝트 파일을 고르기 때문에
참조하는 부분을 정의하는 부분보다 먼저 읽어야한다.

## 6. Relocation - 재배치

### 정리

1. 재배치의 단계
    - 심볼 해석이 끝나면,
    심볼의 각 참조들은 하나의 정의와 연결되어있게 된다.
      - 링커는, 오브젝트 파일의 코드 / 데이터 섹션의 정확한 크기를 파악하게 된다.
    - 링커는 재배치 단계에서 여러 오브젝트 파일을 병합하고 각 심볼에 런타임 주소를 할당한다.
    - 1. 섹션 / 심볼 정의 재배치
      - 여러 오브젝트 파일의 동일한 유형의 섹션을 하나로 통합한다.
      - 그리고 통합된 섹션들과 각 심볼에 런타임 주소를 할당한다.
    - 2. 섹션 내 심볼 참조 재배치
      - 코드 / 데이터 섹션의 모든 심볼 참조를 수정해서,
      각 심볼의 올바른 런타임 주소를 가리키도록 하게 한다.
      - 이 과정을 실행하기 위해 재배치 엔트리로 알려진
      오브젝트 파일 내의 자료 구조를 활용한다.

### 느낀 점 & 배운 점

말 그대로 재배치가 어떤 단계로 일어나는지 설명하는 챕터네.

1. 일단 여러 오브젝트 파일의 섹션을 합치며 
심볼의 정의(데이터 / 코드)를 명확한 런타임 주소로 넣어버리고,
2. 그렇게 명확한 런타임 주소가 결정되었으니
그 심볼들을 참조하는 부분들을 실제 각 심볼의 런타임 주소로 교체하는게

링크의 재배치 과정이라고 이해했어.

근데 솔직히 지금까지 공부하면서 의문이 드는게 있는데,
바로 심볼 해석으로 여러 오브젝트 파일의 참조와 정의를 이었는데,
그 참조 - 정의 관계는 대체 어디에 저장되는건지..

이게 각 오브젝트 파일의 심볼 테이블에 저장되는건 아닌 것 같은게,
각 오브젝트 파일의 심볼 테이블은 오직 해당 오브젝트 파일을 나타내는 심볼 테이블이니까,
다른 오브젝트 파일의 정의를 써놓지는 않을 것 같단 말이야..?

이게 두 가지 생각이 드는데,
`.rel`이 붙은 섹션에 그 정보를 저장하든가,
파일이 아닌 링커 자체에서 임시로 그 정보를 저장하는 자료구조를 쓰던가
둘 중 하나일 것 같아.

내가 다시 알아봤더니,
링커에서 여러 오브젝트 파일의 심볼 참조 관계를 정리하는 별도의 자료구조를 쓴다고 하더라고.

(재배치 엔트리랑은 별개임, 
그건 `.rel`에 들어가있는 정보로, 
그저 재배치 과정에서 **수정해야하는 부분**과 그 특성이 정리된 엔트리지
여러 오브젝트 파일 간의 참조 정보가 기록되어있지 않음.)

(물론 링커 내부의 자료구조에도 참조 관계만 정리되어있지
정확히 어느 코드 / 데이터를 수정해야하는지는 안 나와있음.)

## 7. Relocation Entries - 재배치 엔트리

### 정리

1. 재배치 엔트리
    - 기본적으로 컴파일 -> 어셈블 과정에서 각 데이터와 코드가 어느 위치에 배치될지 알 수 없고,
    해당 오브젝트 파일에서 참조하는 외부의 함수 / 전역 변수의 위치를 알지 못하기 때문에,
    최종 위치가 정해지지 않은 객체에 대한 참조를 발견할 때마다
    재배치 시 해당 참조를 어떻게 수정해야하는지를
    `.rel.text` / `.rel.data`에 저장한다.
      - 결국, **최종 위치가 명확히 정해지지 않은 정보에 대한 참조**들은
      재배치 과정에서 수정되어야 하기에
      그 정보들을 `.rel.text` / `.rel.data`에 저장해놓는 것이다.
    - 재배치 엔트리는
      - 오프셋(offset) : 해당 섹션의 시작 주소에서 얼마나 떨어져있는지를 나타내는 오프셋
      - 타입(type) : 참조를 어떻게 수정해야하는지
        - `ELF`는 32가지의 재배치 유형을 정의하고 있으며, 대표적인 두 종류로는
          - `R_X86_64_PC32` : 32비트 PC 상대 주소를 사용하는 참조로 재배치
          - `R_X86_64_32` : 32비트 절대 주소를 사용하는 참조로 재배치
          (이 두 타입은 소형 코드 모델에서 지원함(코드 + 데이터가 2GB 미만))
        - 이 있으며, 실제로는 더 난해한 타입들이 많이 있다.
      - 심볼(symbol) : 해당 오브젝트 파일의 심볼 테이블에서의 해당 심볼의 인덱스
      - 가산항(addend) : 일부 유형의 재배치에서 수정된 참조 값에 편향을 주기 위해 사용되는 상수
    - 로 구성된다.

### 느낀 점 & 배운 점

결국 재배치 시에 코드의 어디를 수정해야할지를 별도의 자료구조로 저장해놓은게
재배치 엔트리라고 할 수 있어.

결국 재배치 시 수정되어야하는 부분은,
컴파일 / 어셈블 시점에서 최종적인 위치가 결정되지 않은 참조니까,
그 참조들이 해당 오브젝트 파일의 어디에 있으며 어떻게 수정해야하는지를 알려주는거지.

- 오프셋으로 해당 심볼 참조가 있는 섹션의 시작 주소로부터 어디있는지를,
- 타입으로 해당 심볼 참조를 어떻게 수정해야되는지를

정해주는거야.

그리고,
해당 심볼이 어느 정의를 참조하고 있는지는 링커 내부의 자료구조로 나타내지는거지.

그리고 결국 **최종적인 위치가 결정되지 않은 참조**를 저장한다는게 중요한데,
이건 전역 변수 / 함수 / 정적 변수 다 해당되는 이야기야.

전역 변수로 예시를 들어보자면,
결국 전역 변수는 실행 파일에서는 데이터 영역에 들어가잖아?
그리고 그 데이터 영역은 여러 오브젝트 파일의 데이터 영역을 합쳐서 나오는거고.
그렇다면 해당 전역 변수를 참조하는 부분이 가리키는 주소는
컴파일 / 어셈블 시점에서 정해지지 않았다는거겠지?
그러니까 재배치 엔트리에 들어가는거야.

이게 신기한게,
결국 컴파일 / 어셈블 시점에서 최종적인 위치가 결정되지 않았다는게 중요하기 때문에,
한 오브젝트 파일에서 같은 오브젝트 파일 내의 레이블로 점프하는 코드 같은 경우에는
최종적인 상대 위치를 컴파일 / 어셈블 시점에 결정할 수 있으므로
굳이 재배치 엔트리에 해당 심볼(레이블)을 넣을 필요가 없다는거지.

```x86asm
# a1.o

foo:
# ...
# ...
je L1.
# ...
# ...
L1:
```

이런 코드가 있을 때,
점프에서는 그저 해당 오브젝트 파일의 PC 상대 주소만으로도
`L1`을 인식할 수 있잖아?

## 8. Relocating Symbol References - 심볼 참조 재배치

### 정리

1. 링커의 재배치 알고리즘
    - (`type` : `R_X86_64_PC32` / `R_X86_64_32`만 있다고 가정)
    - 링커가 들고있는 주소와 실제 실행파일의 런타임 주소를 분리해서 보는게 중요하다.
    - `s` : **링커가 들고 있는** 해당 섹션(바이트 배열)
    - `r` : 해당 재배치 엔트리
    - `ADDR(s)` : **실제 실행 파일에 배치되었을 때**의 해당 섹션의 런타임 주소
    - `ADDR(r.symbol)` : **실제 실행 파일에 배치되었을 때** 
    해당 재배치 엔트리가 가리키는 심볼(정의가 있는 심볼)의 런타임 주소
    - `r.type`을 보고 분기한다.
    - `R_X86_64_PC32` 타입의 재배치 과정은(의사 코드)
      - 1. `refptr = s + r.offset`으로 
      링커가 들고있는 데이터의 수정할 부분을 구한다.
      (링커도 프로그램이므로 메모리에 바이트열로 올려놓고 작업하니까,
      실제 런타임 주소와는 다르다.)
      - 2. `refaddr = ADDR(s) + r.offset`으로 
      실제 런타임 주소 관점에서의 수정될 부분의 위치를 구한다.
      - 3. `*refptr = (ADDR(r.symbol) + r.addend - refaddr)`로
      런타임 주소에서의 해당 코드를 실행할 위치(수정할 위치)(`refaddr`)와 
      실제 가리키는 심볼의 위치(`ADDR(r.symbol)`)의 상대적인 주소를 구해서
      링커 관점에서의 수정할 위치(`*refptr`)에 배치한다.
      (`addend`로 PC 상대 주소에서의 오차(**다음 명령어 주소**& + 오프셋 해야함)를 없애준다.)
    - `R_X86_64_32` 타입의 재배치 과정은(의사 코드)
      - 1. `refptr = s + r.offset`으로
      링커가 들고있는 데이터의 수정할 부분을 구한다.
      - 2. `*refptr = (ADDR(r.symbol) + r.addend)`로
      실제 가리키는 심볼의 런타임 주소(`ADDR(r.symbol)`)를
      링커 관점에서의 수정할 위치(`*refptr`)에 배치한다.
      (`addend`로 추가적인 오프셋 적용)

### 느낀 점 & 배운 점

음.. 솔직히 이 파트는 되게 어려운데,
간단하게 보려면 딱 이 정도만 머리에 넣고 가면 돼.

- 실제 정의를 가리키도록 수정되는 부분 : 링커가 바라보고있는 위치
- 정의의 주소를 나타내는 부분 : 런타임 주소

이렇게 보면 돼.

사실, 상식 선에서 컷할 수 있어.

- 결국 해당 파일에 대해 재배치를 수행하는건 링커이기 때문에
링커가 바라보고있는 메모리 주소의 값을 수정을 해야하고,
- 실제로 실행되는건 실행 파일이기 때문에
실행 파일의 런타임 주소를 기반으로
수정할 값인 각 정의의 주소를 계산해야하는거지.

즉,

- 수정해야할 코드의 메모리 위치 : 링커 입장에서 계산
  - 재배치는 링커가 하니까..
- 참조해야할 정의 위치 : 런타임 주소 입장에서 계산
  - 이건 실제로 실행될 때 영향을 미치니까..

이렇다는거야.

근데 이거 단어를 어떻게 선택해야하는지 감이 잘 안온다ㅋㅋ

- 수정해야할 코드의 메모리 위치(실제로 수정되는 부분)
- 참조해야할 정의 위치(수정되는 부분이 참조하는 부분)

이렇게 해도 이해가 되나?

실행 파일의 런타임 주소는
이미 데이터 / 코드를 수정하기 전에
각 섹션들을 병합할 때 다 나올테니,
링커가 보는 주소 + 실제 실행 파일의 런타임 주소를 
둘 다 이용할 수 있는거지.

### Relocation Summary - 재배치 요약

1. 재배치란,
    - 각 코드 / 데이터의 최종 런타임 위치를 확정하고,(섹션 / 심볼 재배치)
    - 해당 코드 / 데이터를 참조하는 위치를 확정된 최종 위치에 맞게 수정하는 것이다.(참조 재배치)
2. 재배치 시, 심볼 해석의 결과와 
각 오브젝트 파일의 `.rel`에 저장되어있는 재배치 엔트리를 사용해서
코드 / 데이터를 참조하는 위치의 코드를 수정한다.
    - 심볼 해석의 결과는 '어떤 참조가 어떤 정의를 참조하는지'를 나타내고,
    - 재배치 엔트리는 '해당 참조가 코드 / 데이터 어디에 있으며 어떻게 수정해야하는지'를 나타낸다.
3. 참조 재배치 시,
    - 참조를 수정해야할 대상의 주소는 링커가 보는 주소를 기준으로 찾고,
    (재배치를 하는 주체가 링커이므로)
    - 참조가 가리키는 대상의 주소는 런타임 주소를 기준으로 계산한다.
    (실제로 실행될 때는 런타임 주소를 기준으로 하므로)
