## 1. Exceptions - 예외

### 정리

1. 예외
    - 예외는 하드웨어 / 운영체제에 의해 구현되는 특수한 제어 흐름이다.
    - 예외는 프로세서 상태의 변화에 대하여
    제어 흐름이 갑작스럽게 바뀌는 것이다.
      - 이 프로세서 상태의 변화는
      단순히 프로세서 내부의 상태의 변화 뿐만 아니라,
      프로세서가 인식한 외부적인 사건도 포함된다.
    - 프로세서의 상태가 바뀌는 것을 이벤트라고 한다.
      - 현재 명령어의 실행과 관련있을 수도 있고,
      (예 : 페이징 오류 / 산술 오버플로우 / 0으로 나누기 시도)
      - 현재 명령어의 실행과 무관할 수도 있다.
      (예 : 시스템 타이머 작동 / I/O 요청 완료)
      
2. 예외의 처리
    - 어떤 경우의 이벤트든,
    프로세서가 이벤트 발생을 감지하면 예외 테이블이라는 점프 테이블을 통해
    해당 유형의 이벤트를 처리하도록 설계된
    운영 체제 서브루틴(예외 핸들러)로
    간접 프로시저 호출(예외, 제어 흐름 변경)을 수행한다.
    - 예외 핸들러가 예외 처리를 완료하면,
    예외를 유발한 이벤트의 유형에 따라 세 가지 중 하나가 발생한다.
      - 다시 원래의 제어 흐름으로 복귀
        - 현재 명령어(이벤트가 발생했을 때 실행중이던 명령어)로 제어 흐름 반환
        - 다음 명령어(예외가 발생하지 않았더라면 실행되었을 명령어)로 제어 흐름 반환
      - 중단된 프로그램을 종료
      
### 느낀 점 & 배운 점

결국 이번 챕터를 요약하면 이거야.

- 예외 : 프로세서의 상태 변화로 인해 발생하는 제어 흐름 변화
- 이벤트 : 프로세서의 상태 변화
  - 지금 실행하고 있는 명령어와 관련이 있는 이벤트도,
  - 지금 실행하고 있는 명령어와 관련이 없는 이벤트도 발생할 수 있다.
  - (프로세서의 내부에서만 발생한 상태 변화가
  이벤트라는 것은 아니다.)
- 예외 처리 : 예외 테이블 조회 -> 예외 핸들러 실행(간접 프로시저 호출)
- 예외 발생 후 처리 : 
  - 1. 이벤트가 발생했을 때 실행중이던 명령어를 실행 후 이어서 실행
  - 2. 예외가 발생하지 않았더라면 실행되었을 명령어를 실행 후 이어서 실행
  - 3. 프로세스 종료
  
이 정도.

그래서 결국,

1. 이벤트가 발생하면
2. 예외가 발생하고
3. 예외 테이블을 조회하여
4. 예외 핸들러를 호출한다.
5. 그리고 예외의 종류의 따라 후처리를 한다.

이게 예외 발생과 실행 흐름의 요약이야.

그런데 지금 안 풀린게,
예외가 발생하는걸 어떻게 감지하고
예외가 발생한 직후에 예외 테이블은 어떻게 조회하게 되는지임..

이건 추후에 나올지도 모르겠네..

그리고 여기서 내가 중요하다고 생각하는게
계속 프로세서의 상태 변화라고 한다는 점이야.

이게 그냥 생각해보면
굳이 '프로세서의 상태 변화'라는 단어 말고도
다양한 단어가 떠오르잖아?

프로세서 말고 프로세스로 대체해도 뭔가 문제가 없어보이지..

근데 굳이 '프로세서의 상태 변화'라고 한건 이유가 있어보여.

프로세서는 직접 명령어가 실행되는 곳이다 보니까
프로세서라고 한 것 같아.
(직접 명령어가 실행되는 곳이니
어떤 실행 흐름의 변화가 필요한 상황도 관측할 수 있을테니까..)
(내부 명령어의 오류 / 외부의 인터럽트 등..)

결국 프로세서가 **인식**하는 프로세서 내 / 외부의 특정 상태 변화가 이벤트고 (명확한 정의)
그 이벤트가 발생할 시 운영체제 / 하드웨어가 해당 이벤트를 기반으로 예외를 발생시키고,
처리한다고 보면 될 것 같아.

결국 예외라는건
프로세스가 아닌 프로세서가 중심이라는거야.

## 2. Exception Handling - 예외 처리

### 정리

1. 예외 번호(Exception Number)
    - 시스템에서 발생할 수 있는 각 예외 타입에는
    고유한 unsigned 정수인 예외 번호가 할당된다.
    - 이 번호 중 일부는 프로세서 설계자가 할당하고,
    나머지 번호는 OS 커널 설계자가 할당한다.
      - 프로세서 설계자가 할당하는 번호의 예 : 0으로 나누기 / 페이지 오류 / 메모리 접근 위반 등
      - OS 커널 설계자가 할당하는 번호의 예 : 시스템 콜 / 외부 I/O 장치로부터의 신호 등
    
2. 예외 테이블
    - 시스템 부팅 시, OS는 예외 테이블이라고 하는 점프 테이블을 할당 및 초기화하고,
    각 예외 번호에 대한 예외 핸들러의 주소가 포함되도록 한다.
    - 프로세서는 이벤트가 발생했음을 감지하고
    예외 번호를 결정 후,
    예외 테이블의 해당 예외 번호의 항목을 통해
    해당 예외 핸들러로 간접 프로시저 호출을 수행한다.
    - 예외 번호는 예외 테이블 내의 인덱스 역할을 한다.
    - 예외 테이블의 시작 주소는
    예외 테이블 베이스 레지스터(Exception Table Base Register)라고 하는
    특수한 레지스터에 저장되어있다.
    
3. 예외 핸들러 호출과 프로시저 호출의 다른 점
    - 일단 같은 점으로는,
    반환 주소를 스택에 Push 후 핸들러로 제어 흐름을 넘긴다는 점이다.
      - 하지만, Push하는 반환 주소는
      예외의 종류에 따라 현재 명령어 / 다음 명령어가 될 수 있다.
    - 핸들러가 반환될 때 중단된 프로그램을 다시 시작하는데 필요한
    추가 프로세서 상태 정보까지 스택에 Push한다.
    - 제어 흐름이 사용자 프로세스에서 커널로 이동될 때는,
    이런 모든 항목들이 커널 스택에 Push된다.
    - 예외 핸들러는 커널 모드에서 실행되므로,
    모든 시스템 리소스에 접근할 권한을 가진다.
    
4. 하드웨어와 소프트웨어
    - 하드웨어(프로세서)가 예외를 트리거하면,
    나머지 처리는 소프트웨어(OS)의 예외 핸들러가 수행한다.
    - 핸들러가 예외를 처리한 후에는,
    선택적으로 특수한 중단 복귀 명령어를 실행해서
    중단된 프로그램으로 복귀할 수 있다.
      - 이 명령어는 적절한 상태를 프로세서의 제어 및 데이터 레지스터로 다시 불러오고,
      사용자 모드로 복원한 다음,
      중단된 프로그램으로 제어 흐름을 반환한다.

### 느낀 점 & 배운 점

이번 챕터는 솔직히 되게 쉬웠어.

요약하면,

- 예외 번호(Exception Number) : 프로세서와 OS에서 각 예외에 할당한 번호
- 예외 테이블 : 예외 번호를 인덱스로 각 예외에 대한 예외 핸들러의 주소를 저장한 점프 테이블
  - 시작 주소는 예외 테이블 베이스 레지스터에 저장됨.
- 프로시저와 예외 핸들러가 다른 점
  - 예외 핸들러는 OS 커널에 있기 때문에 커널 모드로 전환됨.
  - 반환 주소를 현재 명령어 / 다음 명령어 중 하나로 저장하지만, 
  추가적으로 핸들러 반환 시 제어 흐름을 원래대로 복구하는데 필요한 정보도 저장함.
- 하드웨어와 소프트웨어
  - 하드웨어(프로세서)가 예외를 감지하고 예외 번호를 매기면,
  소프트웨어(OS 커널의 예외 핸들러)가 예외를 처리함.
  
이 정도겠네.

결국 발생한 예외는

1. 프로세서가 발생한 예외의 예외 번호를 매기고
2. 그 번호에 맞춰 예외 테이블 베이스 레지스터의 주소를 참조해서 예외 테이블을 참조하고
3. 예외 테이블에서 예외 번호에 맞는 인덱스의 점프 주소로 점프해서 예외에 맞는 예외 핸들러를 트리거하고
(이 시점에서 반환 주소 및 반환 시 필요한 정보 저장?)
(예외 핸들러를 트리거한 시점부터 커널모드)
4. 예외 핸들러가 예외를 처리하고
5. 예외 핸들러가 반환 시 필요한 정보를 이용해서 제어 흐름을 원래대로 돌려놓고
(원래 제어 흐름으로 복귀해야하는 경우에만)

이렇게 처리되는거야.

근데 여기서 핵심은,

프로세서가 예외 번호를 매기고 예외 테이블에서 예외 핸들러를 호출 
-> OS가 예외 핸들러로 처리하는 흐름과,
예외 핸들러가 커널 모드로 실행된다는 점이라고 생각해.

## 3. Classes of Exceptions - 예외의 종류

### 정리

1. 인터럽트(interrupt)
    - 인터럽트란,
    프로세서 외부에서 발생하는 신호(signal)의 결과로,
    비동기적으로 발생한다.
    (다른 세 가지는 동기적으로 발생한다.)
    - (하드웨어 인터럽트는 특정 명령어의 실행에 의해 유발되지 않는다는 점에서
    비동기적이라고 할 수 있다.)
    - 인터럽트에 대한 예외 처리는 인터럽트 핸들러가 담당한다.
    - 인터럽트의 처리는,
      - 인터럽트를 보내는 장치가
      인터럽트를 유발한 장치를 식별하는 예외 번호(Exception Number)를
      시스템 버스에 전송해서 인터럽트를 트리거하고,
      - 현재 명령어의 실행을 완료된 후
      프로세서가 인터럽트를 확인하고 예외 번호를 읽은 후
      적절한 인터럽트 핸들러를 호출한다.
      - 핸들러가 반환되면,
      제어 흐름을 다음 명령어로 넘긴다.
      (인터럽트가 발생하지 않았던 것처럼 실행을 계속한다.)

2. 트랩(trap)과 시스템 콜(system call)
    - 트랩은 명령어의 실행으로 발생하는 의도적인 예외이다.
    - 인터럽트 핸들러와 마찬가지로,
    트랩 핸들러는 반환될 때 제어 흐름을 다음 명령어로 넘긴다.
    - 트랩의 가장 중요한 용도는,
    시스템 콜이다.
      - 시스템 콜이란,
      사용자 프로그램이 커널의 서비스를 요청하는 콜이라고 생각하면 된다.
    - 시스템 콜은 일반 프로시저 호출과 비슷하지만,
    커널 모드로 실행된다고 보면 된다.

3. 폴트(fault)
    - 폴트는 핸들러가 수정할 수 있는 폴트 상태에서 발생한다.
    - 폴트가 발생하면 프로그램은 제어 흐름을 폴트 핸들러로 넘긴다.
    - 핸들러가 오류 상태를 수정할 수 있다면
    반환 시 제어 흐름을 오류가 발생한 명령어로 되돌려보내고,
    그렇지 않은 경우 커널 내의 어보트 루틴으로 가서
    오류를 일으킨 응용 프로그램을 종료시킨다.
    
4. 어보트(중단, abort)
    - 어보트는 복구 불가능한 치명적인 오류로 인해 발생한다.
    - 절대로 제어 흐름을 응용 프로그램으로 반환하지 않는다.
    - 핸들러는 제어 흐름을 어보트 루틴으로 반환해서
    응용 프로그램을 종료시킨다.

### 느낀 점 & 배운 점

이번에는 말 그대로 예외의 종류에 대해 배운 것 같아.

- 인터럽트
  - 책에서는 I/O 장치의 작업 완료로 대표되는 하드웨어 인터럽트 위주로 소개
  - 외부 장치에 의해 발생하므로 비동기적
  - 외부 장치가 인터럽트 트리거 -> 프로세서가 현재 명령어를 실행한 후 인터럽트를 확인
  -> 프로세서가 인터럽트 핸들러를 호출
  - 핸들러 반환 시 제어 흐름을 다음 명령어로 넘김
- 트랩 / 시스템 콜
  - 트랩은 동기적으로 발생하는 의도된 예외
  - OS의 기능을 사용하는 시스템 콜이 대표적
  - 핸들러 반환 시 제어 흐름을 다음 명령어로 넘김
- 폴트
  - 의도되지 않은 오류 중에 핸들러가 수정할 수 있을지도 모르는 오류
  - 핸들러가 수정할 수 있는 경우,
  폴트가 발생한 명령어로 제어 흐름을 넘긴다.
  - 핸들러가 수정할 수 없는 경우,
  프로그램을 종료시킨다.
- 어보트
  - 무조건 프로그램을 종료해야하는 심각한 오류
  - 무조건 프로그램을 종료한다.
  
이 정도라고 볼 수 있겠네.

분류를 제대로 해보자면,

정상적인 예외는
인터럽트 / 트랩이라고 할 수 있겠고,
정상적이지 않은 예외는
폴트 / 어보트라고 할 수 있을 것 같네.

그리고
주로 I/O 디바이스에 의해 발생하는 인터럽트,
주로 시스템 콜에 의해 발생하는 트랩,
주로 오류에 의해 발생하는 폴트와 어보트로
분류할 수 있기도 하고,

비동기적으로 발생하는 인터럽트,
동기적으로 발생하는 트랩 / 폴트 / 어보트로 분류할 수도 있겠고?

반환 시 다음 명령어를 이어서 실행하는 
인터럽트 / 트랩,
반환 시 핸들러가 처리 가능하면 현재 명령어를 이어서 실행하는
폴트,
반환 시 핸들러가 처리 불가하면 프로그램을 종료시키는
폴트,
반환 시 무조건 프로그램을 종료시키는
어보트로 분류할 수 있기도 하겠네..

결국 정상적이냐 / 정상적이지 않냐
발생시키는 주체가 무엇이냐
동기적이냐 / 비동기적이냐
핸들러 반환 시 무엇을 어떻게 실행하냐
이런 기준으로 분리할 수 있겠네.
