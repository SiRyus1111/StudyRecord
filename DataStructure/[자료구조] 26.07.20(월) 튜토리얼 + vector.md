## 2. Pointers

### 2-1. 포인터 기본

포인터.

  - 메모리 주소를 저장하는 변수.
  - 포인터 변수를 통해 다른 변수에 간접적으로 접근할 수 있다.
  - `*`을 붙여서 포인터 변수를 선언하고, `&`으로 다른 변수의 주소를 받아올 수 있다.
  - 포인터 변수가 가리키는 메모리 주소에 접근할 때는, `*p`의 형태로 접근할 수 있다.
  - 포인터 변수가 가리키는 객체의 멤버에 접근할 때는, `->`로 접근할 수 있다. (`(*p).member`)
  - 포인터 변수의 주소도 포인터 변수에 할당될 수 있다. (물론 포인터 타입은 이중 포인터로 달라짐.)
  (그리고 N중 포인터도 가능은 함.)

그리고 추가로,

```cpp
int* p = new int{}; // {} 붙이는건 0으로 초기화한다는 의미임
```

처럼 `new` 동적 할당한 객체도 업어올 수 있고
(애초에 메모리를 할당받는 `new` 자체가 포인터를 반환함)

```cpp
delete p;
```

처럼 동적 할당한 객체를 해제할 수 있음.

그리고 만약 이미 해제된 메모리 주소를 포인터가 가리키고 있다면
그 포인터를 댕글링 포인터라고 해.

댕글링 포인터 문제가 발생한 포인터 변수를 역참조(`*` / `->`)하면
정의되지 않은 동작(Undefined Behavior, UB)임.
막 세그폴트(Segmentation Fault)도 발생할 수도 있고.

그리고 포인터는 레퍼런스와 다르게 `null`값이 들어가는게 가능함.
`nullptr`로.

그리고 동적 할당된 객체는 메모리를 해제해주지 않으면 
해당 객체가 해제되지 않고 계속 메모리에 남아있는
메모리 누수가 발생함.

### 2-2. 포인터와 배열

C++에서의 배열 이름은 대부분의 표현식에서는 해당 배열의 첫 주소를 가리키는 포인터로 쓰여.
물론 배열 자체는 여러 원소가 연속해서 배치된 하나의 배열 객체고.

배열의 각 원소의 주소가 일정한 간격으로 배치되어있기 때문에,
배열 이름 + 오프셋으로 접근할 수 있는거임.

```cpp
int a[5];

a[0]; // a의 메모리 주소에서 오프셋 0
a[1]; // a의 메모리 주소에서 오프셋 1
// 등등..
```

물론 역참조 + 포인터 연산으로 접근할 수도 있음.

```cpp
*(a + 0); // a의 메모리 주소에서 오프셋 0
*(a + 1); // a의 메모리 주소에서 오프셋 1
```

물론 포인터 연산은 포인터 연산을 하는 대상에 따라 달라짐.

`int`면 `+ 1`할 때마다 포인터 주소는 `sizeof(int)`, 즉 일반적인 환경에서는 `+ 4`씩,
`char`이면 `+ 1`할 때마다 포인터 주소는 `sizeof(char)`, 즉 `+ 1`씩
증가하는 식으로..

```text
기본 메모리 주소 + 오프셋 * sizeof(자료형)
```

이렇게.

그리고 만약 `new`로 힙에 동적 할당된 배열을 delete할 때도

```cpp
int* a = new int[5]{};

delete[] a;
```

이렇게 따로 `[]`를 붙여줘야함..

### 2-3. 포인터와 복사 생성자

딱 한 문장 요약.

> 객체 안에 포인터가 있을 때,
> 해당 객체를 그냥 복사하면 포인터가 가리키는 데이터가 복사되는 것이 아닌
> 포인터 변수에 저장되어있는 주소값만 복사된다.
> 그렇기 때문에, 객체를 복사할 때 포인터가 가리키는 데이터까지 복사해야한다면
> 따로 복사 생성자를 구현해주어야한다.

```cpp
class Array {
public:
    int* data;
    std::size_t size;
};

Array a;

a.size = 3;
a.data = new int[3]{10, 20, 30};
```

여기서,

```cpp
Array b = a;
```

이렇게 복사한다고 해서,
`data`가 가리키는 배열이 복사가 되는게 아니라,
배열의 주소만 복사하게 되어

```text
a.data ─┐
        ├────> [10][20][30]
b.data ─┘
```

이렇게 됨.
실제로 포인터 변수가 가리키고 있는 배열이 복사되지는 않아.

이걸 얕은 복사(shallow copy)라고 함.

이럴 때, `a`를 삭제하며 `a.data`가 가리키고 있는 배열까지 삭제하면
아직 `b`의 포인터 변수가 해당 배열까지 가리키고 있으므로
댕글링 포인터 / double delete 문제가 발생할 수 있겠지.

그래서,

1. 클래스가 포인터를 통해 동적 자원(메모리 주소도 포함)을 직접 소유하고
2. 객체 복사 시 자원도 독립적으로 복사되어야하면

그냥 기본 복사 생성자의 얕은 복사로는 부족해.

그래서,

```cpp
class Array {
public:
    int* data;
    std::size_t size;
    
    explicit Array(std::size_t size) : data(new int[size]{}), size(size) {   }
    
    // 복사 생성자
    Array(const Array& other) : data(new int[other.size]), size(other.size) {
        // 복사할 객체의 포인터 변수가 가리키고 있던 배열을 그대로 복사
        std::copy(other.data, other.data + other.size, data);
    }
    
    // 물론 복사 대입 연산자도 함께 정의해야하지만, 분량상 스킵
    
};
```

이렇게 따로 복사 생성자를 구현해야해.

이렇게 해서

```cpp
Array b = a;
```

를 수행하면,

```text
a.data ──────> [10][20][30]

b.data ──────> [10][20][30]
```

이렇게 포인터 변수가 복사되는 느낌이 아니라
아예 새로운 배열을 할당하고 그대로 복사해오는 느낌이야.
그래서 결국 두 포인터는 다른 배열을 가리키게 되고.

이건 깊은 복사(deep copy)라고 함.

결국,

> 포인터 멤버로 자원을 소유하는 객체는 기본 복사 생성자를 사용하면
> 주소만 복사되어서 여러 객체가 같은 자원을 공유할 수 있기 때문에,
> 독립적인 복사가 필요하다면 직접 복사 생성자를 정의해서 복사해야한다.

라고 할 수 있지.

### 2-4. 포인터와 소멸자

이것도 한 문장 요약 가능함.

> 해당 객체가 소멸되었다고 해서
> 해당 객체가 포인터를 통해 소유하는 객체까지 소멸되는 것은 아니다.
> 그래서 따로 소멸자에서 해당 객체의 멤버였던 포인터가 소유하던 객체까지 해제시켜줘야한다.

객체가 소멸하면 해당 객체의 포인터 멤버 자체도 함께 소멸하지만,
해당 포인터 멤버가 가리키는 객체의 수명까지 자동으로 끝나는게 아니야.

그래서 결국,
소멸자에서 **해당 객체의 포인터가 가리키는 객체까지** 소멸시켜줘야 해.

물론, 포인터가 가리키는 객체를 해당 클래스가 소유하지 않는다면,
즉 해당 객체의 생명 주기에 간섭할 수 없다면,
소멸자에서 해제하면 안되고.

예시를 들어보면,

```cpp
class Array {
public:
    int* data;
    std::size_t size;
    
    explicit Array(std::size_t size) : data(new int[size]{}), size(size) {   }
    
    // 복사 생성자
    Array(const Array& other) : data(new int[other.size]), size(other.size) {
        std::copy(other.data, other.data + other.size, data); 
    }
    
    // 소멸자에서 data가 가리키고 있는 객체의 메모리를 해제시켜줌
    ~Array() {
        delete[] data;
    }
};
```

이렇게 소멸자에서 해당 객체의 멤버였던 포인터가 가리키는 객체까지 메모리 해제(소멸) 시켜주는거임.

### 2-5. 굳이 포인터를 복습하는 이유

솔직히 포인터에서도
복사 생성자 / 소멸자 관련해서 좀 알아둬야할 필요가 있어서야.

초반에 짧게 포인터 + 배열을 설명하는건 그거에 관한 빌드업이고.

이게 결국 복사 생성자(+ 복사 대입 연산자) / 소멸자를 사용하는 경우는

1. 포인터가 가리키고 있는 해당 자원(객체)를 직접 소유함(소멸자는 이것만 해당)
2. 복사를 할 때 해당 자원(객체)를 아예 따로 복사할 수 있고, 복사할 필요가 있음
3. 복사본이 독립적인 자원(객체)를 가져야 함.

이 세 가지가 충족되어야하거든?

이건 특히 연결리스트를 구현할 때 좀 문제가 체감이 돼.

연결 리스트에서는 여러 노드가 포인터로 이어져있어서 이 문제가 특히 시각적으로 잘 체감돼.

만약 연결 리스트 객체를 복사할 때
포인터 변수만 복사하고 그 포인터를 통해 소유하고 있는 객체를 복사하지 않으면

연결 리스트 정보를 담고 있는 객체는 두 개지만
실제 연결 리스트는 같은 연결 리스트를 가리키고 있는 그런 상황이 벌어질 수 있어.

```text
(예시 느낌)

연결리스트 HEAD를 가리키고 있는 객체 1 ─┐
                                   ├────> [원소 1] -> [원소 2] -> [원소 3] -> [원소 4] -> ...
연결리스트 HEAD를 가리키고 있는 객체 2 ─┘
```

이렇게.
근데 여기서 한 객체가 해당 연결 리스트를 삭제한다?
앞에서 말했듯 반대편 객체는 큰일나는거고(댕글링 포인터, double delete).

그리고 연결 리스트 객체를 소멸시킬 때도
딱 연결 리스트의 정보를 담고 있는 객체만 소멸시킨다면
실제 연결 리스트는 소멸되지 않아서

소멸자에서 따로 모든 노드를 순차적으로 지워줘야 한다는거.

```text
(소멸 전)

연결리스트 HEAD를 가리키고 있는 객체 ──────> [원소 1] -> [원소 2] -> [원소 3] -> [원소 4] -> ...
```

-

```text
(소멸 후)

(소멸됨)                                 [원소 1] - [원소 2] -> [원소 3] -> [원소 4] -> ...
                                           ↑
                               더 이상 접근할 포인터가 없음
```

이렇게 연결 리스트의 정보를 담고 있는 객체만 소멸시키면 
연결 리스트의 각 노드들은 소멸되지 않을 수 있으니까.

어쨌든, 복사 생성자 / 복사 대입 연산자 / 소멸자 요약 해보면,

```text
소멸자
→ 객체가 소유하는 자원을 정리한다. 

복사 생성자
→ 객체의 복사를 허용할 때, 자원을 어떤 방식으로 복사할지 정한다.
→ 여러 방식이 있지만, 대표적으로 얕은 복사(shallow copy)와 깊은 복사(deep copy)가 있다.

복사 대입 연산자
→ 이미 존재하는 객체에 다른 객체의 상태를 대입할 때의 자원 처리 방식을 정한다.
→ 복사 생성자와 비슷하지만, 이건 대입 연산자이다.
```

어쨌든 이런 이유들로 포인터 복습 한거임.

여담으로,
이런 이유로

- 복사 생성자
- 복사 대입 연산자
- 소멸자

를 정의하는 것을
Rule of Three라고 해.

마지막으로,
지금까지를 보면 무조건 포인터로 자원을 소유하고 있으면
깊은 복사를 구현해야한다고 생각할 수 있는데,

사실

- 깊은 복사(독립적인 복사)
- 복사 금지(복사 생성자 및 복사 대입 연산자 막기)
- 공동 소유(얕은 복사 사용, `std::shared_ptr`처럼 소유권을 관리하는 별도의 수단 사용)

등의 형태를 사용할 수 있어.
딱 깊은 복사만 허용되는게 아니라, 상황에 맞춰 쓰는거지.

## 3. The Standard Template Library

C++ 표준 라이브러리는

- Container(컨테이너)
- Iterator(이터레이터)
- Algorithm(알고리즘)

등의 템플릿 라이브러리를 제공해.

컨테이너는 데이터를 저장하는 자료구조로 보면 되고,
알고리즘은 다양한 자료구조에 적용할 수 있는 함수로 보면 되고,
이터레이터는 알고리즘이 컨테이너의 각 원소의 위치를 표현하고 순회할 수 있게 연결해주는 인터페이스로 보면 돼.

이거 자료구조 공부니까, 나름 중요하지.

결국

- 컨테이너 = 자료구조
- 알고리즘 = 자료구조를 조작하는 용도로 쓸 수 있는 함수
- 이터레이터 = 알고리즘이 자료구조를 조작할 수 있게 해주는 연결고리

이렇게 되니까.

이렇게, C++에서는 프로그래머가 직접
다양한 자료구조와 자료구조를 다루는 함수를
직접 구현할 필요가 없어.

근데 이건 자료구조 자체의 내용이라기보다 자료구조와 C++과의 연결고리라..
그렇게 깊게는 안 들어갈거야.

### 3-1. Containers

컨테이너는 앞서 말한 대로,
데이터를 저장하는 자료구조라고 할 수 있어.

각 컨테이너가 저장하는 원소의 타입은 템플릿 인자로 정해져.
그리고 컨테이너 객체 하나마다 정해진 데이터(객체)만 저장할 수 있지.

물론 컨테이너의 종류에 따라 내부의 데이터 저장 방식은 달라.

컨테이너는,

- `map` : key-value 자료구조(중복 key 미허용)
- `multimap` : 중복 key 허용하는 map
- `set` : 원소 자체를 key로 사용하는 정렬 집합(중복 key 미허용)
- `multiset` : 중복 key 허용하는 set
- `vector` : 동적 배열
- `deque` : 양방향 큐
- `list` : 이중 연결 리스트

(이것들은 다른 컨테이너를 기반으로 하는 컨테이너 어댑터)

- `stack` : LIFO(후입선출) 자료구조
- `queue` : FIFO(선입선출) 자료구조
- `priority_queue` : 우선순위 큐

등이 있어.

STL 컨테이너는 템플릿 클래스로 구현되고, 
이런 템플릿 클래스들에는 
해당 컨테이너에 저장한 **데이터나 자료구조 자체에 수행할 수 있는 연산**들이
멤버 함수로 포함되어있어.
이건 알고리즘이랑 별개야.

해당 컨테이너 자체를 관리하는 연산이지.

물론 각 컨테이너마다 각 멤버 함수의 구현은 다를 수 있고.

### 3-2. Iterators

이터레이터는 컨테이너에 저장된 요소들을 참조하는데 사용되는 객체라고 볼 수 있어.

더 정확하게는 컨테이너의 각 요소를 나타내고 순회할 수 있게 해주는 객체라고 할 수 있겠네.

앞에서는 간단하게

- 알고리즘이 자료구조를 조작할 수 있게 해주는 연결고리

라고 했었는데,
새로 설명한게 좀 더 이터레이터에 더 잘 맞아.

이터레이터는 포인터의 일반화된 형태라고 할 수 있는데,
이터레이터를 사용하면 컨테이너에 저장되어있는 데이터에 접근할 수 있어.

좀 쉽게 보면 알고리즘이 자료구조를 조작할 수 있게 해주는 연결고리도 맞긴 하지..

물론 이터레이터도 포인터와 같이 역참조도 할 수 있어.

이터레이터에 대한 연산은 포인터 연산과 비슷하지만,
모든 컨테이너에서 이터레이터에 대한 연산이 허용되는 것은 아니야.

`stack` / `queue` / `priority_queue` 컨테이너에서는 이터레이터가 지원되지 않는 것 처럼.

근데 여기까지 보면 좀 너무 개념이 추상적인데..ㅋㅋ

좀 쉽게 설명하자면,

컨테이너의 각 원소를 가리킬 수 있는 포인터라고 보면 돼.
물론 진짜 포인터는 아님.
포인터와 유사한 방식이라는거..

어쨌든 컨테이너의 각 원소의 위치를 나타낼 수 있는 포인터같은 객체라고 보면 될듯.

이게 단순 동적 배열(`vector`)같은 것들은 각 원소가 일자로 놓아져있어서
그냥 인덱스(`[]`)로 포인터와 오프셋을 사용해서 각 원소를 찾을 수 있겠지만,

연결 리스트(`list`)같이 각 원소가 일자로 놓여있지 않고 흩어져있는 것들은
오프셋을 사용해서 각 원소를 찾을 수 없고,
계속 포인터를 이동시켜서 각 원소를 찾아야해.

이터레이터를 사용하면 `vector`처럼 연속된 자료구조와 
`list`처럼 노드가 흩어진 자료구조를 
비슷한 문법으로 순회할 수 있어.

```cpp

std::vector<int> vec = {1, 2, 3, 4, 5};

for (auto it = vec.begin(); it != vec.end(); ++it) {
   // *it으로 vector의 각 원소 사용
}

std::list<int> lst = {1, 2, 3, 4, 5};

for (auto it = lst.begin(); it != lst.end(); ++it) {
    // *it으로 list의 각 원소 사용
}

// 비슷한 문법으로 vector와 list 모두 순회할 수 있음! (이터레이터 추상화의 핵심)
```

STL 알고리즘은 이런 이터레이터 인터페이스를 통해 
특정 컨테이너의 내부 구현에 강하게 의존하지 않고 여러 자료구조를 처리할 수 있게 되고.

결국 이터레이터는
컨테이너의 각 원소를 순차적으로 탐색하기 위한,
컨테이너의 각 원소를 나타낼 수 있는 객체라고 생각하면 돼.

앞에서 설명한 것처럼 각 원소가 일자로 놓여있지 않으면
계속 메모리 여기저기에 흩어져있는 다음 노드를 찾아야하잖아?

그런거지 뭐.

### 3-3. Algorithms

STL은 알고리즘이라 불리는 수많은 함수들을 제공해.

알고리즘은 STL 컨테이너와 배열에 적용할 수 있는 함수로,
다양한 연산들을 제공하지.

예를 들어,

- 특정 원소 찾기
- 원소 개수 계산
- 특정 원소 값 변경
- 원소 복사 / 이동
- 원소 비교
- 원소 정렬

등등..

거의 대부분의 STL 알고리즘은 연산의 범위를 지정하기 위해
앞에서 설명한 이터레이터를 사용해.

보통 첫 번째 이터레이터는 범위의 첫 원소를 가리키고,
두 번째 이터레이터는 범위에 포함되지 않는 끝 위치를 가리켜.
(그래서 첫 번째 이터레이터를 증가시켜서 두 번째 이터레이터에 도달할 수 있어야 함)

```text
[first, last)
```

```cpp
std::sort(vec.begin(), vec.end());
```

```text
vec.begin()  → 첫 번째 원소의 위치
vec.end()    → 마지막 원소 다음의 끝 위치
```

그리고, 어떤 알고리즘이든 컨테이너에 상관 없이
동일한 이터레이터 인터페이스를 적용할 수 있기 때문에

컨테이너에 묶이지 않고
알고리즘이 사용될 수 있는거야.

물론, 그만큼 알고리즘은 컨테이너 타입 자체보다 이터레이터 인터페이스에 따라
사용할 수 있고 사용할 수 없는 알고리즘이 갈려.

알고리즘이 요구하는 이터레이터 기능을 제공하는 컨테이너라면 
동일한 알고리즘을 적용할 수 있는거지.

다음의 `sort()` 알고리즘은
이렇게 임의 접근 이터레이터(Ramdom Access Iterator)를 제공하는 컨테이너만 
사용할 수 있는 식으로.

```cpp
std::vector<int> vec = {2, 1, 4, 5, 3};

std::sort(vec.begin(), vec.end());

std::deque<int> deq = {2, 1, 4, 5, 3};

std::sort(deq.begin(), deq.end());
```

## 4. Vectors in the Standard Template Library

### 4-1. `vector`란?

`std::vector`는 어떻게보면 가장 간단한 컨테이너인데,
메모리 상의 연속된 블록으로 구성된 자료구조야.

각 인덱스의 메모리 주소가 연속되어있으니까
각 원소에 임의 접근(Random Access)을 할 수 있고,
그렇기 때문에 모든 원소에 대한 접근 시간이 일정해.

그리고 이 메모리 공간은 자동으로 관리돼.
만약 해당 `std::vector` 객체의 모든 원소가 다 찼는데
새로운 원소를 추가하게 된다?

그러면 다시 메모리 할당을 받고 기존 객체를 복사한 후
기존 메모리 공간은 해제돼.

쉽게 말하면, 동적 배열이라고 할 수 있어.

C++에선 요즘에는 동적 배열(Array)같은거 대부분 잘 안쓰고, 
이 `std::vector`를 주로 쓰지.

### 4-2. size와 capacity

근데 `std::vector` 객체의 모든 원소가 다 찼다면
다시 메모리 할당을 받고 기존 객체를 복사한다고 했지?

이건 뭘 이용해서 모든 원소가 다 찼다는걸 알 수 있을까?

일단 그걸 하기 위해서 `std::vector`에는 두 가지 요소가 있어.

바로 `size`와 `capacity`야.

두 요소의 차이는,

- `size` : 현재 실제로 들어 있는 원소 수
- `capacity` : 재할당 없이 저장할 수 있는 원소 수

이렇게 돼.

```text
원소:     [10][20][30][  ][  ]
size:      3
capacity:  5
```

이런 식으로.

즉,

`std::vector` 객체의 모든 원소가 다 찼다는건
`size == capacity`라는 말이겠지?

그리고 실제 멤버 함수들도 이 두 가지를 분리해서 다뤄.

`std::vector`에 대한 `size()` 함수를 호출하면
말 그대로 현재 실제로 들어 있는 원소 수인 `size`가 나오고,

`capacity()` 함수를 호출하면
말 그대로 재할당 없이 저장할 수 있는 원소 수인 `capacity`가 나오는 식이야.

결국, 이후에 나오는 멤버 함수는 이렇게 셋 중 하나야.

1. `std::vector` 객체의 원소에 접근한다.(Random Access, 기존 원소에 변경 없음)
2. `std::vector` 객체의 원소 개수를 바꾼다.(`size`와 때로는 `capacity`에 대한 변경이 일어남)
3. `std::vector` 객체에 할당된 메모리 공간을 관리한다.(`capacity`에 대한 변경이 일어남)

### 4-3. `vector`의 재할당

이건 `std::vector`의 핵심이라 꼭 제대로 살펴봐야해.
사실상 `std::vector`의 주의점이 대부분 이 재할당에서 오거든.

일단 굳이 왜 재할당을 해야하는지 살펴보자면,
재할당을 하지 않으면 메모리 공간의 연속성을 유지할 수 없기 때문이야.

기존 메모리 공간에서 메모리 공간의 연속성은 유지할 수가 없어.

```text
현재 vector 메모리 : [A] [B] [C] [D] [E]
```

만약 이렇게 `std::vector`가 있고 꽉 찼다고 했을 때,
메모리 공간의 연속성을 유지하려면 어떻게 해야할까?

```text
vector 메모리 : [A] [B] [C] [D] [E] [] ...
```

논리적으로는 이렇게 뒤에 다른 메모리 공간을 이어붙여야겠지.

근데 이렇게 하려면 재할당밖에 답이 없어.

```text
현재 vector 메모리 : [A] [B] [C] [D] [E]
바로 뒤의 메모리 :   [다른 변수의 데이터...]
```

기존 메모리 공간을 이용하려 해봐도,
만약 기존 `std::vector` 객체 뒤의 메모리가 이미 사용 중이라면?

그러면 메모리 공간을 늘릴 수가 없잖아?
(애초에 이렇게 기존 메모리 공간을 늘릴 수가 없기도 하고..)

그래서 아예 새로 메모리 공간을 할당받는거야.

그리고 재할당 과정을 가볍게 살펴보자면,

1. 기존 `capacity`보다 더 큰 새로운 메모리 블록을 힙에 할당한다.
2. 기존 메모리에 있던 원소들을 새 메모리로 복사(또는 이동)한다.
3. 기존 메모리 공간을 해제한다.

이렇게 돼.

그리고 재할당 때문에 발생하는 문제점이 있는데,
결국 메모리를 재할당 받을 때 기존의 원소들의 메모리 주소가 싹 다 바뀌어서,
재할당 후에는 **재할당 전에 사용하던**

- 해당 `std::vector` 객체의 내부 원소에 대한 포인터
- 해당 `std::vector` 객체의 내부 원소에 대한 이터레이터
- 해당 `std::vector` 객체의 내부 원소에 대한 대한 참조

이런 것들이 싹다 댕글링 상태가 돼.
즉 무효화돼.

### 4-4. 재할당 최적화 : `resize()` / `reserve()`

앞의 `size`와 `capacity`의 차이까지 보면,
이 두 가지의 함수를 이해할 수 있어.

언뜻 보면 비슷해보이거든.

- `reserve(n)` : `capacity`를 최소 `n` 이상으로 재지정함, 원소의 개수는 재지정되지 않음
- `resize(n)` : `size`를 `n`으로 재지정함, 즉 원소의 갯수를 재지정함

이게 `size`와 `capacity` 개념을 모르면 구분이 잘 안되겠지만,
이렇게 보니까 확실히 구분이 되지.

```cpp
std::vector<int> v;
v.reserve(100); // capacity = 100, size = 0
v.resize(10);   // capacity = 100, size = 10
```

앞으로 저장할 원소 수를 예상할 수 있다면
`reserve()`로 필요한 저장 공간을 미리 확보할 수 있다는거야.
그러면 실제 원소 수가 확보한 `capacity`를 넘지 않는 동안에는 
재할당을 피할 수 있겠지.

그렇게 미리 해당 `std::vector`에 저장될 수 있는 원소의 최대를 알고있으면
재할당을 최적화할 수 있다는거.

### 4-5. 기타 시간복잡도들

1. 인덱스 접근
    - 주소 계산 한 번만 하면 되므로 $O(1)$
2. 맨 뒤 추가 / 삭제
    - 딱 원소 하나에 대한 연산만 하면 되므로 $O(1)$
    - 재할당을 해야할 경우에 $O(N)$
    - (평균적으로는 $O(1)$, 가끔 재할당 시 $O(N)$)
3. 중간 삽입 / 삭제
    - 뒤의 원소들을 밀거나 땡겨야하므로 $O(N)$
4. 원소 탐색
    - 순차 탐색으로 $O(N)$
    
### 4-6. 최종 요약

결국, `std::vector`란,

> 최대 가능한 원소 개수인 `capacity`를 넘는 경우 메모리 재할당을 해주는 동적인 배열

이러고 할 수 있겠지.

그리고 어디에 사용하는게 좋을지도 확실히 알 수 있어.

- 장점 :
  - 메모리가 연속적이어서 캐시 적중률이 높음
  - 임의 접근(Random Access)가 $O(1)$으로 매우 빠름
  - 맨 뒤 원소 추가 / 삭제가 일반적인 경우 $O(1)$로 매우 빠름
- 단점 :
  - 중간 삽입 / 삭제는 $O(N)$으로 느림
  - 재할당을 해야할 경우 재할당 비용이 발생함
